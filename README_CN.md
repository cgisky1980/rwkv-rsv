## 1. 作用

`rwkv-rsv` 是一个纯 Rust 实现的 **RWKV-7** 推理引擎，推理运行在 **Vulkan / CUDA 计算着色器**上，跨 GPU 厂商（NVIDIA / AMD / Intel / 移动端）与操作系统（Windows / Linux / macOS）。

核心目标有二：

1. **降低显存占用**：通过离线权重量化（int8 8-bit 省 41%）在不大幅损失精度的前提下，把 3B 模型权重从 5.49GB（fp16）压到 3.22GB。
2. **可复现的精度验证**：提供 CPU fp32 参考实现与 GPU 内核级单测，把「内核误差」与「量化误差」隔离，逐层逐 token 验证。

默认面向 **RWKV-7 Goosed g1h-3B** 模型，但模型结构按 safetensors 张量形状自适应，可加载同系其他规模模型。

## 2. 设计目标

- **可移植性优先，但要说清代价**：以 Vulkan 为主后端，换取跨厂商 / 跨平台可用性。本机实测：**SIMT 对口径下与 CUDA 无差距**，**默认（张量核）口径下批量 decode 为 0.941×（B=1）/ 0.945×（B=8）/ 0.806×（B=32）/ 0.730×（B=64）/ 0.690×（B=128）/ 0.762×（B=256，2026-10-12 第八次同会话复测；★ 这一行的口径 = `power.limit` 300 W、SM 随时钟热飘 1680…1845，与它上面那些 250 W 档的行不可互减——上一版是 0.900 / 0.972 / 0.824 / 0.765 / 0.690 / 0.688，第五次复测在 250 W 未锁频档）**、批量 prefill **不是单调落后**（2026-10-12 第八次同会话六档成对，§20.2）：**B=1/8/32 反而领先**（2.47× / 1.44× / 1.085×），从 B=64 起反转，落后 6.1 % / 12.4 % / 16.5 %（B=64/128/256，即 0.94 / 0.89 / 0.86×；更早那组「0.79~0.84×」是只看大档的过期读数）。⇒ 差距只在 decode，两处的瓶颈不同（见 §6.1、README.md §6.6~§6.9）。
- **两路量化共存**：fp16（无损参考）/ int8（近无损）按模型文件自动路由，同一二进制全部兼容。
- **运行时自编译 shader**：`build.rs` 在构建期用 `glslangValidator` 把 `*.comp` 编译为 SPIR-V，`constant_id` 做跨硬件自适应。
- **研发向**：内嵌 CPU fp32 参考、DIAG 三方核对、logits 对比、teacher-forced Top-1 一致率等验证工具链。

## 3. 构建

需要 **Rust（edition 2024）** 与 **Vulkan SDK**（`glslangValidator`；`build.rs` 在构建时把 `assets/shaders/src/*.comp` 编译为 `assets/shaders/spv/*.spv`）。

```bash
cargo build --release
```

## 4. 运行

加载模型（默认 `c:\work\niceui\rwkv-g1h-3B.st`，可用 `MODEL_PATH` 切换；含 `.int8_idx` → int8，否则 fp16）：

```bash
cargo run --release
```

主要 env 变量（详见 [src/main.rs](src/main.rs)）：

| 变量 | 作用 |
|---|---|
| `MODEL_PATH` | 模型路径；含 `.int8_idx` → int8，否则 fp16 |
| `BACKEND` | `vulkan` / `cuda`，显式选择后端 |
| `TOP1_MULTI_SAVE` / `TOP1_MULTI_COMPARE` | 多 prompt 的 teacher-forced Top-1 一致率验证 |
| `TOP1_REF_SAVE` / `TOP1_REF_COMPARE` | 单 prompt 的 CPU fp32 参考一致率 |
| `SAVE_LOGITS` / `COMPARE_LOGITS` | 单 prompt logits 的 RMSE / Top-10 对比 |
| `GEN_TOKENS` / `REPORT_EVERY` | 连续自回归生成（`memtest` 子流程） |
| `DIAG` | 三方核对（seq / tok / CPU）+ dequant 校验 |
| `PROF_GPU` / `PROF_HOST` | GPU / 主机端性能剖析 |
| `UNIFORM_POOL_MB` | Vulkan uniform 池容量（MB，默认 8；占用是「批内不同 params 组合数」的 O(1)，实测高水位 69KB —— 这是极端形状兜底项，不是需要调的参数） |
| `GEMM_TILE_*` / `GEMV_BLOCK_SIZE` / `GEMV_ROWS` | 覆盖跨硬件自适应参数 |

### 4.1 示例程序（web-rwkv 风格）

```bash
# 模型信息：加载模型、打印 ModelInfo、probe 前向
cargo run --release --example model_info
# 自回归生成：prefill + GPU self-loop（argmax 确定性 / sample 采样）
cargo run --release --example generate          # env: NTOKENS, TEMP, TOPK, TOPP, GEN_MODE, VOCAB_JSON
# 吞吐基准：infer_seq / infer_tokens / argmax_selfloop / sample_selfloop
cargo run --release --example benchmark
# 稳态 prefill 基准（同长度预热后测第二次起，排除一次性 pipeline 创建开销）
cargo run --release --example prof_prefill_steady   # env: PTOKENS
# 批量并发吞吐/正确性基准：SLOTS × SEGS × NTOK，含 STEP=1 两条路径对拍、SLOT_BENCH=1 槽位分发、
# BUCKET_BENCH=1 长度桶预热四档、BENCH_JSON=<路径> 把「读数 + 完整门控」落成一行 JSON
cargo run --release --example batch_decode_bench    # env: MODEL_PATH, SLOTS, PAD_TO, TOPK, STEP, BENCH_JSON
# 同会话**交错 A/B** 编排器（基准可信度的唯一正当姿势）：轮换测量顺序、串行子进程，
# 出中位数 + 离散度 + 倍率 + 跨后端指纹一致性表；AB_SLOTS/AB_ROUNDS/AB_JSON/AB_SUMMARY
cargo run --release --example bench_ab
# State 序列化：前进→state_back→存盘→state_load→state_back 无损闭环
cargo run --release --example state_persist     # env: OUT=state.bin
```

### 4.2 库 API 与 GPU 采样

`rwkv-rsv` 同时以 **library** 形式导出，便于服务端（如 `ai00-server`）集成，对标 [web-rwkv](https://github.com/cryscan/web-rwkv)：

- **`ModelBuilder` + `Bundle`**：加载模型并绑定零初始化 `State`；`infer_tokens` / `infer_seq` / `infer` 推进会话并返回 logits。
- **`State`**：一等公民的会话状态——`state_back()` 下载为 CPU `Vec<f32>`，`state_load()` 回灌，`reset()` 清零，序列化逐位无损。
- **GPU 采样（`SamplerParams`）**：`infer_sample` / `infer_sample_selfloop` 全 GPU 端过滤 logits，只回传采样 token 索引。
- **并发池原语（批量布局 `State`）**：`create_batch_state(B)` + `forward_seq_batch_padded` / `submit_sample_selfloop_batch` / `batch_step_sample`；
  槽位管理走 `state_slot_back` / `state_slot_load`（宿主往返）与 `state_slot_broadcast`（**设备内**把一份状态分发给多个槽，
  会话 fork / 同 prompt 多路采样用，省掉每目标 2× 单槽状态的 PCIe 往返）；
  启动期用 `warmup_len_buckets(state, &[T_pad…])` 把长度桶的序列缓冲重建从首个真实请求挪到启动期
  （★ 缓冲单槽：只有列表里最后一个桶留在显存）。批量 **decode** 的前提查 `supports_batch_decode()`，
  不满足时 `batch_decode_blocker()` 给出**是哪一条**前提（后端缺算子 vs 模型无 int8 句柄）。
  ⚠️ 这条门只管批量 decode：`forward_seq_batch_padded`（批量 prefill）走 seq 并行核，
  **fp16 模型一样可用**，且每槽状态与单流逐位一致（2026-10-10 两后端实测）。
  返回值是各槽提示词的末 token（解码种子），不是下一 token 预测。

## 6. 指标

硬件：**RTX 2080 Ti**。模型：RWKV-7 Goosed g1h-3B（weights fp16 5.49GB / int8 3.22GB，省 41%）。详细报告见 [参考/](参考/)。

**端到端精度（teacher-forced Top-1 一致率，对比 fp16 参考）：**

| 路径 | 一致率 | 说明 |
|---|---|---|
| int8 | **98.8%**（506/512） | 近无损；权重级 avg cos 0.999820 / rel 0.6135% |

**GPU decode self-loop 吞吐**（argmax self-loop，1000 tokens，GPU ~53°C 冷态起；`memtest` + `SELFLOOP_ONLY=1` / `SELFLOOP_N=1000`）：

| 权重 | Vulkan | CUDA |
|---|---|---|
| fp16 | 88.1 tok/s | 92.4 tok/s |
| int8 | 116.0 tok/s | 126.0 tok/s |

int8 较 fp16 约 +32%（Vulkan）/ +36%（CUDA）。

> **2026-10-04 同会话交错复测**（int8，同测法）：Vulkan **68.4** vs CUDA **68.3** tok/s —— 完全持平。
> 绝对值跨会话漂移很大（本次差 40% 以上），所以只有交错比值有意义；上面 2026-08 那张表早于
> Vulkan r/k/v 内核改造，且当时并非交错测得。详见 §6.1。
>
> ⚠️ 那次单流配对的 **CUDA 门控口径没有记录**，而它决定这条「持平」成不成立：2026-10-10 同会话
> 交错在**默认口径**（CUDA 三个张量核开关全开）下测得 **91.4 vs 79.2 = 0.87×**，B=1 就已经不平了。
> 「B=1 持平」请按 SIMT 对口径读。

**GPU prefill 吞吐**（T=256 稳态，即同长度预热后的第二次起；`prof_prefill_steady`，Vulkan cooperative-matrix GEMM 路径）：

| 权重 | Vulkan 稳态 | 备注 |
|---|---|---|
| fp16 | **2677-2700 tok/s** | GEMM 有效算力 21-25 TFLOPS（f32 累加 tensor 峰值 75-89%） |
| int8 | 2263-2307 tok/s | 含每层 dequant 开销（见「已知限制」） |

这条路径上 Vulkan ⇄ CUDA 同样打平：同会话交错（2026-10-04，`PTOKENS=256`）**2455.6 vs 2433.0 tok/s**（1.01×）。⚠️ 与上面同一条注意事项：那次配对的 CUDA 门控没有记录，所以按 SIMT 对口径读；**批量** prefill 在默认口径下位次随 B 反转 —— B=1 时 Vulkan 更快（1,169 vs 2,238 ms），B≥32 起被 CUDA 反超并越拉越远（B=256：86.5 s vs 46.7 s），见 §6.1 prefill 两列。

> ⚠️ **2026-10-11 订正**：上面那组 86.5 / 46.7 s 与「B≥32 越拉越远」读自被污染的 bench prefill 列（`t0` 在 `create_batch_state` 之前、`t1` 在解码循环之后，含 `WARMUP` 自循环的图捕获 / JIT）。按干净口径（`PROF_CHUNK=1 PAD_TO=512 NTOK=1 SEGS=1 WARMUP=0 SKIP_SINGLE=1`，只读 chunk 循环自身墙钟）批量 prefill 现为 **0.84×（B=128：18.2 vs 15.3 s）/ 0.79×（B=256：36.0 vs 28.5 s）**。完整经过见 README.md §6.6–§6.7（这两节暂未回译到本文档）。**2026-10-12 再订正**：加上块序 swizzle（本文档 §6.6）后，同一干净口径 B=128 为 **0.828×**（core 15 690.8 vs 同会话 CUDA 12 983.5 ms）；0.84× 与 0.828× 属**不同会话**，绝对值不可相减。

单次冷启动 prefill 会额外付出该长度桶（m_pad）首次的 pipeline 创建成本（~几十-上百 ms，一次性）；服务端可在加载后按常用长度桶各跑一次 dummy prefill 预热。详见 [参考/Vulkan-prefill单发与稳态差异排查记录.md](参考/Vulkan-prefill单发与稳态差异排查记录.md)。

**口径**（SIMT 对 SIMT vs 默认）：2026-10-04 的「0.98×~1.03× 持平」与「逐位一致」都是**对齐口径**
——CUDA 侧需 `LOWRANK_GEMM=0 FFN_VALUE_GEMM=0 GEMV_IMMA=0`。抽查（同日 B=8）：CUDA 默认 624.6 /
关 503.5 / Vulkan 514.6；B=32 默认 1900.7 / 关 583.4 / Vulkan 929.1。默认口径与对齐口径差到 3 倍，
所以「Vulkan 追平 CUDA 张量核路径」这句话从来不是事实。

**正确性 —— 同后端两条路径**：逐步路径（`batch_step_sample`，主机在环）与 GPU 自循环路径
在两后端的**每一档批量**上 sum/xor 指纹**逐位一致**。这是 `batch_decode_bench` 的 `STEP=1`
回归探针（2026-10-10 加入；当时 Vulkan 的回读 bug 让两条路径结果不一致，见
[参考/2026-10-10-Vulkan批量残留修复-实施记录.md](参考/2026-10-10-Vulkan批量残留修复-实施记录.md)）。

**正确性 —— 跨后端**：**只有两边跑同一条 SIMT kernel 序列时才逐位一致**。把 CUDA 压到
Vulkan 的路径（`LOWRANK_GEMM=0 FFN_VALUE_GEMM=0 GEMV_IMMA=0`）后 B=8 两边完全一致
（同为 `0xd08ada`/`0x2ea`）。CUDA 的**默认**路径走 int8 张量核（这三个开关自 2026-09-21 起默认开），
此时指纹不同 —— 上面主表那 16 格里**只有 B=1 两边全等**（`0x1acbfa`/`0x6d5c`），B≥8 一律分叉
（例：B=8 CUDA `0xd02e16`/`0x6d08` 对 Vulkan `0xd08ada`/`0x2ea`；B=256 CUDA `0x1a493fad`/`0x7e01`
对 Vulkan `0x1a407915`/`0x6713`）。两边 logits 数值相邻，采样把罕见的单点翻转放大成后续序列分叉，
所以这**不是**正确性缺陷；但任何「跨后端逐位一致」的说法都必须写明口径。
同一份记录里另一条硬事实：**同后端 3 轮同参数指纹逐位复现**（全部 16 格 det=Y），所以分叉
只来自后端，不来自时序抖动。
（CUDA 保留了同一个 `gemv_int8_rkv_stage1_batch` 签名，但忽略新增的 fp16 激活入参、
仍走原 fp32 路径，所以对齐口径下的 CUDA 列是真正未经改动的基准。）
2026-10-04 那句「每一档批量两后端逐位一致」是按对齐口径写的，**在默认口径下不成立**。

**CUDA 路径反超信天翁的途径**：**int8 张量核**（`mma.m8n8k16.s8`；Turing 的 int8 张量核峰值是 fp16 档的 2×）跑在
**int8 常驻权重**上（每 token 读 2.68 GB，fp16 引擎要读 5.37 GB）、**split-K + 确定性归约内核**
（不增加总流量就能加块数）、**多链合并 launch**（r/k/v 三条 + 低秩四条）、**形状感知 tile**
（BM 按 batch 取、BN ≈ batch、块数凑满 68 个 SM）、**warp-per-row + `__shfl` 归约**
（替掉每行一次整块树归约）、**稀疏 FFN 无原子累加**，以及把采样器的每个扫描趟都展开以提
内存级并行。完整机理：[int8 IMMA 实施记录](参考/2026-09-21-int8-IMMA实施记录.md) ·
[跨架构基线表](参考/2026-09-21-跨架构基线表.md)。

**Vulkan 在同 SIMT 口径下的提速手段**（全在 r/k/v 融合核 `gemv_int8_rkv_stage1_batch`；注意这**不**等于追平 CUDA 默认张量核路径）：

- **fp16 激活**：此前该核每槽每 k 读一个完整 `vec4`（16 B）的 fp32 激活，而权重已是 int8 紧凑格式 ——
  成为 L2 流量的第二个大头。现在改读 `f16vec2` 缓冲（8 B，**减半**），再展宽成 `vec4` 参与 fp32 累加。
- **权重 `vec4` 打包 + `dot`**：解量化权重按行打包成 `vec4`，与激活 `vec4` 走 `dot()` —— 4 条 FMA 并成 1 条。
- **x 分块常驻 shared memory**（`XTILE=256`）：原先 x 的每个 k 元素要被全部 `BGRP=8` 个槽 × `ROWS`
  行重复读；现改为每块只读一次。smem 占用从 80 KB（超 sm_75 的 48 KB 上限）降到 32 KB。
- **`BGRP=8` 槽分组**，跨槽复用权重。

细节与踩坑记录：[参考/2026-10-04-Vulkan追平CUDA实施记录.md](参考/2026-10-04-Vulkan追平CUDA实施记录.md)。

### 6.2 2026-10-10 追加实测：对 §6.1 三处结论的更正

三件事都是在**同一会话、交错 A/B**下测的（本机 GPU 同时是显示卡，跨会话读数不可比）。
本轮把两条「已知结论」推翻了，并定位了一个此前被误记成性能问题的崩溃。

**① `GEMV_BGRP` 的上限是 8，不是「越大越省带宽」**（此前从未在 batch≥16 做过 A/B）。
B=256、其余参数固定，逐档扫：

| BGRP | 4 | **8** | 16 | 24 | 32 |
|---|---|---|---|---|---|
| tok/s | 795.2 | **986.9 / 974.3**（重复跑，1.3% 漂移） | 890.3 | 750.7 | 718.1 |

按「权重遍数 = ⌈B/BGRP⌉」的带宽模型，BGRP=32 应把 r/k/v 的权重读 8 遍而不是 32 遍、理应当然更快；
实测反而更慢 27%。原因是 `float acc[ROWS][BGRP]` 的寄存器压力：BGRP>8 时溢出到 local memory，
省下的带宽被 spill 的存取吃掉。**所有档位的 token 指纹逐位一致**（`sum=0x68ce489 xor=0x7243`），
顺带证明 `slot_cnt` 尾块守卫在 BGRP 不整除 batch（24）时也正确。
⇒ 「靠调 SIMT 分组把 B=256 的带宽账算平」这条路是死的，差距只能在**更多槽共用一次权重读取**
的张量核路径上找（见 ②）。

**② 张量核 r/k/v 路径的「净亏 3.3×」不成立——它是崩溃，不是慢**。
该路径在任何 batch（256/128/64/8/4/2/1）都直接 `ERROR_DEVICE_LOST`，所以「3.3×」从来无法复现。
二分定位到 `gemv_int8_rkv_mid_batch`（`RKV_OFF=1` 的 mid 投影臂）的 a/g 链；根因是它的
`params` 数组只写了 **24 项，而 shader 的 `Params` 有 26 个 `buffer_reference`**——从 `in_g1`
之后所有槽位整体前移两位，`out_am`/`out_v` 落到从未写过的池字节上，被当指针解引用。
偏移固定所以只在部分分支发作（v/w 链读到的是「移位后仍然有效」的指针，于是**跑通但算错**；
a/g 链读到垃圾指针，于是**崩**），这正是它六天没被看懂的原因。自 `3374512` 写下那天起
这条路径就没有一次成功执行过。修好后（同会话交错，`VK_IMMA_OPS=…,rkv` 对比默认 SIMT）：

| batch | 32 | 64 | 128 | 256 |
|---|---|---|---|---|
| SIMT r/k/v | 849.0 | 921.4 | 965.1 | 679.0 / 693.0 |
| 张量核 r/k/v | **1086.1** | **1231.0** | **1378.9** | **899.0 / 906.7** |
| 比值 | +27.9% | +33.6% | **+42.9%** | +29.7% |

每一档都赢，且两次重复的区间不重叠（非漂移）。但当时**仍保持默认关闭**，原因换成了唯一还没过的门：
这条路径把 r/k/v 的**激活也量化成 int8**，数值口径与 SIMT 的「fp32 激活 × int8 权重」不同
（token 指纹逐档不一致，符合预期），而端到端质量门还没做。没有质量证据就默认换数值口径，
不属于性能优化。**→ 该门已在同日做完并通过，默认已翻转为张量核；见 §6.3。**

**③ B≥192 的吞吐断崖是显存溢出，不是核质量**。`TOPP=1.0`（关掉 top-p 兜底循环）扫并发曲线：

| batch | 64 | 128 | 192 | 256 |
|---|---|---|---|---|
| decode tok/s | 1275.3 | **1430.1** | 1034.7 | 1019.1 |
| `sample.spv` 单次 | 0.58 ms | 0.87 ms | **49.99 ms** | **68.0 ms** |

采样核在 128→192 之间跳了 **57 倍**，而同一段代码在 64→128 只涨 1.5 倍——这是内存放置问题，
不是算法问题。`nvidia-smi` 在 B=256 的 decode 期间实测 **21 775 / 22 528 MiB**（本机是被改成
22 GB 的卡；桌面与其它进程常驻 ~8.6 GB，本进程峰值 ~13.1 GB）——显存被推满后 WDDM **静默
落到系统内存**，于是采样核那 4 张 `[batch, vocab]` 工作区（B=256 各 67 MB）变成 PCIe 访问。
两条推论：
- **批量 decode 的实用甜点是 B≈128**，不是 B=256；把 SLOTS 拉到 256 是负收益。
- §6.1 默认口径里 B=256 的 **0.27×** 有一部分是**容量效应**而非核质量。要拿到干净的对比，
  先把每槽占用降下来（候选：RNN 状态，每层每槽 `H·N·N = 163 840` 元素 ⇒ 状态合计 B=256 约
  5.3 GB；以及 `WorkBuffers` 的每槽工作区）。
  ⚠️ **这条推论的前提已作废**（第五次复测，2026-10-11）：B=256 实测 **0.688×**，与 B=64/128 单调一致，
  说明 0.27× 是过期构建而非容量效应。「大批量断崖」这个叙事至今已被收回四次；上面的降占用工作按它
  自己的价值（显存）成立，与比值无关。
  **状态占用这一半 2026-10-11 已完成**：Vulkan 侧补上与 CUDA 同档的 fp16 **存储**（`supports_f16_wkv_state()`
  已为 true，三处状态核各有 `_s16` spv 变体，`WKV_STATE_F16=0` 可切回），同会话交错实测
  **B=128 登记张量 −1290 MiB**（7788 → 6498）且 decode **+3.5 %** ⇒ B=256 收回约 2.6 GB。
  `WorkBuffers` 未动。

另记一条与 ③ 同批暴露的问题：`log_vram` 在 B=256 全程打印「登记张量 0 MiB」——**显存记账是坏的**，
所以「溢出」这件事在日志里完全看不出来，只能靠外部 `nvidia-smi`。

**③的订正（2026-10-10，同日）**：上面那句记账问题**已修**，而 ③ 里的占用数字是**低记**，
要按「至少这么大」来读：
- `device_bytes` 原来汇总一张旁路表（`lens`），而 `u32`／批量张量根本没进表 ⇒ 静默算成 **0**；
  现在改成逐张量取 `GpuTensorU32::len` 求和，并且 `log_vram` 多打一列 **host 镜像**——Vulkan
  侧每个张量都有一份 host-visible 镜像，那些字节是**系统内存**，`nvidia-smi` 看不见，
  绝不能再从显存预算里减。
- 把没打印的 self-loop 段补回来之后，**B=256 的登记占用是 17 869 MiB，不是 ~13.1 GB**；
  外部峰值 **20 662 / 22 528 MiB**（桌面基线 2 128~2 786 MiB，这张卡同时是显示输出）。
  登记 vs 外部现在只差 **+7 MiB（B=256）／+36 MiB（B=128）**，所以旧「6 GB 说不清」是
  **打印时机**，不是泄漏：`WARMUP=0` 时 self-loop scratch 是在被计时的那一段里才第一次分配，
  那一行 `log_vram` 打在分配之前。
- 因此「**B=256 必然 OOM** 作废」——它装得下，还剩 ~1.8 GB 余量。③ 里 B≥192 采样核变慢
  仍是实测数据，而且真实占用更大 ⇒ ③ 的方向（**容量效应，不是核质量**）是**被加强**的；
  变的是预算算术，现在按项拆：RNN 状态 **每槽 20.6 MiB**（B=256 就是 5.3 GB）≫ 采样工作区。
- 采样 mask 在 Vulkan 侧已改成**位图档**（新增 spec 常量 `MASK_WORD_STRIDE`，host 侧按缓冲
  实际长度反推跨距；CUDA 靠 `supports_compact_sample_mask() = false` 保持稠密口径）：
  B=256 的 64 MiB → 2 MiB，外部口径实测**峰值 −61 MiB**（理论 −62 MiB）。
  **吞吐实测持平**（B=128 稳态 1039.0 vs 改动前 1037.6 tok/s）⇒ **别把它写成加速项**，
  它真正省的是 top-p 循环每趟 `reduce_max` 的 mask 访存（每槽 256 KiB → 8 KiB）。
  守护用例：`tests/batch_parity.rs::top_p_sampled_tokens_stay_inside_the_nucleus`——mask 路径
  此前**零 CI 覆盖**（原有采样用例全是贪心，而贪心根本不进 top-p 兜底循环）。用例同时带
  **正向**判据（采到的 token 不许掉出宿主侧同口径算出的候选集 ⇒ 抓跨槽污染／上一轮残留）
  和**反向**判据（候选集 ≥2 的槽必须偶尔采到非 argmax ⇒ 抓「mask 完全没生效」，
  那种故障会退化成贪心、正向判据照样通过）。两个方向都用故障注入验证过。

**③-bis（2026-10-11）：self-loop 阶段那 ~5.3 GB 找到了，是 `imma_partial` 超配 64 倍**。
上面③的订正留了一个没交代的数：`log_vram` 从「prefill 后」到「self-loop 图捕获后」涨了
+5471 MiB（B=256）／+2735（B=128）／+1352（B=64），即**每槽 21.4 MiB**——状态量级，
而采样 scratch + `WorkBuffers` 只占每槽 ~0.5 MiB。归因手法值得留在工具箱里（约十行）：
在 `Runtime::create_tensor{,_f16,_u32}` 里加一个 env 门控的日志，把 ≥4 MiB 的分配连
`len`/MiB 一起打出来。B=64 下抓到**单条 335 544 320 元素的 f32 张量 = 1280 MiB**，而
`335 544 320 = 8(KS 上限) × 64(一波槽数) × max(c, ffn_hidden) × batch`——槽维被**乘了两遍**，
因为 `WorkBuffers::new` 里的 `mk(len)` 助手已经替你乘过 `bsz` 了。`imma_ksplit` 的真实约束是
`ks·batch·m ≤ partial.len` ⇒ 正确长度是**每槽** `8 × max(c, ffn_hidden)`。

| batch | self-loop 后登记张量 | 外部峰值 | decode tok/s（交替两轮） | 指纹 |
|---|---|---|---|---|
| 192 旧尺寸 | 15 135 MiB | 17 885 | 1486.3 / 1465.4 | `0x4f09628/0x8e94` |
| 192 修正后 | **11 335**（−3800） | **14 085** | 1491.8 / 1474.1 | `0x4f09628/0x8e94` **相同** |
| 256 旧尺寸 | 17 807 MiB | 20 585 | 1505.1 / 1497.6 | `0x6875c61/0x876b` |
| 256 修正后 | **12 747**（−5060） | **15 528** | 1490.0 / 1496.2 | `0x6875c61/0x876b` **相同** |

- **逐位等价是推出来的，也是实测出来的**：新容量下 `ks·m ≤ 8·10 240` 对任何 `m ≤ ffn_hidden`
  都不构成约束（ks 仍取 8），head（`m = vocab 65 536`）因块数超过 split-K 目标本来就恒取 ks=1
  ⇒ kernel 序列没变。A/B 是用一个临时的 `IMMA_PARTIAL_PAD` 旋钮把两种尺寸交替跑出来的（量完即删），
  两侧解码指纹完全相同。
- **这里吞吐是持平的（±1%）——而这本身就是结论**：旧尺寸在 20 585 MiB 峰值下本机**还没**开始溢出，
  所以 ③ 那条 57 倍采样断崖**在当前构建里完全复现不出来**（1465~1505 tok/s，随批宽单调上升）。
  ③ 那次记录时其它进程占着 ~8.6 GB；这次改的是那条余量本身——B=256 现在留 ~7 GB 空闲而不是 ~2 GB，
  共存负载不会再把批量路径推进 WDDM 溢出。
- **从来不只是 Vulkan 的问题**：`WorkBuffers::new` 与后端无关，CUDA 同样分配了这份在它那侧根本用不到的
  5.1 GB（CUDA 的 split-K 部分和在别的缓冲里）⇒ 历史上所有 CUDA 大批量读数都含着这笔开销。
- 顺带订正 §9 里那句「`imma_partial` **不能**按 `bsz` 配……按 `bsz` 预留反而多要 63 MiB」：那句是**错的，
  而且当时并没有被回滚**——助手里的 `× bsz` 一直在，外面又乘了一遍 64，于是付出的是正确尺寸的 **64 倍**
  （B=256 上 5.1 GB），直到 2026-10-11 才定位收回。

**④ 「重编 shader 后的第一个进程」不能用作 A/B 的任一侧**——本轮就栽在这里，把一条假收益
写进了结论。`vulkan/app.rs` 的 `pipeline_cache` 只建在**内存**（`PipelineCacheCreateInfo` 不给
初始数据、也不落盘），而驱动自己的盘缓存按 SPIR-V 哈希索引 ⇒ `build.rs` 重编之后的第一个进程
会在**计时区内**编译一批管线。实测：`batch_summarize` batch=8、同一份输入，SIMT 那一档作为
「那个进程」时读到 0.52 条/秒（decode 35.3s），交错重跑之后是 **2.46 / 2.34 条/秒**
（decode 5.4 / 5.8s）——与张量核那一档（2.36 / 2.38）**持平**，6.4× 差额整个是产物。
输出侧完全不受影响：同一配置三次独立进程的 20 条摘要**逐字全同 20/20** ⇒ 被污染的只有计时。
⇒ 纪律：动过 `assets/shaders/` 就先跑一个丢弃用的进程；单轮单侧的读数一律不用。
★ 2026-10-10 把这条量化了（`sample.comp` 加一个 spec 常量，同参数连跑两个新进程）：decode 增量
是**与批宽无关的 ~4.5 s**（B=128/192/256 分别 +4692/+4385/+4665 ms），即一次性开销而非每轮变慢；
第 1 个进程 479.3 tok/s，第 2 个 **1039.0** tok/s，token 指纹完全相同。`sample.spv` 单条管线就要
4.4~4.7 s（它对全词表循环做了 `[[unroll]]`），而且**每一种 spec 常量组合各付一次**
（`N/HIST_STRIDE/SAMPLER_ROW/BATCH/MASK_WORD_STRIDE` 全组合独立）⇒ 加 spec 常量等于给下一轮扫描
悄悄加税。

### 6.3 2026-10-10 默认翻转：Vulkan 的 r/k/v 也走 W8A8 张量核

§6.2② 把「净亏 3.3×」证伪成一次崩溃之后，还剩一道**质量门**：这条路径把 r/k/v 的**激活**也
量化成 int8，改了数值口径。门已做完并通过，`VK_IMMA_OPS` 的默认从「除 rkv 外全开」改成
**全开（含 rkv）**；要复现旧口径显式写 `VK_IMMA_OPS=key,out,val,head` 即可。

**质量（翻转的正面依据）**——部署同款摘要管线 batch=8、10 个真实多轮场景 20 条摘要，CUDA 为基准：

| rkv 口径 | 与 CUDA 的平均公共前缀比 | 平均字数（CUDA = 88.3） | 拒收 |
| --- | --- | --- | --- |
| SIMT（旧默认） | 0.332 | 48.8 | 0 |
| 张量核（新默认） | **0.501** | **77.9** | 0 |

### 6.4 `gemm_imma` 取数结构（2026-10-11）：B≥64 +12~16 %，逐位等价

**瓶颈是怎么定位的。** 给 `examples/kernel_bench.rs` 补了 W8A8 一族（`imma_key / imma_out /
imma_value / imma_head`，每个都是 `quant_x_i8` + `gemm_imma`，部分和容量按引擎真值给，
好让 `imma_ksplit` 选出与真实推理一致的 `ks`）并加了 **TOPS** 列。四条形状的 TOPS 全落在
14~22 这一档，而这张卡 int8 张量峰值约 107 TOPS。若是带宽受限，读权重最多的 `head` 应该最差、
读得最少的 `att.output` 应该最好——事实不是，所以限制在**每 warp 的共享内存载入指令数**上：
A 片段（`m16k32` int8，16 B/lane ≈ 4 条 LDS）只跟行块有关，却在槽组循环里被反复
`coopMatLoad` ⇒ 每两条 mma 配两条取数指令。

**两处改动，目标都是逐位等价**（`assets/shaders/src/gemm_imma.comp`）：

1. A 片段提到槽组循环外面，落进 `a0..a3`（每 k-tile 每 warp 只载一次）；
2. 槽组分给多列 warp——`SW = min(NST,2)`、每 warp 跑 `RPG = NST/SW` 组、block = `(BM/16)·SW·32`
   线程。累加器从 `acc[NST][4]` 减半（NST=8 时 32 个累加寄存器正是溢出到 local memory 的那条线），
   warp 数翻倍 ⇒ 延迟有地方藏。`BM=128` 档本来就有 8 个行 warp（`tile` 第一维就是 warp 数上限），
   所以那一档只吃到改动 1。

必须尊重的连带后果：`wid` 现在是二维编号，凡拿 `wid * WR` 当**行基址**的地方（flush 取 `szs`、
epilogue 的输出行号、OP=9/10 诊断）一律要换成 `row_warp * WR`。漏一处是**静默的错结果**而不是崩溃
——2026-10-04 那次「同配置两跑指纹不同」的竞态，根因就是同一个基址漏乘。

**A/B（同会话、三臂串行构建+扫描、同一时刻只有一个 bench 进程、每臂 2 轮取均值）**——
`base` = `7dd5a15` 的那组文件，`#29` = base 只换 shader：

### 6.5 v 链 split-K（2026-10-11）：B≤64 +2~4 %，质量门在 n=232 上通过

`gemm_imma_f16`（v 链）是唯一不做 split-K 的 IMMA 臂：M=C=2560 时 `grid.x = M/BM` 只有 40 块，
低于这张卡的 68 个 SM，而同样形状的 r/k 两链（走 `gemm_imma`）早就抬到 40×`ks` 块。原因很具体——
归约内核只有 f32 出口，`OP=3`（落 fp16）只能配 `ks = 1`。现在 `gemm_imma_reduce.comp` 多了一个
`Out16` buffer_reference 和 `OP == 3` 分支，v 也写 f32 部分和、再按 `ks` **升序**归约成 fp16：
确定性成立，但**落盘字节与旧路径不同**——同样的量化、同样的 fp32 累加，只是加法结合顺序变了。

+3.3 / +2.2 / +3.5 / +2.6 / 0.0 / +0.3 % —— 形状符合机制：v 只是三条链之一且只有 40 块，这是**小批量的

### 6.6 批量 prefill 的块序（2026-10-12）：A 面板被每一列重读一次 —— chunk **1 077 → 981 ms**

`gemm.comp` 的块按线性序 `pid = x + y·NUM_TILE_M` 派发（x 最快），所以一个 wave（本机 68 个 SM）
**先把一整条 M 带走完才换 N 列**。于是 A 面板（`rows × K × 2 B`）**每个 N 列都要从显存重流一遍**：
8 192 行 × K=2560 时 41.9 MB × 80 列 ≈ 3.4 GB 流量，只为 430 GFLOP 的活 ⇒ 内核跑在
**23.3 TOPS = 这张卡 fp16 张量峰值（≈54）的 43 %**，是带宽受限而不是算力受限。
改法是 Triton 风格的分组 swizzle：`GROUP_SWZ`（spec constant 42）把同一个线性 id 重新解码，
让一个 wave 覆盖 `GROUP_SWZ` 个 m 瓦片 × `wave/GROUP_SWZ` 列 ⇒ **两块面板都进 L2 复用**。
每个输出元素仍然由唯一一个块、按同样的 k 升序求和 ⇒ **逐位不变是构造出来的**；
打包的 `g0`（GROUP_SWZ 折成 0）与改动前的模块**逐字节相同**。

host 侧规则只有一个尺度——这张卡的 **6 MB L2**：`g = clamp(floor_pow2(L2/(TILE_M·K·2)), 2 或 4, 16)`
（下界随 m 瓦片数分档：≥16 时 2，否则 4 —— 见下面的「遗留」与台账 §6.10），
且只在形状整除、`A > L2`（A 本来就放得下就没得省）、grid ≥ 2 波时开启；
`GEMM_SWZ=<n>` 是常驻的 A/B / 可移植性开关。规则在 15 个扫描格子里全部命中实测最优
（K=2560 取 g8、K=10240 取 g4 —— 后者当天被 §6.10 改成 g2，见下面「遗留」）。

内核级（同一个二进制、同一份模块字节，`GEMM_SWZ=0` vs 默认，3 轮，Δmin，`/c/tmp/swz/ship2`）：

| 行数 | 形状 | 关 ms | 开 ms | Δ | TOPS 关 → 开 | CUDA（同会话） |
| --- | --- | --- | --- | --- | --- | --- |
| 4096 | ffn up 10240×2560 | 5.667 | **4.544** | −19.8 % | 37.9 → 47.3 | 3.815 / 56.3 |
| 4096 | attn out 2560×2560 | 1.473 | **1.221** | −17.1 % | 36.5 → 44.0 | 1.017 / 52.8 |
| 4096 | ffn down 2560×10240 | 8.393 | **7.468** | −11.0 % | 25.6 → 28.8 | 3.907 / 55.0 |
| 8192 | ffn up | 18.435 | **9.078** | −50.8 % | 23.3 → 47.3 | 7.481 / 57.4 |
| 8192 | attn out | 4.477 | **2.320** | −48.2 % | 24.0 → 46.3 | 2.020 / 53.2 |
| 8192 | ffn down | 19.339 | **16.501** | −14.7 % | 22.2 → 26.0 | 7.642 / 56.2 |

规则**故意不动**的六格（512 行，以及 K=2560 / 1024 行——那里 A = 5.2 MB < L2）动了 −0.2…+0.6 %，
这就是本轮的空白对照。`pf_key` 的**关**臂是机制证明：1024 行 46.5 TOPS、4096 行 37.9、8192 行 23.3
——断崖正好在 A 越过 L2 的地方，而开臂是平的（46.6 / 47.2 / 47.3）。**吞吐不再随行数衰减。**

端到端（`PROF_CHUNK` chunk 循环墙钟，B=128 / PAD_TO=512 / PREFILL_SLOTS=8 ⇒ 4096 行一块，
两轮轮换顺序，末尾同会话 CUDA）：core **17 228.9 → 15 690.8 ms（−8.9 %）** = **每 chunk −96 ms**，
total 18 535.7 → 17 055.5 ms，于是 **Vulkan/CUDA 0.753× → 0.828×**（bench 那个被污染的 prefill 列
读作 0.793× → 0.857×，方向一致；但**不能**与 §6.5 之前的 0.84× 相减——那一会话的 CUDA 绝对值是
15.3 s，这里是 16.8 s）。`prefill seeds sum=0x1b9664 xor=0x0` 在**三臂六次全部相同**，两后端也相同
⇒ 真实权重上的逐位一致性。把档位强行统一（`GEMM_SWZ=16`）比规则慢 +3.7 % ⇒ 按 K 分档是真收益。
遗留：ffn-down（深 K、窄 N）仍是 cuBLAS 的 **0.52×**——K=10240 时一列瓦片已 2.6 MB，clamp 把 g
钉在 4，一个 group 的 A 足迹（10.5 MB）还是超过 L2。**当天已补（台账 §6.8–§6.10）**：那个下界 4
是「只扫了 g∈{4,8,16}」的产物，公式对 K=10240 的原始值本来就是 2；同会话 4 轮 Δmin 配对给出
发货形状 4096 行 **7.571 → 7.270 ms（−4.0 %，4/4 不重叠）**，于是下界改成
`m 瓦片数 ≥ 16 ⇒ 2，否则 4`（1024 行实测 g2 反而 +3.8 %，保持 4；K=2560 那一族公式给 8，一字不改；
`sum(y)` 全程逐位相同）。另有三根**证伪**：`TILE_M=64`（任何 g，最好一格仍 +24 %）与
`TILE_K=64` 减半 K 链（最好 +3.0 %）与 `TILE_N=64` 换占用率（shmem 15.4 KB ⇒ 每 SM 3 块，
**+8.5~+17.7 %**）⇒ 那 26 TOPS 既不是每迭代固定开销、也不是占用率；静态核算给了理由：
**每 subgroup 每 K 步都是 12 次 `coopMatLoad` + 16 次 mma，与 K 长度无关**，两形状的内层循环
逐字节相同，差的只有「每步全局跨步 `K·2 B`（20 KB 对 5 KB）」与 grid 宽度。
⇒ 四个可换量（`GROUP_SWZ`/`TILE_M`/`TILE_K`/`TILE_N`）**全部扫完**，
**7.261 ms / 29.6 TOPS 就是 fp16 coopmat 在这个形状上的地板**（同会话 cuBLAS 3.907 ms / 55.0 TOPS
= **0.54×**，swizzle 前 0.45×）；剩下的是权重布局 / DRAM 局部性问题，归 §9 的 int8 张量核 prefill。
（★ §6.7 把这句修正了一半：`pf_value` 确实如此，但 K=2560 那一族还有**第五个可换量 = 累加器位宽**。）
−4 % 摊到整块 ≈ −11 ms / chunk = **−1.1 %**，在本机 ±2~3 % 的端到端分辨率之下
⇒ 只按内核级记账。decode 不受这根杠杆影响
（它的 GEMM 走 `gemm_imma`，批量解码的低秩 fp16 形状都在 `A > L2` 门槛之下）。

门禁：`cargo fmt --all`、`clippy --all-targets -D warnings`、`BACKEND=vulkan cargo test --release`
（batch_parity 10/1 ignored、ffn_sparse 1、0 失败）。细节见

### 6.7 第五个可换量：累加器位宽（2026-10-12）—— K=2560 那一族 **5.065 → 3.967 ms**，ffn-down 只 −3.9 %

起因：用户让看 <https://github.com/cryscan/rosalia/tree/ember> 的算子。源码级结论 —— 它 prefill 没有块序
swizzle、没有 split-K、没有 int8，decode GEMV 按槽重读权重、没有槽分组，**两条主线都在我们后面**；
唯一值得拿的机制是它 `C_TYPE=float16_t` 的 coopmat **累加器**（Turing 上半精度累加的名义 mma 速率翻倍：
54.4 → 108.8 TFLOPS）。而这个档**我们早就编好了、只是从来没接线**：`build.rs` 把 `C_BITS`/`C_TYPE` 当变体维度跑，
产出 `gemm_f16_f16{,_relu2,_tanh,_affine,…}.spv` 六条，而 `record_kernel` 只点 `gemm_f16_f32*` 那六个名字
⇒ 那六条一直是死字节。（`C_BITS` 在 `gemm.comp` 里根本没被引用；`C_TYPE` **同时**决定累加器与落盘类型
`Output { C_TYPE data[] }` —— 这就是下面全部麻烦的来源。）

零代码探针：`VK_SPV_DIR` 指一份「把六条 f16 模块的字节顶到 f32 的六个名字上」的目录
（`/c/tmp/f16acc/{base,h16}`，md5 `06d24cd0…` vs `872da250…`）。4 轮轮换、同会话、4096 行、Δmin：

| 形状 | f32 累加 ms | f16 累加 ms | Δ | TOPS |
| --- | --- | --- | --- | --- |
| 10240×2560（ffn key / 合并投影那一族） | 5.0648 | **3.9674** | −21.7 % | 42.4 → 54.1 |
| 2560×2560（att o 那一族） | 1.2966 | **1.0256** | −20.9 % | 41.4 → 52.3 |
| 2560×10240（ffn value） | 7.9841 | **7.6733** | −3.9 % | 26.9 → 27.4 |

半累加器臂的**每一轮**都低于 f32 臂的每一轮（三格全 4/4 不重叠）。⚠️ 本会话整体偏慢
（f32 臂 ffn value 7.9841 对 §6.6 发货档的 7.261，+10 %）⇒ **只读同会话配对比值，别和任何历史绝对值比**。

**两个读数**：① 深 K 的 ffn value 只动 −3.9 % ⇒ 它那块 0.54× 地板**不是 mma 速率、也不是累加器宽度**，
§6.6 结尾的「布局 / DRAM 局部性」判断保留，家仍在 int8 张量核 prefill（任务 #26）。
② K=2560 那一族**确实是累加器受限**：+28 % 吞吐，从「fp32 累加峰值 54.4 的 78 %」推到 54.1 ≈ 那个峰值本身
（也就是 108.8 的半精度累加峰值的 50 %）⇒ 翻倍没兑现，但累加器链条吃掉四分之一时间是实打实的。
存储减半能解释多少有个上限：ffn key 输出 4096×10240×4 B = 168 MB，省 84 MB ≈ 0.15 ms = 5.0648 的 **3.0 %**
（att o 同量级 ≈ 2.9 %）⇒ 累加器本身 ≈ 18 %。

★ **顺手挖出一个仪器坑（可复用的部分）**：`detect_backend()` 只要机器上有 CUDA 设备就**默认返回 CUDA**，
而 `VK_SPV_DIR` 只有 Vulkan 后端会读 ⇒ **不带 `BACKEND=vulkan` 的 `VK_SPV_DIR` A/B 是同一条 cuBLAS 路径自比**，
会开心地报出 1.6× 的假胜利且指纹逐字节相同。定根前用三种方式复现（字节全错的模块 ⇒ `sum(y)` 不变 /
只剩 16 字节头的模块 ⇒ 结果照样对 / 文件删掉 ⇒ 照样跑）。坑的第二半：`kernel_bench` 内核失败时只打一行
`pf_value batch=4096 失败: …` 然后**仍以 exit 0 结束** ⇒ 空表会被当成成功，抓输出要 `grep -E "^pf_|失败"`。
回查历史：`/c/tmp/pfv/arm3.sh:21` 一直带了 `env BACKEND=vulkan` ⇒ §6.6 之前的 Vulkan pf 读数**没被污染**。

**为什么这一臂还不能发货，以及可发货的形态长什么样**：探针把**落盘 dtype** 一起改了
（`sum(y)` 动了：4195.4004 → 62.8091、1049.0018 → 0.0007），所以它量的是一种用不了的变体。
把累加器与落盘拆开在现在的 GLSL 里**写不出来**：`coopMatStore` 要求矩阵元素类型 = 缓冲元素类型，
唯一的转换入口 `coopMatConvert` 在 glslang 15.2 的 `GL_KHR_cooperative_matrix` 下 8 种签名全不匹配
（`/c/tmp/acc16/`）。**零 dtype 改动的形态**是只挑「下游本来就是 fp16」那条链：Vulkan 稠密 prefill 的 ffn key
现在是 `gemm_relu2 → r2(f32)` + `to_f16 → r2_16`，而 ffn value 只吃 `r2_16` ⇒ 一条直接写 `r2_16` 的
`gemm_f16_f16_relu2` 同时拿到累加器的 −1.10 ms **和**省掉那一遍 `to_f16` 的 ≈0.45 ms：
≈ **−1.55 ms / 层 = −50 ms / chunk**（对 981 ms 的 chunk ≈ −5 %），**在本机 2~3 % 的端到端分辨率之上**。
代价没结账：K=2560 在 fp16 里累是 ~2 % 相对误差量级的改动，判据只能是质量门
（`cargo test --release` + `DIAG=1` + 逐 token 等价），不是秒表。
台账细节见 §6.12。

### 6.8 路 ② 已发货为默认档（2026-10-12）：ffn key 走 fp16 累加器 = **每 chunk −49 ms**

上面那句预测量完了，现在**默认开**（`PREFILL_ACC16=0` 才关；门 = `supports_gemm_f16_acc() && m_pad >= 2048`
⇒ CUDA 后端与小形状完全不受影响）。改点在 `src/gpu_model.rs:2090`（批量分块 prefill）与 `:4761`（单序列）：
`gemm_relu2 → r2(f32)` + `to_f16 → r2_16` 合成一条 `gemm_f16_acc(…, act=relu²)` 直接写 `r2_16`；
prefill 侧没有别的读者 ⇒ dtype 契约一字未改。

**为什么不能用端到端墙钟判**（本节真正可复用的产出）：一块 ≈1 s、一轮 16 块 ≈16 s，
而 SM 时钟正是在这个尺度上**准静态跳台阶**（1695~1830 MHz，1830/1710 = 1.07）⇒ ±5 % 的杠杆被 ±7~10 % 的漂移吃掉。
更糟的是进程内 `AB_VAR` 那台仪器**结构上偏置**：每轮固定先跑 A ⇒ `min(A)` 永远拿到本轮最冷的一次采样，
于是同一份日志读成「prefill +0.08 % = 打平」外加「B 档解码慢 14 %」——**两条都是伪影**。
⇒ 判这个量级必须用**逐 dispatch** 的尺，不能用整块墙钟。

**尺一（链尺）**：`kernel_bench` 新增成对臂 `pf_key32` / `pf_key16`，4096 行 = 发货 chunk 形状，同进程交替，
`env BACKEND=vulkan`，min over 3×40 iters，4 轮：

| 臂 | ms/call | TOPS |
| --- | --- | --- |
| `pf_key32`（fp32 累加 + 单独一遍 `to_f16`） | 5.1024 / 5.1144 / 5.1182 / 5.1326 | 41.8~42.1 |
| `pf_key16`（fp16 累加直写 fp16） | **3.7644 / 3.7772 / 3.7792 / 3.7880** | 56.7~57.0 |

= **−1.338 ms/call（−26.2 %）**，4/4 **两臂整个集合互不重叠**，抖动 ≤1.5 %。
（比 §6.12 的 −21.7 % 更大，因为这一臂把 `to_f16` 那遍算进了 OFF 侧。）
表尾的 `sum(y)`（268.5 vs 281.0）**不是质量门**：合成输入全正是 fp16 累加偏置的最坏情况，只证明两档确实不同。

`AB_RESTART=1` ⇒ 每档从同一状态重新 prefill；每档读**自己那 512 发**（= 16 块 × 32 层）的平均：

### 6.10 设备内批量清零：分块 prefill 的 reset 段 1409.6 ms → 4.6 ms（2026-10-12）

`State::reset` 要把 32 层 × 3 条张量 + `v_first` 共 **97 块缓冲**写零，而 Vulkan 每次 `upload` 都是
「一条 command buffer + 一次 `queue_wait_idle`」。分块 prefill 每个 chunk 开头都要把那 8 槽的小状态
清零一次（每条 prompt 都从零独立 prefill），于是每个 chunk 白付 97 次全队列同步。
同会话 `PROF_CHUNK=1` 实测：`reset=1409.6ms / total=38928.2ms` = **3.6 %**（≈88 ms/chunk、
≈0.9 ms/次提交 —— 正好是主机侧提交+等待的延迟量级）。

`ComputeBackend::fill_zeros(&[(TensorId, elems)])`：默认实现 = 逐张量零 `upload`
（**CUDA 一侧故意逐字节不变**），Vulkan 覆盖 = `Runtime::fill_zeros`，把 N 条 `vkCmdFillBuffer`
录进**同一条** command buffer，一次提交、一次等待。

| B=128、627 token prompt、w=8 ⇒ 16 chunk，同会话 | reset | core | xfer | 墙钟 total |
| --- | --- | --- | --- | --- |
| 改前 | **1409.6 ms** | 37503.8 ms | 14.8 ms | 38928.2 ms |
| 改后 | **4.6 ms** | 35751.5 ms | 13.9 ms | 35770.0 ms |

**只有 reset 那一列是证据**——它是确定性的（300 倍差距，每一遍内部可复现）。
`core` 那一列自己动了 −1.75 s（时钟/温度跳档；单次运行里逐 chunk 的 core 就在 1154~2856 ms 之间摆），
所以这**不是**「prefill 快了 8 %」那种结论。能入账的是：这一 prompt 长度下 **38.9 s 里省 1.41 s = 3.6 %**，
prompt 落进 `T_pad=512` 时 ≈**7 %**（chunk 本体减半而固定成本不变），B=256 时 ≈**2.8 s**（32 个 chunk）。

零风险的说法：写进显存的字节与原来的逐张量零上传完全一致 ⇒ 门禁是一把**逐位指纹**而不是秒表——
`decode tokens sum=0x13e742 xor=0x79b4` 改前改后相同（同 seed 同配置）。两点语义值得写明：清零**不动主机镜像**
（状态一律经 `download` 读，即设备→主机拷贝；`download_host` 只用于「内核会写进它」的张量，状态张量不是），
且 `vkCmdFillBuffer` 要求字节数被 4 整除——这里每条状态元素数都是偶数，但只要有任一项不对齐，
`Runtime::fill_zeros` 就把**整批**回落到逐张量上传，而不是静默走一条错路。

⚠️ **CUDA 故意不发这一档**（任务卡里那句反直觉的话依然成立）：CUDA 自己的 `reset` 更贵
（2.37 s 对 1.907 s），两边一起优化只会**拉大** B=256 的差距。这一格的价值在 Vulkan 的绝对墙钟，
以及主机内存与提交次数（清零不再需要那块 165 MB 主机零缓冲）。
⚠️ 值得重复一遍的仪器坑：第一次「改后」读数与「改前」逐位相同，原因是 `cargo build --release`
**不构建 examples**——那一遍跑的是过期的 `batch_decode_bench.exe`（它的指纹「相符」是空过，不是证明）。
bench A/B 之前一律 `cargo build --release --examples`，并且绑一个**只能随改动而动**的读数。
原始数据 `/c/tmp/ac16/chunk128_{base,fill,fill2}.log`；门禁 `/c/tmp/ac16/fill_gates.log`。台账 §6.15。

### 6.11 批量状态读回/回灌：一次会话换手只花 1 次同步，不是 97 次（2026-10-12）

与 §6.10 同一根杠杆，方向相反。`State::back`（整态存盘）与 `State::slot_back`（单槽存盘）每次要搬
**97 段**（32 层 × 3 张量 + `v_first`），`load`/`slot_load` 再把同样的 97 段搬回去。Vulkan 上每条
`download_part`/`upload_part` 都是「建一条 command buffer + 提交 + `queue_wait_idle`」；而旧的 `State::back`
更亏——它**每个槽都把整张量重下一遍**再切出那一行。

`ComputeBackend::download_parts(&[(张量, 元素偏移, 元素数)]) -> Vec<f32>` /
`upload_parts(&[(张量, 元素偏移, &[f32])])`：默认实现就是逐段循环 ⇒ 不覆盖的后端语义不变；Vulkan 两条都覆盖成
`Runtime::download_parts` / `Runtime::upload_parts`，把全部 N 段区间拷贝录进**同一条** command buffer，
一次提交、一次等待（`upload_parts` 先把每段 memcpy 进各自的主机镜像再提交 ⇒ 与 `fill_zeros` 不同，
**镜像保持同步**）。f32 与 fp16 状态张量都支持（`IoTensor`），偏移先做边界检查，拼接出来的布局与旧的逐字节相同。

| 同会话、同一把探针、每档取 reps 的 `min` | batch=1 load | batch=1 back | batch=8 load | batch=8 back |
| --- | --- | --- | --- | --- |
| 改前 | 15.0 ms | 24.2 ms | 119.4 ms | **819.0 ms** |
| 改后 | **6.9 ms** | **9.2 ms** | **57.1 ms** | **77.0 ms** |

两档的指纹改前改后**逐位相同**（batch=1 `sum=0x2b3b4523b71a9b xor=0x66c33dd`，
batch=8 `sum=0x159da230e933117 xor=0xe1d839d`）——这是必需的门禁，因为这次改动只是搬运方式的重组。

### 6.12 逐步解码每步 4 次宿主提交 → 1 次（2026-10-12，任务 #72）

§6.10、§6.11 收的是 prefill 与会话换手的宿主往返，这一格在**解码**，而且是客户端并发池真正跑的形态：
`batch_step_sample` = 每步一个 token、每步回主机（停词判定与流式增量都在主机侧做，自循环路径用不上）。
改前每一步要 **4 次** Vulkan 提交：上传 token、32 层前向那个批窗口、上传采样器参数（每槽 10 个 f32）、
采样窗口 —— 每一次都是 `queue_submit` + `queue_wait_idle`（§6.15 量到小拷贝单次 ≈0.155 ms 纯宿主延迟）。

- **`Runtime::upload_record(tensor, data)`**：先写主机可见镜像，再把一段**元素数精确**的宿主→设备拷贝
  **录进当前批窗口**（`record_copy_range` = 依赖追踪的 barrier + `cmd_copy_from_range` + `mark_written`），
  不再单独起一条 command buffer。窗口没开时回落 `copy_buffer`，所以在任何原来能调 `upload` 的地方都合法。
  ⚠️ 它只搬 `data.len()` 个元素，而 `upload`/`copy_buffer` 搬的是整块镜像。
- **`ComputeBackend::upload_in_batch(id, data)`**：trait 默认实现 = 普通 `upload` ⇒ **CUDA 逐字节不变，
  而且是刻意的** —— CUDA 的 `begin_batch`/`end_batch` 既不提交也不等待，那边「合并窗口」是空操作。
  契约（两处都写了注释）：批内上传之后**不要**在同一个窗口里对该张量做**独立** `download`
  —— 那样读回会抢在录进去的拷贝之前跑。
- **`batch_step_sample` 拆成两半，让两条臂执行完全相同的 kernel 序列**：`batch_step_plan`
  （定容 / `batch_buffers` —— 故意放在窗口**外面**，因为批宽变化时它会释放并重建张量）+
  `batch_step_record`（上传 token → 32 层 → norm → head，带一个只有对照臂才置 false 的 `merge_upload`）。
  门 = `STEP_ONE_SUBMIT=0` 回到旧的 4 次提交序列；**默认 = 合并档**。

**结构判据**（`PROF_SUBMIT=1`，B=1，16 步）：对照臂每步打 **2 个窗口**（8.6~9.2 ms 前向 + 0.62~0.96 ms
采样）再加上那两次不打印的独立上传；合并臂每步 **1 个窗口**（9.1~9.6 ms —— kernel 一个不少，采样只是搬进
同一个窗口）。16 步合并臂打 20 行、对照臂 36 行。

**实测**。⚠️ 原先那台进程内 `AB_VAR` 双臂**看不见这根杠杆**：它驱动的是
`submit_sample_selfloop_batch`，那条路径根本不调 `batch_step_sample`，而且它每 *n* 个 token 才提交一次
⇒「每步几次提交」在那边天生是零成本。新块 `STEP_AB=1`（配 `STEP_AB_ROUNDS=<n>`）把两臂配做在逐步路径上，
同一进程只加载一次模型，每臂各自 reset + prefill。门控与 §6.1 发货表一致，只测 Vulkan：

### 6.13 槽位迁移/广播：97×目标数 次提交 → 1 次（2026-10-12，任务 #73）

宿主同步这根杠杆的第四格（§6.10 清零 → §6.11 读回/回灌 → §6.12 逐步解码 → 这一格）。
`State::slot_move` = `3·层数 + 1` = **97** 次设备内 `copy_range`；往 *k* 个目标做 `slot_broadcast`
以前是 *k* 次独立的 `slot_move` ⇒ **97·k** 次提交，每次都是「一个临时 command buffer +
`queue_submit` + `queue_wait_idle`」（`Runtime::copy_range_standalone`）。这一格不在 §6.1 的 decode 路径上
——它是并发池里**一次会话 fork / 一次槽位紧凑化**的代价，实测 7 个目标 ≈40 ms、31 个目标 ≈176 ms。

- **`ComputeBackend::copy_ranges(&[(src, src_off, dst, dst_off, len)])`**，并把「逐条来」那圈循环单列成
  `copy_ranges_each`。trait 默认实现 = 那圈循环 ⇒ **CUDA 一侧逐字节不变**（它的 `copy_range` 是 stream
  上的一次 launch、本来就不带同步，没有东西可合）。Vulkan 覆盖 = 查门 → `begin_batch` → 记完 97·k 条
  → `end_batch` = **一次**提交 + 等待。两个守卫都是承重的：
  ① `if self.rt.recording()`（新加的只读访问器）时在窗内就**记进调用者的窗** —— 窗内嵌套 `begin_batch`
  会把正在记录的那条 command buffer `reset` 掉，**把已经记进去的 dispatch 全丢了**；
  ② 某条拷贝报错也照样收窗（`res.and(end)`），不然 `recording` 一直挂着，下一批会把这些拷贝一起带出去。
- **`State::push_slot_rows`** 现在独占「行布局」这件事（`tmix_x`/`tmix_rnn`/`cmix_x`/`v_first` 分别在
  `slot·c` / `slot·rnn`），`slot_move` 与 `slot_broadcast` 因此不会再各自漂移；`slot_broadcast` 把**所有**
  目标合成一个 item 列表，而不是每目标一窗。它的 `t >= batch` 越界校验从原来间接调的 `slot_move`
  移了进来（同一句错误信息形状）。
- `COPY_ONE_SUBMIT=0` = 对照臂（逐条提交，即改动前的行为）；**默认合并**。
  ⚠️ `State::copy_rows_from`（分块 prefill 的状态回灌）本来就自己开了一个窗，这一格没动它 ——
  但它**没有** `recording()` 守卫，所以它必须继续只作顶层调用。

**实测**（`SLOT_BENCH=1 SLOT_AB_REPS=<n>` = 新增的进程内配对块：门是**每次调用**读的 ⇒ 一个进程、
一次加载模型、一次 prefill；奇数轮换序；广播是幂等的 —— 同样的字节反复拷同样的东西，两臂除了时间
不会有别的东西不同）：

| 目标数 | 拷贝条数 | 逐条提交 Δmin ms | 合并 Δmin ms | 逐轮配对均值 Δ（逐条 − 合并） | 符号检验 | 倍数 |
|---:|---:|---:|---:|---:|---|---:|
| 7 | 679 | 38.56（均值 41.22） | **2.26**（均值 2.40） | **+38.2 ms**（+44.1 +37.4 +36.3 +38.3 +38.8 +38.1） | 6/6 | 17.1× |
| 31 | 3 007 | 175.97（均值 178.99） | **10.50**（均值 11.07） | **+167.9 ms**（+165.5 +169.9 +168.7 +167.6） | 4/4 | 16.8× |

这一格**不在尺子地板之下**：那段时间是孤立测的、内容是纯宿主往返、效果是 16~17 倍且 10/10 配对同号、
两臂区间零重叠。合并臂剩下的那点是**真实设备流量**（31 个目标 ≈335 MB 读 + 写在 10.5 ms 里），

## 8. 与信天翁 Albatross、cryscan/rosalia 的关系

本项目最初参考了两份已有的 RWKV 推理实现：

- **信天翁 [Albatross](https://github.com/BlinkDL/Albatross)**（Apache-2.0）：RWKV-7 的 **CUDA** 高性能推理引擎（官方声称 7.2B fp16 单卡 5090 上 **15000+ tps decode**）。本仓库的 **kernel 融合、sequence-parallel 批量提交、argmax 采样（只回传 token 索引）、pipeline 编译一次复用**等设计均对标/借鉴其思路。
- **[cryscan/rosalia](https://github.com/cryscan/rosalia)**：**Rust + Vulkan 计算着色器**的 RWKV 推理引擎。本仓库在 **Vulkan 内核骨架、运行时结构与部分算子的初始设计**上受其启发。

| 维度 | Albatross | rwkv-rsv |
|---|---|---|
| 计算后端 | CUDA（单厂商） | Vulkan / CUDA（跨厂商/跨平台） |
| 路线 | 极致性能，硬件特定优化 | 可移植性优先，运行时自编译 shader |
| 权重精度 | fp16 | fp16 / **int8**（自动路由，显存下限 8GB） |
| 相对差距（CUDA 批量解码） | 基准 | **已反超** —— 同会话交错那一次（2026-09-22）B=8~256 快 **+11% ~ +26%**；信天翁已不在本机，**该列不可刷新，也不可与 §6.1 主表跨会话相除**（见 §6.1） |

在 CUDA 路径上，这个差距后来被**int8 张量核 + int8 常驻权重**（每 token 字节数减半、张量核峰值翻倍）、split-K、多链合并 launch 与形状感知 tile 追平并反超（见 §6）。在 **Vulkan** 路径上，**同一 SIMT 口径**的追平也已达成：r/k/v 融合核改读 **fp16 激活**（流量减半）、权重 `vec4` 打包 + `dot`、`x` 分块常驻 shared memory —— 最后约 40% 的差距由此关闭，Vulkan 在**两边跑同一条 kernel 序列时**相对 CUDA 吞吐中性，同时保留跨厂商能力。但**对 CUDA 默认口径并不中性**：`VK_IMMA_OPS` 默认唯独把 r/k/v 批量核留在 SIMT，而 CUDA 侧它走 int8 张量核，大批量的差距主要就在这里（见 §6.1 主表与「口径」段）。

在以上两者的启发下，本仓库随后独立演进，新增了它们都没有的能力：**两路权重量化推理**（fp16 / int8 自动路由）、**CPU fp32 参考实现与 GPU 内核正确性单测**、**离线量化工具链**与可复现的精度验证工作流。

## 9. 已知限制与后续方向

- **prefill dequant 开销 ~10%**（T=512 时 int8 vs fp16）：彻底消除需 cooperative-matrix 融合反量化+GEMM（Marlin 式零副本），列为长期方向。
- **prefill 每 token 耗时随 T 近二次方增长**（T=256: 0.33ms → T=512: 0.81ms，WKV 并行形式的 chunk 内项），长 prompt 可关注 WKV 分块策略。
- **Vulkan dplr_seq 占用率偏低**（40 workgroup × 64 线程 + 每 token 2 次 barrier，稳态 prefill 中 ~10ms）：可对齐 CUDA 版结构（block 并行行 + shuffle 归约）。
- **新长度桶首次 prefill 付 pipeline 创建成本**（kernel cache 已按 (shader, spec) 共享 uniform 池 + DYNAMIC offset 解耦，条目 1722 → ~30；剩余为 spec 首现的固有创建费）：可用启动预热消除。★ 2026-10-10 `BUCKET_BENCH=1 SLOTS=8`（3B int8，新桶 = `PAD_TO+128`）实测这条**不止** pipeline 创建：换一个长度就整表重建 45 个 `[bt,·]` 序列缓冲，代价是**秒级**——冷桶首请求 CUDA 1809.0 ms vs 同桶重复 942.7 ms（省 864.1 ms）、Vulkan 3641.0 vs 2493.2 ms（省 1152.2 ms）。`warmup_len_buckets` 把它从「用户等」变成「启动期等」，**总代价一点不省**（预热成本 1845.3 / 3623.4 ms ≈ 冷桶首请求），而且 `SeqBuffers` 是**单槽**缓存 ⇒ 预热列表里只有最后一个桶留在显存；长度来回变的请求得固定 `pad_to` 或按桶各留一个模型。
