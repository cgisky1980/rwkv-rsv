[English primary doc](README.md) · [中文版](README_CN.md)

**RWKV-7 推理引擎（Rust + Vulkan/CUDA 计算着色器）**，支持 **fp16 / int8(8-bit)** 两路权重量化推理，按模型文件自动路由、互斥共存；附 **CPU fp32 参考实现**用于精度验证与内核调优。

## 一眼看懂（2026-10-12）

同一会话、两后端交错配对、轮次间反序、4 轮、`power.limit` 300 W、RWKV-7 Goosed g1h-3B int8。**给绝对数字；倍率是从绝对数字算出来的，不是反过来。**

| 路径 | Vulkan | CUDA | Vulkan / CUDA | 大白话结论 |
|---|---|---|---|---|
| **单流，一次一个 token**（桌面客户端走的就是这条） | **8.842 ms/token** | 10.131 ms/token | **1.15×** | Vulkan 更快 |
| 批量解码 B=1 | 9.85 ms/步 | 11.37 ms/步 | **1.16×** | 更快 |
| 批量解码 B=8 | 11.73 ms/步 | 14.11 ms/步 | **1.20×** | 更快 |
| 批量解码 B=32 | 18.23 ms/步 | 18.41 ms/步 | **1.01×** | 打平 |
| 批量解码 B=64 | 29.07 ms/步 | 24.52 ms/步 | 0.84× | 慢 4.55 ms/步 |
| 批量解码 B=128 | 52.61 ms/步 | 39.77 ms/步 | 0.76× | 慢 12.84 ms/步 |
| 批量解码 B=256 | 96.64 ms/步 | 75.86 ms/步 | 0.79× | 慢 20.78 ms/步 |
| 批量 prefill B=1 … 256 | 768 / 2 373 / 5 613 / 9 994 / 19 350 / 39 195 ms | 2 721 / 4 284 / 8 123 / 12 445 / 22 084 / 42 561 ms | **3.55× … 1.09×** | **六档全部**更快 |

## 1. 作用

`rwkv-rsv` 是一个纯 Rust 实现的 **RWKV-7** 推理引擎，推理运行在 **Vulkan / CUDA 计算着色器**上，跨 GPU 厂商（NVIDIA / AMD / Intel / 移动端）与操作系统（Windows / Linux / macOS）。

核心目标有二：

1. **降低显存占用**：通过离线权重量化（int8 8-bit 省 41%）在不大幅损失精度的前提下，把 3B 模型权重从 5.49GB（fp16）压到 3.22GB。
2. **可复现的精度验证**：提供 CPU fp32 参考实现与 GPU 内核级单测，把「内核误差」与「量化误差」隔离，逐层逐 token 验证。

默认面向 **RWKV-7 Goosed g1h-3B** 模型，但模型结构按 safetensors 张量形状自适应，可加载同系其他规模模型。

## 2. 设计目标

- **可移植性优先，但要说清代价**：以 Vulkan 为主后端，换取跨厂商 / 跨平台可用性。同一张卡、同一会话、与本仓自己的 CUDA 后端实测：
  - **并发低的那一侧——也就是真实应用待的地方——Vulkan 领先**：客户端走的单流 1.15×，B=1 / B=8 为 1.16× / 1.20×，B=32 打平。
  - **大批量 decode 仍然落后**：B=64 / 128 / 256 为 0.84× / 0.76× / 0.79×。
  - **批量 prefill 六档全部领先**（3.55× → 1.09×），且两后端种子逐位相同。
  - 剩下的差距**不是摊在整个引擎上**：§6.6 把它归到一个核。
- **两路量化共存**：fp16（无损参考）/ int8（近无损）按模型文件自动路由，同一二进制全部兼容。
- **运行时自编译 shader**：`build.rs` 在构建期用 `glslangValidator` 把 `*.comp` 编译为 SPIR-V，`constant_id` 做跨硬件自适应。
- **研发向**：内嵌 CPU fp32 参考、DIAG 三方核对、logits 对比、teacher-forced Top-1 一致率、逐核 GPU 时间戳、同会话 A/B 编排器，以及一套**不需要模型文件**的内核级基准。

## 3. 构建

需要 **Rust（edition 2024）** 与 **Vulkan SDK**（`glslangValidator`；`build.rs` 在构建时把 `assets/shaders/src/*.comp` 编译为 `assets/shaders/spv/*.spv`）。

```bash
cargo build --release
cargo build --release --examples   # ★ 跑任何示例/基准前必须有这一行
```

⚠️ **第二行不是可选项。** `cargo build --release` **不会**重建 `examples/*`，所以改完代码去跑基准，默默执行的是**旧二进制**，报出来的是旧数字。本仓的实测记录里已经因此产出过错误结论（§6.5 第 10 条）。

## 4. 运行

加载模型（默认 `c:\work\niceui\rwkv-g1h-3B.st`，可用 `MODEL_PATH` 切换；含 `.int8_idx` → int8，否则 fp16）：

```bash
cargo run --release
```

主要 env 变量（详见 [src/main.rs](src/main.rs)）：

| 变量 | 作用 |
|---|---|
| `MODEL_PATH` | 模型路径；含 `.int8_idx` → int8，否则 fp16 |
| `BACKEND` | `vulkan` / `cuda`，显式选择后端。⚠️ A/B 脚本里**必须显式写**；不写会沿用上一臂留下的状态。 |
| `TOP1_MULTI_SAVE` / `TOP1_MULTI_COMPARE` | 多 prompt 的 teacher-forced Top-1 一致率验证 |
| `TOP1_REF_SAVE` / `TOP1_REF_COMPARE` | 单 prompt 的 CPU fp32 参考一致率 |
| `SAVE_LOGITS` / `COMPARE_LOGITS` | 单 prompt logits 的 RMSE / Top-10 对比 |
| `GEN_TOKENS` / `REPORT_EVERY` | 连续自回归生成（`memtest` 子流程） |
| `DIAG` | 三方核对（seq / tok / CPU）+ dequant 校验 |
| `PROF_GPU` / `PROF_HOST` / `PROF_GAPS` | 逐核 GPU 时间戳 / 宿主录制成本 / dispatch 之间的间隙。⚠️ `PROF_GPU` 的查询池**每窗只装 2 048 条 dispatch**，超出的被丢弃——此时会打印 `⚠ 查询池已满`，那张表和 `SUM` 都只是**窗内前缀**，不能当整窗 GPU 忙碌时间。宽批下一窗≈一步。⚠️ 与 `SELFLOOP_PIPE` 互斥（硬报错，不产出假时间戳）。 |
| `PROF_LOW` | 打印低秩链真实的绑档决定（`stage1=true/false`、每个形状选中的瓦片）——一条**与速度无关**的「哪条臂在跑」证据 |
| `SELFLOOP_PIPE` | **仅 Vulkan 的分窗提交**（`<每窗轮数>`，**默认 2=开**；设 0 关闭）。不开时一整段自循环录进**一条** command buffer、末尾才提交一次，于是 GPU 在整段宿主录制期间空转（`PROF_HOST` 稳态量到：B=128 = 3.14 ms/步，单流 = 0.69 ms/步）。开了每 k 轮提交一次且**不等待**，录下一窗时 GPU 正在吃上一窗。**两条自循环路径都吃这根杠杆**——批量解码与桌面客户端走的单流。单流侧另有两道安全门：段长必须大于一窗，且必须走「每轮各写自己的采样参数行」那条路，否则在飞的窗口会读到后面轮次的采样参数。值为**固定** −2.25 / −3.19 / −2.93 / −3.20 ms/步（B=8/32/64/128）、单流 −1.08 ms/步 ⇒ 并发越低相对收益越大。台账：合集 §6.23，原始配对表在 [参考/2026-10-11-Vulkan-prefill-fp16-GEMM瓦片档修正-实施记录.md](参考/2026-10-11-Vulkan-prefill-fp16-GEMM瓦片档修正-实施记录.md) §6.24。 |
| `VK_IMMA_OPS` | 哪些批量张量核（W8A8 int8）算子开启；2026-10-10 起默认**全开**（head/out/key/val + rkv）。`VK_IMMA_BM` / `VK_IMMA_NST` 选瓦片，`VK_IMMA_KSPLIT*` 选 split-K 形状。 |
| `LOWRANK_GEMM2` / `LOWRANK_GEMM1` / `LOWRANK_MIN` | 低秩链上 coopmat fp16 张量核。二级默认 `batch >= 32`；一级（mid 投影）默认 `batch >= 64`，因为 B=32 实测是 **−8…−10 % 净亏**。`GEMM_SK`（split-K）**默认关**——汇总 +2.6 % 且符号不一致，等于没收益，只在被抢占时有用。 |
| `WKV_STATE_F16` | Vulkan 侧 RNN 状态存 fp16（`_s16` 臂）。B=128 省 **−1290 MiB**，B=1 贪心 token 逐位相同（0/64 分歧）——但**不会**让状态核时间减半，因为算术仍是 fp32。 |
| `GEMV_BGRP` / `MID_GG` | SIMT 臂每 workgroup 服务的槽数。两个后端都实测 **8 是最优**（16/32 = −8.6 / −7.1 %）；CUDA 侧同族旋钮 `MID_GG` 实测 GG=1 1.03 ms 对 GG=8 4.66 ms。 |
| `SKIP_GRAPH` | **仅 CUDA** 的空对照。在 Vulkan 上是空操作——这正是它的用处：Vulkan 下「`SKIP_GRAPH=1` 赢了」等于什么都没测（曾据此造出过 −8.31 %、6/6 同号的假杠杆）。 |
| `ABLATE` | **跨后端的「移除法」尺**。CUDA：逗号分隔核名，跳过这些 launch。Vulkan：同样的名字，实现在唯一 dispatch 出口（`src/runtime.rs` 的 `record_kernel`），保留管线/uniform/barrier，只去掉 dispatch 和它那两条时间戳。⚠️ 名字打错会**静默匹配不到**、读成「零收益」，所以每个名字首次命中都打日志。⚠️ 只有「被删核的输出去向不影响别的核」时读数才成立：消融 `gemm_imma_bm64_nst8` 读出 **−47 %**（垃圾进 `relu²` ⇒ 稀疏 FFN 不再稀疏），所以张量核 GEMM 的份额只能看 `PROF_GPU`，不能用消融。 |
| `VK_SPV_DIR` | **着色器 A/B 仪器**。从这个扁平目录加载全部 `*.spv`，而不是内嵌副本。必须有它，是因为 release 构建把 `assets/shaders/spv/*.spv` 烘进了二进制（[src/vulkan/asset.rs](src/vulkan/asset.rs) 的 `#[derive(RustEmbed)]`）——把新字节拷到磁盘**不会**改变正在跑的 exe 执行什么，没这个开关就会在以为换了内核的情况下默默基准测旧内核（合集 §6.10 的读数就是这么作废的）。指向某一臂的目录，并把实际绑定的每枚 spv 的 md5 打日志。文件缺失是**硬报错**（无静默回落），所以它能当臂标记用。 |
| `GEMM_TILE_M` / `GEMM_TILE_N` / `GEMM_TILE_K` / `GEMM_MIN_BLOCKS` / `GEMM_SWZ` / `GEMV_BLOCK_SIZE` / `GEMV_ROWS` | 覆盖跨硬件自适应参数。⚠️ `GEMM_TILE_*` 是**直接覆盖**，会绕过 `gemm_tile_for` 的结构下界（§6.6）。 |
| `UNIFORM_POOL_MB` | Vulkan uniform 池容量（MB，默认 8；占用是「批内不同 params 组合数」的 O(1)，实测高水位 69KB —— 这是极端形状兜底项，不是需要调的参数） |

### 4.1 示例程序（web-rwkv 风格）

```bash
# 模型信息：加载模型、打印 ModelInfo、probe 前向
cargo run --release --example model_info
# 自回归生成：prefill + GPU self-loop（argmax 确定性 / sample 采样）
cargo run --release --example generate          # env: NTOKENS, TEMP, TOPK, TOPP, GEN_MODE, VOCAB_JSON
# 吞吐基准：infer_seq / infer_tokens / argmax_selfloop / sample_selfloop
cargo run --release --example benchmark
# 稳态 prefill 基准（同长度预热后测第二次起，排除一次性 pipeline 创建开销）
cargo run --release --example prof_prefill_steady   # env: PTOKENS
# 批量并发吞吐/正确性基准：SLOTS × SEGS × NTOK，含 STEP=1 两条路径对拍、SLOT_BENCH=1 槽位分发、
# BUCKET_BENCH=1 长度桶预热四档、BENCH_JSON=<路径> 把「读数 + 完整门控」落成一行 JSON
cargo run --release --example batch_decode_bench    # env: MODEL_PATH, SLOTS, PAD_TO, TOPK, STEP, BENCH_JSON
# 同会话**交错 A/B** 编排器（基准可信度的唯一正当姿势）：轮换测量顺序、串行子进程，
# 出中位数 + 离散度 + 倍率 + 跨后端指纹一致性表；AB_SLOTS/AB_ROUNDS/AB_JSON/AB_SUMMARY
cargo run --release --example bench_ab
# 内核级 A/B，**不需要模型文件**（权重与激活都是合成数据）：按形状单独计时，
# 打印 `sum(y)` 作为「内核确实跑了」的守卫。env: KB_OPS（逗号列表）, KB_BATCH, KB_ITERS, KB_REPEATS
cargo run --release --example kernel_bench
# State 序列化：前进→state_back→存盘→state_load→state_back 无损闭环
cargo run --release --example state_persist     # env: OUT=state.bin
```

⚠️ `kernel_bench` **哪怕所有臂全失败也 exit 0**。只看返回码的驱动脚本等于没验证；必须 `grep` 每臂的结果行。

### 4.2 库 API 与 GPU 采样

`rwkv-rsv` 同时以 **library** 形式导出，便于服务端（如 `ai00-server`）集成，对标 [web-rwkv](https://github.com/cryscan/web-rwkv)：

- **`ModelBuilder` + `Bundle`**：加载模型并绑定零初始化 `State`；`infer_tokens` / `infer_seq` / `infer` 推进会话并返回 logits。
- **`State`**：一等公民的会话状态——`state_back()` 下载为 CPU `Vec<f32>`，`state_load()` 回灌，`reset()` 清零，序列化逐位无损。
- **GPU 采样（`SamplerParams`）**：`infer_sample` / `infer_sample_selfloop` 全 GPU 端过滤 logits，只回传采样 token 索引。
- **并发池原语（批量布局 `State`）**：`create_batch_state(B)` + `forward_seq_batch_padded` / `submit_sample_selfloop_batch` / `batch_step_sample`；
  槽位管理走 `state_slot_back` / `state_slot_load`（宿主往返）与 `state_slot_broadcast`（**设备内**把一份状态分发给多个槽，
  会话 fork / 同 prompt 多路采样用，省掉每目标 2× 单槽状态的 PCIe 往返）；
  启动期用 `warmup_len_buckets(state, &[T_pad…])` 把长度桶的序列缓冲重建从首个真实请求挪到启动期
  （★ 缓冲单槽：只有列表里最后一个桶留在显存）。批量 **decode** 的前提查 `supports_batch_decode()`，
  不满足时 `batch_decode_blocker()` 给出**是哪一条**前提（后端缺算子 vs 模型无 int8 句柄）。
  ⚠️ 这条门只管批量 decode：`forward_seq_batch_padded`（批量 prefill）走 seq 并行核，
  **fp16 模型一样可用**，且每槽状态与单流逐位一致（2026-10-10 两后端实测）。
  返回值是各槽提示词的末 token（解码种子），不是下一 token 预测。

## 6. 指标

本节所有硬件读数出自一张 **RTX 2080 Ti**（68 SM，实测 DRAM 屋顶 616 GB/s，同时驱动显示器）。模型：RWKV-7 Goosed g1h-3B——`C=2560 / H=40 / N=64 / V=65536 / L=32`，权重 fp16 5.49 GB / int8 3.22 GB。完整报告在 [参考/](参考/)。

**量化路径怎么选**：选 int8——显存省 41 %，对 CPU fp32 参考的 Top-1 一致率 98.8 %（§6.4），而且**所有张量核臂与批量 decode 都长在 int8 上**（fp16 模型根本没有批量 decode，见 §9）。fp16 保留为无损参考，也是裸 `.st` 的格式。早年那组 fp16↔int8 吞吐对（2026-08，未交错）读 int8 ≈ **+32 %（Vulkan）/ +36 %（CUDA）**，此后没重测过，只能当方位感，不能当现行数字。

下面每一行都是**同会话、两后端交错、轮次间反序、≥ 4 轮、同轮配对中位**（除标注外）。倍率 = CUDA 吞吐 / Vulkan 吞吐，所以 **> 1.0 表示 Vulkan 更快**。`power.limit` 300 W（现行发货档）。

### 6.1 桌面客户端真正走的那条路（单流）

§6.2 那张六档表的 B=1 是**批量核跑宽度 1**；客户端是**一条流一次一个 token**（`submit_sample_selfloop`）。这一格第一次有同会话成对表（2026-10-12）。

| 口径 | Vulkan | CUDA | 倍率 |
|---|---|---|---|
| 同轮配对中位（4 轮） | **8.842 ms/token**（113.1 tok/s） | 10.131 ms/token（98.7 tok/s） | **1.146×** |
| Δmin（各轮最好） | 8.696 ms/token | 10.070 ms/token | 1.158× |
| 轮间极差 | **1.9 %** | 14.9 % | — |

**Vulkan 每 token 领先 1.29 ~ 1.37 ms**，四轮全部 ≥ 1.14×，所以方向不依赖任何单格。8 臂打印**同一枚顺序敏感指纹** `sum=0x278a9c xor=0x7354 mix=0xcfeeb6baaf81b753` ⇒ 两后端在这条路上逐位等价。CUDA 那 14.9 % 的极差来自有一轮读到 86.4 tok/s，期间卡从 46 ℃ 走到 62 ℃。

仅作方位感（**跨会话，不可相减**）：2026-10-10 这一格读的是 CUDA 91.4 / Vulkan 79.2 tok/s = **0.87×，即落后**。转向出自分窗这根杠杆（合集 §6.23 及其单流补记）。原始数据 `/c/tmp/ac16/s52/`，台账 [参考/2026-10-11-Vulkan-prefill-fp16-GEMM瓦片档修正-实施记录.md](参考/2026-10-11-Vulkan-prefill-fp16-GEMM瓦片档修正-实施记录.md) §6.27。

### 6.2 批量 decode 六档（第十二次复测，2026-10-12）

构建 = 合集 §6.23 的分窗提交**默认开启**。口径：`SEGS=4 NTOK=32 PAD_TO=512 WARMUP=1 SKIP_SINGLE=1 PROMPT_REPEAT=6 TOPK=1 PREFILL_SLOTS=8 TEMP=1`，六档 × 4 轮，48 臂全 clean。

| 并发 | Vulkan ms/步 | CUDA ms/步 | Δ（Vulkan − CUDA） | CUDA / Vulkan | 对第十一次 |
|---|---|---|---|---|---|
| B=1 | **9.85** | 11.37 | **−1.52** | **1.155** | 0.914 → 1.155 |

| 检查 | 结果 |
|---|---|
| int8 对 CPU fp32，teacher-forced Top-1（512 个下一 token） | **98.8 %**（506/512） |
| int8 对 fp16 的 logits | 权重级 avg cos **0.999820** / rel **0.6135 %** |
| int8 权重 vs fp16 | 5.49 GB → **3.22 GB**（−41 %） |
| Vulkan 状态 fp16 化（`_s16` 臂），B=128 | 注册显存 **−1290 MiB**；logits rmse 3.227 → 3.223（未变），贪心 token **0/64 分歧** |
| `STEP=1` 两条路径对拍（批量 vs 逐槽） | 批量 prefill 之后的每槽状态**逐位相同**，两后端都是 |
| Vulkan 对 CUDA，B ≥ 8 | **按设计就不同**（内核与累加顺序不同）——不是 bug，这也是跨后端 A/B 只能读**吞吐**、不能读「相等」的原因 |

**一个改动动了数值要怎么才能发货。** 动了算术的改动（某一级 fp32 → fp16、归约顺序变了、split-K 求和）**不能**拿「token 流没变」当证据，因为它真的会变：一级 fp32→fp16 会让贪心 token 流分叉，而二级的发货判据是逐位相同。本仓改用**同一把尺的三角对照**——全旧 vs 已发货、全旧 vs 新、已发货 vs 新——按**距离**准入，外加 argmax 分歧计数。另有两条**已知伪证指标**，永远不许当证据引用：`seq vs cpu max_abs_diff`（第一个 token 就定死了，之后一切都不敏感）、`deployment-summarize` 的 2×2（把两种不同误差舍进同一格）。台账：合集 §6.9、§6.20 – §6.21，以及 [参考/2026-10-11-Vulkan-mid投影臂向量化-实施记录.md](参考/2026-10-11-Vulkan-mid投影臂向量化-实施记录.md) §11 – §12（那两个真的会分叉的臂的三角对照）。

### 6.5 这些数字该怎么读（十条纪律）

这条线上的差距是 1 ~ 3 %，噪声是 5 ~ 15 %，所以**纪律本身就是测量**。每条规则都是用一条错误结论换来的，出处都在合集里。

1. **一个进程独占显卡。** 绝不同时跑两个基准，也别拿时间上重叠的两个进程互比。
2. **绝对 ms 不许跨会话搬运。** 倍率同样不搬：同一枚编译好的着色器，逐核 per-avg 跨进程摆过 **±12 %**（0.1854 – 0.2219 ms）。凡是「比两个不同进程」的设计，结论只能是方向性的。
3. **同轮配对中位、≥ 4 轮、轮次间反序。** 「各轮最好值再取最小」在有一臂每轮先跑时是**结构性偏置**，在单调回暖（卡从 1695 飘到 1830 MHz）时彻底失真。本表的分辨率 ≈ 2 ~ 3 %。
4. **写明功耗档。** 这张卡有四个不同的档（250 W / 300 W / `-lgc` 锁 1860 / 热态），不同档的数字是不同的物理。300 W 基线以上的行不可与它互减。
5. **必须跑空对照。** `SKIP_GRAPH` 在 Vulkan 上是空操作，所以 Vulkan 下它的「赢」在量一件不存在的事——它抓到过一条编造的 −8.31 %（6/6 同号）。
6. **配对跑完必须 grep 臂标记行。** 一臂压根没启动时什么也不打印，读起来像通过（`STEP_AB` 缺 `STEP=1` 就是静默空跑）。「两臂数值相同」对逐位不变的改动是**预期结果**，不能当臂标记；标记要走硬报错（`VK_SPV_DIR` 缺文件）或实际绑定字节的 md5。
7. **首段是脏的。** `record_kernel` 未命中会走 `create_kernel`（VkPipeline 创建，一次性 82 – 88 ms）⇒ 首段的宿主读数是 5.1 – 6.1 ms/步，而稳态是 3.14。旧记录里那个 5.15 就是这么来的，**已撤回**。
8. **要知道哪些仪器可信。** `PROF_CUDA_KERNEL` 在 150 ms 的墙钟窗口里报出 6 249 ms。「移除法」（消融）只有在被删核的输出去向不影响别的核时才可读：消融 `gemm_imma_bm64_nst8` 报 **−47 %**（垃圾进 `relu²` ⇒ 稀疏 FFN 不再稀疏），所以张量核份额一律看 `PROF_GPU`。
9. **任何着色器 A/B 都要走 `VK_SPV_DIR`**，并打印每臂实际绑定的 spv md5（见 §4）。
10. **跑任何示例前先 `cargo build --release --examples`**（见 §3），否则测的是昨天的二进制。

### 6.6 差距里还剩什么

一个核。B=128 解码一步的 `PROF_GPU` dump（它自己那次会话——下面的 46.19 ms 是 GPU 忙碌时间，**不是** §6.2 那 52.61 ms 的墙钟步；合集 §6.19 在另一次会话里复核过这批份额，`gemm_imma` 读到 50.6 % 对这里的 51.7 %）：

| 内核 | ms/步 | 份额 |
|---|---|---|
| `gemm_imma_bm64_nst8`（int8 张量核 GEMM） | **23.90** | **51.7 %** |
| `fuse_ka_dplr_norm_s16`（批量状态核） | 8.73 | 18.9 % |
| 低秩整链（一/二级**都**已在 coopmat fp16 上：`gemm_f16_f32` 3.52 + `to_f16_triple` 0.94 + `gemm_f16_f32_tanh` 0.83 + 四条 epilogue 0.95） | ≈6.2 | ≈13.4 % |
| `gemm_imma_reduce`（split-K 归约） | 1.99 | 4.3 % |
| `sample` | 1.49 | 3.2 % |
| `quant_x_i8`（激活量化） | 1.35 | 2.9 % |
| GPU 合计 | 46.19 | — |

**`gemm_imma` 一家的 23.90 ms 就比这一档 12.84 ms 的整步差距还大。** 在**同一形状**上，Vulkan 臂跑到 **34.8 TOPS**，CUDA 是 **50.9 TOPS**，而候选解释已被逐一实测排除：

- **不是带宽（在宽批这一点上）。** 同一个核族在 B=1 时把 2.5 GB int8 权重读一遍用 5.53 ms/步 = **455 GB/s ≈ 616 GB/s 屋顶的 74 %** ⇒ 窄批贴在屋顶上，没得赢。B=128 用 20.8 ms：读一遍相当于 120 GB/s，读两遍 240 GB/s ⇒ **远离屋顶**，约束在算力/占用。这也解释了为什么 `NST=16`（「把权重只读一遍」）实测无效——重读确实存在，但省掉它也不会快。
- **不是延迟隐藏。** Vulkan 的跨瓦片软流水（`IM_PIPE`，正是从 `rosalia/ember` 抄来的那一手）实测 20 格里 **13 格更慢**且符号不一致；CUDA 自己那份同名想法（`IMMA_PIPE` / `IM_NBUF`）实测 **−36 %**。驻留块（smem ≈23.8 KB ⇒ 每 SM 2 块 × 8 warp）本来就互相盖住了载入延迟。
- **不是指令量，也不是落盘时序。** 指令砍到 1/4 反而更慢；累加器 flush 的三种换列各得 −1.1 / −2.0 / −5.2 %（低于 3 % 的内核级立项门槛），而且写侧与 smem 读侧互相锁死。

剩下的唯一解释是 **coopmat 累加器必须绕 smem 一圈**：GLSL 不暴露「哪个 lane 拥有 m16n8 片段的哪个元素」，于是 `coopMatStore` → `subgroupBarrier` → 标量 `LDS` 读 → `subgroupBarrier` → 落盘是**唯一**的消费方式，`subgroupShuffle` 也搬不动它（源寄存器下标随 lane 变，不是 uniform）。nvcc 是把 mma 片段直接握在寄存器里，去量化与写回都在寄存器完成。**要补这一格就得动编译器/接口层**（SPIR-V 片段直取，或自有的瓦片约定），在 GLSL 里继续调度已经用尽。这才是剩下的工作，不是笼统的「Vulkan 更慢」。

### 6.8 已经走死的路（实测证伪，没有新证据别再试）

- **`gemm_imma` 的重排，五条子路**：① 跨瓦片软流水（`IM_PIPE`，13/20 格更慢）；② split-K 当**吞吐**档（`GEMM_SK`；它是**抢占保险**，只有被抢占时 +34 ~ 41 %）；③ 权重片段直读全局（−32 … −42 %）；④ 宽列 `BN=16` 档（+6.5 … +39 %）；⑤ epilogue 落盘换序（最好 −1.1 %）。flush 的双 barrier 结构走**读码即死**。根因见 §6.6。
- **批量状态核**：DRAM 受限，已在屋顶（418 GB/s = 616 峰值的 68 %）。两行交织与相邻列对访问都已发货，但**两者都没有端到端收益可记**——产出「−0.98 %」的那个四臂扫描比的两个 `VK_SPV_DIR` 臂里装的是**同一份内嵌字节**。
- **mid 投影臂的形状**：`GEMV_BGRP` 16/32 = −8.6 / −7.1 %；把那四个循环改成 `vec4` + `dot` = −6 … −9 %（CUDA 在同族旋钮上量到同一道断崖）。「这条臂受指令发射限制」这个前提本身被证伪：指令 ÷4 反而输。
- **fp16 seq 路径上的 `pf_value` / ffn-down**：停在自身流量下界的 **0.54×**（swizzle 之前是 0.45×），mma 速率与累加器位宽两个解释都被实测排除，剩下的是权重布局 / DRAM 局部性问题 ⇒ 归到 §9 的 int8 prefill，而不是一次调参。
- **`SELFLOOP_CHUNK`**（另一种流水方案）：打平。
- **`batch ≤ 4` 的专用瓦片档**：**仍然开着**，而且它是「没测过」而不是「已证伪」——`IM_BM` / `IM_NST` / KSPLIT 在小批档从未扫过。
- **参考仓库**：信天翁 Albatross 已不在这台机器上（它那组 +11 … 26 % 无法刷新，也**不许**除进 §6 任何 CUDA 列）。`cryscan/rosalia` @ `ember` 已逐算子勘察完：它**根本没有 int8 路径**（全树 grep `int8`/`coopmate` 零命中），也就是真正落后那个核它没实现；唯一可学的一招是「下一瓦片留在寄存器里的预取」，而那一招就是上面第 ① 条——我们这边已实测证伪（EN 合集 §6.22 / CN 合集 §6.18）。

## 8. 与信天翁 Albatross、cryscan/rosalia 的关系

本项目最初参考了两份已有的 RWKV 推理实现：

- **信天翁 [Albatross](https://github.com/BlinkDL/Albatross)**（Apache-2.0）：面向 RWKV-7 的高性能 **CUDA** 引擎（声称单张 5090 上 7.2B fp16 解码 15 000+ tps）。本项目的**内核融合、序列并行批量提交、argmax 采样（只回传 token 索引）、一次编译反复使用**等设计取自或对标它的做法。⚠️ 它**已经不在这台机器上**，所以它那一列实测（「B=1 打平，B=8 – 256 领先 **11 % … 26 %**」）无法刷新，也**不许**除进 §6 的 CUDA 列。
- **[cryscan/rosalia](https://github.com/cryscan/rosalia)**：**Rust + Vulkan 计算着色器**的 RWKV 引擎。本项目的 **Vulkan 内核骨架、运行时结构、部分算子的初始设计**受它启发。2026-10-12 已把 `ember` 分支逐算子勘察完：它**没有 int8 张量核路径**（合集 CN §6.18），对 §6.6 那一格没有可抄的东西。

当年与 Albatross 的差距来自 ① 它更激进的内核融合，② CUDA Graph 捕获削掉 launch 开销，③ 它成熟的针对性硬件库。此后 CUDA 路径上这笔差距已被**反超**，靠的是 **int8 张量核跑常驻显存的 int8 权重**（每 token 字节数减半、张量核峰值翻倍）、split-K、多链合并 launch 与形状感知瓦片。

在两者启发下，本仓此后独立演化，加入了两者都没有的能力：**两路权重量化**（fp16 / int8 自动路由）、**CPU fp32 参考 + GPU 内核级单测**、以及带可复现精度验证流程的**离线量化工具链**。

## 9. 已知限制与后续方向

- **大批量 decode 仍落后 CUDA**（B=64/128/256 = 0.84× / 0.76× / 0.79×），而且这是**一个核的问题**——见 §6.6。还能动的只有 §6.8 之外那两条：`batch ≤ 4` 的专用瓦片档，以及能否破掉 coopmat 累加器的 smem 绕行。
- **批量 prefill 没有 int8 张量核路径。** prefill 跑的是 fp16 coopmat GEMM（`gemm_f16_f32_affine` 37 % + `_relu2` 27 % + `gemm_f16_f32` 22 % = **86 %**，`dequant_int8_f16` 只占 **0.9 %**）⇒ 它**本来就比 CUDA 快**，但 int8 权重是被反量化后消费的，没吃到 int8 的带宽与峰值红利。
- **prefill 的反量化开销 ≈ 10 %**（T=512 时 int8 对 fp16）：彻底消除需要 cooperative-matrix 融合反量化 + GEMM（Marlin 式零副本），列为长期方向。
- **prefill 每 token 耗时随 T 近二次方增长**（T=256：0.33 ms → T=512：0.81 ms，WKV 并行形式的 chunk 内项）；长 prompt 需要考虑 WKV 分块。
- **批量 prefill 的 padding 浪费**：序列维按固定长度桶补齐，实测那份 workload 里 **4 – 5×** 是白算的（各槽 prompt 104..139 tok 却按 `PAD_TO=512` 走）——这是消费侧的长度桶问题，两后端共有，别记到后端头上。
- **fp16 模型没有批量 *decode* 路径**（批量 prefill 是可用的）：批量 decode 的 r/k/v 核只有 int8 变体，所以 fp16 模型会退回逐槽单流；`GpuModel::batch_decode_blocker()` 把原因作为字符串返回，调用方（客户端会话池、mytown 引擎）能记下**为什么**走串行，而不是读一个沉默的 `supports_batch_decode() == false`，也不会因为「没有批量 forward 路径」而连 prefill 一起串行化。
- **`LOWRANK_MIN` 一级取 64 而不是 32**：B=32 时张量核 mid 臂实测 **−8 … −10 % 净亏**（块饥饿已被那条瓦片规则修掉，但这个形状仍然不划算）。B=32 正是「专用小 M 瓦片档」必须赢下的那一格。
- **Vulkan 没有 CUDA 那样的 `RKV_MERGE`**（r/k/v 三链合并成一次 dispatch），所以每层多记 3 次 `quant_x_i8` + 3 次 `gemm_imma_reduce`。对「再合并」的预期已被 §6.2 的低并发事实**下调**：它救不了 B=1，价值只在大批宽的部分流量与宿主录制——而大批宽落后的原因是另一个。
- **新长度桶的首次 prefill 很贵**：换一个长度会整表重建 45 个 `[bt,·]` 序列缓冲，代价是**秒级**（冷桶首请求 Vulkan 3 641.0 ms 对同桶重复 2 493.2 ms；CUDA 1 809.0 对 942.7）。`warmup_len_buckets` 把它从「用户等」挪到「启动期等」，但**总代价一点不省**，而且 `SeqBuffers` 只缓存**一个**形状 ⇒ 预热列表里只有最后一个桶留在显存；长度来回变的请求需要固定 `pad_to` 或按桶各留一个模型。
- **`dplr_seq` 占用率偏低**（40 workgroup × 64 线程 + 每 token 2 次 barrier，稳态 prefill 中 ~10 ms）：可对齐 CUDA 版结构（block 并行行 + shuffle 归约）。
- **测量环境的天花板**：这张卡同时驱动显示器，SM 时钟按 ~7 % 一级跳（1695 – 1830 MHz），温度从 46 走到 82 ℃ ⇒ 端到端分辨率 ≈ 2 – 3 %，任何小于它的单格读数都不是证据。见 §6.5。
