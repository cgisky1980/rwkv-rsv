# Vulkan 批量 prefill fp16 GEMM 瓦片档修正（2026-10-11）

对应任务 #26（原立项为「Vulkan 批量 prefill 的 int8 张量核 GEMM」，口径 0.59×）。
本轮**没有**写 int8 prefill 内核——先做了一件更基础的事：把 prefill 的 GEMM 变成
可跨后端对拍的测量对象，结果发现差距的大头是**默认瓦片档选错**，一行选档逻辑
换掉就吃掉了 0.574× → 0.96×。int8 张量核 prefill 因此降级为「锦上添花的后续项」。

## 一、先修测量：两个「假胜利」

### 1. CUDA 的 `begin_batch`/`end_batch` 不提交也不同步

Vulkan 侧 `end_batch` = end command buffer + submit + `queue_wait_idle`；CUDA 侧两个
方法都不做提交（内核直接 launch 到 stream 上），`end_batch` 只 dump profiling。
于是 kernel_bench 的计时圈量到的是 **host 入队时间**，`gemm` 报出 1840~112 640 TOPS
（fp16 张量峰值只有 ~54）。不是 cuBLAS 快，是没等它。

修法：`ComputeBackend::synchronize()` 作为**必需** trait 方法加入（故意不给默认实现——
默认 no-op 会让下一个后端悄悄重现同一个 bug），Vulkan = `rt.wait_queue()`
（新增，`queue_wait_idle`），CUDA = `cuStreamSynchronize(self.stream)`。
kernel_bench 每轮 `end_batch` 之后显式同步。

⚠️ **此前所有 CUDA 的 kernel_bench 行一律作废**，任何跨后端比较都要重测。

### 2. `sum(y)` 输出指纹列

修好同步之后 CUDA 给出物理上合理的 33.5~57.8 TOPS，但 Vulkan 的瓦片扫描里
`32×32×32` 那一档报 **234 TOPS = fp16 峰值的 4.3 倍**，而且在表里跟别的档看不出
任何区别。给基准加了 `sum(y)` 列（计时圈**外**单独跑一次 + 部分读回前 4096 个元素），
该档 `sum(y) = 0.0000` ⇒ 内核从未写过输出。

根因（结构性的，值得记住）：`gemm_spec` 里 `SUBTILE_M = TILE_M/4`、
`NUM_MAT_SUBTILE_M = SUBTILE_M / MAT_M`，MAT_M=16 ⇒ **TILE_M < 64 时零次迭代**，
内核合法地什么都不做并「成功」返回。同理 TILE_N < 32。顺带发现旧的共享内存兜底
返回 `(subgroup_size, subgroup_size, 16)` = `(32,32,16)` 就是这么一个静默空转档，
已把下界抬成 `(64,32,16)`。

结论：**没有读回的 GPU 基准数字不可引用**。给基准加「结果不可验证」的显式失败分支，
比给每个配置加人工怀疑便宜得多。

## 二、瓦片扫描（`pf_*` 族，带指纹，同会话）

`pf_out` = [rows,2560]×[2560,2560]、`pf_key` = k=2560→n=10240、`pf_value` = k=10240→n=2560。
batch 列是 **token 行数**（prefill 的 B·T_pad）。`pf_*` 走稠密 fp16 `gemm`，两后端都实现
⇒ 这是唯一能跨后端对拍的 prefill 口径（`supports_int8_imma()` 在 CUDA 上为 false，
`imma_*` 族压根没法对比）。判断看 TOPS 列，不看「有效 GB/s」。

| pf_out 1024 | 22.5 | 27.1 | **30.1** | 27.7 |

## 三、选档逻辑改两处（`src/runtime.rs`）

### 1. NVIDIA 的档位判据从「绝对阈值」改成「共享内存需求」

旧代码 `max_shared_memory >= 163840` 才给 128×128，这张 Turing 的 API 返回 48 KB
⇒ 永久锁在 64×64×32（阈值口径参照的是 AMD 的 64 KB+，对 NVIDIA 不成立）。
现在按 `gemm_shmem(tm,tn,tk)` 实际需求量与 `max_shared_memory` 比较：128×128×32 只要
36 KB（行填充 ROW=TILE_K+8 ⇒ 真实 40 KB），48 KB 的卡照样选得上。
共享内存兜底公式也统一到同一个 `gemm_shmem`，不再有两套口径。

### 2. 形状整除性守卫（这是「能不能默认打开」的关键）

`gemm.comp` 是 Khronos 风格的 coopmat 内核：三层循环全是编译期定长 trip count、
内层没有任何边界检查，而 dispatch 用 `div_ceil` ⇒ **M/N 不是 TILE_M/TILE_N 的整数倍时，
最后一个 tile 会读写越过缓冲末尾**。低秩投影正是这种形状：n = `round_up(mid, 64)`
可以恰为 64，128×128 会往 `[M_PAD, 64]` 的 v_mid 上多写 64 列、并越过 v1_16 尾部。

新增 `gemm_tile_for(app, m, n, k)`：从硬件偏好档往下**二分收缩到能整除的最大档**，
下界 = 结构约束（M 64 = 4·MAT_M，N 32 = 2·MAT_N，K 16 = MAT_K）。
`gemm_spec` 与 `gemm_grid` 都走它，且 TILE_M/TILE_N 只依赖 M/N ⇒ 两处必然一致。
收缩只降低共享内存需求，与上限校验不冲突。

前置事实（所以整除守卫今天不会把主路径降档）：`SeqBuffers::m_pad = t.div_ceil(256)*256`
（gpu_model.rs:5601）恒为 256 的倍数；c=2560 / fh=10240 / vocab=65536 都能被 128 整除；
只有低秩 n 会落到 64 档。

## 五、遗留

### 5.1 批量 prefill 的残余差距在 B=256，而且是**墙钟**问题不是内核问题（新发现，下一步）

同会话（`PAD_TO=512 NTOK=1 SEGS=1 SKIP_SINGLE=1`，prefill seeds 三臂全等 `0x372cc8`）：

| B | PREFILL_SLOTS | Vulkan prefill | 登记显存 | vs CUDA |
| --- | --- | --- | --- | --- |
| 128 | 8（默认） | 24 119 ms | ~9.5 GB | **0.961×** |
| 128 | 16 | 27 910 ms | 11 638 MiB | 0.830× |
| 128 | 32 | 30 998 ms | 15 438 MiB | 0.748× |
| 128 | 64 / 0（不分块） | `ERROR_OUT_OF_DEVICE_MEMORY` | — | — |
| 256 | 8（默认） | 75 197 ms | 12 747 MiB | **0.614×** |
| 256 | 16 | 54 409 ms | 14 279 MiB | 0.849× |
| 256 | 32 | 59 670 ms | 18 079 MiB | 0.774× |
| 256 | — CUDA | 46 173 ms | — | 1.00× |

B=256 仍只有 0.61×，而 B=128 已经 0.96× ⇒ 差距不是内核。剖一个 chunk（B=256/ps=8，
bt=4096 行，32 个 chunk）：

- `[PROF_GPU] SUM 1023 ms / 1723 kernels`（gemm_affine 369 + gemm 193 + relu2 186 + tanh 6 = **74 %**）
- `[PROF_GAPS] 间隙合计 0.693 ms / 1722`（最大 159 us，`to_f16_triple → gemm_tanh`）⇒ **GPU 侧没有 inter-dispatch 停顿**
- `[PROF_HOST] host=26.1 ms [key=0.12 cache=22.71 barrier=1.33 dispatch=1.27]` ⇒ 录制也不是瓶颈（cache 查表占大头）
- `[PROF_SUBMIT] submit=0.05ms wait=1029ms` ⇒ 与 GPU SUM 对得上（wait 就是 GPU 时间，无排队损失）

而墙钟是 75 197 / 32 = **2350 ms 每 chunk**。1029(GPU) + 26(host) + 0.7(gap) ≈ 1056 ms，
**剩下约 1.3 s / chunk（占 B=256 prefill 墙钟的 55 %）落在 chunk 与 chunk 之间**，
既不在内核里也不在录制里。ps=8→16 在 B=256 上省 20.8 s ≈ 16 chunk × 1.3 s，
正好是这个量级——但同一改法在 B=128 上**反而更慢**（+3.8 s），因为登记显存
从 ~9.5 GB 涨到 11.6 GB；再涨到 15.4 GB / 18.1 GB 就分别把 B=128、B=256 拖回更慢，
64 与不分块直接 `ERROR_OUT_OF_DEVICE_MEMORY`。

所以这不是「把 PREFILL_SLOTS 调大」能白拿的收益，而是一个**每 chunk 固定开销 × 显存
占用**的双目标问题。下一步先归因那 1.3 s：候选是 chunk 循环里走 batch 路径**之外**
提交的活（状态写回 / 历史上传 / 未计时的 dispatch）、以及 seq 缓冲按桶重建。
显存侧的联动项是 #27（RNN 状态 fp16：B=256 时 5.3 GB → 2.6 GB），它把「更大子批」
重新变成可选项。

#### ⚠️ 订正（同日，见 [2026-10-11-Vulkan-分块prefill状态回灌设备化-实施记录.md](2026-10-11-Vulkan-分块prefill状态回灌设备化-实施记录.md)）

上面这段的**结论错了**，错在把污染的窗口当分母：

1. `2350 ms / chunk` 是 `75 197 / 32` 得来的，而 `75 197` 是 bench 的
   `[批量] prefill` 列——它从 `create_batch_state` 之前起表、到**解码循环之后**停表，
   含 tokenize、状态分配与 `WARMUP` 自循环（图捕获 / NVRTC JIT）。chunk 循环自己的墙钟
   加进 `PROF_CHUNK=1` 后实测为 **42 430 ms**（旧代码）/ **36 023 ms**（修好以后），
   即每 chunk 1 326 / 1 126 ms，不是 2 350 ms。
2. 因此「1.3 s 落在 chunk 与 chunk 之间」不成立。它**在 chunk 里面**，而且就在候选清单的
   第一条：状态写回走宿主往返，每槽 194 次「独立提交 + `queue_wait_idle`」
   （`download_part`/`upload_part` 各录一个临时 command buffer）。实测拆分为
   reset 62 + core 1 030 + **xfer 210** ms / chunk（B=256 / ps=8）。改成设备内行段拷贝
   （`State::copy_rows_from`，一块一次提交）后 xfer 6 713 → **44 ms**（整轮），
   B=256 对 CUDA **0.67× → 0.79×**、B=128 **0.84×**。
3. 上面那张 PREFILL_SLOTS 六臂表的全部 ms 与 `vs CUDA` 列都读自被污染的 prefill 列，
   **只有定性结论仍成立**：登记显存随子批宽度上涨、64 / 不分块放不下（OOM 两行是真实
   观测）。ps=8→16「省 20.8 s ≈ 16 × 1.3 s」的对应关系是巧合而非机制——干净口径下
   `PREFILL_SLOTS` 各臂需要重测才能引用。
4. 顺带发现一条跨后端口径差异：**CUDA 上 `PREFILL_SLOTS` 是影响结果的旋钮**
   （w=1 与 w=2 逐位相同、两者与 w=4 差 ~1 %，即批形跨阈值换 kernel），Vulkan 上逐位
   不变。已由 `tests/batch_parity.rs::cross_state_rows_copy_matches_host_roundtrip` 分档钉住。

## 六、块序 swizzle（2026-10-12）：5.2 第 1 条与「行数越多越差」的正解

### 6.1 仪器与绑定

- 内核级用 `examples/kernel_bench.rs`（**不加载模型**，一条命令 ≈40 s 跑完三形状×五行数），
  A/B 用 host 侧的 `GEMM_SWZ` 开关：`0` = 恒等序，`<g>` = 强制 group 尺寸。**两臂跑的是同一份
  模块字节**，只差一个特化常量 ⇒ 不需要 `VK_SPV_DIR`，也免疫「跨会话比值不可比」那条坑。
- 发货模块 `assets/shaders/spv/gemm_f16_f32.spv` md5 `872da25058…`；探针里把 `GROUP_SWZ` 当
  **常量 0** 编出来的 `g0.spv` 与改动前的发货字节**逐字节相同**（都是 `ab4fa6ecef…`）
  ⇒ 「关掉就是原来的序」同时有结构证明（恒等映射）和字节证明（编译产物一致）。
- 统计口径按台账 §… 的 Δmin（每格 3 轮取最小），分辨率下限 ≈2~3 %，null control 用规则本来
  就判关的格子。

### 6.2 机制：线性块序把一个算力瓶颈做成了带宽瓶颈

grid 是 `(NUM_TILE_M, NUM_TILE_N)`，块的线性序 `pid = x + y·NUM_TILE_M`（x 最快）。驱动按 pid
升序铺 wave，于是一个 wave（本机 68 个 SM）基本**铺满一整条 M 带再换列** ⇒ A 面板
（`rows×K×2 B`）被整条重读 ≈ `NUM_TILE_N` 次。行数一多，A 早就超出 6 MB L2，这些重读全部落 DRAM。

`pf_key`（n=10240、k=2560）在 8192 行算一遍：FLOPs = 2·8192·10240·2560 = **430 GFLOP**。
- 原序 18.44 ms ⇒ 23.3 TOPS = fp16 张量峰值（≈54）的 43 %，而 A 侧流量 41.9 MB × 80 列 ≈ 3.4 GB
  ⇒ 360 GB/s 量级 —— **它是带宽受限的**。
- swizzle（g=8）9.08 ms ⇒ **47.3 TOPS = 峰值的 88 %** —— 回到算力受限。
同形状 cuBLAS 同会话 7.48 ms（57.4 TOPS）。所以这不是「Vulkan 的内核写得慢」，是**块序**在跟
L2 作对；CUDA 那边 cuBLAS 自己就在做类似的分组，以前没意识到我们这边缺了这一步。

### 6.4 发货规则：一个尺度（L2）+ 两条门

`src/runtime.rs::gemm_spec`（`GROUP_SWZ` = 特化常量 42，`gemm.comp` 里做反解码）：

```
g = clamp( floor_pow2( L2 / (TILE_M·K·2) ), 4, 16 )      L2 = 6 MB（本机改过功耗墙的 2080 Ti）
开 = 整除(M,TILE_M) ∧ 整除(N,TILE_N) ∧ (M·K·2 > L2) ∧ (块数 ≥ 2·68)
```

- **尺度只有一个：一个 group 的 A 足迹 ≈ L2**。它同时复现两个 K 的最优档：
  K=2560 ⇒ 6.0/0.66 = 9.2 → 8 ✓；K=10240 ⇒ 6.0/2.62 = 2.3 → 2 → 夹到 4 ✓。
- **A 放不下 L2 才有重读问题**：K=2560 在 1024 行时 A=5.2 MB < 6 MB，原序本来就在 L2 里命中，
  swizzle 只多花反解码（实测 +1.6…+3.3 %）⇒ 判关 ✓。
- **grid 要跨两波以上**：512 行的 `pf_value` A=10.5 MB 已过线，但只有 80 块（< 136）⇒ 判关 ✓。
- **不整除一律关**：内核没有边界检查，而反解码用的是向下取整的 `NUM_TILE_M`，与 `div_ceil` 的
  grid 会在尾块错开。`GEMM_SWZ` 的覆盖**也**受这条守卫约束（不整除时恒 0），所以这个 A/B 开关
  不可能把内核推出越界写。
- 15 个格子逐个核对：规则选的档 = 实测最优档（13 个严格最优，2 个持平）。

### 6.8 §6.7 第 1 条「TILE_M 与 swizzle 协同」：**证伪**，但顺带挖出 clamp 下界是错的（2026-10-12）

先订正 §6.7 的算术：TILE_M 降到 64 时**公式并不会给 16**。`floor_pow2(L2/(64·10240·2))`

### 6.9 「每迭代 K 链太长」假设（TILE_K=64 + TILE_N=64）：**证伪**（2026-10-12）

§6.5 的比值给出一条算术：`pf_key`（K=2560，每块 80 次 K 迭代）跑 47.5 TOPS，`pf_value`
（K=10240，同一内层循环跑 320 次）只 25.9 TOPS。而按「一个 wave 沿 k 锁步」重算流量：
`pf_value` 全 wave 的最坏流量 ≈ A 84 MB + B 52 MB ≈ 136 MB ÷ 560 GB/s = **0.24 ms**，
相对实测 16.6 ms 可以忽略 ⇒ 深 K **不可能**是带宽受限。既然每步的 FLOP/字节与 `pf_key`
完全一样，差距只能在**每步的固定开销**（两次 barrier + 全局载入延迟，而 36 KB 共享内存
⇒ 每 SM 只住一个块 ⇒ 没有跨块隐藏）。链长 320 步就是 320 次这份开销。可测的修法是把
`TILE_K` 抬到 64（链长减半）：(128, 64, 64) 合法（shmem 27.6 KB < 48 KB，下界 8192/4096 ≥
2048，k=10240 % 64 = 0，n=2560 % 64 = 0 ⇒ 1280 块）。

| --- | --- | --- | --- | --- |
| 4096 | 13.783 (15.6 T) | 8.341 (25.7 T) | **7.590 (28.3 T)** | 7.909 (27.2 T) |
| 8192 | 34.269 (12.5 T) | 19.235 (22.3 T) | **18.023 (23.8 T)** | 18.246 (23.5 T) |

`sum(y)` = `4195.4004` 与 §6.8 / §6.5 逐位相同 ⇒ 这一族几何改动同样等价。两件事：

1. **swizzle 的机制在完全不同的瓦片下再次复现**：13.783 → 7.590 = **−45 %**（4096 行）、
   34.269 → 18.023 = **−47 %**（8192 行）——与 §6.5 在 (128,128,32) 上量到的 −50.8 %/−48.2 %
   同一量级。这是本轮最硬的一条独立佐证。
2. **但减半链长没有换来任何收益**：最好档 g4 = 7.590 / 18.023 ms，比 §6.8 的
   (128,128,32)+g4（7.368 / 16.593 ms，同机不同进程 ⇒ 只做方向判断）慢 **+3.0 % / +8.6 %**。
   ⇒ `pf_value` 的 25.9 TOPS **不是**「K 迭代次数太多 × 每步固定开销」造成的，
   `TILE_K` 这条路封死（连同它顺带的 TILE_N=64）。

⇒ `pf_value` 剩下的候选只有两类：① clamp 下界（§6.8 第 2 条，纯 host 一行，正在扫）；
② **内核结构本身**——coopmat 的 `coopMatLoad` 每步从 smem 重取 A/B 片段、且累加器在
`NUM_MAT_SUBTILE_*` 上完全展开，深 K 时这条 LDS/mma 比例与 `pf_key` 相同但更吃发射槽。
第二类要动 `gemm.comp` 的循环结构（不是换档），代价与风险都远高于本轮已结账的三档，

### 6.12 第五个可换量：累加器位宽（2026-10-12）—— K=2560 那一族 −21 %，`pf_value` 只 −3.9 %；外加一台会造假的仪器

**来源**：用户让看 <https://github.com/cryscan/rosalia/tree/ember> 的算子有没什么可学。
源码级评估：它 prefill 没有块序 swizzle、没有 split-K、没有 int8；decode GEMV 按槽重读权重、没有 BGRP
⇒ 两条主线我们都在它前面。**唯一值得偷的机制 = `C_TYPE=float16_t` 的 coopmat 累加器**
（Turing 上 fp16 累加的名义 mma 速率是 fp32 累加的两倍：54.4 → 108.8 TFLOPS）。
而**这个档在我们自己的树里早就编好了、只是没接线**：`build.rs` 的 gemm 变体矩阵带
`C_BITS`/`C_TYPE` 两个维度，产出 `gemm_f16_f16{,_relu2,_tanh,_affine,_affine_relu2,_affine_tanh}.spv` 六条；
`record_kernel` 只认 `gemm_f16_f32*` 那六个名字 ⇒ 那六条一直是死字节。
顺带两处事实：`C_BITS` 在 `gemm.comp` 里**根本没被引用**（只有 `gemm_splitk.comp` 写死 `#define C_BITS 32`），
而 `C_TYPE` **同时**决定累加器类型与落盘类型
（`coopmat<C_TYPE,…,gl_MatrixUseAccumulator>` + `layout(buffer_reference) buffer Output { C_TYPE data[]; }`）。

**零代码探针**：`VK_SPV_DIR` 指向一份把六条 `gemm_f16_f16*.spv` 的字节顶到 `gemm_f16_f32*` 六个名字上的目录

- ① 「半累加器 + fp32 落盘」= 把累加器类型与 `C_TYPE` 拆开。**GLSL 侧现在做不到**：
  落盘只有 `coopMatStore` 一条合法写法，它要求矩阵元素类型 = 缓冲元素类型；想插一步类型转换只有
  `coopMatConvert`，而本机 `glslangValidator 11:15.2.0` 在 `GL_KHR_cooperative_matrix` 下对它试了
  8 种签名全是 `no matching overloaded function found`（名字已声明、重载不匹配，`/c/tmp/acc16/`）
  ⇒ 要么换 glslang 的显式分量扩展，要么放弃这条路。
- ② **只挑「下游本来就是 fp16」的那条链**：Vulkan 稠密 prefill 的 ffn key 现在是
  `gemm_relu2(xb16, fk → r2 f32)` + `to_f16(r2 → r2_16)`，而 ffn value 只吃 `r2_16`

  判据只能是质量门（`cargo test --release` + `DIAG=1` + 逐 token 等价），不是速度。
  ⚠️ 另外 `r2` 在 int8 / 稀疏 FFN 臂上另有读者，接线时只在探针档改这条链，别把 f32 出口拆掉。

本节只交**证据 + 一条新线的量级估算**，代码没动；②的实现挂在任务 #66 之后。

### 6.13 路 ② 落地并**默认开启**（2026-10-12）：ffn key 走 fp16 累加器，实测 −49 ms / chunk

**改了什么**（只有两条链，Vulkan-only，`src/gpu_model.rs:2090`（批量分块）与 `:4761`（单序列））：

```
OFF：gemm_relu2(xb16, ffn_key → r2 fp32)  然后  to_f16(r2 → r2_16)
ON ：gemm_f16_acc(… → r2_16, act=relu²)   ← 一条 dispatch 直接落 fp16，to_f16 不发
```

`r2` 在 prefill 侧没有别的读者（int8 / 稀疏 FFN 臂走的是 decode 路径），所以 dtype 契约一个字没改。
门 = `backend.supports_gemm_f16_acc() && m_pad >= 2048 && PREFILL_ACC16 != "0"`；
CUDA 后端不覆盖该能力位 ⇒ **CUDA 侧行为不变**。§6.12 那条「−21.7 % 只在 4096 行口径上结过账」
的形状门保留，低 M 扫描挂在任务 #68。

**为什么不能拿端到端墙钟判**（这一节的主要产出是仪器，不只是杠杆）：
一次 chunk 墙钟 ≈1 s、一轮 16 块 ≈16 s，而 SM 时钟在几十秒尺度上是**准静态台阶**
（1695~1830 MHz，1830/1710 = 1.07）⇒ 16 s 粒度上 ±7~10 % 的漂移把 ±5 % 的杠杆吃掉。
更糟的是 `AB_VAR` 那台进程内仪器**结构上偏置**：每轮固定先跑 A ⇒ A 永远拿到本轮最冷的一次采样，
于是 `Δmin` 读成 **+0.08 % 「打平」**，同一份日志的 decode 臂还读出「B 慢 14 %」——
**两条都是伪影**。同一条链的教训：`min` 只在两档各取多次独立采样、且采样顺序对称时才是配对统计量。
⇒ 判这种量级的杠杆要用**逐 dispatch** 的尺，不能用整块墙钟。

**尺一：链尺**（`kernel_bench` 新增成对臂 `pf_key32` / `pf_key16`，4096 行 = 发货 chunk 形状，
同一次进程内交替，`env BACKEND=vulkan`，min over 3 repeats × 40 iters）：

| 臂 | ms/call（4 轮） | TOPS |
| --- | --- | --- |
| `pf_key32`（fp32 累加 + `to_f16` 一遍） | 5.1024 / 5.1144 / 5.1182 / 5.1326 | 41.8~42.1 |
| `pf_key16`（fp16 累加直写 fp16） | **3.7644 / 3.7772 / 3.7792 / 3.7880** | 56.7~57.0 |

⇒ **−1.338 ms/call（−26.2 %），4/4 两臂整个集合互不重叠**，抖动 ≤1.5 %。
（比 §6.12 探针的 −21.7 % 更大，因为这里连 `to_f16` 那遍一起算进去了。）
⚠️ 表尾那两个 `sum(y)`（268.5 vs 281.0）**不是质量门**：合成输入全正，是 fp16 累加偏置的最坏情况，
只能证明「两档确实不同」，不能判误差大小。

**尺二：现场尺**（`PROF_GPU=1`，引擎内逐 dispatch GPU 时间戳，真实 forward 里 6 个 round-pair，
`AB_RESTART=1` ⇒ 每档从同一状态重新 prefill 16 块 × 32 层 = 512 发）。
每档读**自己那 512 发的平均**（对时钟漂移不敏感，因为两档在同一轮内相邻且各自内部对称）：

| 轮 | OFF avg (ms/dispatch) | ON avg | Δ |
| --- | --- | --- | --- |
| r0 | 4.9230 | 4.1702 | −0.753 |
| r1 | 5.2056 | 4.2313 | −0.974 |
| r2 | 5.2989 | 4.2822 | −1.017 |
| r3 | 5.3374 | 4.3822 | −0.955 |
| r4 | 5.4367 | 4.2560 | −1.181 |
| r5 | 5.6016 | 4.3756 | −1.226 |

⇒ **6/6 为负，均值 −1.018 ms/dispatch，且两臂整个集合互不重叠**（ON 最大 4.382 < OFF 最小 4.923）。
A 先跑 / B 先跑的三轮子集均值分别 −0.983 / −1.052 ⇒ **位置效应对这个比值统计量几乎没有影响**，
这就是它和 `Δmin` 的区别。折成每 chunk：−1.018 × 32 = **−32.6 ms**。

**被消掉的那遍 `to_f16`（同一份日志，直接数 dispatch）**：OFF 每轮 3824 发 / 425~438 ms，
ON 每轮 3312 发 / 156~161 ms ⇒ 差 **512 发**（= 16 块 × 32 层，正好是 ffn key 那一族）
= **−269 ms/轮 = −16.8 ms/chunk**。

**合计（可归因给这个杠杆的）**：−32.6 − 16.8 ≈ **−49 ms/chunk**，

整块 GPU busy 的配对 Δ（只取 prefill 块，5 个干净轮）：−98.8 / −89.7 / −47.1 / −57.4 / −102.0 ⇒
5/5 为负、均值 −79 ms，比可归因量更大 ⇒ **多出来的是共漂移，记在上界里不记在杠杆上**。
r0 那对（−19.5）被进程初始 prefill 混进 A 段，弃。
顺带一条**订正 §5.1 的话**：chunk 的 GPU busy `SUM` = 904 ms vs 墙钟 `core` 944 ms ⇒
**分块 prefill ≈96 % 是 GPU-bound**，「1.3 s 宿主空隙」那条旧叙事在设备侧写回（§5.1 订正）之后已经不成立。

**踩到的第二个解析坑（差点得出完全相反的结论）**：聚合脚本按 `$i=="count="` 匹配字段，
而 `count=` 的值是 `%3d` 右对齐——三位数时**没有空格**（`count=318`）⇒ 最大的那几个 label

**假象，并据此得出「prefill 39 % 是宿主绑定」这个错结论**。修正后才是上面的 96 %。
⇒ **规则：读 `[PROF_GPU]` 行必须同时容忍 `count= N` 与 `count=N` 两种宽度；分母用 `SUM over N kernels` 自检。**

**质量门**（这才是默认开的依据，不是速度）：
`DUMP_LG` rmse **1.128** = logits rms(16.84) 的 **6.70 %**，落在已发货的 fp16 档同一带内
（1.10~1.15 / 6.6~6.9 %）；噪声地板 0.000；top1 8/8、top3 6/8；
decode 逐 token 指纹两档不同（A `0x149ca7/0x1b4f` vs B `0x149b27/0x14cf`）⇒ 绑定标记成立。
发货门禁：`BACKEND=vulkan cargo test --release`（77+10+1 通过 / 0 失败）与
`BACKEND=cuda cargo test --release`（同样 77+10+1 / 0 失败，CUDA 不覆盖能力位 ⇒ 那侧本来就走原路径），
另跑一遍 `PREFILL_ACC16=0` 证明关档仍然可用（回退开关必须是活的）。
★ **开关的绑定标记要用 label，不能用 `[ACC16]` 那行**：测试套件里 `log::info!` 没接 handler ⇒
两档都打不出 `[ACC16]`（`grep -c` 都是 0），而且测试的 prompt 短 ⇒ `m_pad < 2048` 两档恒关
（★ 后半句到 §6.14 就**失效**了：门放到 256 ⇒ 单序列路径的测试真的会走到这一档，那才是它的数值门）。

`=0` 档 `ACC16行=0 f32relu2=1 f16relu2=0`（`/c/tmp/ac16/marker_{default,off}.log`，SLOTS=8×PAD_TO=512=4096 行）。

**没接的三条（查过、记在这儿免得重走）**：
① `gemm_f16_f32_affine`（`gemm_add` 残差融合）是**全 chunk 最大的内核族**——64 发/块、
324.98 ms/块 ≈ **35 %**，但它写的是 fp32 残差缓冲，`C_TYPE` 一个类型同时决定累加与落盘 ⇒ **不能上这档**；

读法：**比例随 M 单调（−6.6 % → −25.6 %），但没有一格是亏的**；绝对量随 M 缩小得更快
（256 行 −0.0715 ms/发 ⇒ 一条最短序列 32 层省 **2.29 ms**；64 行只剩 −0.022 ms/发）。

64/128 两档在**这棵树里产生不出来**（见下），列出来只为确认「更小 M 不会翻负」，不据此发货。
⚠️ 两遍里最大抖动只有 4.7 %（64 行的 fp16 臂），比本段先前写的「23.9 % 散布」小 —— 那个读数是
**上一版表的来源，那一版作废**：同一次扫描里 `pf_key32` 在 64 行读到 0.3802（vs 现在的 0.3281，
偏高 ~16 %），而 `pf_key16` 两遍一致（0.3092 vs 0.3063）⇒ 偏的是先跑那一臂的位置效应，
不是档位效应。按纪律第 22 条（AB 顺序 ⇒ 先跑者拿到最冷样本）把整张表按新的两遍重算后，
**低 M 的百分比明显缩小（−18.7 % → −6.6 %），但结论一字未改**（每一格仍为负）。

**门限取 256 而不是 64 的理由 = 可达形状的量化下限**，不是「哪里开始亏」：
单序列路径 `m_pad = t.div_ceil(256) * 256`（`SeqBuffers` 分配处，`src/gpu_model.rs:6114`）
⇒ 它最小就是 256；批量分块路径的 `m_pad` 是 `PAD_TO=512` 的倍数 ⇒ 这一改动对它**没有任何影响**
（4096 行早就是发货档）。所以「放到 256」的实际含义是：**让单序列 prefill 也吃到这一档**，
而 64/128 的测量只是把「再往下会不会亏」这个疑问提前关掉。

**数值风险不随 M 变**：fp16 累加的是 K=2560 这一维，与行数无关 ⇒ §6.13 那个 rmse 1.128（6.70 %）
就是这一档的误差带，不需要重开一个新的质量口径。真正的**新覆盖**是：门放到 256 之后，
测试套件里的单序列用例会第一次走到这条链（§6.13 那句「测试 prompt 短 ⇒ 两档恒关」当场失效）

★ **这一档跳过 `to_f16` 会连带改掉 pad 行的内容**，必须写清楚（读代码的人一定会问）：

### 6.15 设备内批量清零：分块 prefill 的 reset 段 1409.6 ms → 4.6 ms（2026-10-12，任务 #35）

**问题**：`State::reset` 每次要清 32 层 × 3 条 + `v_first` = **97 条**张量，而 Vulkan 侧每一次
`upload` 都是「单独一条 command buffer + 一次 `queue_wait_idle`」（`src/runtime.rs` 的
`copy_buffer`）。分块 prefill 每个 chunk 开头都要 reset 一次那个 `w=8` 的小状态
（每条 prompt 独立从零开始 prefill），于是每 chunk 白付 97 次全流同步。
**实测（同会话、同命令、`PROF_CHUNK=1`）**：`reset=1409.6ms / total=38928.2ms`（**3.6 %**，
每 chunk ≈88 ms ⇒ 每条 ≈0.9 ms，量级正好是「一次 submit + wait_idle」的宿主延迟）。

**改法**：`ComputeBackend::fill_zeros(&[(TensorId, elems)])` —— 默认实现 = 逐条 `upload` 零
（⇒ **CUDA 逐字节不变**，那边历史实测 reset 更贵 2.37 s，故意不动它，见下）；
Vulkan 覆盖 = `Runtime::fill_zeros` 把 N 条 `vkCmdFillBuffer` 记进**一条** command buffer、
一次 submit、一次 wait。`State::reset` 改成先把 97 条 `(id, elems)` 收进一个 Vec 再一次提交。

| 口径（B=128，627 tok prompt，w=8 ⇒ 16 chunk，同会话两遍） | reset | core | xfer | total 墙钟 |
| --- | --- | --- | --- | --- |
| 改前 | **1409.6 ms** | 37503.8 ms | 14.8 ms | 38928.2 ms |
| 改后 | **4.6 ms** | 35751.5 ms | 13.9 ms | 35770.0 ms |
| Δ | **−1405.0 ms（−99.7 %）** | −1752.3 ms（时钟，不记账） | −0.9 ms | −3158.2 ms |

★ **只有 reset 那一格是证据**：它是确定性的（300 倍差距，且两次读数各自内部一致），
而 `core` 那 −1.75 s 是本会话里常见的时钟/散热台阶（同一次跑里逐 chunk core 就在
1154~2856 ms 之间摆），**不许**据此报「prefill 快 8 %」。
按能记账的口径：B=128 这一轮省 **1.41 s / 38.9 s = 3.6 %**；prompt 短到 `T_pad=512`
（chunk 主体减半）时同一笔固定开销占比 ≈**7 %**；B=256 是 32 个 chunk ⇒ 约 **2.8 s**。

**为什么这是零风险改动**：写进去的字节与逐条零上传完全相同，所以判据用**逐位指纹**而不是秒表——
`decode tokens sum=0x13e742 xor=0x79b4` **改前改后逐位相同**（同 seed 同配置）。
两条要说清的语义差别：
① `fill` **不动 host 镜像**（旧 `upload` 会先把 host 侧写零）。状态的读数全部走
`download`（device→host 回拷，`State::back`/`slot_back` 都是），`download_host` 那条
「kernel 直写 host 缓冲」的路子不适用于状态张量 ⇒ 镜像陈旧不可能影响任何结果；
② `vkCmdFillBuffer` 要求字节数是 4 的倍数：fp16 状态的元素数在这里全是偶数，
但 `Runtime::fill_zeros` 仍保留「任一条不对齐 ⇒ 整批回落逐条零上传」，不留静默错路。

⚠️ **CUDA 侧故意不做**（任务卡里那条反直觉的话仍然成立）：两边一起省会让 B=256 的
vs CUDA **变差**（CUDA 的 reset 更贵 2.37 s vs 1.907 s），这一根的价值是 **Vulkan 的绝对墙钟**
与主机内存/提交次数（顺带：`fill` 不再需要那条 165 MB 的主机零缓冲）。
⇒ 它的「追平」记账是正的（只有 Vulkan 变快），但别把它当性能杠杆去给 CUDA 也做一遍。

**踩到的一条仪器陷阱（值得单列）**：第一遍「改后」读数与改前**一字不差**（1409.6 vs 1410.9），
原因不是改动无效，而是 `cargo build --release` **不构建 examples** ⇒
`target/release/examples/batch_decode_bench.exe` 还是旧二进制，那一遍量的就是改动前的代码
（它的解码指纹也因此「完美一致」，看着像最强的正确性证据，其实是空转）。
⇒ bench 前后必须 `cargo build --release --examples`，并绑定一个**只有改动才会变**的读数
（这里是 reset 段）。Raw：`/c/tmp/ac16/chunk128_{base,fill,fill2}.log`、`/c/tmp/ac16/fill_gates.log`。
