# Vulkan 低秩链二级 fp16 张量核（2026-10-11）

| 项 | 结论 |
|---|---|

## 1. 挑杠杆：先量两级形状，再决定换哪一级

上一轮（`参考/2026-10-11-Vulkan-状态fp16存储-实施记录.md` §3.7）重 dump 的 B=128 decode 分核表里，
低秩链升到 **20.9 %**（25.59 ms / 122.17 ms），是当时唯一还没有张量核档的批量链。

但「换张量核」在 Vulkan 上是**两级各自的一笔账**，所以先用 `examples/kernel_bench.rs`
（新增 `lrb_*`/`lr_g`/`lr1_*` 六档，min-of-5 轮 × 200 次）把两级分别量了一遍：

| 形状（rows=batch） | b=64 | **b=128** | b=256 | 备注 |
|---|---:|---:|---:|---|
| 二级 `lrb_w` n=2560 k=128（w/a 同形状，计两次） | 0.0154 | **0.0200** | 0.0249 | `gemm_bias` |
| 二级 `lrb_v` n=2560 k=64 | 0.0132 | **0.0162** | 0.0204 | `gemm_bias` |
| 二级 `lr_g` n=2560 k=320 | 0.0167 | **0.0262** | 0.0288 | `gemm`（14.6 TOPS @256） |
| **二级四链合计** | | **0.0824 ms/层** | | 对 chain4 的 0.398 ms/层 ⇒ **4.8× 便宜** |
| 一级 `lr1_w` n=128 k=2560（w/a 同形状，计两次） | 0.0950 | **0.1450** | 0.1225 | 只有 0.4~1.4 TOPS |
| 一级 `lr1_v` n=64 k=2560 | 0.0427 | **0.0762** | 0.0775 | |
| 一级 `lr1_g` n=320 k=2560 | 0.0434 | **0.0771** | 0.0786 | |
| **一级四链合计** | | **0.443 ms/层** | | 对 SIMT `gemv_int8_rkv_stage1_batch` 的 0.274 ms/层 ⇒ **慢 1.7×** |

**结论决定了形态**：一级是「窄 N 深 K」（n=64/128/320、k=C=2560），coopmat 在 TILE_M/TILE_N 下限
64/32 下整个 grid 只有 2~3 个块 ⇒ 没有并行度可榨。CUDA 的两级融合不受这个问题影响（它有自己的
tile 配置 + 四链合并 launch），所以 `lowrank_gemm_batch` **保持 CUDA 独有**，Vulkan 走拆法。

顺带把 `sum(y)` 数值标记打在每一档上（纪律：探针必须自带与性能无关的证据），二级/一级读到的
`sum` 分别为 462.05 / 1049.00 ⇒ 内核真的跑了、真的写回了。

## 2. 实现

### 2.1 新核 `lowrank_epilogue.comp`（四档 spec 变体）

`gemm`/`gemm_bias` 的输出是 f32 累加器，而批量 decode 的 `bb.w/a/v/g` 与 `state.v_first` 都是
**fp16**，`elementwise_*` 一族只有 f32→f32 ⇒ 要么补 8 条 cast dispatch，要么写一个融合 epilogue。
选了后者，四档语义与 `gemv_lowrank_chain4_batch.comp` L22-25 逐式对应：

| CHAIN | 输出 | 语义 |
|---|---|---|
| 0 w | `exp(sc * sigmoid(acc))` | `sc = scale_w.data[0]`（标量，同 chain4） |
| 1 a | `sigmoid(acc)` | |
| 2 v | `out += sigmoid(acc) * (v_first - out)` | 读改写 fp16 的注意力 v ⇒ `out` 同时进读集与写集 |
| 3 g | `(float16) acc` | 纯降位：g 的数学是 `sigmoid(xg) @ G2`，sigmoid 在**一级 mid** 上（§2.3） |

`build.rs` 注册 `CHAIN => [def(0,"w"), def(1,"a"), def(2,"v"), def(3,"g")]` ⇒ 产出
`lowrank_epilogue_{w,a,v,g}.spv`。

### 2.2 后端接口

- `ComputeBackend::supports_lowrank_gemm_stage2()`（默认 false，Vulkan 返回 true）。与
  `supports_lowrank_gemm_batch()`（CUDA 两级融合）**互斥使用**。
- `ComputeBackend::lowrank_epilogue(acc, scale, v_first, out, chain, c, batch)`：默认实现返回 Err，
  Vulkan 侧转发到 `runtime.rs` 的同名方法（`spec = [C, BATCH]`，dispatch `(batch,1,1)`，
  未用的 buffer_reference 传 0 地址——沿用 `gemm` 的做法）。

### 2.3 每层的 dispatch 序列（14 条，替掉原来的 1 条 chain4）

```
to_f16(w_mid→w_mid16)                  # 一级的 SIMT 输出是 f32、步长=真实 mid（96/96/64/320）
to_f16(a_mid→a_mid16)
to_f16(v_mid→v_mid16)
elementwise_sigmoid_inplace(g_mid)     # g 的 sigmoid 本来就在 mid 上（与 prefill 同式）
to_f16(g_mid→g_mid16)
gemm_bias(w_mid16, w2_16, w0 → w_full) gemm_bias(a…)  gemm_bias(v…)
gemm(g_mid16, g2_16 → gate)            # g 无 bias
lowrank_epilogue(w_full → bb.w, chain0)  … a(1)  v(2)  gate→bb.g(3)
```

一级四条链仍由 `gemv_int8_rkv_stage1_batch` 的 mid 臂算（`mvm/mwm/mam/mgm` 传真实 mid，不是 0）。

### 2.4 补行与零初始化（两条会咬人的约束）

1. **`gemm.comp` 没有边界检查**，而 `gemm_tile_for` 把 TILE_M 的下限收到 64 ⇒ 行维必须是 64 的倍数。
   批量路径因此用 `rows = batch.div_ceil(64) * 64`，`WorkBuffers` 相应扩到 `lr_rows`（`bsz < 16` 时
   仍按 `bsz`，单 token 路径不为补行付 2.6 MB 显存）。`to_f16` 对 `token >= T` 的补行写 0 ✓。
2. **补列必须零初始化**：`to_f16` 只写前 `mid` 列（96），列 96..127 从不被触碰；权重侧 `*_2_16`
   是 `[pad_out, pad_in]` 的零填充副本，`0 × 未初始化 = NaN` 会把整行毒掉 ⇒ 四个 `*_mid16` 与四个
   累加器一律 `upload(zeros)`。
3. 四个 f32 累加器复用 `WorkBuffers` 里**已从 prefill 借来、在 SIMT decode 路径闲置**的名字
   （`w_full/a_full/v_full` + `gate`），不新增缓冲：已核对 `bb.gate` 等在批量 decode 里无人读写
   （只有 `sb.*` 的 prefill 路径用同名槽）。`gemm_bias` 输出 f32、`gemm` 输出 f32 与 prefill 一致。

### 2.5 门控

`gpu_model.rs` 的 `lowrank_stage2`：`!lowrank_gemm && batch >= 32 && c % 64 == 0 && 各 mid_pad % 64 == 0
&& supports_lowrank_gemm_stage2() && LOWRANK_GEMM2 != "0"`。默认开，`=0` 回退 SIMT 融合核。

⚠️ 首版写的是 `batch >= 16`，**批宽扫之后抬到 32**（B=16 实测净亏 6.9 %，见 §5.3）。

## 3. 生效自证（纪律 3：与性能无关的路径标记）

`LOG_BARRIERS=1 SLOTS=128 SEGS=1 NTOK=16`，看它实际绑定的 spv：

| 档 | 派发计数 |
|---|---|
| `LOWRANK_GEMM2=0` | `gemv_lowrank_chain4_batch × 1024`、`to_f16 × 3568`、`sigmoid × 2032`，**无** `lowrank_epilogue_*` |
| 默认（开） | `lowrank_epilogue_{w,a,v,g} × 1024` 各一条、`to_f16 3568 → 7664`（+4/层步）、`sigmoid 2032 → 3056`（+1/层步）、**`gemv_lowrank_chain4_batch` 归零** |

⚠️ 记录一条流程教训：**第一轮对拍两档读数完全相同**（token 指纹逐位一致、chain4 仍 1024 次），
差点被判成「门控没生效的门控 bug」。真相是 `cargo build --release` **不带 `--examples` 时没有重建
example 二进制**（exe 时间戳比 `gpu_model.rs` 早 53 分钟）⇒ 两档跑的都是旧码。凡是拿
`examples/*` 当探针，改完必须 `cargo build --release --all-targets` 并核对 exe 时间戳。

## 4. 正确性门

### 4.1 批量正确性套件

`BACKEND=vulkan cargo test --release --test batch_parity`（默认开）：**10 passed / 0 failed / 1 ignored**，
含 72 槽 × 8 步的 wave 用例（batch=72 ⇒ `rows=128`，正是补行路径）。

### 4.2 贪心分叉率（同口径参照，饱和指标）

`TOPK=1 DUMP_TOK` 逐 token 落盘，B=128 × 16 步 = 2048 token，新档 vs SIMT 档：**366 / 2048 = 17.9 %**，
分叉槽位稳态 25/128（19.5 %），首步 8/128。参照留档：CUDA 早已接受的 W8A8 档 23.26 %、
Vulkan fp16 状态档 21.59 %（`参考/2026-10-11-Vulkan-状态fp16存储-实施记录.md` §3.3）。
**这条只作量级参照**——上一轮已经确认贪心把任意单点翻转放大成整条序列分叉，指标会饱和。

### 4.3 采样无关的逐元素门（本轮新造的尺子，默认开关的依据）

批量路径的改动**单流门（`ARGMAX_VERIFY=1 SELFLOOP_N=64`）碰不到**（batch=1 走不到门控），所以上一轮
那把尺子在这里没有刻度。改用 `batch_decode_bench` 的 `PROBE`（`STEP=1 PROBE=1`：重置 → prefill →
**一步** `batch_step_logits`）加新的 `DUMP_LG=<路径>`，把整行 logits 逐元素落盘
（SLOTS=16 × 65536，`PREFILL_SLOTS=8` 与两档完全同口径），离线算 rmse：

| 对照 | logit 逐元素 rmse | 相对（/rms(logits)=16.84） | max\|Δ\| |
|---|---:|---:|---:|
| 同一档跑两次（噪声底） | **0.000** | **0.000 %** | 0.000 |
| **本档** vs SIMT 档 | 1.153 | **6.850 %** | 5.021 |
| **已经默认开着**的 fp16 状态档 vs fp32 状态档 | 1.119 | **6.646 %** | 5.820 |

判据不是「谁离 fp32 更近」（那条必然偏向 fp32 侧），而是**「新扰动是否与一个已经上线的同规模扰动
同量级」**：6.85 % 对 6.65 % ⇒ 同一量级，且噪声底为 0 证明尺子可信。附带的结构性证据同向：
单步 argmax **127/128** 一致、每槽 top3 **集合与次序都不变**（算错会打乱名次，而这里只是整条
logit 分布平移/缩放）。⇒ **默认开成立**。

一条必须记下的读数：`6.85 %` 看起来「很大」，但这是**一步 decode 走完 32 层**之后的 logit 尺度——
这个模型对 1e-3 级的状态扰动就是混沌放大的，fp16 状态档（同一把尺 6.65 %）早已上线并被判定为
「零贪心偏移」。所以**绝对值不可引用，只有对照读数可引用**。

## 5. 性能

### 5.1 分核（`PROF_GPU=1`，B=128，取 per-avg，窗口长度无关）

| 项 | SIMT 档 | 张量核档 |
|---|---:|---:|
| 低秩二级每层 | `chain4` **0.3977 ms** | `gemm_f16_f32 ×4` 0.0508 + `gemm_bias ×3` 0.0132 + `epilogue ×4` 0.0312 + `to_f16 ×4` 0.0088 + `sigmoid` 0.0029 = **0.1069 ms** |
| 每步（32 层） | 12.7 ms | 3.4 ms（**−9.3 ms**） |

其余核的 per-avg 都在跨进程噪声内（`fuse_ka_dplr_norm_s16` 0.2928→0.2866、
`gemv_int8_rkv_stage1_batch` 0.2738→0.2626、`gemm_imma` 0.1210→0.1165）⇒ 没有把成本搬到别处。

⚠️ `SUM` 与 `count` 在两档**不可直接对比**：ON 档每层多 13 条 dispatch，剖析环形缓冲在 2048 条
处截断（表头 `over 2048 kernels`），所以窗口只覆盖 ~50 个层步；引用 per-avg 才安全。

### 5.3 批宽扫描：门限从 16 抬到 32（2026-10-11 补测）

§5.2 只在 B=128 上量过，而 `rows = ceil64(batch)` 意味着 **batch≤64 时张量核那半边的工作量
不随 batch 下降**（永远按 64 行算），SIMT 的 chain4 却随 batch 线性变便宜 ⇒ 收益必然在某个
批宽翻负。这不是推测，扫一遍（脚本 `C:\tmp\lr2gate.sh`：每个批宽**交错** 3 轮 × 两档，
`SEGS=4 NTOK=64`、`PREFILL_SLOTS=8 SKIP_GRAPH=1 SKIP_SINGLE=1 TOPK=1`，只计 decode 段）：

| B | SIMT 档中位（每步） | 张量核档中位（每步） | 结果 | 分布是否重叠 |
|---|---:|---:|---:|---|
| 16 | 4 528 ms / 17.7 ms | 4 841 ms / **18.9 ms** | **慢 6.9 %** | 否（OFF 全部更快） |
| 32 | 6 119 ms / 23.9 ms | 5 946 ms / **23.2 ms** | 快 2.8 % | 否（ON 全部更快） |
| 64 | 9 477 ms / 37.0 ms | 8 462 ms / **33.1 ms** | 快 10.7 % | 否 |
| 128 | 8 553 ms / 66.8 ms | 7 316 ms / **57.2 ms** | 快 14.4 %（§5.2） | 否 |

（tok/s 口径：16 档 904.4 → 845.9、32 档 1 338.6 → 1 377.6、64 档 1 728.8 → 1 936.2）

⇒ 默认门从 `batch >= 16` 改成 **`batch >= 32`**（`gpu_model.rs` 的 `lowrank_stage2`）。
32 是唯一被实测证明赢的下界，17~31 留在 SIMT 侧；B=16 是「净亏」而不是「没赚到」，
所以这条改动的价值等于把一个小批量回归从默认路径里摘掉。

绑定复验（改门后，`LOG_BARRIERS=1`）：B=16 默认档重新出现 `gemv_lowrank_chain4_batch`
且 `lowrank_epilogue_*` 归零；B=32 反之（chain4 归零、epilogue 128 次）。
每档每臂仍是**逐位确定**的：B=16 `0x3463b6e/0x14fc` vs `0x356cdcc/0x944`、
B=32 `0x698e312/0x7284` vs `0x6a7f370/0x7a16`、B=64 `0xd2e99df/0x6f27` vs `0xd45066c/0x6082`。

## 6. 遗留 / 下一步

1. **一级仍是 SIMT**（0.274 ms/层，占 B=128 decode 13.9 %）。 coopmat 在 n≤320 的形状上没有并行度；
   真要动它，方向是 CUDA 那种「四链合并 launch + 自己的 tile 档」，而不是换 dtype。
2. **10 条新增 dispatch/层**（4 cast + 1 sigmoid + 1 gemm + 3 gemm_bias + 4 epilogue）。`PROF_GAPS`
   量过间隙不是瓶颈（§上一轮），但 `to_f16` 四条 + `epilogue` 四条理论上能各自合并成一条
   （同 spec、四 buffer_reference，仿 `to_f16_triple`）。收益上界 = 这 8 条的 0.04 ms/层，
   先不做。
3. ~~**B=16~63 档没测**~~ —— **已测并改掉默认门（§5.3）**：B=16 净亏 6.9 %，B=32 起赢，
   所以门限从 `batch >= 16` 抬到 **`batch >= 32`**。剩下的空档是 17~31（按 §5.3 的单调性
   留在 SIMT 侧是安全的一侧），以及「小批宽要不要干脆用比 64 小的 tile」——那要改
   `gemm.comp` 的 `TILE_M` 下限，不在本项范围。
4. `kernel_bench` 新增六档、`batch_decode_bench` 的 `DUMP_LG` 都留在仓库里当量尺；
   `lrb_*`/`lr1_*` 只量 GEMM 本体，不含 cast/epilogue。
