# Vulkan RNN 状态 fp16 存储（2026-10-11）

| 项 | 结论 |
|---|---|
| 目标 | 把 Vulkan 侧 WKV 状态（`tmix_rnn`）从 **fp32 存储** 换成 CUDA 同档的 **fp16 存储 + fp32 计算**，这是 B=128 decode 里 `fuse_ka_dplr_norm` 占 14.5 % 的那块带宽，也是每槽 20.6 MiB 的占用大头 |
| 做法 | 三处状态核各加一个 `WKV_S16` spec 维（产出 `*_s16.spv`），host 侧新增 `StateTensor` 枚举让 spv 文件名跟随状态张量 dtype。**基线档逐位不变**（fp32 臂的 spv 与改动前唯一差异是一行 `OpSourceExtension` 元数据） |
| 吞吐 | 同会话交错 3 轮，B=128：fp16 **1977.5 / 1947.0 / 1914.8** vs fp32 **1881.5 / 1881.7 / 1863.0** tok/s ⇒ 中位数 **+3.5 %**（逐轮 +5.1 / +3.5 / +2.8 %），**两臂分布不重叠**（fp16 最低 > fp32 最高） |
| 占用 | B=128 登记张量 **7788 → 6498 MiB（−1290 MiB）**，host 镜像同步 −1290 MiB；外推到 B=256 ≈ **−2.6 GB** |
| 门 | **采样无关精度门（§3.6）= 默认开关的依据**：Vulkan 换 fp16 状态付 rmse **−0.12 %**（还略降）+ 64 步贪心 **零**偏移，而 CUDA 同一改动付 rmse **+42 %** + 46/64 偏移 ⇒ 不是打平，是 Vulkan 付得更少。贪心分叉率（B=64×512 **21.59 %** vs CUDA 已接受档 23.26 %）只作同口径参照；部署摘要门（§3.4/3.5）经 2×2 矩阵判定**对本改动无判别力** |
| 默认 | **开**（`supports_f16_wkv_state()` 在 Vulkan 侧翻为 true，与 CUDA 一致）；`WKV_STATE_F16=0` 切回 fp32 |

## 1. 为什么挑这一项（按实测排序，不按任务编号）

`参考/2026-10-10-Vulkan-rkv张量核默认翻转-实施记录.md` §3.5 的 B=128 decode 分核表：

| 核 | 占比 | 数值档 |
|---|---|---|
| `gemm_imma` | 48.7 % | 张量核（已默认） |
| 低秩链 | 15.5 % | SIMT |
| **`fuse_ka_dplr_norm`（状态）** | **14.5 %** | SIMT + **fp32 状态**（CUDA 有 fp16 变体） |
| rkv 二级 | 10.6 % | SIMT |

状态核的开销由**带宽**决定：S 是 `[H,N,N]` = 163 840 元素/层/槽，每步整表读一遍再写一遍，
fp32 ⇒ 每层每槽 1.3 MB 的往返。CUDA 侧同一块早在 Phase 2-2 就靠 `WKV_S16` 减半（−5.3 ms/步、
−2.6 GB @ B=256，实测 +4.9 %）。所以这一项**同时是占用杠杆和速度杠杆**，而 §9 当时把它记为
「Vulkan 未实现」——那条叙述的来源不是「实测否决」，是「`BufS{float data[]}` 写死了 f32」。

同一批被降级的是 #24（合并 rkv 三链 dispatch）：`PROF_GAPS=1` 实测相邻 dispatch 间隙
1.3~1.8 µs、一整批 2047 条合计 0.5 ms，且强制 `VK_IMMA_KSPLIT=1`（每层少排 3 条）**更慢**
⇒ dispatch 条数不是瓶颈，合并是死路，已在任务表存档。

## 2. 实现

### 2.1 shader 侧：一个 spec 维，三处同改

三处状态核对状态臂做同样的条件化（计算全程 fp32，只在**载入/回存**降位）：

```glsl
#ifdef WKV_S16
#define S_TYPE float16_t
#else
#define S_TYPE float
#endif
layout(buffer_reference) buffer BufS { S_TYPE data[]; } buf_s;
...
sreg[j] = float(buf_s.data[...]);        // 载入升位
buf_s.data[...] = S_TYPE(ns);            // 回存降位
```

- `dplr_seq.comp` / `dplr_seq_batch.comp` 需要补 `GL_EXT_shader_explicit_arithmetic_types_float16`
  （`fuse_ka_dplr_norm.comp` 本来就开了）；
- **三处必须同 dtype**：状态张量只有一份，任何一处按 f32 解释就会读到错值。这条纪律写在
  `build.rs` 的三个 spec 表和 shader 头注释里。

`build.rs` 三处各加一维 `WKV_S16 => [none(""), flag("s16")]` ⇒ 基线文件名不变，新增
`fuse_ka_dplr_norm_s16.spv`、`dplr_seq_f32_f32_s16.spv`、`dplr_seq_batch_s16.spv`
（命名与 CUDA 侧 `dplr_variant` 的 `{base}_s16` 一致）。

### 2.2 host 侧：`StateTensor` 而不是「到处加 if」

`src/runtime.rs` 新增枚举，把「状态张量是 f32 还是 f16」这件事收进一个类型：

```rust
pub enum StateTensor { F32(GpuTensor), F16(GpuTensor16) }
impl StateTensor {
    fn spv(&self, base: &str) -> String { if self.is_f16() { format!("shaders/spv/{base}_s16.spv") } else { ... } }
}
```

4 个 kernel（`fuse_ka_dplr_norm` / `_batch` / `dplr_seq` / `dplr_seq_batch`）的 `s` 参数从
`&mut GpuTensor` 改为 `&StateTensor`，spv 字面量改为 `&s.spv("…")`。`Params` 槽位本来只是
64 位设备地址 ⇒ **换 dtype 不需要动 dispatch 参数布局**，这是本项比 §9 原先估计小得多的原因。

`src/backend.rs` 加 `take_state` / `put_state`（张量池取出时校验 dtype，非状态 dtype 直接报错而不是
静默 reinterpret）。Vulkan 侧 `supports_f16_wkv_state()` 翻 true ⇒ `wkv_state_dtype()` 的环境变量口径
（`WKV_STATE_F16=0` 退回 fp32）自动对两后端生效，单流路径也走 `new_batched(…, 1)` 同样减半。

## 3. 门与实测

### 3.1 探针自证（新增纪律，本轮第一次执行）

按 `MEMORY` 的 GPU 测量纪律第 3 条，变体档必须自证生效，不能只靠「代码看起来改了」：

1. **SPIR-V 层**：`spirv-dis` 对比 `_s16` 与基线 ⇒ 状态臂的 `OpTypeFloat 16` +
   `_runtimearr_half` + `ArrayStride 2`，且 `OpCapability StorageBuffer16BitAccess`（该 capability
   现有 a/v/w 臂已在用，驱动支持无疑问）。
2. **运行时层**：`LOG_BARRIERS=1` 的 dispatch 轨迹直接打出变体文件名：
   `[K] shaders/spv/dplr_seq_f32_f32_s16.spv R[0x…050,…] W[…]`，读写地址首项即状态张量，
   与 fp32 臂不同基址。
3. **基线未被污染**：改 `.comp` 后两个已提交的基线 spv 显示 `M`，逐指令 diff HEAD 与工作区
   ⇒ 唯一差异是一行 `OpSourceExtension "GL_EXT_shader_explicit_arithmetic_types_float16"`（元数据，
   无代码变化）；`fuse_ka_dplr_norm.spv` 字节不变。

### 3.2 吞吐 + 占用（同会话交错，B=128，SEGS=4 × NTOK=32 = 每槽 128 步）

脚本 `C:\tmp\st16ab.sh`（临时），两臂只改 `WKV_STATE_F16`，其余门控同一：

| 轮 | fp16（默认） | fp32（`WKV_STATE_F16=0`） | 比 |
|---|---|---|---|
| 1 | 1977.5 | 1881.5 | +5.1 % |
| 2 | 1947.0 | 1881.7 | +3.5 % |
| 3 | 1914.8 | 1863.0 | +2.8 % |
| 中位 | **1947.0** | **1881.5** | **+3.5 %** |

fp16 臂逐轮下滑（1977.5→1914.8）是本轮会话内的热漂（fp32 臂同样下滑，且 fp32 的 8707 ms 在两轮
逐毫秒复现 ⇒ 采集本身可复现）。**分布不重叠**是这里唯一可引用的判据。

占用：`[VRAM] 建 batch state 后 7788 → 6498 MiB`（−1290 MiB = 128 槽 × 10.1 MiB，与理论的
128 × 10.3 MiB 相符）；`host 镜像` 同减 ⇒ 系统内存也省 1.3 GB。

### 3.3 数值契约

**先记一条方法论**：贪心逐 token 对拍这个指标在本项目**没有判别力**，是 2026-10-10
`参考/2026-10-10-Vulkan-rkv张量核默认翻转-实施记录.md` §2 已经踩过的坑（贪心把任意单点 logit
翻转放大成整条序列分叉，指标直接饱和）。本轮照旧量它，只作为**与 CUDA 留档同口径的可比读数**，
不作为默认开关的依据；依据最终放在 §3.6 的采样无关精度门（§3.4 的部署摘要门先被指望，后来在
§3.5 判定它对本改动无判别力）。

口径对齐 CUDA 侧留档（`参考/2026-09-21-int8-IMMA实施记录.md` §3g.4）：`TOPK=1` 贪心、
`DUMP_TOK` 逐 token 落盘、与 fp32 状态逐位对拍。

| 配置 | 样本 | 分叉 token | 分叉槽 | 首处分叉 |
|---|---|---|---|---|
| Vulkan B=8 × 512 步 | 4096 | 1066 / 4096 = **26.03 %** | 3 / 8 | slot 1 / slot 3 均在**第 0 步**，slot 7 第 74 步 |
| Vulkan B=64 × 512 步 | 32768 | 7073 / 32768 = **21.59 %** | 18 / 64 | — |
| *CUDA 同档参照* | 32768 | 7621 / 32768 = 23.26 % | — | slot 1 第 0 步 |
| *CUDA B=8 参照* | 4096 | 0 %（**该档 CUDA 自己标注为假阳性**） | — | — |

⇒ **Vulkan 的分叉率与 CUDA 早已接受的量级一致**（B=64 档 21.59 % vs CUDA 23.26 %，甚至略低）。
「第 0 步就分叉」在这里是**预期**而非缺陷征兆：两臂的 `prefill seeds` 逐位相同
（B=128 冒烟里两臂都是 `sum=0x1b9664`），分叉来自 prefill 结束时**状态回存的 dtype** 而非前向
口径——这正是状态 dtype 改动的定义性影响，与「前向算错」那种 step 0 分叉要区分开，区分手段就是
seed 指纹是否一致。

分叉槽内也不是全崩：slot 1/3 是 486/512、491/512 不同（分叉后再没汇回），slot 7 只有 89/512
（分叉后回汇）。另外 `[WARN] MISSING-BARRIER` 在 B=128 两臂都是 **0 次** ⇒ 冒烟日志里那条
不是本档引入的。

### 3.4 部署质量门（一度被指望成默认开关的依据）

`examples/batch_summarize`（线上 `SessionSummaryService` 同款提示词与采样参数，BATCH=8，
10 个真实多轮场景 → 20 条摘要），CUDA 为基准，比**平均公共前缀比**（口径：从第一个词起连续相同
的词数 ÷ 两条的较大词数，逐条求平均）+ 平均字数 + 逐字全同数。

脚本 `C:\tmp\sumgate.sh`（`BACKEND=cuda` / `BACKEND=vulkan` 默认 / `BACKEND=vulkan WKV_STATE_F16=0`
三跑），比较器 `C:\tmp\sumcmp.js`。

三臂读数（模型换成 `rwkv7-3B-int8.st`，原门模型已不在盘上，见 §5；明细在 §3.5 的 2×2 矩阵）：
VK-fp16 对 CUDA-fp16 的平均公共前缀比 **0.373**，而 VK-fp32 对 CUDA-fp16 反而 **0.508** ⇒
**方向与预期相反**（若要「同契约更像」，fp32 臂该更低）。
结论：这一轮先判为「不能判」，补成 2×2 后判为**该门对本次改动无判别力**（理由见 §3.5 三条读数）；
真正的判据换成 §3.6 的采样无关精度门。

**判据方向**：CUDA 侧的状态**本来就默认 fp16**（`supports_f16_wkv_state() = true`，已核对
`backend_cuda.rs:10350`），所以这一改动的预期方向是「把 Vulkan 挪到与 CUDA **同一数值契约**」
⇒ 若 fp16 臂的前缀比高于 fp32 臂，默认开同时拿到「+3.5 % 吞吐 / −1290 MiB 占用 / 更靠近 CUDA」
三件；若反向，默认必须翻回 fp32。

### 3.5 第一轮读数**与预期相反**（这是本轮真正的发现）

同一模型（`rwkv7-3B-int8.st`——原门用的 `rwkv7-g1i-2.9b.int8.st` **已不在盘上**，见 §5）、
同一 10 个场景 20 条摘要、BATCH=8：

| 配置 | 与 CUDA(fp16) 平均公共前缀比 | 平均 LCS 比 | 逐字全同 | 平均字数 |
|---|---|---|---|---|
| CUDA fp16（基准） | — | — | — | 15.7 |
| Vulkan **fp16**（本档） | 0.373 | 0.528 | 6/20 | **15.3** |
| Vulkan **fp32**（`WKV_STATE_F16=0`） | **0.508** | **0.639** | 9/20 | 10.5 |

**方向是反的**（fp32 臂更「像」CUDA），但两个相似度指标都被**长度**污染了：公共前缀比与 LCS 比
都按 `max(len)` 归一，于是「开头相同、提前被 `clean_summary` 截短」的输出天然得高分
（fp32 臂平均 10.5 词 vs CUDA 15.7 词 ⇒ 上界 15.7/10.5 的结构性偏置）。而**长度这一维是 fp16 臂
明显更贴近 CUDA**（15.3 对 15.7，fp32 臂 10.5）。两个指标给的是相反的信号 ⇒ **这一轮不能判**。

处理办法不是挑一个指标，而是补上缺失的那一格，做 **2×2 契约矩阵**（CUDA 侧同样有
`WKV_STATE_F16` 开关 ⇒ 四档全跑）：

| 公共前缀比（LCS 比 / 逐字全同） | vs CUDA-fp16 | vs CUDA-fp32 |
|---|---|---|
| **Vulkan-fp16** | 0.373（0.528 / 6） | 0.620（0.734 / 12） |
| **Vulkan-fp32** | 0.508（0.639 / 9） | 0.653（0.687 / 13） |
| 平均字数 | CUDA-fp16 **15.7** / CUDA-fp32 12.4 | VK-fp16 **15.3** / VK-fp32 10.5 |

三条读数：

1. **同契约没有吸引力**：`VK-fp16 ↔ CUDA-fp16`（0.373）不比 `VK-fp16 ↔ CUDA-fp32`（0.620）高，
   对角线方向完全相反 ⇒ 「把 Vulkan 挪到与 CUDA 同契约 ⇒ 输出更像」这条预期**没有被这个门验证**。
2. **状态 dtype 这一轴本身是一阶扰动**：只换 CUDA 自己的状态档（fp16 → fp32）就只剩
   0.385 前缀比、7/20 全同 —— 与「换后端」同量级。也就是说这条管线上，
   「状态存 fp16 还是 fp32」和「跑 Vulkan 还是 CUDA」造成的输出差异**一样大**。
3. **长度这一维确实按契约分簇**（两个 fp16 档都 ≈15.5 词、两个 fp32 档 10.5/12.4 词），
   而公共前缀比 / LCS 比都按 `max(len)` 归一 ⇒ 天生奖励「开头一致但提前被 `clean_summary`
   截短」的一侧（fp32 臂正好处在劣势长度上却拿了高分）。指标与被测对象不同向。

⇒ **判定：部署摘要管线这个门对本次改动没有判别力**，既不能用来支持默认开，也不能用来反对。
它当年（2026-10-10 rkv 翻转）有判别力，是因为那次两档的差异是**前向数值口径**（SIMT 的 fp32 激活
vs W8A8），幅度大到一个饱和指标也能分开；状态回存位宽是**逐元素的小扰动**，在 20 条 × 采样放大
下分不开。硬拿它当门会把结论建在指标偏置上 —— 这正是 §2 那条「指纹类指标饱和」的老坑换了个形态。

### 3.6 换用**采样无关**的精度门

同一批场景改成「与**同一个 CPU fp32 参考**比」，不经过采样器：
`ARGMAX_VERIFY=1 SELFLOOP_N=64`（`src/main.rs` 里打印 `== GPU vs CPU ==` 的
`max_abs_diff` / `rmse`，以及贪心 self-loop 序列与逐 token 参考的一致性），四档各跑一次。

判据**不是**「谁更接近 fp32 参考」（那条必然偏向 fp32 档，因为 CPU 参考就是 fp32 状态），而是：

> Vulkan 从 fp32 档换到 fp16 档所**付出的** logit 误差 / 贪心序列偏移，是否与 CUDA 付出的一致。

同量级 ⇒ 「状态 fp16 化」这件事在两个后端上**代价打平**，默认开就是把 Vulkan 摆到与 CUDA
相同的代价点上；若 Vulkan 明显付得更多，说明本实现（fp16 存 + fp32 算、RTNE 回存）之外还有
额外的数值损失，默认必须翻回。

已核对：CUDA 侧 `WKV_S16` 与本实现**同一约定**（`backend_cuda.rs:7404` / `:4264` 的
`typedef __half stype` + `st_ld = __half2float` / `st_st = __float2half_rn`，注释写明
「计算全程 fp32，只在载入/回存时降位」；批量核 `dplr_variant` 在
`fuse_ka_dplr_norm{,_batch}` / `dplr_seq{,_batch}` 四处**全部**注入 ⇒ 早前设想的
「CUDA 只在单流用 fp16 状态、批量仍是 fp32」**不成立**）。GLSL 侧 `S_TYPE(x)` 的
`OpFConvert` 到 float16 同样是 round-to-nearest-even，故两边舍入约定一致。

**四档读数**（脚本 `C:\tmp\verifygate.sh`，同一模型 `rwkv7-3B-int8.st`、同一批 token、
同一个 CPU fp32 参考；`exit=0` 四档全通）：

| 档 | `GPU vs CPU` rmse | max_abs_diff | `ARGMAX_VERIFY` | 64 步贪心 self-loop |
|---|---|---|---|---|
| CUDA fp32 | **2.690677** | 6.715429 | match（37480） | 参照序列 |
| CUDA fp16 | **3.823020**（+42.1 %） | 7.647006 | match（37480） | 与自家 fp32 臂 **46/64 = 71.88 % 分叉**，首处第 14 步 |
| Vulkan fp32 | 3.227278 | 8.211637 | match（37480） | 参照序列 |
| Vulkan fp16 | **3.223274**（−0.12 %） | 8.201856 | match（37480） | 与自家 fp32 臂 **0/64 分叉（逐位相同）** |

⇒ **代价不对称，而且偏向 Vulkan**：CUDA 把状态降 fp16 要付 rmse **+42 %** 和 64 步里 46 步换词；
Vulkan 付的是 rmse **−0.12 %**（数值上 fp16 臂还略近于 fp32 参考）与**零**贪心偏移。
按 §3.6 开头的判据（「Vulkan 付出的是否与 CUDA 一致」），这里不是打平而是**Vulkan 明显付得更少**
⇒ **默认开成立**，且不需要像 CUDA 当年那样用「上游也是 fp16」来背书。
跨后端同档对照（VK-fp16 vs CUDA-fp16 self-loop 56/64 不同）不属于本门范围——那一条量的是
两个后端**前向**的既有差异被贪心放大，与状态位宽无关。

**生效自证**（纪律 3：探针必须带与性能无关的标记）`LOG_BARRIERS=1` 两档各跑一次，看它实际绑定的
状态核 spv 名：

| 档 | 绑定的状态核 |
|---|---|
| 默认（fp16） | `dplr_seq_f32_f32_s16.spv`、`fuse_ka_dplr_norm_s16.spv` —— 全程**没有**不带 `_s16` 的状态核 |
| `WKV_STATE_F16=0` | `dplr_seq_f32_f32.spv`、`fuse_ka_dplr_norm.spv` —— 全程**没有** `_s16` |

⇒ 开关不是空转：两处状态核都真的换了变体（`StateTensor::spv()` 跟随张量 dtype，见 §2）。

**★ 一条必须记下的伪证**：上表刻意不含 `seq vs cpu max_abs_diff`，因为四档里它两两同值
（Vulkan 两臂都 0.100290，CUDA 两臂都 0.483808），看起来像「状态 dtype 对 prefill 无影响」。
真相是：这个 max 取在**整条拼接序列**上，而极大值由**第 1 个 token** 贡献——第 1 步的输入状态全零，
fp16 对零无损 ⇒ 后面 token 的状态扰动全被这个天花板遮住。它是「指纹类指标饱和」的第三种形态
（前两种：贪心分叉率、公共前缀比）。可引用的只有 `rmse`（对全元素取均方，不被单点支配）
和贪心序列本身。


### 3.7 重 dump 分核表（补上 `2026-10-10` 那份的账，也是下一轮的挑杠杆依据）

口径：`SLOTS=128 SEGS=1 NTOK=2 PREFILL_SLOTS=8 SKIP_GRAPH=1 PROF_GPU=1`，取最后一个 decode dump
（1738 条 kernel = 2 步 × 128 槽），两档各一次独立进程。⚠️ 与 `2026-10-10` §3.5 那份**不可逐行对比**：
其间 `gemm_imma` 落了 smem 打包 staging 与 split-K 口径修正两轮，分母从 ≈200 ms/2 步降到
122–126 ms/2 步，占比整体被推高。

| kernel | fp32 状态 | fp16 状态 | 绝对变化 | fp16 档占比 |
|---|---:|---:|---:|---:|
| `gemm_imma_bm64_nst8` | 45.94 ms | 47.18 ms | +2.7 %（跨进程噪声） | 38.6 % |
| `gemv_lowrank_chain4_batch` | 26.49 ms | 25.59 ms | −3.4 %（噪声） | **20.9 %** |
| `fuse_ka_dplr_norm{,_s16}`（状态） | 22.79 ms | **18.35 ms** | **−19.5 %** | 15.0 % |
| `gemv_int8_rkv_stage1_batch` | 17.30 ms | 17.00 ms | −1.7 %（噪声） | 13.9 % |
| `gemm_imma_reduce` | 4.01 ms | 4.06 ms | — | 3.3 % |
| `quant_x_i8` | 2.87 ms | 2.84 ms | — | 2.3 % |
| 其余 8 项合计 | 6.19 ms | 6.15 ms | — | 5.0 % |
| **SUM** | **126.59 ms** | **122.17 ms** | **−3.5 %** | 100 % |

三条结论：

1. **+3.5 % 的吞吐全部来自状态核自己**：SUM 的降幅（−3.5 %）与状态核的绝对降幅（−4.42 ms =
   SUM 的 3.5 %）在数值上就是同一件事，其余每一项都在跨进程噪声内。同进程墙钟同步验证：
   剖析态 decode 1908.4 → 1981.8 tok/s（+3.8 %），与 §3.2 交错 A/B 的 +3.5 % 一致。
   ⇒ 这条改动**没有**副作用性地饿到别的核，也没有把时间挪到别处。
2. **状态核没有腰斩，只降了 19.5 %**：省下的是 load/store 的位宽，S 上的**计算**（exp/mul/加权和）
   仍是 fp32 且仍是该核的主要指令流量。所以「fp16 存储」的收益上限本来就远低于 50 %，
   实测 19.5 % 是符合结构的读数——留档以免下次有人按「带宽减半 ⇒ 时间减半」预期。
3. **下一根杠杆由此排序**（三个 SIMT 核仍占 49.8 %）：低秩链二级 `gemv_lowrank_chain4_batch`
   **20.9 %** > 状态核 15.0 % > rkv 二级 13.9 %。低秩链现在是**唯一还没有张量核档的批量链**
   （`supports_lowrank_gemm_batch()` 对 Vulkan 恒 false），且它离两个 bound 都很远：
   权重 (96+96+64+320)×2560×4B = 5.9 MB/层 ⇒ 128 槽整步带宽下界 ≈0.31 ms，实测 12.8 ms/步（40×）；
   按 FLOP 算整步 12.1 GFLOP ⇒ 实测 ≈0.94 TFLOP/s，只有本卡 fp32 SIMT 峰值的 **6.6 %**。
   ⇒ 这是算力形态问题（subgroup-per-row 在 K=64/96 上做归约，纯延迟受限），不是带宽问题，
   张量核档有实质空间。
