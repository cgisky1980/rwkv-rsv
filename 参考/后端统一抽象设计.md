# rwkv-rsv 后端统一抽象设计

> 状态：S1 已完成（trait 接口 + Vulkan 实现，抽象层验证通过），详见 [`后端统一抽象-S1完成记录.md`](后端统一抽象-S1完成记录.md)。
> 方向：**轻量算子 trait**（`ComputeBackend`），现有 Vulkan 实现包成 `VulkanBackend`，未来可插 CUDA/Metal。
> 明确不引入 MNN（MNN 无 RWKV-7 WKV 原生算子、量化格式不兼容、且是更重的通用框架耦合）。

---

## 1. 背景与目标

当前 `rwkv-rsv` 的推理 runtime 深度耦合 Vulkan（`runtime.rs` 绑定 `vulkanalia`，算子全部为自研 GLSL shader）。用户希望有**后端统一抽象**，让 CUDA / Vulkan / Metal 等后端可插拔，并在启动时**自动判断**用哪个后端。

目标：

1. 定义一层**算子级抽象**（`ComputeBackend` trait），Vulkan 与未来后端各自实现。
2. 引入**平台无关张量句柄**，算子签名不依赖 Vulkan 类型。
3. 提供**后端选择逻辑**（`Backend::detect()`：CUDA 可用 → CUDA，否则 Vulkan）。
4. **不破坏**现有 CPU fp32 参考、逐层精度验证、三路量化体系。

> 注：`自动判断用 cuda 还是 vulkan` 与抽象层是**同一件事**——即抽象层里的后端选择逻辑，并非额外需求。

---

## 2. 现状分析

| 项 | 现状 | 抽象难点 |
|---|---|---|
| Runtime 公开方法 | 约 72 个（约 40 个算子 + 张量管理/批处理/采样） | 算子签名依赖 Vulkan `Tensor<>` |
| 张量类型 | `GpuTensor` / `GpuTensor16` / `GpuTensorU32` / `GpuTensorAny4` / `GpuTensorInt8`（见 `runtime.rs:23-70`） | 直接持有 Vulkan `Tensor<T>`（`device` + `host`） |
| 持有方式 | `GpuModel` 直接持有具体 `Runtime`（`gpu_model.rs:102`） | 需改为持有 `Box<dyn ComputeBackend>` |
| 批处理模型 | `begin_batch()` / `end_batch()` + 持久 command buffer，整段记录一次 submit | Vulkan(command buffer) 与 CUDA(stream) 语义不同 |
| 自动调参 | 检测 `vendor_id` / `subgroup_size` / 共享内存等选 `constant_id` | Vulkan 专属，后端自身负责 |

核心难点：**张量句柄与算子的平台无关化**。Vulkan 的 `Tensor<>` 使用 buffer device address + shader 内 buffer_reference，CUDA 用 `cudaMalloc` 指针，二者句柄不同，必须先抽象。

## 3. 抽象层设计

### 3.1 平台无关张量句柄

引入 `TensorId(u32)` 作为平台无关句柄；后端内部维护 `id → 设备张量` 映射表。

```rust
/// 平台无关张量句柄（由后端分配，内部映射到设备内存）
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct TensorId(pub u32);
```

- 后端 `create_tensor(len, dtype)` 返回 `TensorId`，内部登记设备缓冲。
- 上传/下载/算子均以 `TensorId` 为参数。
- 量化权重（any4/int8）用组合句柄或附加元数据（`m`/`k`/`group`）的结构体。

> 兼容策略：为避免一次性重写所有调用点，`TickerId` 可包裹现有 `GpuTensor`（`enum TensorHandle { Vulkan(GpuTensor), Cl(TensorId) }`），或直接全局改用 `TensorId`。**推荐直接改用 `TensorId`**，避免 `enum` 分支污染算子签名。

### 3.2 ComputeBackend trait

只抽象**核心算子**，张量管理（alloc/upload/download）也进 trait。首期抽象面聚焦高频算子，降低重构成本：

```rust
pub trait ComputeBackend {
    // —— 张量管理 ——
    fn create_tensor(&mut self, len: usize) -> R<TensorId>;
    fn create_tensor_f16(&mut self, len: usize) -> R<TensorId>;
    fn create_tensor_u32(&mut self, len: usize) -> R<TensorId>;
    fn upload(&self, t: TensorId, data: &[f32]) -> R<()>;
    fn download(&self, t: TensorId) -> R<Vec<f32>>;

    // —— 批处理（一次提交多条 kernel）——
    fn begin_batch(&mut self) -> R<()>;
    fn end_batch(&mut self) -> R<()>;

    // —— 核心算子（RWKV-7 关键路径）——
    fn gemv_f16(&self, w: TensorId, x: TensorId, y: TensorId, m: usize, k: usize, n: usize) -> R<()>;
    fn norm(&self, x: TensorId, g: TensorId, b: TensorId, y: TensorId, c: usize, n: usize, eps: f32, rows: usize) -> R<()>;
    fn norm_lerp6(&self, x: TensorId, prev: TensorId, xr: TensorId, /* ... */) -> R<()>;
    fn fuse_ka_dplr_norm(&self, s: TensorId, /* ... */) -> R<()>;
    fn cmix_norm_lerp(&self, x: TensorId, prev: TensorId, /* ... */) -> R<()>;
    fn sample(&self, logits: TensorId, /* ... */) -> R<()>;
    // ... 其余算子按需补齐
}
```

> 首期不必全量抽象 40 个算子。**建议先抽象 decode 路径的算子**（`gemv_*`/`norm*`/`fuse_ka_dplr`/`cmix_*`/`sample`），把 `gpu_model.rs` 的 decode 路径切到 trait；seq/prefill 路径（`gemm`/`dplr_seq`）二期再补。这样首期改动可控，且能立刻验证抽象可行性。

### 3.3 批处理模型（batch）

- Vulkan：`begin_batch`→记录 dispatch→`end_batch` 一次 submit + wait（现状）。
- CUDA：可用单一 stream 等价，`begin/end` 近似对应 `stream_synchronize` 边界。
- trait 只暴露 `begin_batch/end_batch`，后端内部实现各自语义。

### 3.4 量化权重张量

- any4/int8 是自研格式，trait 需提供 `GpuTensorAny4` / `GpuTensorInt8` 的平台无关等价物（`TensorId` 组合 + `m`/`k`/`group`）。
- 未来 CUDA 后端需实现 same dequant 公式（`w = scale*lut[idx]+zero`），保证与 Vulkan 逐位一致。

## 4. 后端选择逻辑

```rust
pub enum BackendKind { Vulkan, Cuda }

pub fn detect_backend() -> BackendKind {
    // CUDA 可用检查（如 cudarc/动态加载 driver）：查到 → Cuda；否则 Vulkan
    if cuda_available() { BackendKind::Cuda } else { BackendKind::Vulkan }
}
```

- 启动时调用 `detect_backend()`，据此构造对应后端；`ModelBuilder::build` 增加后端参数（默认自动）。
- 现有 Vulkan 的 `vendor_id/subgroup_size` 自动调参保留在 `VulkanBackend` 内部。

## 5. 分阶段迁移方案

| 阶段 | 内容 | 产出 |
|---|---|---|
| **S1** | 引入 `TensorId` + `ComputeBackend` trait；`VulkanBackend` 封装现有 `Runtime`（不动 shader） | trait 接口 + Vulkan 实现 |
| **S2** | `GpuModel` 改为持有 `Box<dyn ComputeBackend>`，decode 路径算子切到 trait | decode 走抽象层，回归通过 |
| **S3** | seq/prefill 路径算子切到 trait | 全路径走抽象层 |
| **S4** | `detect_backend()` + `ModelBuilder` 后端参数 | 自动选择可视化 |
| **S5**（可选） | 新增 `CudaBackend` 实现（首期可只做 decode 核心算子） | CUDA 后端雏形 |

每阶段保持 `cargo fmt` + `cargo clippy --release` 零警告 + 现有精度验证通过。

## 6. 风险与权衡

| 风险 | 说明 | 缓解 |
|---|---|---|
| 抽象面过大 | 40 个算子全抽象成本高 | 首期只抽象 decode 核心算子，S3 再补 seq |
| 张量句柄迁移 | 全局改 `TensorId` 涉面广 | 分阶段；`TensorId` 内部映射现有缓冲，shader/精度不变 |
| Vulkan/CUDA 语义差异 | command buffer vs stream | 只暴露 `begin/end_batch`，内部实现各自语义 |
| CUDA 开发成本 | CUDA kernel 需重写部分算子 | 可先只做 decode 核心，验证后逐步扩展 |

**不做的事**：不引入 MNN；不重写量化器；不破坏现有精度验证与 CPU fp32 参考。

---

## 7. 结论

- 采用**轻量算子 trait**（方案 A），不引入 MNN。
- 首期（S1–S2）即可获得"抽象层 + Vulkan 实现 + decode 走 trait"的可用骨架，成本可控。
- 自动判断 CUDA/Vulkan（`detect_backend`）随抽象层自然落地，S4 完成。
