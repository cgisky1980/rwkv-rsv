05对照原项目（Albatross）后补做的三个实验

原项目对 rows ≤ 16 用 WMMA 张量核、rows = 8~2047 直接丢 cuBLAS。我们的 T=4 正落在这一档，于是实测了「换 fp16 走张量核」是否更快。

实验decodeT=4 验证 passverify/decode判定
int6（2.48 GB，自研 GEMV）8.25–8.65 ms16.3–16.4 ms1.89–1.98当前档
fp16（5.89 GB，GEMM/cuBLAS，即原项目同载体）12.63 ms29.21 ms2.31慢 1.8×
按块数自适应 split-K（目标 300 / 480 块）—18.7 / 18.6 ms—负优化
块大小 4 / 32 warps11.6 / 9.4 ms18.2 / 19.4 ms1.56 / 2.0616 最优

为什么 fp16 + 张量核不划算：int6 读 0.75 B/权重、fp16 读 2 B/权重（2.67×）。小 T 时权重只读一遍， 「一条 load 服务 16 行」的优势换不回 2.67 倍流量；原项目自己对 rows=4 也要把 M 补到 16（4× 计算浪费）。 而把 int6 每步反量化成 fp16 再 GEMM 是 4.75 B/权重（6.3×），数学上直接出局。

一个读数陷阱：W=4 的端到端倍数看着是 1.25–1.36×，比 1.12× 好看 —— 那是分母被拖慢的假象 （decode 从 8.65 掉到 11.6 ms）。用 verify/decode 比值一照就露馅。所有倍数只认「同配置下 plain vs spec」。

06int6 张量核档：B=8 提速 13%，T=4 反而慢（已按 batch 分档）

按 MTP 原项目 kernels/int6_gemm.py 的 USE_DOT 分支实现：6-bit 解包成精确 fp16 → mma.m16n8k8 → scale 在 chunk 末乘。

场景SIMT（原档）张量核判定
批量解码 B=8（聚合吞吐）244.0 / 238.6 tok/s275.8 / 273.5+13%，已默认
MTP 投机 T=4（M=4）验证 pass15.9 ms17.9 ms留 SIMT

为什么 T=4 变慢：mma 的 M 只有 16 行，T=4 补到 16 = 75% 空转，再加解包成本；B=8 能填一半，收益才出来。 所以按 batch 分档：8..=16 走张量核，≤7 留 SIMT。

两份上游交叉印证：rwkv_lightning_cuda/quant/gemmv/README_w4a16.md 明写「M≤16 保留原寄存器解包路径」， Tensor Core 只给 M>16 —— 与实测分档点完全一致；而 MTP 原项目的 RED_MAX_M = 1 是 服务端 B=32 口径， 它的 1.8–1.9× 建立在 128 行验证上。B=8 两轮的 token 流 sum/xor 逐位相同，数值档无影响。

07口径与不确定性（必读）

测量方式同一进程内先跑 plain（逐 token decode）再跑 spec（起草→验证→回滚），两者从同一 prompt 出发；三轮独立复测取一致方向。
为什么不用单次端到端倍数本机没有 nvidia-smi，锁频/锁屏做不到；同一份代码两次进程曾出现 13.4 与 34.7 tok/s。单次读数出现过 2.02× 与 0.77× 两个荒谬值，已全部作废。
正确性自检（全部通过）回滚 max|Δstate| = 0（540 万个数，含二次回滚/图重放）；head 与主模型 argmax 前 3 步一致；T=4 seq vs 解码 argmax 一致；cargo test --release 96 通过。
距 1.5× 还差什么按 2.84 token/步，1.5× 需步时间 ≤ 16.2 ms ⇒ 验证 pass 要从 16.3 压到 ~12 ms。剩下的空间全在两处：ffn 段（170 GB/s，占 39%）与 r/k/v 段（152 GB/s）。两者都是「23 个节点各自扫一遍 DRAM」的结构性问题，需要 decode 那种深度融合，不是单点 patch。
