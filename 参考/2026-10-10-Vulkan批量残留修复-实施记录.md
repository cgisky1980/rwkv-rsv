## 0. 结论

**`batch_step_sample`（并发池每步回主机的那条路径）在 Vulkan 后端此前是完全坏的**，且坏在两处，
任一单独存在都会让它报错或返回恒定 token。本轮两处都修掉，并补上一条能长期防回归的基准对拍
（`examples/batch_decode_bench.rs` 的 `STEP=1`）。

| 判据 | 结果 |
|---|---|
| STEP 与自循环逐位对拍（两后端 × B∈{1,2,8,16} × TOPK∈{0,1}，16 组） | **16/16 一致** |
| 长 prompt（1094..1217 tok，> `PAD_TO=512` 走分块 prefill）B=4 | 两后端一致，且两后端之间也逐位相同 |
| `cargo test --release -- --test-threads=1` | 64 passed / 0 failed（+1 ignored）→ A4 后 **66 passed** |
| `cargo fmt --all` · `cargo clippy --all-targets -- -D warnings` | 零警告 |
| A2 · `upload_u32_part`（Vulkan） | 两后端单测过；`PENALTY=1` 五档对拍全「一致」（§6.3） |
| A3 · uniform 池自动定容 | **前提证伪，机制未实现**：三条批量路径高水位一律 ≤ 69KB / 8MB，与 B、NTOK 无关（§7） |
| A4 · 「仅 CUDA」叙述 | 逐条核对后**该改的改、该留的留**（graph 捕获与 `build_shared` 两处确实 CUDA 专有）（§8.1） |
| A4 · 跨后端逐位一致 | **口径问题而非缺陷**：CUDA 压回 SIMT 后 B=8 逐位一致；B=32 因 CUDA 另有张量核用法仍不同（§8.3） |

修复前后**不可直接比较**：修复前 Vulkan 的 STEP 路径根本不产出可用文本（每槽每步返回同一个
token），没有「吞吐」可言，只有「错」。

## 1. 复现（先复现再修，按用户要求）

在 `batch_decode_bench.rs` 里加 `STEP=1` 模式：与自循环路径（`submit_sample_selfloop_batch`）
共用同一批 prompt、同一 batch State、**同一 seed 口径**（段初基 = 该槽上一段末 token，段内第 r
步 seed = 基 + r），但走 `batch_step_sample` 逐步回主机；两条路径各打一套 `sum/xor` 指纹并直接
对比。惩罚历史在该模式固定为零（`hist_len≡0`），把「采样读数是否正确」与「逐 token 追加历史
需要的部分上传」（下一批 A2）**解耦**。

| 配置 | 自循环 | STEP | 判定 |
|---|---|---|---|
| `BACKEND=cuda TOPK=1 SLOTS=8 SEGS=3 NTOK=16` | sum=0x4da0e8 xor=0x7d52 | sum=0x4da0e8 xor=0x7d52 | 一致 |
| `BACKEND=vulkan TOPK=1 SLOTS=8 SEGS=3 NTOK=16`（修复前） | sum=0x4de113 xor=0xff3 | sum=0x537270 xor=0x0 | **不一致** |

修复前的逐 token dump（`DUMP_TOK_STEP`）是关键证据：**每个槽 16 步全是同一个 token**，而该 token
正好等于该槽**这一步喂进去的输入 token**：

```
slot0 恒 16417   slot1 恒 12308   slot2 恒 10901   slot3 恒 16744
slot4 恒 15758   slot5 恒 15466   slot6 恒 15931   slot7 恒 10408
```

（prefill 的 `seeds` 正是这些值；`STEP sum = seeds sum × 16` 严格成立 ⇒ 读回的是输入而非采样结果，
不是「状态不前进」也不是「采样核没跑」。）

诊断用的第二把刀：`PROBE=1` 在 STEP 块里只跑**一步** `batch_step_logits` 并下载 logits 求 argmax，
把「前向算错」与「采样读数错」分开。实测 **Vulkan 与 CUDA 的 probe argmax 完全相同**（B=2：两槽都是
10080，top-3 一致）⇒ 批量单步**前向**在 Vulkan 上是对的，坏的只有采样结果的回读。

## 2. 根因（两处，都在 Vulkan 侧）

### 2.1 读回用错了缓冲：`download` 覆盖掉 kernel 写在 host 镜像上的结果

Vulkan 后端的张量是 **host-visible 镜像 + device-local 两块独立 `VkBuffer`**
（`Runtime::create_tensor`：`app.create_tensor(.., true)` 与 `(.., false)`）。批量自循环的 token
通路整个闭环在 **host 镜像**上：

- `record_sample` 的 token 写出目标是 `tok_g.host.address`（`sample_into_host*` 的语义就是
  “into host”）；
- 下一轮的 `gather_rows_device_f16` 也从 **host** 侧读 token（`backend.rs` 里那句注释
  「与单流路径一致走 host 可见缓冲」就是这件事）；
- 需要落盘的历史才由 `record_token` 显式拷进 device 侧的 `token_seq`，所以 `download(ticket.token_seq)`
  是对的。

而 `batch_step_sample` 用的是 `download(bb.current_token)`。`Runtime::download` 的第一步是
`copy_buffer(device → host)`——于是它把 kernel 刚写回 host 镜像的采样结果**用 device 侧的内容覆盖
掉**，而 device 侧正是本步开头 `upload()` 进去的「输入 token」。这就是 dump 里那个恒等式的来源。

顺带，原代码的 `download` 还夹在 `begin_batch()`/`end_batch()` 之间：Vulkan 侧采样 dispatch 只是被
记录进持久 command buffer，真正的 submit + `queue_wait_idle` 在 `end_batch`，所以即便读对了缓冲，
读时也还没提交。**两处都得改**：先 `end_batch()`，再读 host 镜像。

（单流路径不受影响：`forward_token` 的采样走 `sample`/`argmax` 算子，它们写的是 **device** 缓冲，
所以那里的 `download(bufs.token_argmax)` 是正确的。两种写法并存才是这个坑的根源。）

CUDA 侧 kernel 直接写 device 缓冲、host 只是缓存，因此 `download` 一直是对的——这解释了为什么
10-03/04 的对拍验收（只在 CUDA 上跑，且只跑自循环路径）没发现它。

**修法**：`ComputeBackend` 增加

```rust
fn download_host(&self, t: TensorId) -> R<Vec<f32>> { self.download(t) }
```

默认实现转发 `download`（CUDA 语义即如此）；Vulkan 覆盖为 `Runtime::download_host`（只
`host.copy_to`，不做 device→host 拷贝）。`batch_step_sample` 改为「`end_batch()` 之后
`download_host`」。没有新增任何 kernel、没动任何 dispatch 序列。

### 2.2 `sample_into_host_seeded_batch` 把 hist 钉死成 f32

`hist` 只被用来取「设备地址 + `VkBuffer`」（kernel 按 u32 位模式读，barrier 按缓冲粒度插），但
实现里写的是 `get_f32(hist)`。批量自循环传的 `token_seq` 是 f32 存储所以一直没暴露；
`batch_step_sample` 传的是客户端池那种 `alloc_u32` 的惩罚历史（U32 存储）⇒ 直接报
`tensor TensorId(1893) must be f32`。

**修法**：改成 dtype 无关地取 `(g.device.address, g.device.buffer)`，F32/F16/U32 三种宿主都接受。
（曾试过简单换成 `get_u32`，那会把自循环那条路径反过来打挂——必须两种都收。）

## 3. 为什么这个 bug 能活到今天

`batch_step_sample` 是**唯一**一条「每步回主机」的批量路径，也是 mytown/client 并发池实际走的
路径（`rwkv_llm.rs` 每步调它）。而基准侧此前只有自循环路径（`forward_seq_batch_padded` +
`submit_sample_selfloop_batch`），10-03/04 的 Vulkan↔CUDA 对拍验收全部走自循环 ⇒ 从未覆盖。
本轮把 `STEP=1` 做成基准里的一等开关，就是为了让这条路径从此有可跑的判据。

## 4. 附带发现（本轮**未修**，留作后续）

1. **跨后端「逐位一致」不是无条件成立**：`BACKEND=vulkan` vs `cuda` 在 `UNIFORM_POOL_MB=64 SLOTS=8`
   （默认 TOPK=0）下为 `0xd08ada/0x2ea` vs `0xd02e16/0x6d08`；后者正是 10-04 记录 §4 表里的 CUDA
   读数（可精确复现），Vulkan 读数在**未改动的 HEAD 上**同样如此（stash 验证过）⇒ 与本轮修改无关。
   按 token 逐位比对：B=8 / 384 token 里 **44 个不同，首处分歧在 slot3 step4**，其余 7 个槽全程一致
   ⇒ 是数值相邻（单点翻转后被贪心放大），不是算子实现分叉。
   **A4 已定案**（见 §8）：把 CUDA 压到同一条 SIMT 序列（`LOWRANK_GEMM=0 FFN_VALUE_GEMM=0 GEMV_IMMA=0`）
   后 B=8 两边**逐位一致** ⇒ 原叙述没错，只是**漏写了口径**；README 两处已按此改写。
2. **同后端两条路径的相邻性**：默认门控下 loop/step 在 48 步/槽上逐位一致；强开
   `FFN_VALUE_GEMM=0` 后 8 个 token 内仍一致，之后出现单点翻转分叉。两条路径共用同一个
   `forward_layer_batch`，所以差异只能来自 reduce 顺序级别的微差被贪心放大，非功能性缺陷。
3. **`GEMM_IMMA` 这个 env 在 Rust 侧根本不存在**（只有 `VK_IMMA_OPS`/`GEMV_IMMA`/`LOWRANK_GEMM`/
   `FFN_VALUE_GEMM`）。计划里「CUDA 侧用 `GEMM_IMMA=0` 对齐采样口径」那行是误记，已按实测口径改写。

## 6. A2 · Vulkan 惩罚历史的部分上传（`upload_u32_part`）

### 6.1 症状

并发池每步只把**新采样的那一个 token**追加进自己的惩罚历史行（`rwkv_llm.rs` 的
`append_hist` → `GpuModel::write_u32_part`），否则每步重传整行 8192 个 u32。
`ComputeBackend::upload_u32_part` 只有 CUDA 实现了，Vulkan 落到 trait 默认实现：

```
upload_u32_part not supported by this backend
```

⇒ Vulkan 上一开 `frequency_penalty` / `presence_penalty` 就直接报错（A1 修好读回之后才轮到它露出来：
两条 bug 叠在一起时，客户端池先是拿恒定 token，再是干脆报错）。

### 6.2 改动

| 文件 | 改动 |
|---|---|
| `src/runtime.rs` | 新增 `Runtime::upload_part_u32(&GpuTensorU32, offset, data)`：写 host 镜像 + 复用已验证的 `copy_range_standalone`（`u32: Scalar`，按 elem=4 自动算字节数）。越界由 `copy_from` 自身报 `tensor len too small`，不重复实现一遍长度校验 |
| `src/backend.rs` | `VulkanBackend` 覆盖 trait 默认 `upload_u32_part`，紧邻已实现的 `upload_part`；trait doc 补一句**为什么不提供对称的 `download_u32_part`**（无需求、零调用方，历史回读走整行 `download_u32`） |

`GpuTensorU32` 没有 `len` 字段（只有 `host`/`device`），所以没按 `upload_part` 那样写显式 range
检查——这一点在函数 doc 里写明了，避免下一个人再去找那个不存在的字段。

### 6.3 验证

单测 `backend::tests::backend_upload_u32_part_roundtrip`（两后端循环，CUDA 不可用时跳过该档）：
整行 `upload_u32` 建基线 → `upload_u32_part` 覆盖中段 5 个 → `download_u32` 断言「覆盖段新值 +
段外原值」；再单独试末元素追加（hist 每步就是这个形状）。通过。

基准侧新增 `PENALTY=1`（只在 `STEP=1` 有意义）：把自循环的惩罚口径**逐字复刻**到逐步路径——
每段开头 `hist_len` 归零、段内第 r 步 `hist_len = r`（本段前 r 步采样出的 token，不含本步刚喂进去
的那个）、采样后立刻 `write_u32_part` 把新 token 写进该行第 r 列；`sp.frequency_penalty` 同时给
两条路径带上 0.2（共用一份 `sp`，所以对拍仍然成立）。`hist_stride` 在该模式取 `max(ntok, 8)`。

| 配置 | 自循环 | STEP | 判定 |
|---|---|---|---|
| vulkan B=4 TOPK=1 SEGS=2 NTOK=16 PENALTY=1 | 0x1a1c4f / 0x6251 | 0x1a1c4f / 0x6251 | 一致 |
| cuda 同配置 | 0x1a38c8 / 0x7bf6 | 0x1a38c8 / 0x7bf6 | 一致 |
| vulkan B=4 TOPK=0 PENALTY=1 | 0x1a1c4f / 0x6251 | 0x1a1c4f / 0x6251 | 一致 |
| vulkan B=8 TOPK=1 PENALTY=1 | 0x4dbf5d / 0x144b | 0x4dbf5d / 0x144b | 一致 |
| cuda B=8 TOPK=1 PENALTY=1 | 0x4dbf5d / 0x144b | 0x4dbf5d / 0x144b | 一致 |

（B=8 这一档两后端连彼此也逐位相同——加惩罚后分布被推离并列区，§4 那种单点翻转没出现。）

`cargo test --release -- --test-threads=1` → **65 passed / 0 failed**；fmt + clippy `-D warnings` 零警告。

## 7. A3 · uniform 池「按批量自动定容」——**前提被实测证伪，机制未实现**

计划里 A3 的目标是：`UNIFORM_POOL_MB` 需人工设、不设就在长批量下 abort，判据是「未设 env 跑通
`SLOTS=32 SEGS=4 NTOK=64` 从 abort 变跑通」。先按纪律量化（`PROF_POOL=1`，`UNIFORM_POOL_MB=64`
只为拿到读数），结果直接推翻前提：

| 配置 | 高水位 pool_cursor | slot 数 | 说明 |
|---|---:|---:|---|
| B=8 / NTOK=32 自循环 | 31,896 | 275 | |
| B=16 / NTOK=32 自循环 | 32,408 | 283 | |
| B=32 / NTOK=32 自循环 | 33,432 | 299 | |
| B=64 / NTOK=64 自循环 | 33,432 | 299 | |
| 批量 prefill（B=8/16/32/64 全部） | **69,080** | 1,048 | 与 B 无关 |
| `SKIP_GRAPH=1` B=32 NTOK=**256**（256 轮记录进**一次** submit） | 33,432 | 299 | 与 n 无关 |
| `STEP=1 PENALTY=1` B=32 | 31,344 | 266 | 逐步路径 |
| `PROMPT_REPEAT=12`（长 prompt，跨 PAD_TO 分块） | 69,080 | 1,048 | |

**默认 8MB 池用最凶的一档 = 0.82 %**；且占用与 `batch`、`NTOK` 都无关。原因写在
`Runtime::pool_slots` 的注释里：批内按 params 内容去重（ba08642，2026-08-25）把占用从
O(dispatch 数) 降到 O(不同 params 组合数)，而批量核本身用 stride 在 shader 内寻 slot、
per-slot 不产生新 params ⇒ 三条批量路径全都在 7 万字节级。

README/README_CN §9 那条「`NTOK=32`、`batch ≥ 16` 会超出默认 8MB 并 abort」因此是
**dedup 之前的陈旧叙述**（写作 2026-10-04，但结论属于 2026-08-25 之前）。

**决策：不实现 `set_batch_scale` + 批边界扩容 + `cache.clear()` 那一套。** 为一个跑不出来的
abort 引入「运行时换 `VkBuffer` + 全量 kernel 缓存失效」这条最危险的路径（descriptor set 绑死
旧缓冲，扩容时机稍有偏差就是 UB），风险收益完全不成比例。改为把事实写进文档，并把
`UNIFORM_POOL_MB` 的语义从「需要认真调的容量」降级为「极端形状兜底项」。

若将来真出现撑爆的形状（例如一次性把 `SLOTS` 抬到数千、或新增大量 per-slot 独立缓冲的算子），
届时按 §0 的表格重测高水位再立项，别提前建机制。

## 8. A4 · 门控与文档真相对齐 + `batch_decode_blocker`

### 8.1 逐条核对「仅 CUDA」断言（先验证再改，不批量替换）

trait 的 15 个 `*_batch` 里 Vulkan 侧的实现状态**逐条查过** `impl ComputeBackend for VulkanBackend`，
不是照着计划改的：

| 断言位置 | 计划里的说法 | 实测真相 | 处理 |
|---|---|---|---|
| `backend.rs` batch 段头「仅 CUDA 支持」 | 错 | **错**（Vulkan 已实现全套） | 改写为「CUDA 与 Vulkan 均已实现，默认 Err 只给未实现批量核的后端兜底」 |
| `seq_shift_batch` / `copy_token_batch` / `dplr_seq_batch` / `segmean`「仅 CUDA」 | 错 | **错**（四个都在 Vulkan impl 里） | 改「CUDA / Vulkan 均实现」 |
| `supports_lowrank_gemm_batch` / `supports_ffn_value_gemm_batch`「CUDA 专有」 | 计划说「Vulkan 已实现但按实测关闭」 | **计划说错了**：这两个 kernel 只有 `backend_cuda.rs` 有，Vulkan 从未实现；被 3374512 实测关闭的是 Vulkan 侧 r/k/v 的张量核**变体**（`VK_IMMA_OPS`） | 保留「只有 CUDA 实现」，把 3374512 的净亏 3.3× 与根因（43ms/步落在 dispatch **之间**）写进 doc，免得下一个人再去写一遍 |
| `supports_f16_wkv_state` | 同上「按实测关闭」 | **不是**实测关闭，是 GLSL 状态核 `BufS` 为 f32 专用（未实现） | 原文准确，不动 |
| `supports_graph_capture`「仅 CUDA」 | 待查 | **准确**（Vulkan 无 graph） | 补一句 Vulkan 的等价物是「n 轮记录进同一 buffer 一次 submit」 |
| `build_shared`「仅 CUDA」 | 待查 | **准确**（`import_tensors_from` 未被 Vulkan 覆盖，走默认 Err） | 把判据写进 doc |
| `gpu_model.rs` `create_batch_state` / `forward_seq_batch_core` / `batch_buffers` / state 回灌「仅 CUDA」 | 错 | **错** | 改「两后端」 |
| `examples/batch_summarize.rs`「仅 CUDA 后端」 | 错 | **错** | 改，并**实跑验证**：`BACKEND=vulkan BATCH=4` 4 场景 → `done: 8 summaries written, 0 rejected` |

### 8.3 跨后端指纹「逐位一致」定案（本轮最有价值的一条）

§4.1 的悬念解开了：**CUDA 侧三个张量核门控（`LOWRANK_GEMM`/`FFN_VALUE_GEMM`/`GEMV_IMMA`）自
2026-09-21 起默认全开**，而 10-04 的对比是**把 CUDA 压回 SIMT 路径**测的。同一口径下：

| 配置 | Vulkan | CUDA（三门控关） | 判定 |
|---|---|---|---|
| B=8 SEGS=4 NTOK=32 | `0xd08ada` / `0x2ea` | `0xd08ada` / `0x2ea` | **逐位一致** |
| B=8 同配置，CUDA 默认（张量核开） | `0xd08ada` / `0x2ea` | `0xd02e16` / `0x6d08` | 不同（= README 旧值，可精确复现） |
| B=32 三门控关 | `0x3477769` / `0x6bcd` | `0x341e052` / `0x7078` | **仍不同** |

⇒ 「对齐门控即逐位一致」在 B=8 成立、B=32 不成立：CUDA 在大批量还有其他张量核用法
（`gemm_imma` 打 att.output 等），三个 env 不足以把两条路径完全对齐。**所以跨后端逐位一致
不能作为无条件结论写**，README 两处（§6.1 正确性段、§8 对比表）已改为「同 SIMT 口径才成立，
且大批量只能近似对齐」。

顺带量化了吞吐口径的坑（同一台机器、同一次会话、冷机单次）：

| | Vulkan | CUDA 默认 | CUDA 三门控关 |
|---|---:|---:|---:|
| B=8 | 514.6 | 624.6 | 503.5 |
| B=32 | 929.1 | 1900.7 | 583.4 |

「Vulkan 追平 CUDA」只在**SIMT 对口径**下成立；对 CUDA 的**生产默认路径**，B=32 差约 2.0×
（§7 的 dispatch 固定代价是同一个根因）。README 的 ⚠ 脚注已写明这一点，并要求引用任一读数
前先在同会话内写明门控重测。
