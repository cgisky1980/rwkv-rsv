# 2026-09-19 batch 内核「权重零摊薄」根因修复记录

承接 [2026-09-19-并发吞吐基线表.md](2026-09-19-并发吞吐基线表.md) 与
[2026-09-19-selfloop-topk0兜底路径慢修复记录.md](2026-09-19-selfloop-topk0兜底路径慢修复记录.md)。

验收对象：**mytown/model-server 的批量路径**（`forward_seq_batch_padded` +
`submit_sample_selfloop_batch`），实测环境 RTX 2080 Ti / RWKV-7 3B int8。

## 1. 问题现象

model-server 官方参数并发扫描（`test/sweep_concurrency.py`，每并发 4 请求、
max_tokens=128、temperature=1.0 / top_p=0.2 / top_k=0）：

| 并发 | 修复前聚合 | 单请求均值 |
|---|---|---|
| 1 | 56.9 tok/s | 1.41 s |
| 2 | 58.7 tok/s | 3.82 s |
| 4 | 51.2 tok/s | 7.81 s |
| 8 | 69.8 tok/s | 11.24 s |

并发 8 仅 1.23×（信天翁 rows 模型理论 8×）。服务端日志同向：批量 8 槽
decode 1024 tok / 9500 ms ≈ 107.8 tok/s，即 **66.9 ms/步**，而单流 11.4 ms/步
——步时随 B 近乎线性，说明 batch 内核**没有摊薄权重读取**。

## 2. 根因定位（per-kernel profiling）

用临时 example（`PROF_CUDA_KERNEL=1` + `batch_step_sample`，跑完已删）取 B=1/4/8/16
逐 kernel 平均耗时：

| kernel | B=1 | B=4 | B=8 | B=8 占比 |
|---|---|---|---|---|
| `gemv_variant(_mb)` | 0.0640 ms | 0.2613 ms | 0.5452 ms | 53.5% |
| `gemv_int8_rkv_stage1_batch` | 0.0993 ms | 0.2820 ms | 0.6127 ms | 29.6% |
| `ffn_value_sparse_add_batch` | 0.0258 ms | 0.0722 ms | 0.1222 ms | 5.9% |
| `gemv_lowrank_chain4_batch` | 0.0284 ms | 0.0671 ms | 0.1187 ms | 5.7% |
| `rwkv_sample_batch` | 1.804 ms | — | 1.591 ms | 2.4% |

B=4→8 时 `gemv_variant_mb` 2.09×、`rkv_stage1_batch` 2.17× —— **严格线性**，
与内核里 `BGRP`（每 block 复用一份权重的 slot 数）的设计意图直接矛盾。

对比：单流 `gemv_variant` 对 ffn_key（10240×2560 int8 = 26.2 MB）耗时 0.064 ms
→ 410 GB/s（带宽 66%），**本身是良性的**。而 `_mb` 在 B=8 时等效带宽仅 ~52 GB/s。

**根因（三类内核同源）**：内层循环把「每 slot 都要用的量」放进了最内层，
导致重复读取——

1. `gemv_variant_mb`（int8 路径）：`x[xb]..x[xb+3]` 4 次标量加载 + 4 次
   `__floats2half2_rn` 写在 **r 循环（4 行）内** → x 片被重复读 4 行 × 4 标量。
   注意 fp16 路径（wtype==0）已用 float4 且 b 循环在外层，**只有 int8 路径写错了**。
2. `gemv_int8_rkv_stage1_batch`：12 次标量 x 加载写在 b 循环（b 又在 r 循环内）
   → x 被重复读 ROWS×BGRP 遍。
3. `gemv_lowrank_chain4_batch`：**嵌套整体反了** —— slot 在外层、权重行在内层，
   权重行被读 bcnt 遍。

顺带排除的两个假设（实测无效，勿再试）：
- `__align__(16) __half w[4]` + `*(const half2*)&w[0]` 取局部数组地址：改成
  `__floats2half2_rn` 直构后耗时 0.5452 → 0.5458 ms，**nvcc 本来就放在寄存器**。
- `gemv_variant_mb` 的 `BGRP` 4→8（让 B=8 时权重只读 1 遍）：总耗时
  165.6 → 191.7 ms **反而更慢**（`half2 hacc[4][8]` 溢出到 local memory），已回退。

## 3. 修复内容

`rwkv-rsv/src/backend_cuda.rs`，三处均为「把每 slot 共享的量外提到行循环之外，
并向量化」：

- `gemv_variant_mb`：新增 `half2 hx01[BGRP]/hx23[BGRP]`，在 kq 循环内**按 slot 取一次**
  （float4 加载 + 预乘门控 + 转 half2），r 循环只做权重反量化与 FMA。
- `gemv_int8_rkv_stage1_batch`：同样外提为 6 个 `half2 hxr0/hxr1/hxk0/hxk1/hxv0/hxv1[BGRP]`；
  权重反量化改为 `__floats2half2_rn` 直构（去掉局部数组取地址）。
- `gemv_lowrank_chain4_batch`：交换嵌套 —— 权重行读一次、逐 slot 累加
  （`lw[BGRP]/la/lv/lg` 四个累加数组），warp shuffle 归约移到最后按 slot 循环。

|---|---|---|---|
| `gemv_variant_mb` | 0.5452 ms | **0.1560 ms** | 3.49× |
| `gemv_int8_rkv_stage1_batch` | 0.5966 ms | **0.2764 ms** | 2.16× |
| `gemv_lowrank_chain4_batch` | 0.1198 ms | **0.0781 ms** | 1.53× |

## 5. mytown/model-server 附带修复

- **`jsonfixer` panic 打死请求**（真实 bug）：`jsonfixer 0.1.0` 在含多字节字符的畸形
  输出上 panic（`start byte index N is not a char boundary`，模型陷入重复循环时必触发），
  panic 冒泡到 axum handler → 连接被掐断，客户端表现为 `RemoteDisconnected`（丢请求）。
  已用 `catch_unwind` 兜住并加回归测试 `extract_does_not_panic_on_multibyte_garbage`
  （样本取自真实服务日志）。
- 存量 clippy 告警清零：`clone_on_copy` / `manual_strip` / `items_after_test_module` /
  未读字段；`presence_penalty` 之前未接线，现已接入采样参数；`EngineConfig.chunk`
  之前完全未用，现用于单流分块 prefill（prompt 短于 chunk 时行为不变）。

## 7. 剩余瓶颈与后续（B=8 每步 37.1 ms 构成）

| kernel | 占比 | 说明 |
|---|---|---|
| `gemv_variant_mb` | ~35% | 权重仍读 2 遍（BGRP=4、batch=8→blockIdx.y=2）；BGRP=8 会溢出，需改结构而非调参 |
| `gemv_int8_rkv_stage1_batch` | ~29% | 同上（BGRP=2） |
| `ffn_value_sparse_add_batch` | ~13% | dispatch 把 batch 放 `blockIdx.z`（每槽独立 block）；但各槽稀疏模式不同，权重复用的并集收益≈0，收益有限 |
| `gemv_lowrank_chain4_batch` | ~8% | |
| `rwkv_sample_batch` | ~6% | 单 block 112 线程扫 65536 词表（~2 ms/步）；改多 block 需跨块归约 |

墙钟结构（8 槽一批）：**prefill 958 ms + decode 4007 ms**。prefill 现已占 19%
（修复前 10%），且**每批都从零全量重算**（无前缀缓存）——世界 prompt 高度重复，
前缀缓存是下一个高价值项。

再往上的量级提升需要换路线：当前 batch GEMV 是 CUDA-core half2 FMA 路径，
要拿到数量级收益须上张量核（小 M 的 int8/fp16 `mma` GEMM，M=16 恰好一 tile）。

## 8. 并发上限与「动态批宽」实测（2026-09-19 补）

### 8.1 更大并发（fixed prompt，132 tok/req，BATCH_SLOTS=8）

| 并发 | 聚合 tok/s | 单请求 p50 |
|---|---|---|
| 8 | 148.4 | 4.82 s |
| 16 | **183.5** | 9.67 s |
| 32 | 178.6 | 19.25 s |

饱和点约在并发 16（再往上只是排队）。

### 8.2 不同提示词（varied：4 居民 × 8 情境轮换，239 tok/req，BATCH_SLOTS=8）

| 并发 | 聚合 tok/s | 单请求 p50 |
|---|---|---|
| 8 | 155.7 | 4.91 s |
| 16 | **188.7** | 9.88 s |

与 fixed 同量级——prompt 内容/长度异构不影响批量收益（归批只按采样参数签名，
长度差异由 lens 机制吸收）。

### 8.3 BATCH_SLOTS 提高反而更差（不要调大）

`generate_batch` 会把 `prompts` 补齐到 `slots` 再 prefill，且解码也按 `slots` 宽跑，
所以槽数必须贴合**实际批宽**：

| BATCH_SLOTS | 并发 8 | 并发 16 | 并发 32 |
|---|---|---|---|
| 8（默认） | 148.4 | 183.5 | 178.6 |
| 16 | 81.6 | 148.5 | 174.2 |
| 32 | 87.8（随后崩溃） | — | — |

- slots=16 在并发 8 时腰斩：4~8 个真实请求白跑 16 槽。
- slots=32 更糟：`bt = 32 × 512 = 16384` → `m_pad = 16384` → SeqBuffers 单缓冲
  168 MB、合计约 5 GB → prefill 从 958 ms 涨到 3413 ms，最终 **access violation
  （0xC0000005）**。
- **结论：BATCH_SLOTS 保持 8**（`DEFAULT_BATCH_SLOTS`），可用环境变量覆盖，
  但调大只会亏。

### 8.4 「按实际批宽动态解码」：可行但未落地（已回退，勿直接重试）

思路：状态按 slots 分配一次，解码只跑 `n` 行（`submit_sample_selfloop_batch` 放开为
`batch ≤ state.batch()`），prefill 仍按固定槽宽 pad（保持 `bt` 恒定）。

实测收益（slots=8）：

| 并发 | 补齐到 8 槽 | 动态宽 |
|---|---|---|
| 2 | 58.7 | **77.0** |
| 4 | 69.8 | **92.4** |
| 8 | 148.4 | 141.7（噪声内） |

低并发 +31~32%，但**并发 16 + 长 prompt 下触发 access violation（0xC0000005）**，
未定位到具体越界点，已回退为 `state.batch() == batch` 严格相等。

要真正落地动态批宽，需先审计以下全部索引假设（`batch < 分配宽` 时的行步长/边界）：
`WorkBuffers` 各缓冲行步长、pinned sampler 行宽（`store_sampler_async_batch` 的
`row_bytes = batch * PINNED_ROW_BYTES` 与 sampler 张量 `10*batch` 的容量关系）、
`State` 各行步长、`sample_into_host_seeded_batch` 的 `hist_stride`。
另一条更省事的路：**状态按实际批宽创建**（`generate_batch` 每批本就
`reset_state_of`，跨批不携带信息），批宽变化时重建 state——代价是 prefill 的
`bt` 随之变化，会触发 `take_seq_bufs` 的 `clear_cache()` + NVRTC 重编译
（每次宽度切换约 0.2~0.5 s），仅在批宽频繁抖动时才亏。

### 8.5 mytown/model-server 崩溃修复（本轮）

- **`jsonfixer` 0.1.0 摘除**：该依赖在模型退化输出上有两种致命行为——① 多字节
  字符上按字节索引切片 panic（`start byte index N is not a char boundary`），
  panic 冒泡到 axum handler 掐断连接（客户端 `RemoteDisconnected`）；② 修复循环
  不推进下标、向 String 无限追加，实测触发
  `memory allocation of 68719476736 bytes failed`（64 GiB）→ **整个进程 abort**。
  它是第 3 层兜底，前两层（精确配平 + `complete_truncated_json`）已覆盖实际观测到的
  全部形态，无测试依赖它。
- **`complete_truncated_json` 补上文档承诺的行为**：原实现缺「字符串外游离 `"`
  剔除」——游离引号被误当字符串起点，把紧随的 `}` 吞成字符串内容导致整体失配
  （真实形态 `..."reaction":"想去看看看收成"}"}`）。补后该形态由第 2 层直接修好。
- 回归测试 `extract_does_not_panic_on_multibyte_garbage` 收录 3 条真实退化样本。
- 另修存量 clippy 告警 6 条（`clone_on_copy` / `manual_strip` /
  `items_after_test_module` / 未读字段），`presence_penalty` 接入采样参数，
  `EngineConfig.chunk` 用于单流分块 prefill。
