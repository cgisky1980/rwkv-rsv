# 2026-10-11 Vulkan `gemm_imma` 取数结构优化（A 片段寄存器复用 + 槽组分 warp）

任务：#29（S8）。目标：把 Vulkan 的 W8A8 张量核 GEMM 从「共享内存取数受限」拉到接近算力受限，
缩小与 CUDA 的比值。分支：`rwkv-rsv` 主工作树；一次只做取数结构这一件事。

## 一、问题定位：瓶颈不是带宽，是 smem 取数指令

先建了可信的隔离计量（`examples/kernel_bench.rs` 加 `imma_*` 四个算子 + TOPS 列），
口径与引擎一致：`quant_x_i8` → `gemm_imma`，容量参数用引擎真值 `cap_rows = 8 * max(fh, c)`
（否则 `imma_ksplit` 会选到与引擎不同的分块数，测的就不是同一条路径）。

实测（C=2560 / FH=10240 / vocab=65536，300 iter × 5 轮取最小）：

| 算子 | 形状 (m,k) | 语义 |
|---|---|---|
| `imma_key` | ffn.key 10240×2560 | OP=0（relu²） |
| `imma_out` | att.output 2560×2560 | OP=1 + 门控量化 |
| `imma_value` | ffn.value 2560×10240 | OP=1 |
| `imma_head` | head 65536×2560 | OP=2 |

改动前的量级判断（TOPS 14~22 档、四条形状同 band）来自本轮的 kernel_bench 初跑；
**改动后的权威 kernel 表在下面的 §三.2**（同构建、同协议重跑一遍，含 TOPS 列）。
两臂的 ms/call 差异只作为**方向性**参考，A/B 的主证据是端到端三臂对照（§三.1），
因为那一份是同一会话里按 base / #29 / #29+#30 顺序构建、每臂 2 轮、单实例跑出来的。

结论性的量级判断：**TOPS 只有 14–22**，而这张卡（RTX 2080 Ti，Turing，68 SM）int8 张量峰
值约 107 TOPS。若是带宽受限，`head`（读权重最多）应该最差、`out`（读得少）应该最好；
实际四条算子的 TOPS 落在同一量级 ⇒ 限制在**每 warp 发出的 smem 载入指令数**上，不是 DRAM。

代码层面的原因（`assets/shaders/src/gemm_imma.comp`，改动前）：

```glsl
for (uint g = 0u; g < NST; g++) {           // 一个 warp 把 NST 组全跑完
    for (uint ks = 0u; ks < 4u; ks++) {
        coopMatLoad(cf, ws, (wid*WR)*WS + ks*32u, WS, RowMajor);   // ← A 片段每组重载
        coopMatLoad(xf, xs, (g*BN)*WS + ks*32u, WS, ColumnMajor);
        ci = coopMatMulAdd(cf, xf, ci);
    }
}
```

一份 A 片段（m16k32 int8）= 16 B/lane ≈ 4 条 LDS。A 片段只跟**行块**有关，与槽组无关，
却在槽组循环里被重发 NST 次 ⇒ 每个 k-tile 每 warp 有 `4×NST` 条 A 载入 + `4×NST` 条 B 载入
对 `4×NST` 条 mma —— **取数指令比 mma 还多**（2:1）。

## 二、两处改动

### ① A 片段提到组循环外，一次性载进 4 份寄存器

`a0..a3` 对应 k-tile 内 4 段 k=32。组循环里只留 B 载入 + mma。取数 : mma 从 2:1 变成 1:1，
且每组少 4 条 LDS。**逐位等价**（同样的操作数、同样的 mma 顺序、同样的累加顺序）。

### ② 槽组分给第二批 warp（`SW`），每 warp 只跑 `RPG = NST/SW` 组

```glsl
const uint RW   = BM / WR;                              // 行 warp 数
const uint SW   = (BM == 64u) ? (NST < 2u ? NST : 2u) : 1u;
const uint RPG  = NST / SW;
const uint BLOCK_SIZE = RW * SW * 32u;
```

- 累加器从 `acc[NST][4]` 缩到 `acc[RPG][4]`（NST=8 时 32 → 16 个寄存器），
  A 片段不再需要每个 warp 各留一份完整副本；
- warp 数翻倍 ⇒ 延迟掩盖翻倍；
- `BM=128` 档已经有 8 个行 warp（`tile[][]` 的第一维就是 8，GLSL 里 warp 数上限），
  所以那一档 `SW=1`，只有改动 ① 生效。
- 写成三元而不是 `min()`：`BLOCK_SIZE` 要进 `layout(local_size_x=…)`，必须是常量表达式。

配套的行号基址：`wid` 现在是「行维 × 槽组维」的二维编号，
`row_warp = wid % RW`、`slot_warp = wid / RW`；凡是用到旧 `wid * WR` 作行基址的地方
（flush 取 `szs`、epilogue 写回行号、OP=9/10 诊断）一律换成 `row_warp * WR`。
**这里漏一处就是静默的错误结果**（不是崩溃）——历史上同一处漏写过，症状是
「8 个 warp 互相覆盖同一批行 + 两跑指纹不同」。

## 四、遗留 / 下一步

- **`tile` 第一维**已由字面量 `8` 改成 `RW*SW`（由构造绑定 warp 数上限；`BM=64` 是 4×2、
  `BM=128` 是 8×1，都等于 8，所以这次改动是纯防未来越界，不改代码）。
- **#30（v 臂 split-K）质量门已过并默认开启**（第 7 条）：本地 commit 见下，`#30` 完结。
- **#31 改成「加块实验」，而不是跨 tile 流水**（本条订正了 §三.2 末尾那句推断）。
  我在 CUDA 侧找到了**同一张卡上的反例**：`backend_cuda.rs:1857-1876` —— `IMMA_PIPE`（k-tile 软流水）
  实测 **−36 %**、`IM_NBUF=2`（smem 双缓冲）实测**完全无效**（B=16/32/64/256 全在噪声内、token 逐位一致），
  注释的结论是「**该内核在小 batch 也不是载入延迟受限**，真正剩下的是每个块摊到的 k 太长（20 个 k-tile
  串行），只有**增加块数**（split-K / 合并链）能解」。这与 `runtime.rs:1664` 记的实测同源
  （head 1024 块 = 77 % 峰值带宽、ffn.key 160 块 = 37 % ⇒ **块数才是瓶颈**）。
  ⇒ 所以 §三.2 那句「两头都没贴满 ⇒ 限制在串行化上」是**我的推断，不是证据**；先做便宜的开关实验：
  K=2560 的三链（r/k/v/out，m=2560、bm=64）现在 40×ks=5 = 200 块，而 `ktiles=20` 允许 `ks ∈ {10,20}`，
  `VK_IMMA_KSPLIT_MAX=16 VK_IMMA_KSPLIT_TARGET=800` ⇒ `ks=10` ⇒ 400 块（部分和容量核算通过：
  `10·batch·2560 ≤ 8·10240·batch`）。脚本 `/c/tmp/ks-arms.sh`（kernel_bench 四形状 × B=8/32/128/256，
  固定 `VK_IMMA_V_KSPLIT=1` 把 #30 那一维钉住）。**若加块有效 ⇒ 限制在块数，#31 的流水方向作废；
  若无效 ⇒ 才轮到流水/取数结构继续。**

  **实验结果：负。** 原始读数 `/c/tmp/ks-arms.txt`（单实例、一次会话四臂连跑）。`ks` 由
  `target/blocks` 反推：`TARGET=800` 与 `1600` 两臂在 `K=2560` 档都收敛到同一个 `ks=10`
  （`ktiles=20`、`max=16` 不整除 ⇒ 收到 10），所以**那两臂是同一条代码路径**，它们之间 0~3 % 的
  差就是本轮的环境噪声地板；而 auto（`ks=5`）与之的差才是信号：

  | 算子 | B | auto ks=5（两次） | target 800 ks=10 | target 1600 ks=10 | Δ |
  |---|---:|---|---|---|---:|
  | `imma_out` 2560×2560 | 128 | 0.0994 / 0.1057 | **0.1279** | 0.1264 | **+23~29 %** |
  | `imma_out` | 256 | 0.1853 / 0.1942 | **0.2348** | 0.2404 | +21~27 % |
  | `imma_key` 10240×2560 | 128 | 0.2998 / 0.3010 | **0.3427** | 0.3393 | +13~14 % |
  | `imma_key` | 256 | 0.5725 / 0.5875 | 0.6704 | 0.6779 | +14~17 % |
  | `imma_value` 2560×10240 | 128 | 0.3163 / 0.3237 | 0.3444 | 0.3483 | +6~10 % |
  | `imma_head` 65536×2560 | 128 | 1.6603 / 1.6846 | 1.6627 | 1.6788 | ≈0（本来就有 1024 块） |

  B=8/32 基本持平（差值落在噪声地板内）⇒ 伤害集中在「块数已经够多、部分和流量占优」的大批档。
  **机制解释**：split-K 不增加权重流量，但**部分和缓冲的写+读 ∝ `ks·batch·M`**（`[KS][batch][M]` f32），
  `ks` 从 5 翻到 10 就在 `out`/`key`/`value` 上凭空多插一轮 128·2560·4 B·10 ≈ 13 MiB 的写与读；
  而 Vulkan 侧的块驻留数本来就够（`head` 1024 块那档纹丝不动，正是「不缺块」的对照）。
  ⇒ **`#31` 的「加块」分支作废**。加上 CUDA 侧 `IMMA_PIPE`/`IM_NBUF` 两条反例（本文开头引的
  `backend_cuda.rs:1857-1876`）⇒ **CUDA 的「加块能解」不能移植到 Vulkan**：那一边缺块是「每次 launch
  只 40 块 < 68 SM」的 launch 形状问题，这一边同一个形状已经能靠 `SW`/`NST` 摊开，缺的不是并发块数。
  下一手因此落在**指令混合**（每 warp 发出的 smem 载入/存回条数）与**结构性大头**（#25/#26）上。
- `imma_nst` 上限 8 ⇒ `SLOT=64`，`batch>64` 时权重按 `ceil(batch/64)` 重读；但 §三.2 的 kernel 表显示
  B=128→256 每槽成本近乎持平（key 0.2898→0.5766 ms，正好 2 倍）⇒ 重读不是当前限制因素，先不做 NST=16。
- #24（合并 rkv 三链 dispatch）的理由仍被 #30 削弱：Vulkan 的 r/k/v 现在都到 200~400 块，
  合并只省 dispatch 开销（§6.3 量到 1.3~1.8 µs/次，一步 ~3 %）。降级。

### 5.1 去量化辅助算术探针 ⇒ 负（`correction-GEMM` 重构作废）

设想：把「尺度还原 + 零点修正」从 k-tile 循环里挪走（改成 int32 一路累加、末尾用一次
额外的 GEMM/reduce 做修正）。这个重构要吃好几轮，所以先花一轮量它想省的那部分到底多贵。

探针只删算术、不删结构（`C:\tmp\gi_probe.comp`，`-DPROBE=1` 编出
`gemm_imma_bm64_nst8.spv`，md5 `2f79191d`；出厂 base `a490b19e`）：

```glsl
#if PROBE == 1
        acc[gg][i] += float(S);              // 数值故意错，只为分箱计时
#else
        const vec2 szv = unpackFloat2x16(szs[row_warp * WR + r]);
        const vec4 au = xas[g * BN + fcol];
        acc[gg][i] += szv.x * (au.x * float(S) + au.y) + szv.y * au.z;
#endif
```

同会话反序热插 A/B（`C:\tmp\giab.sh`，只读 `gemm_imma_bm64_nst8` 的 per-avg）：

| 轮 | 绑定 spv | per-avg ms | 内核总和 ms |
|---|---|---|---|
| 1 | base `a490b19e` | 0.1120 | 73.126 |
| 2 | probe `2f79191d` | 0.1159 | 74.390 |
| 3 | probe `2f79191d` | 0.1155 | 74.582 |
| 4 | base `a490b19e` | 0.1152 | 74.800 |

base 均值 0.1136、probe 均值 0.1157 ⇒ **+1.8 %（更慢）**，而 base 自己两轮的差就有
2.9 % ⇒ 落在噪声线上，**算术不是瓶颈**。⇒ 「挪走修正」这条路**作废**（省 0 的东西不值得重构）。

⚠️ 结论的边界要说清：探针**保留了** `coopMatStore` + `tile` 的标量 LDS + 两次
`subgroupBarrier`，所以它只证伪了 flush 的**算术**成本，没有证伪 flush 的**结构**成本。
不过结构那半边也不能靠「挪走修正」来解——`BK = 128` 正好一个量化组，组尺度在变，
int32 累加跨组在语义上不成立，除非牺牲量化精度。

### 5.3 口径订正：小批量档是 **DRAM 受限**，不是「槽道浪费」

Vulkan 侧同进程、`KB_REPEATS=5` 取最小、抖动列随行（`C:\tmp\kb-xbackend.log`）：

| 算子 | batch | ms/call | 有效 GB/s | 占 616 GB/s 峰值 | TOPS |
|---|---:|---:|---:|---:|---:|
| `imma_head` 65536×2560 | 1 | 0.4295 | 402.8 | 65 % | 0.8 |
| `imma_key` 10240×2560 | 1 | 0.0739 | 365.9 | 59 % | 0.7 |
| `imma_value` 2560×10240 | 1 | 0.0731 | 369.9 | 60 % | 0.7 |
| `imma_out` 2560×2560 | 1 | 0.0236 | 286.6 | 47 % | 0.6 |
| `imma_head` | 8 | 0.4449 | 388.9 | 63 % | 6.0 |
| `imma_head` | 128 | 1.2129 | 142.6（×2 遍 = 实际 285） | — | 35.4 |

B=1 时四个形状每 token 的权重字节 = 27.03 + 6.76 + 27.03 + 173.02 = **233.8 MB**
⇒ DRAM 地板 `233.8 MB / 616 GB/s = 0.38 ms`，实测 0.60 ms ⇒ **达成率 63 %**。

这直接改写 §9 里那条关于小批量的归因：「BN=8 在 batch=1 只用 1/8 的槽道」讲的是**张量核**
利用率，而这一档张量核本来就闲（0.6–0.8 TOPS，峰值 107 的 0.7 %）⇒ 槽道浪费**不是**小批量
慢的原因。限制因素是 achieved bandwidth。⇒ 小批量档的全部杠杆量级 = 把 63 % 推到纯读的
实测上界（状态核记录 §4.2 量到 80–85 %）≈ 每 token 省 0.13 ms，而不是「×8」。

顺带一条对照：`head` 的 402.8 GB/s 是四臂里最高的，它的块数也最多（1024 块 ≥ 68 SM×3）
⇒ 与 §三.1 大 batch 侧的结论（「缺的不是并发块数」）不冲突：小 batch 的块数由 `M/BM` 决定，
`out`（m=2560 ⇒ 40 块 × ks5 = 200）才是最少的，也正是达成率最低的那一臂。
⇒ 下一手 = 在 B=1/8 扫 `VK_IMMA_KSPLIT` / `VK_IMMA_BM` / `VK_IMMA_NST`（纯 env，无需重编），
看「加块提达成率」在小批量档是否成立（大 batch 档 §三.1 已证伪，两者不互相外推）。
扫描日志 `C:\tmp\kbsmall.log`（六臂 × 同序两轮，`KB_REPEATS=3`、B=1/8）。

2. 唯一可复现的正向是 **`BM=128` 帮 `head`**（−1.9 % / −2.8 %，机制与 §6.8 大 batch 侧

3. `NST=2` 在小批量档稳定劣化（+4 %）⇒ §9 里「小批量要一个专用 tile 变体」这句话
   的**旋钮部分已经见底**：`IM_BM`/`IM_NST`/`VK_IMMA_KSPLIT*` 四个开关在 B=1/8 扫完了，
   没有免费的 12 %。剩下的可能性只在 kernel 内部（staging 形态），见 §5.5。

### 5.5 B=1 的账：imma 占 token 墙钟的 53 %，而它只跑到峰值带宽的一半

`PROF_GPU` 稳态窗口（`/c/tmp/p1vk.log`，2048 条内核；以每层一次的核 `count=85` 反推窗口

### 5.6 分箱探针：staging-only（跳过全部片段载入与 mma）

为把「访存形态」与「片段/mma」分开，做了第二个编译期探针（`C:\tmp\gi_probe2.comp`，

`acc[0][0] += …; barrier(); continue;` ⇒ 后续 A/X 的 `coopMatLoad`、4×`coopMatMulAdd`、
`coopMatStore`、flush 全部成为不可达代码被删掉，保留的正是「全局载入 → 寄存器 → STS →

结果：（`C:\tmp\gi1ab.log`，ABBA + 反序，8 次独立进程，`head` 的抖动 ≤0.5 %。
下表每格两个值 = 该臂**四次**读数的最小/最大，A/B 各四读）

| 臂 | 绑定 md5 | head B=1 | head B=8 | key B=1 | key B=8 |

| base（出厂，含全部 mma） | `4298aab4` | 0.4292 / 0.4293 | 0.4444 / 0.4452 | 0.0710 / 0.0716 | 0.0760 / 0.0771 |

## 六、仪器修好之后：真正的瓶颈是**连续段长度**，而宽窗口这条路的代价是占用

### 6.1 仪器：`VK_SPV_DIR`（这就是 §五 开头那块作废横幅的原因）

`.spv` 在 release 构建里被 rust-embed 编进可执行文件（`src/vulkan/asset.rs`：
`#[folder="assets"] #[include="shaders/spv/*.spv"]`），所以「编译一份探针 spv 覆盖到
`assets/shaders/spv/` 再跑」**从未换掉运行时用的字节**——§5.1/§5.6/§5.7 的 A/B 全是
同一个臂跑两次。修法（`src/vulkan/asset.rs::shader_bytes` + `runtime.rs::load_shader`）：

```rust
if let Some(dir) = spv_dir() {            // VK_SPV_DIR = 平铺目录，按 basename 取
    return std::fs::read(&path).map(Cow::Owned)
        .map_err(|e| format!("VK_SPV_DIR shader not found: {} ({})", …));  // ★ 硬错，不静默回落
}
```

三条纪律（都是这两轮踩出来的）：
1. **设了 `VK_SPV_DIR` 而文件不存在必须报错**，不能回落到嵌入版——否则又是假 A/B。
2. **每臂打印所绑定 spv 的 md5**（脚本里 `md5sum` 进表头）。
3. **绑定判据要与 base 比，不能两臂互比**：两个结构不同的臂可能读出**同一个** `sum(y)`
   （它们读到同一批字节时就是这样，p9/p10 都报 `3276975636480.0000`），这时
   「标记相同」根本不能证明着色器被换过。
4. 顺带：`float(sink + 7u)` 这种「把被删的载入接出去」的写法会被 fp32 精度吞掉；
   删除类探针必须另带一个**与性能无关**的数值出口。

编译口径能**逐字节复现出厂 spv**（这是所有窄臂对照的前提）：
`glslangValidator --target-env spirv1.3 -DIM_BM=64 -DIM_NST=1 -V assets/shaders/src/gemm_imma.comp`
→ md5 `4298aab471`、17904 B ✓。

### 6.2 分箱重测（同会话，B=1，`imma_head`）：计算确实免费，LDG 流就是全部

| 臂 | 删掉了什么 | ms | 相对 base |
|---|---|---|---|
| base（出厂全量） | — | 0.4466–0.4496 | 1.000 |
| p2 | `barrier(1)` 后 `continue`：全部片段载入 + mma + `coopMatStore` + flush | ≈0.452 | **1.006** |
| p3 | 只删权重/激活的 STS（载入留作 `sink`） | ≈base | 免费 |
| p4 | 只删权重的**全局载入**（STS 写常量） | **0.0496** | **0.11** |
| p5 | 只留权重全局载入流（原地址顺序）+ `sink` | 0.4182–0.4241 | 0.93 |
| p6 | p5 + 两次块级 barrier | ≈p5（差 0.006 ms） | 免费 |

⇒ **STS 免费、barrier 免费、整个计算半边免费；时间 ≈100 % 在权重的全局载入流上**
（p4 把它删掉就只剩 11 %）。§5.6 的定性结论在有效仪器下成立，数字换成上表。

### 6.3 曲线：**同样的字节、同样的 grid，只改地址时序**

p5/p9/p10/p11 读的是**完全相同**的一批权重字节（同一 block 同一 k 窗口），唯一区别是
每 warp 连续 4 条载入落在哪里 ⇒ 段长度不同：

| 连续段 | 臂 | ms（head B=1） | 有效带宽 |
|---|---|---|---|
| 128 B（= 真实 kernel 的走位） | p5 | 0.4182–0.4241 | **408–415 GB/s** |
| 256 B | p11 | — | head 557–562，但 **key/value 只 ~458** |
| 512 B | p10 | 0.3064–0.3100 | **558–566 GB/s** |
| 2560 B（整行） | p9 | 0.3050–0.3113 | 556–567 |
| — SIMT 平坦核对照 `plain` | — | 0.3101 | **557.9 GB/s** |
| — SIMT 平坦核对照 `f16` | — | — | 563.1 GB/s |

⇒ 本机实用上限 ≈ **560 GB/s**（616 的 91 %），`gemm_imma` 小批量档只有 **408**，

### 6.4 实施：`BM=16` 宽窗口档（`BKW=512`，沿 k 分组 staging）

- `gemm_imma.comp`：`IM_WIDE = (IM_BM == 16)`、`BKW = 512`（其余档 `= BK`）、`NGW = BKW/BK`；
  staging 拆成 **chunk**：`for (cg…; cg += CH)` 外层**不** unroll、内层 `CH=16` 条先全部
  取进寄存器再统一落 smem，走位 `i = index + (c/NGW)*BLOCK_SIZE`、`s = c % NGW`
  ⇒ 同一行连续读 4 组 = 512 B；`xs`/`szs`/`xas` 与计算/flush 一起套进 `for (s < NGW)`，
  组序升序 ⇒ 逐位等价。窄档（`BM=64/128`）用 `#else` **保持原文**。
- host：`imma_bm(m, k)` 认 `VK_IMMA_BM=16`（要求 `m%16==0` 且 `K` 按窗口对齐）；
  `imma_ngw(bm)` 进 `imma_ksplit` ⇒ 段必须按**窗口**对齐（`ktiles % (ks·NGW) == 0`）；
  `build.rs` 产 `gemm_imma_bm16_nst{1,2,4}.spv`。
- ⚠️ 已知副作用：`BM=64/128` 的字节**不再与出厂相同**（`s` 循环 glslang 不折叠，多 31 行
  SPIR-V）。同会话实测窄臂 N vs 出厂 A 四形状差 ≤0.5 %、`sum(y)` 逐位相同 ⇒ 接受。

2. **B≥16 崩掉**是结构问题：`BM=16` 时 `SW=1` ⇒ 一个 warp 串行跑 `RPG=NST` 个槽组，

3. 量级：head 只在 B=1 赢，`−0.051 ms` 占 12.44 ms/token 的 **0.4 %** ⇒ 不值得为它加一条

4. 数值契约：head 两臂 `ks` 都是 1 ⇒ `sum(y)=20024912.0000` **逐位相同**，证明宽窗口重排

   属于既有的「结合顺序」契约。

### 6.6 下一根杠杆（本轮未做，按证据排第一）：权重 **k-分块布局**

段长问题真正的解法不是「把窗口摊宽」（smem 会吃掉占用），而是**改内存布局**：
把 int8 权重索引缓冲从 `[M, K/4]` 存成 `[K/128][M][32]`（组内行连续）。这样一次 staging
读的是 `BM × BK` = **连续 8 KB**，段长与整行等价（≈560 GB/s），而 smem、瓦片、warp 数、
mma 全部不动 ⇒ 408→560 的收益可以在**所有形状**上拿到（head −32 %、key/value −31…35 %）。
代价（也是本轮没做它的原因）：权重上传时做一次置换，且**所有**读 `in_idx` 的消费者
（`gemm_imma`、SIMT `gemv_int8` 家族、CUDA 侧的 IMMA 准备）必须同轮改；显存不变
（是换布局不是加副本）。这是 §6.1 那条「B=1 比值 0.88」的正解，量级 ≈ 墙钟 −11…13 %。

### 6.9 实施：布局迁移（全消费者同轮改）+ 复测

机制见 §6.8。落地口径：

- **布局**：int8 权重索引缓冲的设备形态 = `[K/128][M][32 uint]`（组主序）。模型文件**不变**
