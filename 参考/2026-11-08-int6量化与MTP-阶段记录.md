## 1. 已完成（P1 + P2 后端抽象/CUDA 内核）

### P1 int6 离线量化 ✅

`tools/quantize_any4.py --bits 6`（choices 由 `[4,8]` 扩为 `[4,6,8]`）。

**文件格式**（W[M, K] 行主序，K = 收缩维，均以 group=128 切分）：

| 键 | dtype | 形状 | 含义 |
|---|---|---|---|
| `{key}.int6_lo` | U8 | [M, K/2] | 低 4 位平面。字节 j 的低 nibble = e[k=c·64+j]，高 nibble = e[k=c·64+j+32] |
| `{key}.int6_hi` | U8 | [M, K/4] | 高 2 位平面。字节 j 的 4 个 2-bit 域 = e[j]、e[j+16]、e[j+32]、e[j+48] |
| `{key}.int6_sz` | U32 | [M, K/128] | 与 int8 同编码：低 16 位 = scale(fp16)，高 16 位 = zero（int6 恒 0） |

其中 `e = q + 32 ∈ [0,63]`，`w = scale · (e − 32)`（对称量化）。
scale = `amax·r/31.5`（fp16 存储），r 从 `{1.0, .97, .94, .91, .88, .85}` 里取组内 MSE 最小者。

**产出**（`g1l-2.9B-20261031`）：

| 项 | 值 |
|---|---|
| 量化矩阵数 | 192（32 层 × 6 类大投影；head 保持 int8） |
| 平均 cos / rel | **0.999536 / 2.7341 %** |
| 每权重字节 | **0.781 B**（6 bit + 每 128 权重一个 fp16 scale） |
| 文件体积 | 5.49 GB(fp16) → **3.07 GB(int8) → 2.48 GB(int6)**（−19.2 % vs int8） |
| 耗时 | 约 9 分钟（numpy，单进程；CUDA 可用时仅用于 torch 探测） |
| 权重级验收 | PASS（`cos ≥ 0.9994 且 rel ≤ 3.3 %`） |

⚠️ **一个必须记住的量化常识**：int6 是 64 级，比 int8 的 256 级粗 4 倍，per-group(128) 的
amax ≈ 2.9σ ⇒ 理论 rms 误差 = (amax/31.5)/√12 ≈ **2.7 %**。所以 int6 的权重 rel **不可能**是
int8 那个 0.35 %；把「rel ≤ 1.2 %」当验收线是算错了（本记录第一版就是这么错的）。真正的验收
在端到端（ΔCE / teacher-forced Top-1），上游实测 int6 ΔCE +0.008、top-1 94.6 %。

报告：[int6量化报告-g1l-2.9b-20261108.md](int6量化报告-g1l-2.9b-20261108.md)

**实测（CUDA，g1l-2.9B，单流 decode，`examples/benchmark`）**：

| 版本 | infer_tokens | 说明 |
|---|---:|---|
| int8（对照） | **67.8 tok/s** | 3.07 GB 权重 |
| int6 初版（一线程整块） | 37.7 tok/s（0.56×） | 见下方坑 ① |
| + half 域反量化 + 树形归约 | 34.6～36.7（无改善） | 说明不是 ALU 也不是归约 |
| + 一线程一个 16 行子块 | 59.1（0.87×） | 见下方坑 ② |
| + 一线程半块（当前） | **60.6（0.89×）** | lo 无重复读、hi 只 2 线程读 |

prefill：int8 828 tok/s vs int6 635 tok/s（0.77×，走 dequant→fp16 GEMM，`dequant_int6` 自身占 prefill 的 49 %）。

**结论：int6 的功能链路已全部打通并验证正确（生成语义连贯），但单流性能只有 int8 的 0.89×，
未达计划里「≥1.15×」的发货门限。** 折算成**有效带宽**：int6 2.48 GB / 16.5 ms ≈ **150 GB/s**，
int8 3.07 GB / 14.75 ms ≈ **208 GB/s**（每字节效率 0.72×）；而同样的 int8 `rkv` 单核
实测 358 GB/s。也就是说 int6 省下的 25 % 字节被「读不快」吃掉了还有余。

真要吃到 6 bit 的 25 % 字节红利，必须换**布局**，不是继续调内层循环：

> 上游 `int6_gemm.py` 的权重布局是 **(K, N)、N 最内**，于是「一个线程负责若干输出列」时
> 相邻线程读相邻 N ⇒ lo/hi 两平面的载入天然合并。我们的文件是 **[M, K]、K 最内**
> （与 int8 一致），一个线程负责若干输出行时只能读到 K 方向的长条 ⇒ 6-bit 双平面的
> 16 B/32 B 步长必然浪费 sector。**下一步应该做的是 int6 专用的 N-major（转置）权重布局
> + 对应的 dot 形式内核**，而不是在 M-major 布局上继续压指令数。

### 性能优化过程里踩到的坑（按发现顺序）

1. **`alut` 形参类型是 `const __half*`**：把 hi 平面按 u32 传进去后直接 `alut + row*hi_w`
   会按 2 字节步进 ⇒ `cuLaunchKernel failed: 716 misaligned address`。必须先
   `reinterpret_cast<const unsigned int*>(alut)`。
2. **sector 利用率**（最大的一笔，0.56× → 0.87×）：一线程吃整块 64-k 时相邻线程的 lo 起点
   相差 32 B，每次 `uint4` 只用掉 32 B sector 的一半 ⇒ 事务数翻倍。改成子块级映射后拉满。
3. **归约不要用「少数线程串行累加 128 项」**：那是依赖链；改确定性二叉树（7 步、每步全线程）。
   同时**不能用 `atomicAdd`**——浮点 atomic 求和顺序不确定，会破坏「贪心 token 流逐位稳定」。
4. **并行度不能只按 K 展开**：int6 的 K 单元数是 C/64（C=2560 → 40），喂不满 128 线程；
   必须把 row 也摊给线程（或子块）。

## 1b. P2 收尾：int6 换 **N-major 布局** ✅（门限达成 1.23×）

M-major 的天花板是布局本身（见上），所以按结论做第二份权重布局 + 专用 dot 内核。

### 格式（`--int6-layout n`）

三个平面整体转置，**字节语义完全不变**，只是把「输出列 M」放到最内层：

| 平面 | M-major（默认） | N-major（`--int6-layout n`） |
|---|---|---|
| lo | U8 `[M, K/2]` | U8 `[K/2, M]` |
| hi | U8 `[M, K/4]` | U8 `[K/4, M]` |
| sz | U32 `[M, K/128]` | U32 `[K/128, M]` |
| 标记 | — | 标量张量 `int6_nmajor` = u8[1]（加载端据此选内核） |

量化值本身与 M-major**逐位相同**（量化器里只是 `.T` 后再 `ascontiguousarray`），
所以两份文件的 cos/rel 报告一致（avg_cos 0.999536 / avg_rel 2.7341 %）。
产物：`rwkv7-g1l-2.9b-int6n.st`（2.48 GB，文件名后缀 `.int6n`，不覆盖旧文件）。

### 加载与路由

- `model::int6_nmajor(&st)` 读标记张量；`Int6Handle` 新增 `nmajor: bool`，**一个开关同时**
  决定四支内核（dequant / plain / relu2 / mul_add / add / rkv）与 CPU 反量化的寻址方式。
- `model::dequant_int6(.., nmajor)` 与 `gpu_model` 的两处形状推导都按布局取
  （N-major 下 `lo` 是 `[K/2, M]`，`ffn_hidden` 必须读 `shape[1]` 而不是 `shape[0]`）。
- 文件布局 = 显存布局（不做上传期重排），这一点与 int8 的 `group-major` 不同，取舍见
  "为什么不在加载期转置"：2.48 GB 字节级转置单线程要 ~2 s/模型，且会让「文件格式」与
  「显存格式」出现隐式分叉；量化器多一次 `.T` 是零成本。

### 内核（`src/backend_cuda.rs`）

`I6NM_COMMON_SRC`（`i6nm_dot<GATED>`）+ 两个 kernel：

- `gemv_int6nm`：单矩阵通用 GEMV（op 0=relu²、1=mul_add、2=add、3=覆盖写，batch 走 `grid.y`）。
- `gemv_int6nm_rkv`：r/k/v 三路 + 4 条 mid 低秩投影（mid 段仍是 fp32 warp-per-row）。
- `rwkv_dequant_int6_nm`：32×32 tile + smem 转置的反量化（prefill / 批量走 dequant→fp16 GEMM）。

**几何**：block = `I6NM_WARPS`×32 线程，**一个 lane 一个输出列**、warp 覆盖 32 个连续列
⇒ 每条载入指令正好 32 B = 1 个满 sector；块内 `I6NM_WARPS` 个 warp 按
`c = w, w+W, w+2W, …` **轮转**切分 k-chunk（连续切分在 W 不整除 chunk 数时失衡），
块内 smem 固定升序归约（不用 atomicAdd ⇒ 贪心 token 流仍逐位可复现）。

### 实测（CUDA，g1l-2.9B，`examples/benchmark`，**同一时段同机 A/B**）

| 路径 | int8 | int6 M-major | **int6 N-major** | N/int8 |
|---|---:|---:|---:|---:|
| infer_tokens（decode） | 68.1 | 60.6 | **83.8** | **1.23×** |
| argmax_selfloop | 69.9 | — | **84.6** | **1.21×** |
| sample_selfloop | 60.8 | — | **69.0** | 1.14× |
| infer_seq（prefill 128） | 691.2 | 635 | **694.1** | 1.00× |

有效带宽：int6 2.48 GB / 11.9 ms ≈ **208 GB/s**（int8 3.07 GB / 14.7 ms ≈ 208 GB/s）
—— 也就是说 int6 现在**和 int8 打平了每字节效率**，0.75 B/权重 的字节红利第一次真正吃到。
（注：int8 prefill 今天在同机实测 691，早前记录过 828；跨时段不可比，表内一律同段对照。）

`I6NM_WARPS` 档位 A/B（decode tok/s）：8→80.1、**16→84.5**、20→79.9、32→78.6，
故默认 16（512 线程块）。环境变量仍可覆盖，仅用于现场 A/B。

### 这一步踩到的坑（都比"性能"更值钱）

1. **`hi` 平面的 2-bit 域必须按 `t` 移位**：dequant 首版写成 `hbv & 3`（漏了 `>> (t*2)`），
   结果只有 `k%64 ∈ [0,16)` 正确 ⇒ 权重高 2 位被读成 0、误差 ~4 %。
   **新增测试 `int6_nmajor_kernels_match_cpu`**（GPU 三件套：dequant / plain(batch=2,m=70) /
   mul_add 门控，全部对 CPU 参考）当场抓住。这类位运算写错的唯一表现是"输出变差但不崩"。
2. **fp16 累加会吃掉 int6 的精度**：先用 `__hfma2` 在 half 域累加，合成权重测试相对误差
   **3.6e-2**（32 个 fp16 加法的舍入）。改 fp32 四路独立累加器后误差回落到 2e-3 以内；
   更关键的是**端到端文本从"7 token 死循环"变回与 M-major 逐 token 相同的连贯英文**
   （同一 prompt、同 argmax）。本核受带宽约束，多出的 ALU 不进关键路径（84.5 vs 80.1 tok/s）。
3. **N-major 反量化不能再按 `[M,K]` 线性铺线程**：那样读平面是「步长 = m」的全散读，
   prefill 从 635 掉到 523。必须 32×32 tile + smem 转置（读合并 + 写合并），才回到 694。
4. **标记张量比"猜形状"可靠**：`[M,K/2]` 与 `[K/2,M]` 在部分形状下会撞车（如 M = K/2），
   不要靠 shape 反推布局。

| 端到端 | ✅ `generate`（argmax 64 tok）与 `benchmark` 全通，无 device lost |

**Vulkan 实测（g1l-2.9B int6n vs int8，同机同时段）**

| 路径 | int8 | int6 N-major |
|---|---:|---:|
| infer_seq（prefill 64） | 174.6 | **174.0** |
| infer_tokens（decode） | 47.1 | **14.8** |
| argmax_selfloop | 51.3 | **15.0** |
| sample_selfloop | 52.4 | **15.6** |

prefill 打平；**decode 慢 3.2×**，原因是并行度：N-major 的「一个 invocation 一个输出列」
让 rkv 只有 C/128 = 20 个 workgroup（int8 版是 invocation 沿 k 展开 + subgroup 归约，
workgroup 数 ×128）。补法是**块内 k 切分 + shared 归约**（CUDA 侧就是这么做的，4 路即可
让 workgroup 数 ×4），属性能项、不影响正确性。

### Vulkan 这次踩到的三条（都是"能跑但算错"型）

1. **`buffer_reference` 匿名类型声明必须带分号**（`layout(buffer_reference) buffer InLo { ... };`），
   漏了报的是下一行 `unexpected LAYOUT`，离真凶很远。
2. `unpackHalf2x16(...).x` 是 **float**，不能初始化 `const uint`（glslang 报
   "cannot convert from temp highp float"）。
3. **`a0[BGRP]` 这种「特化常量长度」的数组在 BGRP=1 时慢一倍**：驱动把它留在 Private 存储，
   每次累加都变成私有内存往返（实测 Vulkan decode 14.5 → 6.8 tok/s）。修法是单流/批量
   **分成两份代码**（用 uniform 分支 `if (BGRP == 1)`，驱动建管线时折叠），不能只靠
   `[[unroll]]` 指望编译器消掉数组。
   ★ 顺带验证了 BGRP 的收益：没有它时 sample_selfloop（batch≈8 的采样自循环）
   只有 2.1 tok/s，有权重摊薄后 15.6 tok/s（**7.5×**）。

## 3. 纪律记录（这次踩到的坑）

1. **rel 阈值不能拍脑袋**：见上文 2.7 % 的推导。int6 与 int8 差 4 倍是物理事实。
2. **全零 group 的 scale 会下溢**：`amax·r/31.5` 在 fp16 下可能变 0 ⇒ 除零 + NaN 编码。
   量化器已加死组保护（scale 置 0、除数置 1），这类组权重本来就是 0，输出恒 0。
3. **int6 的 `hi` 平面 4 个 2-bit 域按子块索引取**：`jj<16 → 域0`、`16..32 → 域1`、
   `32..48 → 域2`、`48..64 → 域3`，且 `lo` 在 `jj<32` 取低 nibble、`jj≥32` 取高 nibble。
   第一版把 `jj≥48` 也当成域2，被 `int6_plane_unpack_and_scale` 抓住 —— 这条测试值得永久保留。
4. **CUDA 的 `gemv_variant` 是 wtype 分派的单一出口**：加 int6 比新写内核省一个几何/归约模板，
   但必须同时检查「batch>1 会不会被 mb/mb16 分支截走」和「grid.y 是不是 batch」。
