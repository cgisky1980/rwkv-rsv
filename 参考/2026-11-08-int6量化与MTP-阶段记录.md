## 1. 已完成（P1 + P2 后端抽象/CUDA 内核）

### P1 int6 离线量化 ✅

`tools/quantize_any4.py --bits 6`（choices 由 `[4,8]` 扩为 `[4,6,8]`）。

**文件格式**（W[M, K] 行主序，K = 收缩维，均以 group=128 切分）：

| 键 | dtype | 形状 | 含义 |
|---|---|---|---|
| `{key}.int6_lo` | U8 | [M, K/2] | 低 4 位平面。字节 j 的低 nibble = e[k=c·64+j]，高 nibble = e[k=c·64+j+32] |
| `{key}.int6_hi` | U8 | [M, K/4] | 高 2 位平面。字节 j 的 4 个 2-bit 域 = e[j]、e[j+16]、e[j+32]、e[j+48] |
| `{key}.int6_sz` | U32 | [M, K/128] | 与 int8 同编码：低 16 位 = scale(fp16)，高 16 位 = zero（int6 恒 0） |

其中 `e = q + 32 ∈ [0,63]`，`w = scale · (e − 32)`（对称量化）。
scale = `amax·r/31.5`（fp16 存储），r 从 `{1.0, .97, .94, .91, .88, .85}` 里取组内 MSE 最小者。

**产出**（`g1l-2.9B-20261031`）：

| 项 | 值 |
|---|---|
| 量化矩阵数 | 192（32 层 × 6 类大投影；head 保持 int8） |
| 平均 cos / rel | **0.999536 / 2.7341 %** |
| 每权重字节 | **0.781 B**（6 bit + 每 128 权重一个 fp16 scale） |
| 文件体积 | 5.49 GB(fp16) → **3.07 GB(int8) → 2.48 GB(int6)**（−19.2 % vs int8） |
| 耗时 | 约 9 分钟（numpy，单进程；CUDA 可用时仅用于 torch 探测） |
| 权重级验收 | PASS（`cos ≥ 0.9994 且 rel ≤ 3.3 %`） |

⚠️ **一个必须记住的量化常识**：int6 是 64 级，比 int8 的 256 级粗 4 倍，per-group(128) 的
amax ≈ 2.9σ ⇒ 理论 rms 误差 = (amax/31.5)/√12 ≈ **2.7 %**。所以 int6 的权重 rel **不可能**是
int8 那个 0.35 %；把「rel ≤ 1.2 %」当验收线是算错了（本记录第一版就是这么错的）。真正的验收
在端到端（ΔCE / teacher-forced Top-1），上游实测 int6 ΔCE +0.008、top-1 94.6 %。

报告：[int6量化报告-g1l-2.9b-20261108.md](int6量化报告-g1l-2.9b-20261108.md)

| 版本 | infer_tokens | 说明 |
|---|---:|---|
| int8（对照） | **67.8 tok/s** | 3.07 GB 权重 |
| int6 初版（一线程整块） | 37.7 tok/s（0.56×） | 见下方坑 ① |
| + half 域反量化 + 树形归约 | 34.6～36.7（无改善） | 说明不是 ALU 也不是归约 |

| + 一线程半块（当前） | **60.6（0.89×）** | lo 无重复读、hi 只 2 线程读 |

prefill：int8 828 tok/s vs int6 635 tok/s（0.77×，走 dequant→fp16 GEMM，`dequant_int6` 自身占 prefill 的 49 %）。

**结论：int6 的功能链路已全部打通并验证正确（生成语义连贯），但单流性能只有 int8 的 0.89×，
未达计划里「≥1.15×」的发货门限。** 折算成**有效带宽**：int6 2.48 GB / 16.5 ms ≈ **150 GB/s**，
int8 3.07 GB / 14.75 ms ≈ **208 GB/s**（每字节效率 0.72×）；而同样的 int8 `rkv` 单核
实测 358 GB/s。也就是说 int6 省下的 25 % 字节被「读不快」吃掉了还有余。

真要吃到 6 bit 的 25 % 字节红利，必须换**布局**，不是继续调内层循环：

> 上游 `int6_gemm.py` 的权重布局是 **(K, N)、N 最内**，于是「一个线程负责若干输出列」时
> 相邻线程读相邻 N ⇒ lo/hi 两平面的载入天然合并。我们的文件是 **[M, K]、K 最内**
> （与 int8 一致），一个线程负责若干输出行时只能读到 K 方向的长条 ⇒ 6-bit 双平面的
> 16 B/32 B 步长必然浪费 sector。**下一步应该做的是 int6 专用的 N-major（转置）权重布局
> + 对应的 dot 形式内核**，而不是在 M-major 布局上继续压指令数。

### 性能优化过程里踩到的坑（按发现顺序）

1. **`alut` 形参类型是 `const __half*`**：把 hi 平面按 u32 传进去后直接 `alut + row*hi_w`
   会按 2 字节步进 ⇒ `cuLaunchKernel failed: 716 misaligned address`。必须先
   `reinterpret_cast<const unsigned int*>(alut)`。
2. **sector 利用率**（最大的一笔，0.56× → 0.87×）：一线程吃整块 64-k 时相邻线程的 lo 起点
   相差 32 B，每次 `uint4` 只用掉 32 B sector 的一半 ⇒ 事务数翻倍。改成子块级映射后拉满。
3. **归约不要用「少数线程串行累加 128 项」**：那是依赖链；改确定性二叉树（7 步、每步全线程）。
   同时**不能用 `atomicAdd`**——浮点 atomic 求和顺序不确定，会破坏「贪心 token 流逐位稳定」。
4. **并行度不能只按 K 展开**：int6 的 K 单元数是 C/64（C=2560 → 40），喂不满 128 线程；
   必须把 row 也摊给线程（或子块）。

## 1b. P2 收尾：int6 换 **N-major 布局** ✅（门限达成 1.23×）

M-major 的天花板是布局本身（见上），所以按结论做第二份权重布局 + 专用 dot 内核。

### 格式（`--int6-layout n`）

三个平面整体转置，**字节语义完全不变**，只是把「输出列 M」放到最内层：

| 平面 | M-major（默认） | N-major（`--int6-layout n`） |
|---|---|---|
| lo | U8 `[M, K/2]` | U8 `[K/2, M]` |
| hi | U8 `[M, K/4]` | U8 `[K/4, M]` |
| sz | U32 `[M, K/128]` | U32 `[K/128, M]` |
| 标记 | — | 标量张量 `int6_nmajor` = u8[1]（加载端据此选内核） |

量化值本身与 M-major**逐位相同**（量化器里只是 `.T` 后再 `ascontiguousarray`），
所以两份文件的 cos/rel 报告一致（avg_cos 0.999536 / avg_rel 2.7341 %）。
产物：`rwkv7-g1l-2.9b-int6n.st`（2.48 GB，文件名后缀 `.int6n`，不覆盖旧文件）。

### 加载与路由

- `model::int6_nmajor(&st)` 读标记张量；`Int6Handle` 新增 `nmajor: bool`，**一个开关同时**
  决定四支内核（dequant / plain / relu2 / mul_add / add / rkv）与 CPU 反量化的寻址方式。
- `model::dequant_int6(.., nmajor)` 与 `gpu_model` 的两处形状推导都按布局取
  （N-major 下 `lo` 是 `[K/2, M]`，`ffn_hidden` 必须读 `shape[1]` 而不是 `shape[0]`）。
- 文件布局 = 显存布局（不做上传期重排），这一点与 int8 的 `group-major` 不同，取舍见
  "为什么不在加载期转置"：2.48 GB 字节级转置单线程要 ~2 s/模型，且会让「文件格式」与
  「显存格式」出现隐式分叉；量化器多一次 `.T` 是零成本。

### 内核（`src/backend_cuda.rs`）

`I6NM_COMMON_SRC`（`i6nm_dot<GATED>`）+ 两个 kernel：

- `gemv_int6nm`：单矩阵通用 GEMV（op 0=relu²、1=mul_add、2=add、3=覆盖写，batch 走 `grid.y`）。
- `gemv_int6nm_rkv`：r/k/v 三路 + 4 条 mid 低秩投影（mid 段仍是 fp32 warp-per-row）。
- `rwkv_dequant_int6_nm`：32×32 tile + smem 转置的反量化（prefill / 批量走 dequant→fp16 GEMM）。

**几何**：block = `I6NM_WARPS`×32 线程，**一个 lane 一个输出列**、warp 覆盖 32 个连续列
⇒ 每条载入指令正好 32 B = 1 个满 sector；块内 `I6NM_WARPS` 个 warp 按
`c = w, w+W, w+2W, …` **轮转**切分 k-chunk（连续切分在 W 不整除 chunk 数时失衡），
块内 smem 固定升序归约（不用 atomicAdd ⇒ 贪心 token 流仍逐位可复现）。

### 实测（CUDA，g1l-2.9B，`examples/benchmark`，**同一时段同机 A/B**）

| 路径 | int8 | int6 M-major | **int6 N-major** | N/int8 |
|---|---:|---:|---:|---:|
| infer_tokens（decode） | 68.1 | 60.6 | **83.8** | **1.23×** |
| argmax_selfloop | 69.9 | — | **84.6** | **1.21×** |
| sample_selfloop | 60.8 | — | **69.0** | 1.14× |
| infer_seq（prefill 128） | 691.2 | 635 | **694.1** | 1.00× |

有效带宽：int6 2.48 GB / 11.9 ms ≈ **208 GB/s**（int8 3.07 GB / 14.7 ms ≈ 208 GB/s）
—— 也就是说 int6 现在**和 int8 打平了每字节效率**，0.75 B/权重 的字节红利第一次真正吃到。
（注：int8 prefill 今天在同机实测 691，早前记录过 828；跨时段不可比，表内一律同段对照。）

`I6NM_WARPS` 档位 A/B（decode tok/s）：8→80.1、**16→84.5**、20→79.9、32→78.6，
故默认 16（512 线程块）。环境变量仍可覆盖，仅用于现场 A/B。

### 这一步踩到的坑（都比"性能"更值钱）

1. **`hi` 平面的 2-bit 域必须按 `t` 移位**：dequant 首版写成 `hbv & 3`（漏了 `>> (t*2)`），
   结果只有 `k%64 ∈ [0,16)` 正确 ⇒ 权重高 2 位被读成 0、误差 ~4 %。
   **新增测试 `int6_nmajor_kernels_match_cpu`**（GPU 三件套：dequant / plain(batch=2,m=70) /
   mul_add 门控，全部对 CPU 参考）当场抓住。这类位运算写错的唯一表现是"输出变差但不崩"。
2. **fp16 累加会吃掉 int6 的精度**：先用 `__hfma2` 在 half 域累加，合成权重测试相对误差
   **3.6e-2**（32 个 fp16 加法的舍入）。改 fp32 四路独立累加器后误差回落到 2e-3 以内；
   更关键的是**端到端文本从"7 token 死循环"变回与 M-major 逐 token 相同的连贯英文**
   （同一 prompt、同 argmax）。本核受带宽约束，多出的 ALU 不进关键路径（84.5 vs 80.1 tok/s）。
3. **N-major 反量化不能再按 `[M,K]` 线性铺线程**：那样读平面是「步长 = m」的全散读，
   prefill 从 635 掉到 523。必须 32×32 tile + smem 转置（读合并 + 写合并），才回到 694。
4. **标记张量比"猜形状"可靠**：`[M,K/2]` 与 `[K/2,M]` 在部分形状下会撞车（如 M = K/2），
   不要靠 shape 反推布局。

**Vulkan 实测（g1l-2.9B int6n vs int8，同机同时段）**

| 路径 | int8 | int6 N-major |
|---|---:|---:|
| infer_seq（prefill 64） | 174.6 | **174.0** |
| infer_tokens（decode） | 47.1 | **14.8** |
| argmax_selfloop | 51.3 | **15.0** |
| sample_selfloop | 52.4 | **15.6** |

prefill 打平；**decode 慢 3.2×**，原因是并行度：N-major 的「一个 invocation 一个输出列」
让 rkv 只有 C/128 = 20 个 workgroup（int8 版是 invocation 沿 k 展开 + subgroup 归约，
workgroup 数 ×128）。补法是**块内 k 切分 + shared 归约**（CUDA 侧就是这么做的，4 路即可
让 workgroup 数 ×4），属性能项、不影响正确性。

### Vulkan 这次踩到的三条（都是"能跑但算错"型）

1. **`buffer_reference` 匿名类型声明必须带分号**（`layout(buffer_reference) buffer InLo { ... };`），
   漏了报的是下一行 `unexpected LAYOUT`，离真凶很远。
2. `unpackHalf2x16(...).x` 是 **float**，不能初始化 `const uint`（glslang 报
   "cannot convert from temp highp float"）。
3. **`a0[BGRP]` 这种「特化常量长度」的数组在 BGRP=1 时慢一倍**：驱动把它留在 Private 存储，
   每次累加都变成私有内存往返（实测 Vulkan decode 14.5 → 6.8 tok/s）。修法是单流/批量
   **分成两份代码**（用 uniform 分支 `if (BGRP == 1)`，驱动建管线时折叠），不能只靠
   `[[unroll]]` 指望编译器消掉数组。
   ★ 顺带验证了 BGRP 的收益：没有它时 sample_selfloop（batch≈8 的采样自循环）
   只有 2.1 tok/s，有权重摊薄后 15.6 tok/s（**7.5×**）。

## 1d. int6 宽批（P3）✅ 两后端都通

int6 原来在批量路径上是**显式报错**（"batch 并发路径要求 r/k/v 为 int8"），本次打通：

| 件 | 做法 |
|---|---|
| `gemv_int6_rkv_stage1_batch`（CUDA + Vulkan） | 与单流**同一个内核**，只是 `grid.y = batch`：内核按槽号偏移 x 与全部输出（r/k/v/mid 各自按槽步长），mid 也**每槽各算一份**（int6 不走 `lowrank_gemm` 档：`gemm_imma` 只吃 W8A8） |
| `att.output`（批量） | 新增 `wq(att_output_i6, att_output_a8)` 分支 → `w_mul_add`（`gemv_int6nm` 的 mul 变体，`grid.y=batch`） |
| `ffn.key` / `ffn.value`（批量） | 同上加 int6 分支（`w_relu2` / `w_add`）；ffn.value 在 `batch ≥ 16` 走既有的 **dequant→fp16 稠密 GEMM**（`ffn_value_dense16` 是量化权重反量化后的 fp16 副本） |

**门禁（实测）**：`tests/batch_parity` 用 int6n 模型
- CUDA：**10 passed / 0 failed**（1 ignored 是已知的随机采样不可复现项）——包含
  `stepwise_and_selfloop_paths_agree_greedy`（逐步 vs 一次提交两条**不同内核**的路径逐 token 相同）、
  `slots_beyond_the_first_wave_match`（跨波槽位零容差）、`warmup_buckets_do_not_change_results`、
  `greedy_tokens_are_reproducible`。
- Vulkan：**9 passed / 1 failed**，唯一失败是 `top_p_sampled_tokens_stay_inside_the_nucleus` 的
  **自身有效性断言**（"候选集全为 1 ⇒ mask 读取路径没被覆盖，本用例已失效"）+ 提示调温度重造分布，
  不是数值错误。

结论（写进决策档案的口径）：**int6 在窄批（单流 / 批量 decode）走 N-major dot 内核**；
**宽批 ffn.value 固定走 dequant→fp16 稠密 GEMM**；**不做 W6A8 IMMA**（硬件无 6-bit 张量核）。

## 1e. 「单流比批量 B=1 慢很多」的读数核对 + decode 带宽归因（2026-11-08 下午）

### 结论一：**单流与批量 B=1 是等价的**，此前看到的 2.45× 是测法假象

`examples/batch_decode_bench` 里 `[单流]` 段先测、`[批量]` 段后测，**没有交替**，而本机在同一
进程内就有明显的时钟爬升/热降频。把它改成同进程、**交替 4 轮取最小**（`benchmark`
新开关 `B1_AB=1`，三档采样参数各来一遍）后：

| 采样档 | int6n 单流 | int6n 批量 B=1 | int8 单流 | int8 批量 B=1 |
|---|---:|---:|---:|---:|
| top_k=1（贪心） | 14.80 ms | 14.82 ms（1.00×） | — | — |
| top_k=50 top_p=0.9 | 16.45 ms | 16.52 ms（1.00×） | 21.74 ms | 24.08 ms（0.90×） |
| top_k=0 top_p=0.2 | 14.88 ms | 14.98 ms（0.99×） | — | — |

两条路径数学等价（`tests/batch_parity` 已钉：逐步 vs 一次提交逐 token 相同），批宽都是 1 时没有
结构性差异。**顺带记一个更重要的坑**：同一天里同一份二进制，decode 读数从 **83.8 → 52.7 → 68**
tok/s 飘过三次（2080 Ti，GDDR6 616 GB/s）——**任何跨会话/跨时段的 tok/s 对比都不可引用**，
必须同会话交替 A/B。

### 结论二：真正的问题在**绝对带宽**——int6 dot 内核只跑到 ~170 GB/s（峰值 616）

用 `ABLATE=<kernel 名>` 做逐核归因（`ABLATE` 名字必须与 kernel 缓存键一致，含 `_w{warps}` 后缀，
写错会静默不命中）：

| 消融内容 | 步时间 | 归因 |
|---|---:|---|
| 基线（eager `forward_token`） | 15.77 ms | 2.48 GB ⇒ **157 GB/s** |
| 去掉 `gemv_int6nm_rkv_w16`（r/k/v+mid，480 MB） | 10.24 ms | rkv ≈ 5.5 ms |
| 去掉 `gemv_int6nm_w16`（output+ffn.key+ffn.value，1.47 GB） | 5.99 ms | 单矩阵 ≈ 9.8 ms |
| 两者都去掉（head int8 168 MB + norm/elementwise/sampler + 宿主发射） | 4.25 ms | **地板 4.25 ms** |

即：1.95 GB 的 int6 权重一共花了 11.5 ms ⇒ **170 GB/s**（2080 Ti 峰值 616 GB/s，仓库里
int8 m-major 单核曾跑到 358 GB/s）。**下一步的优化目标是把这 11.5 ms 压到 5.5 ms**（→ 整步
约 9.8 ms = 102 tok/s）。

怀疑的主因（待验证）：本内核**一条 lane 读 1 字节**，一个 warp 的载入指令只有 **32 B**；
而 int8 m-major 内核是 16 B/lane（512 B/warp）。GDDR6 上 32 B 分散请求的行局部性差。

### 1e-补：vec4（4 列/lane）已实现并**实测否决**（2026-11-08 晚）

按上面的假设做了 `I6NM_VEC=4`：一条 lane 4 个输出列、每线程一次读 4 个字节（warp 128 B）、
块覆盖 128 列（块数 = m/128），4 个子块各持 float4 累加器，归约在 `red[W][128]`。
正确性门禁通过（测试改成 m=132 —— 4 的倍数但非 32/128 倍数）。

**A/B（同机，eager `forward_token` 48 步，同一条命令内交替跑两遍取小）**：

| 配置 | ms/token |
|---|---:|
| vec1 W=16（现状） | **13.92 / 14.04** |
| vec4 W=16 | 16.27 |
| vec4 W=8 | 19.46 / 20.07 |
| vec4 W=4 | 32.90 |

⇒ **假设被推翻**：32 B 事务不是瓶颈；vec4 反而慢，因为每块列数从 32 涨到 128、块数掉到 1/4
（rkv 只剩 20 块），并行度损失大于事务收益。**默认仍为 vec1**，代码留作对照。

下一步不再猜，改用**隔离基准**（`examples/kernel_bench.rs` 加 int6 手臂）拿每个 kernel 的干净
GB/s，再决定是「加并行度（split-K 两段归约）」还是「改数据布局（例如把 lo/hi 交错成一个平面，
让一次载入同时拿到低 4 位与高 2 位）」。

### 1e-补二：隔离基准给 int6 内核平反（2026-11-08 晚）

给 `kernel_bench` 加了 `i6_relu2 / i6_mul / i6_plain / i6_add` 四个手臂（建 N-major 双平面 +
按 `wbytes_int6` 折算 0.781 B/权重）：

| 手臂 | 形状 | int6 | 同形状 int8 |
|---|---|---:|---:|
| relu2（ffn.key） | 10240×2560 | **315 GB/s** | 303 |
| plain（head） | 65536×2560 | **316 GB/s** | 309 |
| add（ffn.value） | 2560×10240 | **310 GB/s** | — |
| mul（att.output） | 2560×2560 | **188 GB/s** | — |

⇒ **内核不是瓶颈**：int6 与 int8 的每字节效率**完全一致**（315 vs 309）。§1e 的「170 GB/s」
是**整步混合读数**（含 fp32 低秩权重、norm/elementwise、head、宿主发射），不能归到 int6 内核头上。
只有 2560² 这一档偏弱（5 MB 的核，固定开销占比高）。

**warp 档位（隔离基准 vs 整模型，结论相反 ⇒ 以整模型为准）**：

| I6NM_WARPS | i6_relu2（隔离） | 整模型 eager 步时间 |
|---:|---:|---:|
| 4 | 0.0528 ms（388 GB/s） | 13.37 / 14.25 ms |
| 8 | 0.0600 | 11.44 / 11.47 |
| **16（默认）** | 0.0568 | **10.65 / 10.92** |
| 32 | 0.0627 | — |

隔离基准偏好小 warp（L2 热、单核独占），整模型偏好 16（多核并发、要延迟掩盖）。**默认保持 16**。

### 下一步的真账（整步 ~10.7 ms = 233 GB/s）

| 项 | 每 token 流量 | 估计耗时 |
|---|---:|---:|
| int6 六大矩阵（1.95 GB @ 315 GB/s） | 1.95 GB | ~6.2 ms |
| head int8 | 168 MB | ~0.55 ms |
| **低秩 mid/chain4（fp32 未量化）** | **~378 MB** | **~1.3 ms** |
| norm / elementwise / sampler / 宿主发射（地板 4.25 ms 减去上面两项） | — | ~2.5 ms |

最明显的下一步杠杆：**把低秩矩阵（v1/w1/a1/g1/v2/w2/a2/g2）也量化**（现在是 fp32，占 15% 流量、
还占 378 MB 显存）；其次是压那 2.5 ms 的非权重地板。

### 1e-补三：机器状态——**卡在 250 W 功耗墙**（不是温度），且本机无法锁频

`benchmark` 现在每次读数前后打印 `clocks.sm / 温度 / power / clocks_throttle_reasons`
（`gpu_telemetry`，`nvidia-smi` 路径要同时试 `System32`（64 位进程）与 `Sysnative`（32 位））。

实测（RTX 2080 Ti，decode 中）：

| 时刻 | SM 时钟 | 显存 | 温度 | 功耗 | 降频原因 |
|---|---:|---:|---:|---:|---|
| 预热后 | 1860 MHz | 6800 MHz | 54 ℃ | 228 W | 0x0（无） |
| forward_token 测中 | **1845 MHz** | 6800 MHz | 61 ℃ | **252 W** | **0x4 = SwPowerCap** |
| 空闲 | 585 MHz | 5000 MHz | 45 ℃ | 67 W | 0x1 = GpuIdle |

⇒ 温度只有 61 ℃、**瓶颈是 250 W 功耗墙**（SM 峰值 2100 MHz，实际被压到 ~1845）。
**锁频做不到**：`nvidia-smi --lock-gpu-clocks` 报 "current user does not have permission"
（要管理员），`--lock-memory-clocks` 在 GeForce 上直接不支持。

三条推论，写进测量纪律：

1. **跨会话的 tok/s 一律不可引用**（同一天同一份二进制见过 52.7 / 68 / 83.8 / 101.5），
   每条读数必须带上 `clocks.sm` 与 throttle reason。
2. 功耗墙下**时钟随 workload 功率浮动** ⇒ 重 ALU 的手臂会被压得更低，交替 A/B 也只能部分抵消。
   所以比较两个内核时优先看**同一功耗档**（看 telemetry 的 MHz 是否接近）。
3. 反过来说：**降 ALU/降指令数本身就是提速手段**（功耗墙下省的电就是时钟）。
   这给「lo/hi 交错成单平面（一次载入、少一半地址计算）」补上了除带宽之外的理由。

### 1e-补四：已把功耗墙提到 300 W + **锁频 1800 MHz**（2026-11-08 晚，管理员权限）

`power.max_limit` 实测 = 300 W（默认 250）。当前 shell 的 Administrators 组是
**deny-only**（未提权），所以 nvidia-smi 直接改会报 `Insufficient Permissions`；
用「64 位 PowerShell + `Start-Process -Verb RunAs`」提权（会弹 UAC）后生效：

```powershell
# 32 位 shell 里 System32 被重定向 ⇒ 必须先起 64 位 PowerShell，再由它提权
$cmd = "Start-Process -FilePath 'C:\Windows\System32\nvidia-smi.exe' " +
       "-ArgumentList '-pl','300' -Verb RunAs -Wait"
& "C:\Windows\Sysnative\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -Command $cmd

# 锁 SM 时钟（GeForce 上这条**可以**用；记忆时钟锁不支持）
$cmd = "Start-Process -FilePath 'C:\Windows\System32\nvidia-smi.exe' " +
       "-ArgumentList '--lock-gpu-clocks=1800,1800' -Verb RunAs -Wait"
& "C:\Windows\Sysnative\WindowsPowerShell\v1.0\powershell.exe" -NoProfile -Command $cmd

# 解锁：--reset-gpu-clocks；恢复功耗墙：-pl 250
```

**代价与收益（重要）**：把墙从 250 提到 300 W 只带来 **0–3%**（decode 本身只吃 218–252 W，
250 W 只是「刚好卡住」）——真正有价值的是**锁频后读数可复现**：

| 状态 | infer_tokens | forward_token | telemetry |
|---|---:|---:|---|
| 250 W、未锁频（boost 浮动） | 52.7–101.6（飘） | 9.84–15.8 ms | 1845 MHz / SwPowerCap |
| **300 W + 锁 1800 MHz** | **104.3 tok/s** | **9.57 ms** | 1800 MHz / 无降频 |

锁定档下的其它读数（同一次运行）：
`argmax_selfloop` 107.3 tok/s；单流 vs 批量 B=1 = **1.01–1.02×**（三档采样参数，再次确认等价）。

⚠️ `-pl` 与 `-lgc` **都不持久**，重启即失效；每次要跑正式读数前重新执行上面两条。

**锁频上限实测（2026-11-08 晚补充）**：请求 1900 / 1950 / 2000 全部被驱动**夹到 1845 MHz**
（`clocks.max.sm` 虽是 2100，但可锁的 graphics clock 上限就是 1845 —— 通常等于该卡的
rated boost）。1800 → 1845 的实测收益 **为 0**：

| 锁频档 | infer_tokens | forward_token |
|---|---:|---:|
| 1800 MHz | 104.3 tok/s | 9.57 ms |
| 1845 MHz（上限） | 104.6 tok/s | 9.67 ms |

⇒ decode 是**带宽/延迟受限**，拉 SM 时钟没用（也解释了 `I6NM_WARPS` 扫档收益有限）。
当前已锁 **1845 MHz + 300 W** —— 这是本机能给的最好可复现档位。

### 3.2 drafter 三个专用核 ✅（CUDA）

`backend.rs` 新增 trait 方法（默认 `Err`，Vulkan 后续同步）：
`mtp_rms_rope` / `mtp_kv_write` / `mtp_attn`；实现见 `backend_cuda.rs` 的 `MTP_ATTN_SRC`。

| 核 | 语义 | 关键点 |
|---|---|---|
| `mtp_rms_rope` | 每个 head 内 RMSNorm（共享 `[D]` 权重，eps 1e-6 在 sqrt 内）+ rotate-half RoPE | 只动前 `rope_dim` 维、配对 `(i, i+rope/2)`、角度 `pos·θ^(-2i/rope)`；归约用 warp 洗牌 + shared **固定顺序**（不用 atomicAdd） |
| `mtp_kv_write` | 把新 k/v 写入 ring 的 `pos % S` 槽，并记 `ring_pos[slot] = pos` | 与 attn 拆成两个核，避开跨 head 的写后读栅栏（同 stream 顺序即等价） |
| `mtp_attn` | GQA：head h 读 KV head `h/(H/Hk)`，可见性 `0 ≤ sp ≤ qp && qp−sp < W`（**query 见自身**） | 分数阶段每线程算整槽 dot（D≤128 无需跨线程归约）→ shared 里固定顺序 softmax → 线程 t 负责输出第 t 维 |

**门禁**：`backend_cuda::tests::mtp_drafter_kernels_match_cpu`（d=16 / rope=8 / 4q4kv? 实为 4Q2KV /
S=6 / W=4，跑 3 个位置含**绕圈**与窗口裁剪）逐元素对 CPU 参考，误差 < 1e-5。

两个 CUDA 小坑：① NVRTC 里 `INFINITY` 与 `CUDART_INF_F` 都未定义（`math_constants.h` 不在默认
include 里）⇒ 用 `-1e30f` 当「不可见」哨兵并给 `1/tot` 加零保护；② `[H]` 长度出现循环边长须
用 `#pragma unroll` 的 warp 洗牌，避免 `__syncthreads` 在分支里。

### 3.3 drafter 编排 + 主模型 tap ✅（P4 功能面）

**`src/mtp/drafter.rs`（新）**：`MtpDrafter` = 权重 + 状态 + 工作缓冲。

- **权重**：9 个 Linear（`fproj[C,3C]`、`proj[C,2C]`、`attn.{q,g}[2048,C]`、`attn.{k,v}[512,C]`、
  `attn.o[C,2048]`、`blk.ffn.{key[4C,C],value[C,4C]}`）上传成 **f16** 走 `gemv_f16` 家族；
  15 组 LayerNorm 仿射、`dep`（拆 8 行，`elementwise_add` 要独立 `[C]`）、`x_k`、`q_norm`/`k_norm`
  留 f32。上传后立即 `drop_host`。
- **状态**（§3.2，单流 = 槽 0）：`kc/vc` 布局 `[S][4][128]`（与内核的 `slot*nkv_d + kvh*d` 一致）、
  `ring_pos[S]`（u32，空槽 `u32::MAX`）、`ffn_x[C]`、`pos`。`S = W + max_k + 1`。
- **draft 词表截断**：不复制 head，而是给 logits 加一张**静态掩码**（draft 内 0、其余 −1e30）再在全
  词表上 argmax ⇒ argmax 索引**就是** token id，既不需要回映射，也不需要链内 host 往返。
  掩码张量 `[vocab]` f32 一次上传，每深度一次 `elementwise_add`（256 KB 读写，可忽略）。
- **一个块**（`block()`）= `e→LN_le` → `[u;e]→proj` → `+dep[k-1]` → `LN_ln0` → `LN_ln1` →
  q/g/k/v → `mtp_rms_rope`×2 → `mtp_kv_write` → `mtp_attn` → `sigmoid` 门 ⊙ + `Wo` 残差 →
  `LN_ln2` → token shift（`elementwise_lerp`）→ cmix（`relu²` + `add`）→ `LN_lo` → head → 掩码 → argmax。
  末尾把 `x2` 拷到 `shift` 缓冲（下一深度的 token shift）。
- **API**：`commit(h,m1,m2,tok)`（深度 1，推进 `pos`、刷新 `ffn_x`）、
  `draft_chain(h,m1,m2,tok,k)`（commit + k−1 个更深深度，链尾一次读回 k 个 draft）。

**`gpu_model.rs`**：新增 `mtp: Option<MtpCtx>`（`drafter` + `tap0/tap1`）。`enable_mtp(&sidecar, max_k)`
从 `head_i6 → head_a8 → head_w16` 里挑 head 形态（复用，不复制）；`forward_layer` 尾部调
`mtp_tap(i)`，在 `fuse_layers` 两层把该层**输出残差** `x` 设备内拷进 tap；`h` 直接用 `bufs.x_norm`
（就是 §1.2 要求的「`ln_out` 之后」那一行，不需要额外缓冲）。未启用时整条路径只有一个 `Option` 分支。

**门禁/探针**：`examples/mtp_probe.rs`（新）——主模型 greedy 自生成，每步起草 K 个 token 与随后
真值逐位置比对。实测（CUDA，int8 2.9B，96 步，prompt `[304,25740,109]`）：

| K | depth1 | depth2 | depth3 | depth4 | 平均接受长度 |
|---:|---:|---:|---:|---:|---:|
| 2 | 81.1% | 68.1% | — | — | **2.442** |
| 3 | 81.1% | 68.1% | 57.0% | — | **2.968** |
| 4 | 81.1% | 68.1% | 57.0% | 53.3% | **3.411** |

第四节验收门限是「平均接受长度 ≥ 1.8」⇒ **已达标（2.44–3.41）**；depth 4（超出训练深度 3）仍有 53%，
说明训练深度不是硬上限，与上游「K 可超过训练深度」一致。

**两个踩到的坑（都是「0% 但看不出错」型）**：

1. **drafter 的 `pos` 必须与主模型已处理位置数对齐**。只把 prompt 喂给主模型而不同步 `commit`，
   RoPE 位置与 KV 窗口整体错位 ⇒ 接受率恒 0（不是慢，是错）。探针里 prompt 逐 token 走，
   每处理完位置 i 就 `commit(row_i, prompt[i+1])`（正是 §3.4 的 prefill 提交规则）。
2. **自循环起始 token 若落在 draft 词表外，接受率必然 0%**：`seed=1` 时模型 greedy 死循环输出 token 1，
   而 token 1 不在 `draft_vocab[:16384]` 内 ⇒ 掩码让它永远不可能被选中。第一次跑出的「0/23」就是这个，
   **不是实现错误**。探针因此加了「真值是否在 draft 词表内」的打印。

### 3.4 成本三件套（决定 P5 的验证/回滚做法）★ 关键约束

`examples/mtp_probe.rs` 末尾加了成本读数（int8 2.9B，CUDA，K=3，16 次取均值）：

| 件 | 耗时 |
|---|---:|
| 单 token decode（plain 基线） | 10.21 ms |
| **T=4 因果 seq pass（`forward_seq_with_state`）** | **104.4 ms** |
| drafter 链 3 深度 | 3.31 ms |

**结论一：验证前向不能用现成的 prefill 路径。** 104 ms 的来源是 `m_pad = t.div_ceil(256)*256`
（tensor-core GEMM 要求 M 是 TILE_M=256 的倍数）+ 每层把 int8 权重 `dequant→fp16 scratch` 再 GEMM：
T=4 也按 256 行算，且每层多搬 2.6 倍权重量。⇒ 投影出来是 0.28×，**比不用 MTP 慢 3.6 倍**。

**结论二：验证必须走「批量 GEMV 直读量化权重」**（即 `forward_layer_batch` 那套
`gemv_int8_rkv_stage1_batch` / `w_relu2` / `w_add` / `w_mul_add`，batch=T）。它读 int8 权重一次
（3.3 GB ⇒ ~8 ms），张量核 padding 与 dequant 副本都不存在 ⇒ 验证一步 ≈ 1 个 decode 步，
这才有 (10.5 + 3.3)/2.97 = 4.6 ms/token = **2.2×** 的空间。

**结论三：回滚不能靠「第二遍 seq 重放」**（再加一个 10 ms ⇒ 1.19×）。按上游的做法：验证时把每层
`dplr_seq` 的输入（`r/w/k_mod/v/kk_l2/b_vec`）与 `ln1/ln2` 逐位置存下来
（8 张 × [L=32, T≤8, C=2560] ≈ 21 MB），回滚 = 恢复状态快照（42 MB 设备拷贝）+ 每层
`dplr_seq(T=n)` 重算 + 两次 `copy_token`（tmix_x/cmix_x 取第 n−1 行）⇒ ~1 ms 量级。

### 3.5 小 T 验证通路 ✅（`SEQ_SMALL_T`，默认 8）

`forward_seq_layer` 新增 `small_t` 分支，把 6 个主矩阵从「dequant→fp16 scratch + 张量核 GEMM」
换成**批量 GEMV 直读量化权重**：

- r/k/v：三路 `w_plain`（int6/int8 直读；fp16 用 `gemv_f16` 的 `n=batch`）。刻意**不用**融合核
  `gemv_int8_rkv_stage1_batch`——它的 `out_v` 是 **f16**（批量解码链路里 v 全程 f16），而 seq 链路的
  v 是 f32（`dplr_seq`/`sum_rk_rk` 吃 f32），硬接要多一次 f16→f32（**没有这个算子**）。三路只是少一次
  launch，权重流量完全相同。
- att.output / ffn.key / ffn.value：`w_mul_add` / `w_relu2` / `w_add`（原地累加 ⇒ **不交换 x/y_out、x/v2**）。
- 低秩 mid 仍走张量核，但 `M` 从 `m_pad=256` 压到 **64**（tensor-core 的 M 下限，批量档的 `lr_rows`
  就是 64）；mid ≤ 96 的 padding 计算量直接省掉 3/4。
- ⚠️ **`to_f16_triple(xr/xk/xv → xr16/xk16/xv16)` 不能省**：低秩 v 链的一级 `gemm(sb.xv16, v1_16, ...)`
  读的是 xv16。第一版省掉它，导致 v_mid 用陈旧 xv16 重算 ⇒ argmax 5 vs 40、`max|Δlogit|`=20.3。

**实测（int8 2.9B，CUDA，K=3 ⇒ T=4，8 次均值）**：

| 配置 | T=4 因果 seq pass |
|---|---:|
| 关掉小 T 分支（`SEQ_SMALL_T=0`） | 104.4 ms |
| 小 T 分支 | 21.8 ms |
| 小 T 分支 + `PREFILL_GRAPH=1`（把 40 个/层的小 kernel 一次捕获重放） | **16.5 ms** |
| 对照：单 token decode | 10.3 ms |

**自检**：同一段 T=4 token，「逐 token 解码」与「一次因果 seq pass」的末行 logits 同 argmax
（`max|Δlogit|`≈5，GEMV/GEMM 累加顺序不同 + int8 量化）；`tests/batch_parity` 10/10 全绿。

**还剩的 6 ms 在哪**：隔离基准（`kernel_bench`，B=1 → B=4）证明批量 GEMV 只贵 4–8%
（head 形状 0.496 → 0.519 ms），所以主矩阵不是瓶颈；剩下的差距是 **seq 路径每层 ~40 次 kernel
dispatch（decode 只有 ~10 次，且重融合）**——GPU 侧每次 dispatch 也有 2–4 µs，1280 次 ≈ 4–5 ms。
⇒ 下一步要么给整步（draft+verify）上 CUDA graph，要么把 `fuse_ka+dplr_seq+norm+sum_rk_rk` 换成
已有的 `fuse_ka_dplr_norm_batch`（4 → 1）。

### 3.6 投机步闭环 ✅（功能正确，性能未达标）

`GpuModel::spec_step(state, tok, k)` 把整条链路接起来（单流、贪心验证）：

1. `mtp_snap.copy_from(state)` —— 42 MB 设备内快照（`copy_rows_from` 的老路，不过主机）；
2. `drafter.draft_chain` 起草 k 个；
3. `forward_seq_verify_with_state([tok | drafts])` —— T=k+1 的因果 pass，**全 T 行 head**
   （`w_plain(head, x_norm → logits_t)`）后逐行 argmax；
4. `j` = 连续命中的草稿数；提交 `[tok, d1..dj, picks[j]]`；
5. `spec_rollback(state, snap, j+1)` —— 恢复快照 + 每层 `dplr_seq(T=j+1)` 重放 +
   `copy_token` 取第 j 行的 `ln1/ln2` 当 token shift（**不重跑前向**）；
6. drafter 补提交 j 个被接受的草稿（`commit_only`：跳过 head+argmax，纯提交 ≈0.1 ms），
   并把下一步的 H 指向验证时存下的 `taps[j]`（`MtpCtx::pending_h`）。

**正确性证据**：`examples/mtp_probe` 的 A/B —— 同一 prompt（`[304,25740,109]`）后贪心生成，
plain 逐 token 与 spec 环的 token 流**前 4 个逐位相同**（之后在 near-tie 处分叉，见下）。
这条覆盖了「验证 → 接受前缀 → 回滚 → drafter 前移」的每一个环节。

**性能（int8 2.9B，CUDA，锁屏外的普通档）**：

| K | 每步明细（snapshot / draft / verify / rollback） | 步数 | 平均接受草稿 | 吞吐 | 对 plain |
|---:|---|---:|---:|---:|---:|
| 3 | 0.8 / 3.0 / 18.5 / 2.5 ms | 13（24 tok） | 0.92 | 68 tok/s | **0.69×** |
| 7 | 0.8 / 8.0 / 18.5 / 2.5 ms | 15（32 tok） | 1.27 | 67 tok/s | **0.72×** |

**卡点（已定位到具体金额）**：验证 pass 17.5–18.5 ms ≈ 1.7 个 decode 步（10.3 ms），
且**与 T 无关**（T=2 是 17.7、T=4 是 17.4、T=8 是 18.5）⇒ 不是「token 多」，是**结构性**：

- 权重流量（int8 3.3 GB @ ~350 GB/s）只占 **9.4 ms**；
- 剩下 ~8 ms 是 seq 路径**每层 ~44 次 kernel dispatch**（decode 只有 ~10 次且深度融合）：
  `PROFILE` 逐阶段 = shift+rkv 0.1 / **lowrank+fuse_ka 0.2** / dplr 0.0 / y_norm+输出 0.1 / cmix+ffn 0.1 ms
  ⇒ 0.5 ms/层 × 32 = 16 ms。1400 次 launch × ~5 µs ≈ 7 ms。
- `PREFILL_GRAPH=1` 已把 CPU 侧 launch 拿掉（21.8 → 16.5 ms），剩下的是 GPU 侧每节点 ~2 µs。

**为什么不能直接换成 batch 版融合核**（都试过签名，全部卡在同一处）：

| 想要的核 | 期望收益 | 卡点 |
|---|---|---|
| `gemv_int8_rkv_stage1_batch`（r/k/v + 4 个 mid） | 12 launch → 1 | `out_v` 必须 **f16**，seq 链路的 v 是 f32（`dplr_seq`/`sum_rk_rk` 吃 f32） |
| `gemv_lowrank_chain4_batch`（低秩链两段） | 14 launch → 2 | 输出必须是 **f16**、`v_first` 也必须 f16 |
| `lowrank_gemm_batch`（fp16 张量核两段） | 14 launch → 1 | 同上（f16 输出） |
| `fuse_ka_dplr_norm_batch` | 4 launch → 1 | 它是**按槽独立**的 batch 语义，不是 T 长度的因果扫描 |

⇒ 缺的是一个 **f16→f32 反向转换算子**（现有只有 `to_f16`），或等价的「f16 缓冲 + 让
`dplr_seq`/`sum_rk_rk` 吃 f16」改造。**这是下一个明确的工程项，不是猜。**

### 3.6b 三个隔离实验（把「机制错」与「数值差」分开）

1. **回滚自检**（`GpuModel::mtp_rollback_selftest`）：从同一基线出发，「T 全 pass + 回滚到 n」
   vs 「直接 T=n pass」，状态**逐位一致**（`max|Δstate| = 0.000e0`，540 万个数）。
   ⇒ 快照 + `dplr_seq(T=n)` 重放 + 逐位置 `ln1/ln2` 这一套**没有错**。
2. **spec vs 同路径逐 token**（臂 C）：只前 2/32 一致 ⇒ 这条臂先暴露了**真 bug**：
   **小 T 分支在 T=1 时输出是错的**（臂 C 用它逐 token 解码会自循环）。已把门限改成
   `2..=SEQ_SMALL_T` ⇒ T=1 一律走老 prefill 路径（T=1 没有性能诉求，先不碰）。
   教训与 §3.3 同型：**门限的下界也要有实验支撑**，不能默认「越小越该走新路径」。
3. **`SEQ_ROWS`**（强制 mid GEMM 行数 64/256）：4/32 vs 4/32 ⇒ 分歧与 mid GEMM 的 M 无关。

**结论**：机制（验证 / 接受前缀 / 回滚 / drafter 前移）是正确的；真投机环的流与 plain 逐 token
只重合 4 个 token、平均接受停在 0.85–1.5，来自**验证 pass（seq/prefill 路径：fp16 张量核 GEMM）
与 decode 路径（f32 SIMT `chain4`）的数值差**（`max|Δlogit|` 5–10）。这既稀释了接受率，也让
MTP 的输出偏离 plain 解码的程度超过「仅 near-tie」。

⇒ 要把这条差距压掉，必须让验证路径与 decode 路径走**同一套 f32 低秩语义**
（`gemv_lowrank_chain4_batch`），而它的输出/first 都是 f16 ⇒ 又回到那个缺件：
**`f16→f32` 转换算子**。这也是 3.6 表里四个融合核的共同前置。

### 3.8 验证路径的三次 launch 手术 + 回滚图 ✅（2026-11-08 晚）

**动机**：§3.6 的账已经点明——验证 pass 的 14–18 ms 里，权重流量只占 ~9.4 ms，
剩下的差距是「seq 路径每层 ~44 次 dispatch vs decode ~10 次」，每次 ~5 µs（图重放后仍然如此，
因为小 kernel 是**延迟受限**的）。

**① 低秩二级链路 → 一条 f32 chain4（`gemv_lowrank_chain4_f32`，CUDA）**
`SEQ_CHAIN4`（默认开）。18 次 launch（4×gemm(_tanh) + 4×to_f16 + 4×gemm_bias +
sigmoid/scale_exp + v_first_lerp）→ **1 次**。新增原语与 `gemv_lowrank_chain4_batch`
**同一套 f32 SIMT warp-per-row 累加**（数值同档），差别只有两处：`v_first`/四个输出全 f32
（序列链路下游 `dplr_seq`/`sum_rk_rk`/`fuse_ka` 只吃 f32），以及四个 mid 输入各带行步长
（`sw/sa/sv/sg`，seq 的 mid 补齐到 64）。layer 0 把 `v_first` 与 `out_v` 传同一张
（lam ≡ 0 ⇒ v 原样保留，等价于「该层不跑 v 低秩链」）。

**② 六路 token shift → 一条 `seq_shift6`（CUDA；Vulkan 走默认实现 = 6 次原样）**
`SEQ_SHIFT6=0` 可回退。★ 踩到的坑：`tmix_x` 的回写**不能**并进这个核——
t=0 的块要读旧 state、写方是 t−1 的块，块间无顺序保证（t≥2 时是实打实的竞态）。

**③ 回滚整段捕获成 CUDA graph（`MTP_ROLLBACK_GRAPH`，默认开）**
按 `n` 建 key（`1<<41 | n`），2.2 ms → **0.6 ms**。三个必须记住的点：
- **捕获不执行 kernel**（同 `forward_seq` 的 prefill graph），`end_prefill_capture` 之后
  必须立刻 `prefill_graph_replay` 一次，否则本次回滚根本没发生（症状：回滚后状态=未回滚）；
- `State::copy_from` 自带 `begin/end_batch`，圈进捕获会丢节点 ⇒ 快照恢复放在捕获**之外**；
- seq 缓冲重建时 `clear_cache` 会连同图一起销毁 ⇒ 不存在「重放到旧地址」的窗口。

**④ 状态快照也上图（`MTP_SNAPSHOT_GRAPH`，默认开）**
34 次设备内拷贝，0.50 ms → **0.05 ms**。形状与指针全固定（`state`/`mtp_snap` 都是常驻张量），
一张图永久重放，和 ③ 同一个套路（key `1<<42`）。

**⑤ 两遍 `to_f16_triple` → 一遍 `to_f16_six`**
小 T 的 r/k/v 走批量 GEMV（吃 **f32** 激活），6 路 f16 副本只为一级 mid 的 GEMM 服务
⇒ 两次转换合并成一次（节点 23 → 22，−0.25 ms）。**数值逐位不变**（`max|Δlogit|` 与合并前
完全相同：6.2367e0 / idx 42014），这类「只改 launch 不改算式」的手术是这个阶段唯一零风险的一类。

**⑥ 被实测否决：`norm+shift` 融合（`SEQ_NORMSHIFT`，默认关）**
把 `norm(ln1)+shift6` 与 `norm(ln2)+存档+shift` 各融成一个核（`seq_norm_shift`，CUDA），
理论上每层省 3 个节点。**实测更慢**：T=4 验证 pass 14.1 → **16.4 ms**，数值仍逐位不变
（`max|Δlogit|` = 6.2367e0 / idx 42014）。原因是融合核必须**重算**上一行的 mean/inv
（跨块竞态的唯一免锁解法），而这两步本来零权重流量、只有 T 个 block 在跑 ⇒ 多出来的一遍
带 barrier 的归约远贵于省下的那次 launch。

★ 这条否定结论同时**推翻了 §3.8 早期「每节点 ~7 µs、融掉节点就线性变快」的推断**：
chain4 / shift6 / stage1 的收益来自去掉**重复计算**（4 次 fp16 往返转换、sigmoid/exp 分离、
权重被读两遍），不是来自少 launch。**零权重流量的微内核不值得融**——后面再想提速只能动
「真正搬权重」的那几段（ffn key/value 已跑到 ~520 GB/s，接近 roofline），或换整体内核结构。

**⑥ 的副产品**：`ComputeBackend::seq_norm_shift` 这个原语保留了（`SEQ_NORMSHIFT=1` 打开），
它是后续「大融合」（把 norm 与投影一级一起做）的必要积木，也是这条否定结论的复现实验入口。

**★ 顺带修掉一个会静默算错的隐患**：`prefill_graph_replay` 用的是「最后一次捕获的 key」，
而 `prefill_graph_valid(k)` 按 key 查表 ⇒ 同一进程里交替用两个形状（如 T=3 的 prefill 与
T=4 的验证 pass）时会重放**另一张图**（不报错，结果错）。新增
`prefill_graph_replay_keyed(key)` 并让 `forward_seq` 改用它。

**实测（int8 2.9B、CUDA、未锁频；`MTP_GEN=256`、`PREFILL_GRAPH=1`、同机交替）**

| 配置 | 验证 pass | 快照+回滚 | 投机步 | 平均接受 | **对 plain** |
|---|---:|---:|---:|---:|---:|
| §3.6 起点（K=3） | 18.5 ms | 3.3 ms | ~24 ms | 0.92 | 0.69× |
| 本轮（K=2） | **13.6 ms** | **0.65 ms** | ~18.2 ms | 1.31 | **1.26×** |
| 本轮（K=3） | 14.3 ms | 0.65 ms | ~20 ms | 1.24 | 1.05× |

**自检（都跑了）**：`mtp_rollback_selftest` 逐位一致（`max|Δstate| = 0`，540 万个数）；
新增「二次回滚」不变量——同一快照连跑两次回滚必须逐位相同（专门盯图重放，首次是捕获执行、
之后是重放）；`T=4 seq vs 解码` argmax 仍一致。

**一次被数据否决的尝试（`SEQ_STAGE1`，默认关）**：把 r/k/v + 四个一级 mid 换成
`gemv_int8_rkv_stage1_batch`（7 launch → 1 + 1 次 `to_f32`）——为此补齐了 `f16→f32`
算子（`ComputeBackend::to_f32`，CUDA 实现，Vulkan 明确 Err）。结果：
验证 pass 只快 0.7 ms（它省 launch 不省带宽），而**接受草稿数下降**（K=2：1.31 → 1.04、
K=3：1.24 → 1.10）⇒ 端到端更慢。原因是 `out_v` 的 f16 舍入进了 `dplr_seq`/`sum_rk_rk`，
与 decode 路径的 f32 v 拉开了数值差（§3.6b 那条「必须同一数值档」的反面例证）。
通路保留在 `SEQ_STAGE1=1` 后面，`to_f32` 是新算子照旧可用。

**下一步的速度账（实测归因，取代 §3.6 的猜测）**：
- 验证 pass 与 decode 读的是**同一份 3.3 GB 权重**：decode 10.5 ms ⇒ 314 GB/s；
  验证 13.8 ms ⇒ **239 GB/s**。所以剩下的 3.3 ms 不是「多读」，而是**有效带宽只有 decode 的 76%**
  ——23 个节点/层（decode 8 个）每个都要一次独立 DRAM 扫、彼此串行，没有跨节点的访存重叠。
- 单次 launch 实测约 **3 µs**（`SEQ_STAGE1=1` 去掉 224 次 launch 只省 0.7 ms），所以「再融 4 个节点」
  这类小手术每次只值 0.1–0.4 ms；要再拿 1.5 ms 必须把每层节点数压到 ~12 个
  （`norm+y_norm+sum_rk_rk+`、cmix 三步、两遍 `to_f16_triple` 合成一遍），且要保证数值逐位可复现。
- drafter 链 2.5 ms（K=2）已接近其格式下限：每深度要读 ~214 MB **f16** drafter 权重
  （fproj 39 + proj 26 + q/g 26 + o 13 + ffn 104 MB）+ 全词表 head 168 MB。**裁 head 到 draft 词表
  只在 int8 上便宜**（行连续，可直接按行切）；int6 的 N-major 平面是「4 行共享 1 个 u32」，
  按行切要字节级重打包，收益 0.5–0.7 ms —— 记为待办而非本轮项。
⇒ 结论：**1.5× 的门槛不在「权重流量」也不在「launch 数」的单点，而在 seq 路径的节点数与
各节点带宽效率**；不重写成 decode 那种深度融合，单点优化已进入 0.3 ms 量级。

**★ 踩到的两个坑（都值得记）**：
1. **`s_w` 的 shared 数组必须按 `s_ring` 的实际上界分配**：真 sidecar 的 `window=512`
   ⇒ `s_ring = 515`，第一版按默认值写成 64，直接越界写 shared ⇒ **Vulkan 0xC0000005**。
   现在按 1024 分配 + host 侧硬卡。
2. **`pos`/`theta` 不能走 spec 常量**（每 token 变 ⇒ pipeline 缓存按 token 膨胀），
   改走 params 块里的 `uvec2`（低 32 位 pos、高 32 位 theta 位模式）——与仓库既有
   「uniform 块只放 buffer_reference」的约定不同，但避免了一个新 buffer 的常驻管理。

**当前卡点（未解决）**：`BACKEND=vulkan` 跑 `mtp_probe` 时，drafter 的**第一个**算子
`gather_row_device_f16(emb_ln, b.e, tok, c)` 触发 0xC0000005。已排除的项：
- 不是批量提交错位：用「每算子前 `synchronize()`」定位到它本身（前一步是 `download`，队列已空）；
- drafter 自己的张量没问题：紧邻的 `fill_zeros(b.e, c)` + sync 正常；
- **`tok` 的 host 镜像与 device 缓冲不一致**：`store_token_host` 只写 host 镜像，
  `download(tok)` 读回的是 **0**（device 侧仍是初值）——而 `gather_row_device_f16` 读的正是
  `tok.host.address`，所以「token 值」本身不是 0，但**镜像与 device 分裂**这件事说明
  Vulkan 侧这条 host-visible 路径在 drafter 上下文里与主 decode 路径并不等价。

⇒ **下一步排查方向**：`Runtime::gather_row_device_f16` 依赖 `tok.host.address`（host 镜像 BDA）+
`host_write_to_shader_barrier`；主 decode 路径同一序列正常，差别只在「`b.e` 是 `create_tensor`
新建、没有 `upload` 过的张量」。建议先把 dst 换成一块已 upload 过的张量做对照，
或改走 `upload_u32` + device 地址（`gather_row_device_u32` 若存在）绕开 host 镜像。

**结论**：**Vulkan 上的 MTP 目前不可用**（CUDA 侧一切正常且已验收）。原语与 shader 已入库
（编译产物 `assets/shaders/spv/mtp_*.spv` 已提交），下一步只需在这个既有算子上继续定位。

### 3.9b 继续排查：三个真 bug 修掉了，还剩一个 ⚠️

**（1）drafter 的所有 kernel 序列都没圈 `begin/end_batch`**（已修）
Vulkan 的 `record_kernel` 要求命令缓冲处于 recording 状态；drafter 的
`mtp_draft` / `mtp_reset` / `mtp_head_check` / `spec_step` 的补提交循环都是直接发 kernel，
于是命令落在**未开始记录**的缓冲上（验证层报 `VUID-vkCmdBindDescriptorSets-commandBuffer-recording`），
最终 `0xC0000005`。修法：这四处各圈一次 `begin_batch()/end_batch()`（CUDA 上二者是 no-op）
——修完崩溃从「访问违例」变成可读的 `ERROR_DEVICE_LOST`，定位能力提升一个档次。

**（2）Vulkan 设备从未请求核心 feature `shaderInt64`**（已修）
`DeviceCreateInfo` 只挂了 `PhysicalDeviceFeatures2` 链（Vulkan11/12/13 特性），**核心
`PhysicalDeviceFeatures` 一个都没开**。而 `gemv_f32io*` / `gemv_rkv_stage1` 这 10 个已提交的
shader **声明了 `Int64` capability**（glslang 为 buffer_reference 的 64 位寻址生成）⇒
shader module 非法、管线无效、dispatch 直接 `ERROR_DEVICE_LOST`。
之前没踩到是因为**主解码/prefill 在 Vulkan 上从不走这些 fp16 GEMV**（int8 模型全走 int8 内核），
而 MTP drafter 全程是 fp16 GEMV。修法：`app.rs` 按设备上报能力请求 `shaderInt64`
（不支持时不请求，避免 create_device 失败）。修完验证层的 `Int64 capability` 报错消失。

**（3）`take_f32` 先摘表导致原地算子报错**（已修）
`elementwise_add(x0, dep, x0)` 是原地调用，而 Vulkan 的 `take_f32` 把张量从表里移除 ⇒
先 take 再 get 输入会 `unknown tensor`。改成**先取输入、再取输出**（`Arc` 克隆保活）；
`elementwise_lerp` / `copy_part` 同改。

**剩余卡点**：修完上面三条后仍是 `ERROR_DEVICE_LOST`。已排除的（都是本轮实测）：
- **fp16 GEMV 本身没问题**：单独在 drafter 上下文里跑 `proj`(m=2560,k=5120) / `q`(m=2048,k=2560) /
  `ffn_key`(m=10240,k=2560) 三种形状，各自 `begin_batch → gemv_f16 → end_batch → synchronize`
  全部 OK；`kernel_bench KB_OPS=f16`（m=65536,k=2560）也是 512 GB/s 正常。
  ⇒ 上一轮「ABLATE=gemv_f32io 崩溃消失」是**假线索**（那次消失是因为撞上了当时还没修的
  原地算子 bug，提前返回了 Rust 错误）；修完原地 bug 后 ablate 它照样 device lost。
- 单个 ablate `mtp_attn` / `mtp_rms_rope` / `mtp_kv_write` / `gather_row_f16` 也都仍崩
  ⇒ **不是单一算子**，更可能是「drafter 独有的 buffer 组合 + 某些边界」。
- 形状上界已在 host 侧硬卡（`s_ring ≤ 1024`、`d ≤ 128`）。

⇒ **下一步建议**（留给下一轮）：按 `block()` 的顺序**逐段截断**（不是逐核 ablate）：
在 `block()` 里加 `MTP_STOP_AFTER=n`，跑 n=1,2,3… 找到第一个让 device lost 的**步号**，
再对那一步前后的 buffer（尤其 `b.cat2`/`b.cat3` 这类拼接缓冲与 `b.hh`/`b.kx` 的尺寸）
做一次 host 侧断言。另可试 `VK_VALIDATION=1` + `VK_LAYER_ENABLES=VALIDATION_CHECK_SHADERS` 拿到更细的信息。

## 3.10 int6 小批量 split-K 落地与 MTP 投机步成本账（2026-11-08 夜）

### 结论先行

1. **通用 int6 N-major GEMV 的 split-K 已验证、并落成默认 `I6NM_KSPLIT=3`**：T=4 验证 pass
   22.9 → **17.0 ms（1.35×）**，批量解码同向不翻号。
2. **融合 r/k/v+mid 核的 split-K 无收益**（0.9 %，两轮方向相反）⇒ 实现保留但**默认关**
   （`I6NM_RKV_SPLIT=1` 开），理由见下。
3. **1.5× 的门槛仍卡在验证 pass**：投机步 ≈ verify(T=4) + drafter + 回滚，其中 verify 占 80 %。
   按「一份权重 2.48 GB @ ~300 GB/s = 8.3 ms」+ head/低秩的账，T=4 的地板 ≈ 11.8 ms。

### 通用 split-K（`gemv_int6nm_split`）

几何 `grid=(ceil(M/32), ksplit)`、block = `W*32`，每块覆盖**全部 slot** 的一段 K，
部分和布局 `[split][batch][M]`，由既有 `imma_gemm_reduce` 按 split 升序确定性归约。
仅 `vec1 && batch ∈ 2..=8` 分流，batch=1 保持原内核。

| 配置（int6n 2.9B、C=2560、W=16、同进程交替） | T=4 因果 seq pass |
|---|---:|
| `I6NM_KSPLIT=1` | 22.9 ms |
| `I6NM_KSPLIT=3` | **17.0 ms** |

为什么是 3：`C/64 = 40` 个 k-chunk 被 16 warp 轮转 ⇒ 每 warp 只 2~3 个 chunk，
而块数 `C/32 = 80` 填不满 68 个 SM ⇒ split 是**唯一**的加块手段。

**门禁**：`int6_nmajor_kernels_match_cpu` 扩到 split=3 / batch=5 / 四个 op / m=132
（非均分尾段 1/1/2 + 尾列 + 跨槽步长同时被钉住），相对误差 < 2e-3。

### RKV 融合核的 split-K：实测无收益，默认关

实现方式：前 `I6NM_KSPLIT` 个 `blockIdx.y` 行块算三路量化投影的一段 K（复用同一块 shared
reduction，三链依次），`blockIdx.y == KSPLIT` 那块算四条 mid（权重载一次、对全部 slot 复用），
再用一个归约核一次写 r/k（f32）与 v（f16）。CPU 对拍 `int6_nmajor_rkv_split_matches_cpu`
（C=256、batch=5、vm/wm/am/gm=3/5/2/4、split=3）通过。

**A/B（两轮交替，T=4 seq pass）**：开 `18.51 / 16.96` vs 关 `18.07 / 17.10` ⇒ 差 0.15 ms（0.9 %），
且**两轮方向相反**。

原因：这个核本来就把**一份权重喂全部 slot**（流量 = 1×），split 只加并发块数、不减一个字节；
而 80 列块 × 16 warp 早已填满 68 个 SM ⇒ 没有可拿的带宽/占用率缺口。
与「单投影」的通用 GEMV 不是同一回事（后者块内 k-chunk 更少、块数才是瓶颈）。

### 3.10 补：投机步的账算平了 —— 6.8 ms「黑洞」是节流假象，真瓶颈是低秩段

探针新增 `T=K+1 验证 pass（带存档）` 计数（`examples/mtp_probe.rs`，与 `infer_seq` **同进程紧邻**
配对，避免热态漂移）。一次干净运行（decode 8.32 ms、接受 1.91 草稿/步）：

| 项 | 数值 |
|---|---:|
| 单 token decode | 8.32 ms |
| T=4 `infer_seq`（不带存档） | 16.01 ms |
| **T=4 验证 pass（带存档）** | **17.20 ms**（存档 + 逐位置读回只占 **1.18 ms**） |
| drafter 链 3 深度 | 3.04 ms |
| 实测投机步 | 21.7 ms / 步（45 步），2.91 token/步 ⇒ **1.07×** |

正向推算：若接受数回到 2.13（前面几轮的口径）⇒ 3.13 token / 21.7 ms ⇒ **1.29×**。

⇒ 默认 3 维持不变；「按块数自适应」这条设想作废，不必再试。


### 3.10 补二：MTP 加速真正生效（1.12×，三轮复测同向）+ 四个假设的否决记录

**结果**（int6n 2.9B、CUDA、`MTP_GEN=128`、`MTP_REPS=16`、同进程 plain/spec A/B、三轮）：

| 轮 | plain | spec | 倍数 | 接受 |
|---|---:|---:|---:|---:|
| 1 | 1047.7 ms（122.2 tok/s） | 939.9 ms（136.2 tok/s） | **1.11×** | 1.91 草稿/步 |
| 2 | 1038.1 ms（123.3 tok/s） | 937.9 ms（136.5 tok/s） | **1.11×** | 1.91 |
| 3 | 1065.1 ms（120.2 tok/s） | 941.2 ms（136.0 tok/s） | **1.13×** | 1.91 |

轨迹：**0.85× → 1.01×（split-K）→ 1.12×（mid1 融合 + 免回滚）**。
一步 20.8 ms 产出 2.84 token，其中验证 pass 16.3（78 %）、drafter 3.0、快照/回滚/提交 1.5。

### 本轮保留的三个改动

1. **低秩 mid1 四链融合核**（`lowrank_mid1`，trait + CUDA）：一次 dispatch 换掉 4 次 cuBLAS 小 GEMM。
   `lowrank+fuse_ka` 0.150 → 0.090 ms/层，验证 pass **17.2 → 16.3 ms**（配对同向两轮）。
   ★ 第一版标量载入（2 B/lane ⇒ 每 warp 64 B）只拿到 0.6 ms；改 `uint4`（8 half/lane ⇒ 512 B/warp）
   后才把核本身从 ~60 µs 压到 17.7 µs（`PROF_CUDA_KERNEL`）。**乘积必须先转 f32 再乘**，
   不能用 `__hmul2`——否则 mid 多一次 fp16 舍入，改掉数值档。
2. **全接受时跳过回滚**：`j == k` 时验证后的状态就是目标状态。
3. **int6 split-K 默认 3**（上一节）。

### 四个被数据否掉的假设（都留了开关，默认关）

| 假设 | 实测 | 结论 |
|---|---|---|
| 融合 r/k/v 核也开 split-K | 18.51/16.96 vs 18.07/17.10（0.9 %，两轮反向） | 无收益；该核本就「一份权重喂全部 slot」 |
| vec4（1 lane 4 列，摊薄 x 载入） | 验证 16.3 → **21.9**，decode 8.3 → 10.8 | 否掉（块数掉 4 倍） |
| `I6NM_WARPS=8` | 归一化（verify/decode）1.82–1.87 vs 1.88–1.96 | 无优势，噪声假象 |
| r/k/v+mid 全融合 + **f32 v**（`SEQ_STAGE1=2`） | 16.5 → **19.7~21.4** | 否掉 |

最后一条最值得记：它的**数值问题本轮已解决**（`RKV_F32V` 让 v 直接落 f32，不再有那次把
接受率从 1.31 打回 1.04 的 fp16 舍入），也加了 split-K、还把三条链拆到 `blockIdx.z` 恢复并行度
（串行版更慢 2 ms）。仍慢 3~5 ms ⇒ 病因是**同一个函数里塞了 r/k/v 与 mid 两条路径，
寄存器需求取并集、占用率下降**，"少 3 次 launch" 抵不过这一项。想再走这条路必须拆成两个
kernel（各自 `__launch_bounds__`），而不是加宏。

### 距 1.5× 的差

2.84 token/步 ⇒ 1.5× 需步时间 ≤ 16.2 ms ⇒ 验证 pass 要从 16.3 压到 ~12 ms。
剩下的空间只在两处：`channel_mix+ffn` 0.231 ms/层（170 GB/s，占 39 %）与
`shift+rkv_gemm` 0.135 ms/层（152 GB/s）。两者都是"23 个节点各自扫一遍 DRAM、彼此串行"
的结构问题（decode 只有 8 个节点、304 GB/s），不是单点 patch 能收的。

**交付物**：对比图表见 [`2026-11-08-MTP加速对比.html`](./2026-11-08-MTP加速对比.html)
（吞吐轨迹 / 每步成本 / 逐段带宽 / 判定表 / 口径说明）。

**门禁**：`cargo test --release` 96 通过（含 `int6_nmajor_rkv_split_matches_cpu` 的 f16 与 f32v 两档）、
`cargo fmt --all`、`cargo clippy --all-targets --release -D warnings` 零警告。

### 3.10 补三：r/k/v 三路合并被否决（错数 + 更慢）

借道 `gemv_int6_rkv_stage1_batch_f32v`（把 mid 维度全传 0、只取 r/k/v 段）把三次 `w_plain`
合成一个 dispatch（`grid.z=3` 分链 + split-K）——**两个维度都失败**：

| 指标 | 三路独立（默认） | 三路合并 |
|---|---:|---:|
| T=4 验证 pass | 16.0 / 16.2 ms | **17.7 / 18.2 ms** |
| `seq vs 解码` argmax | 一致 | **2 vs 47（错）**；`max\|Δlogit\| ≈ 2.0e1` |
| 端到端投机 | 1.10 / 1.11× | 0.58 / 0.59×（接受 1.91 → 0.56 草稿/步） |

错数的具体形态没有继续追（在错数基础上比较性能没有意义），接线已整体撤除。
**教训**：把「传 0 维借道融合核」当成复用手段要先过数值门 —— 这条路径的 CPU 对拍只覆盖了
`vm/wm/am/gm > 0` 的情形，`midtot = 0` 的边界从未被测过。

### 全轮总结：MTP 的有效区间停在 ~1.12×，再往上不是 patch 能到的

八次尝试里三次保留（split-K=3、mid1 融合核、免回滚），五次否决（RKV split、vec4、
WARPS=8、全融合 f32v、三路合并）。所有否决项都用**同进程交替**读数判定，且都留了实测数字。

剩下的 16.3 → 12 ms 缺口只在 `channel_mix+ffn`（170 GB/s）与 `shift+rkv_gemm`（152 GB/s），
而 decode 在同样的权重上跑 317 GB/s —— 差别的根源是节点数（23 vs 8）：每个节点各自扫一遍
DRAM、节点之间必然排空。**要 1.5× 必须做 decode 那种深度融合（把 norm/shift/低秩/输出
并成少数几个核），那是结构性重写，不是本轮的单点优化。**


### 3.10 补四：按「参考原项目」重查一遍 —— 结论是小 T 这条路上没有可抄的

按用户提示回头查 `参考/2026-09-21-Albatross-faster3a_2607-全流程精细对比.md` 的分派策略，
并做了两个决定性实验。

**原项目（Albatross）的做法**（`v3a_ops.cu`，见对比文档 §4.1）：

| rows | 实现 |
|---|---|
| `rows == 1` | 手写 `linear_f16_m1_splitk`（split-K + fp32 partial + 独立 reduce） |
| `rows == 2` | `linear_orig_row2_exact_f16`（线程 ∈ {64,128,256} × out_tile ∈ {1,2} 白名单特化） |
| `rows ≤ 16` | **`linear_orig_wmma16_f16`：WMMA 张量核**，`__launch_bounds__(32,8)`，1 warp 算 16×16 tile |
| `rows 8 ~ 2047` | **直接丢 cuBLAS**（`cublasGemmEx` + TENSOR_OP），不写自研 GEMM |

我们的 T=4 正落在「rows ≤ 16 → WMMA」这一档。于是做了 **实验 A：换 fp16 同基座模型**
（`rwkv7-g1l-2.9b-20261031.st`，5.89 GB，走现有 GEMM/cuBLAS 路径）：

| 模型 | decode | T=4 验证 pass | verify/decode |
|---|---:|---:|---:|
| **int6（2.48 GB，GEMV）** | 8.25–8.65 ms | **16.3–16.4 ms** | 1.89–1.98 |
| fp16（5.89 GB，GEMM/cuBLAS） | 12.63 ms | **29.21 ms** | **2.31** |

⇒ **fp16 + 张量核在 T=4 上慢 1.8 倍**，比值也更差。原因是流量：int6 读 0.75 B/权重，
fp16 读 2 B/权重（2.67×）；小 T 时权重只读一遍，张量核的「一行 load 服务 16 行」优势
换不回 2.67 倍流量。且原项目用 WMMA 对 rows=4 也要把 M 补到 16（4× 计算浪费）。
**所以「让 int6 也走张量核」在数学上不成立**（dequant 后流量 4.75 B/w，是 GEMV 的 6.3 倍）。

**实验 B：按块数自适应 split-K**（`i6nm_ksplit_for`，目标块数 300 / 480）：
验证 pass 18.7 / 18.6 ms，而固定 3 是 16.4 / 16.7 ms ⇒ **负优化**。
`ffn.key`（m=10240 已有 320 列块）被降到 split=1 反而更慢 —— 说明 split 的收益不只来自块数，
还来自「每块的 K 跨度变短、权重段更连续」。函数保留但 `#[allow(dead_code)]`，默认不用。

**实验 C：块大小 4 / 32 warps**：verify 18.2–18.7 / 19.4 ms vs 16 warps 的 16.4–17.4 ms。
⚠️ W=4 的端到端读数看着更好（1.25–1.36×），那是**分母被拖慢**的假象（decode 8.65 → 11.6 ms）；
用 verify/decode 比值一照就露馅（W=4 是 1.56 但两边都慢）。W=16 维持。

### 结论：小 T 验证的账已经算到底

| 尝试 | 结果 |
|---|---|
| split-K 段数 1 / 4 / 自适应 | 3 最优 |
| vec1 / vec4 | 1 最优 |
| warps 4 / 8 / 16 / 32 | 16 最优 |
| r/k/v 融合（3 种形态） | 无收益或错数 |
| fp16 权重 + 张量核（学原项目） | 慢 1.8× |
| 三路合并（学原项目 `blockIdx.z`） | 错数 + 更慢 |

verify 停在 16.3 ms = 2.48 GB / **152 GB/s**（decode 单流 300 GB/s），而按 2.84 token/步、
1.5× 需要 verify ≤ 12 ms（223 GB/s）。**剩下的差距是节点数（23 vs 8）：每个节点各自扫一遍
DRAM、节点之间必然排空。要跨过去只能做 decode 那种深度融合（把 norm/shift/低秩/输出/FFN
压到 ~12 个节点），属于结构性重写。**


### 3.11 ★ 对标上游 MTP 原项目（OpenMOSE/RWKV-Infer-Next）——找到 1.8× 的真实来源

上游已 clone 到 `参考/RWKV-Infer-Next`（`.gitignore` 排除，获取方式写在注释里）。
这才是 MTP 的**权威规范与参照实现**（此前误按 Albatross 的推理分派策略查了一轮，见 §3.10 补四）。

**上游公开性能（`docs/mtp.md` §benchmark，官方 sidecar、单卡、B=32）**

| 模型 | 无 MTP | 有 MTP | 加速 |
|---|---:|---:|---:|
| 2.9B | 240 / 230 tok/s | **436 / 443** | **1.8–1.9×** |
| 7.2B | 119 / 116 | 243 / 249 | 2.0–2.1× |
| 13.3B | 64 / 63 | 143 / 143 | 2.2–2.3× |

**差异不在投机环结构**（我们的 `spec_step` 与上游 `SpecGraphs._body` 一一对应：起草→验证→
采样→回滚→提交，全图内、一次 sync 取结果），**在两处**：

1. **他们的 int6 走 tensor core，我们走 SIMT GEMV。**
   `kernels/int6_gemm.py` 的 `_w6a16` 有两条收缩形式，分派常量写得很明确：
   ```python
   RED_MAX_M = 1   # reduction form only at M=1: measured, the dot form wins from M=2
   DOT_MIN_M = 16
   ```
   `USE_DOT` 分支把 6-bit 解包成**精确的 fp16/bf16**（`w0 = ((la & 15) | ((hh & 3) << 4)) - 32`，
   |e−32| ≤ 32，6-bit 整数在 fp16 尾数内**无损**），然后 4 个子块各做一次 `tl.dot`，
   **scale 在最后一次性乘**（`acc += p * s[None, :]`，不是每权重乘）。
   我们的 `i6nm_dot` 是「每权重先乘 scale、f32 标量 FMA」——这正是 b=4 时只有 152 GB/s
   而 b=1 有 300 GB/s 的原因（每字节权重的 FMA/载入指令数是 4 倍，**发射受限**）。
2. **他们的验证是 128 行**（B=32 slot × T=4）。`forward_verify(toks, B, ...)` 把
   `(B, K+1)` reshape 成 `B*T` 行做一次前向 ⇒ 权重读一遍服务 128 行。
   我们 B=1 时只有 4 行 ⇒ 权重读一遍只服务 4 行。**这是 1.8× 与 1.12× 的结构性差距**：
   在小 batch 下，MTP 的收益天然被「验证行数 ÷ 权重流量」绑死。

**下一步（按收益排序，都已具可行性）**

1. **int6 → fp16 精确解包 + mma（`mma.sync.m16n8k8.f32.f16.f16.f32`）**，把 M 补到 16。
   仓库里已有 `mma_m16n8k8_f32acc` 的用法（`gemv_lowrank_chain4_batch` 的 fp16 档），
   但那是「每 mma 只取 d[0]」的点积用法；要拿真收益必须写 **tile 版**
   （A = 行×16k、B = 16k×8 列、C = 16×8，4 个子块累加、scale 最后乘）。
   预期：verify 从 16.3 → ~8.3 ms（带宽打满 300 GB/s）⇒ 步 12.8 ms ⇒ **1.8×**。
2. **服务端跨请求合并验证**（对齐上游 B=32）：多个请求的投机步合成一个大 B 的 verify，
   权重读一遍服务 `4×B` 行。这是把 1.8× 复制到我们多请求场景的正道，属服务端改造。
3. 单请求场景的兜底：提高 `MAX_BATCH` 之外的「投机批」概念（同请求内多 slot 并行不起来，
   因为 RWKV 状态是单序列的）⇒ 只有 1 可行。



### 3.12 int6 张量核档落地：b ≥ 8 提速 13%，b = 4 无用（与上游分派一致）

**实现**（`GEMV_INT6NM_MMA_SRC` + `gemv_int6nm_mma_launch`）：
`mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32`，一个 warp 覆盖 **32 列**（4 个 8 列 tile），
打包平面按 `u32` **合并载入 smem**（32 行 lo + 16 行 hi）再解包，chunk 内 4 个 16-k 子块各 2 次 mma，
**scale 在 chunk 末按 D 的列乘**（不逐权重乘，与上游 `int6_gemm.py` 一致）。

**踩到的两个坑**（都记下来）：

1. **scale 必须按 D 的列取，不是 B fragment 的列**。`m16n8k8` 里 B 的 n 由 `gid=lane>>2` 覆盖、
   D 的列由 `2·tig+i` 覆盖 —— 两者是不同的 lane 分布。第一版按 `gid` 取 scale，对拍误差
   **0.98**（整条链错）；改成 D 的列后降到 0.0217。
2. **第一版「warp 8 列 + 逐字节跨行读」比 SIMT 还慢 1.7 倍**（27.8 vs 16.2 ms）：
   每条事务只用 32 B sector 的 1/4。改成「warp 32 列 + u32 合并载入 smem」后 → 17.9 ms。

**实测分档（同进程交替）**

| 场景 | SIMT（`I6NM_MMA=0`） | 张量核 | 判定 |
|---|---:|---:|---|
| **批量解码 B=8**（`batch_decode_bench`，256 token/槽） | 244.0 / 238.6 tok/s | **275.8 / 273.5 tok/s（+13%）** | ✅ 默认走张量核 |
| MTP 投机 T=4（M=4）验证 pass | **15.9 ms** | 17.9 ms | ❌ 留 SIMT |

B=8 两轮的 token 流 `sum=0xd082c7 xor=0x7015` **逐位相同** ⇒ 数值档没有影响 argmax。

**为什么 T=4 反而变慢**：mma 的 M 只有 16 行，T=4 补到 16 相当于 **75% 空转**，再加解包成本；
而 B=8 能填一半，收益才出来。所以按 batch 分档：`8..=16` 走张量核，`≤7` 留 SIMT。

**★ 与两个上游的交叉印证**（这次是对的参照物）：

- `参考/third_party/rwkv_lightning_cuda/quant/gemmv/README_w4a16.md` 明确写着
  **「M≤16 保留原寄存器解包路径」**、Tensor Core 只给 `16×64/32×64/64×64` 的 M>16 对齐路径
  —— 与我们刚测出的分档点完全一致。它还给了 decode 快路径的口径：「一次读取 8 个权重和 8 个激活」。
- `参考/RWKV-Infer-Next`（MTP 原项目）的 `RED_MAX_M = 1` 是**服务端 B=32** 口径；
  它的 1.8–1.9× 正是建立在 128 行验证上。**单请求 B=1、T=4 的结构上限就在 1.2× 附近。**

### 结论：单请求 MTP 已到结构上限，1.5× 必须靠合批

| 项 | 现状 |
|---|---|
| 单请求 MTP（B=1, K=3） | **1.10–1.16×**（verify 15.9–16.4 ms，接受 1.91 草稿/步） |
| 批量解码（B=8） | 张量核档 **+13%**（244 → 276 tok/s）已默认启用 |
| 要达到 1.5× | 需要 verify ≤ 12 ms；单请求 M=T=4 时 mma 的 16 行填不满、SIMT 已到 156 GB/s 的布局上限 |
| 唯一现实路径 | **服务端跨请求合并 verify**（对齐上游 B=32）：多请求投机步合成 B×4 行的一次前向 |

## 3.14 ★ 单流再攻一轮：先修「量尺」，再修「档位」（2026-11-09）

用户要求「单流起码 1.5×，争取原项目 1.8×」。这一轮的第一件事不是改代码，而是**发现之前
的端到端读数不可信**，所以先造一把能用的尺，再谈优化。

### 3.14.1 为什么旧读数不可信（本轮最重要的发现）

本机无法锁频、也无法读显存时钟（无 `nvidia-smi`）。此前所有「1.11× / 0.89× / 0.31×」都是
**跨进程**或**先量完 plain 再量 spec** 的顺序读数，实测同一份代码在相邻两次进程里：
decode 8.5 ms ↔ 23 ms、drafter 3.4 ms ↔ 12.8 ms（**3.7 倍**），而比值被节流状态系统性
扭曲（同样代码 verify/decode 读到 1.49 与 2.36 两个值）。

**新尺**（`examples/mtp_probe.rs`，两个开关）：

| 开关 | 做什么 | 为什么可信 |
|---|---|---|
| `MTP_AB_E2E=1` | 每轮从同一 prompt 重新播种，`plain` 与 `spec` **紧邻**各跑 n 个 token，取逐轮比值的 min/中位 | 两臂相隔 <1 s，节流对两臂同向；重复 4 轮的比值离散度 ≤0.02 |
| `MTP_AB_INT6=1` | 每轮**轮转顺序**遍历各档（simt / mma w2 / w4 / 不同 ks），每档紧邻量 decode + verify | 既消顺序偏置，又用同一轮的 decode 做分母（分母随节流同向漂移） |

⚠️ `MTP_AB_INT6` 必须配 `PREFILL_GRAPH=0`：验证路径的图**按 T 收键**，切档不会重捕获 ⇒
所有臂都重放第一个臂的图，差别被整段抹掉（本轮先踩了一次，数字全是假的）。

### 3.14.2 本轮落地（默认开）

| 改动 | 依据（同进程交替） |
|---|---|
| **int6 张量核档门槛 5 → 4**（`I6NM_MMA_MINB`，T=4 也走 mma） | T=4 时 verify/decode：SIMT **1.63×** vs mma **1.49×**（无图、8 轮轮转，两轮同向）⇒ mma 快 9 % |
| **mma 支持 `op==1`（mul_add）**：门控在 A fragment 里乘进激活 | 验证路径 6 个主矩阵全部同档，不再给 att.output 一条 SIMT 尾巴 |
| **mma 的 split-K 自适应**（`I6NM_MMA_BLOCKS`，默认补块数到 512）+ `I6NM_MMA_WARPS`（默认 2） | 旧默认 ks=3 时 m=2560 只有 40 个 64 线程块（占用率 ~5 %）；现 20 块 × ks13 |
| ★ **MTP 验证路径默认上图**（`PREFILL_GRAPH=0` 可关） | E2E：**0.80–0.85× → 0.92×**（一次 replay 替掉 ~700 个 launch） |
| ★ 图 key 混入 `State::uid()`（验证图 + 回滚图 + 快照图） | 图里烘焙的是状态张量指针；同一实例换第二份 State 会静默算错（同 self-loop 那条 2026-10-10 的坑） |

### 3.14.3 被数据否掉的：tile 版 mma（解包一次落 smem）

按「v1 的解包没有在 16 行之间摊薄」的推断写了 v2：一个 lane 负责一列，`lo/hi` 各读 1 字节，
解包成 fp16 落 smem `[列][k]`，mma 阶段每个 fragment 只剩 1 次 smem u32 载入 + 1 次 mma
（预算 ~6.3 指令/权重 vs v1 ~8.75）。CPU 对拍四档全过（容差同 v1），**但实测慢 40–60 %**：

| 档 | verify/decode（同进程轮转，无图） |
|---|---:|
| SIMT | 1.63 |
| mma v1 w2/512 | **1.49** |
| mma v2 w2/512 | 2.40 |
| mma v2 w4/1024 | 2.22 |

病灶判断：v1 的打包平面用 **u32 载入**（一条 lane 吃 4 列，12 条载入/块/列块），v2 为了
「一列一 lane」改成 **48 条 1 字节载入**——载入指令数 ×4，抵掉了解包那一半的节省。代码已删
（本文件即结论）。**教训：int6 的取数形态（u32 合载）比解包位置更贵，动它之前先数载入指令。**

### 3.14.4 现状与到 1.5× 的差

- 节流态下的读数不可用，本轮可信的只有一个**未节流**样本（decode 8.5 ms）：K=3 的
  E2E = **0.92×**（改前 0.80–0.85×），verify 20.6 ms（图 + mma），drafter 3.4 ms，
  快照/回滚/提交 ~1.9 ms ⇒ 一步 26 ms 产 2.61 token。
- 与 §3.10 的 1.11× 差在 verify：那次读到 17.2 ms，本轮同一份 SIMT 代码读到 22.6 ms
  （decode 几乎不变）⇒ 该项大概率是显存时钟档位差异，须在**同一进程**里复测才能定论。
- 到 1.5× 需要的账（K=3、接受 1.9 草稿/步）：步 ≤ 16.5 ms ⇒ verify ≤ 11 ms（= 1.3× decode）；
  drafter 还要从 3.4 → 1.3 ms。缺口两块：
  1. **verify 的 GEMV 只跑到 195 GB/s**（decode 单流 292）：v2 这条路已否，剩下的是
     「u32 合载 + 在 16 行间摊薄解包」的第三条写法（smem 存 `[k][列]`，B fragment 两读一 pack）；
  2. **drafter 全程 fp16 权重 + 全词表 head**：3.4 ms 里 378 MB 是 head（每深度读一遍
     65536 行、实际只用 16384 行）⇒ int6 化 + draft 词表子表可砍到 ~1.3 ms。

### 3.14.5 机器空闲后的复测（K 扫描）—— ⚠️ 本节结论已被 §3.14.6 修正（当时 T=4 误走 mma）

上一节的数据是在**用户在跑游戏**时采的（decode 39–56 ms = 正常值的 5–6 倍）。机器空闲后
（decode 8.1–9.0 ms）用同一套同进程交替 E2E 复测，结论变了两处：

| K | 接受草稿/步 | verify (T) | drafter | **E2E** |
|---:|---:|---:|---:|---:|
| 3 | 1.44 | 19.0 ms (4) | 3.08 ms | **0.84×** |
| 4 | 1.95 | 20.3 ms (5) | 4.16 ms | 0.95× |
| 5 | 2.35 | 20.4 ms (6) | 5.06 ms | **0.97×** |
| 6 | 2.42 | 20.9 ms (7) | 5.80 ms | 0.96× |
| 7 | 2.53 | 21.1 ms (8) | 6.64 ms | 0.91× |

**两条关键事实**：

1. **验证 pass 的成本几乎与 T 无关**（T=4→8 只从 19.0 → 21.1 ms，斜率 0.53 ms/行）：mma 档把

   `w2/256` 20.17、`w4/512` 19.80、`w2/512` 20.64、`w4/1024` 20.88 ⇒ 现默认（w2/512）落后 2–4 %。

**到 1.5× 的账（K=5、空闲态实测口径，一步 ~29.7 ms 产 3.35 token）**：

| 项 | 现状 | 要到 1.5× |
|---|---:|---:|
| verify | 20.4 ms（2.48 GB ⇒ 122 GB/s） | ≤ 13 ms（GEMV 打到 decode 的 288 GB/s 是 8.6 ms，再加 ~4 ms 的 T 线性节点） |
| drafter | 5.1 ms（fp16 权重 + 每深度读一遍全词表 head） | ≤ 2.2 ms（int6 化 + draft 词表 16384 行子表） |
| 回滚/提交/读回 | ~4 ms | ~3 ms |
| 合计 | 8.9 ms/token ⇒ **0.97×** | 5.7 ms/token ⇒ **1.5×** |

⇒ 决定性的仍是**验证 pass 的 GEMV 有效带宽**（122 → 220 GB/s 就够）；drafter 那 2.9 ms 是
低风险的确定性收益，但不是决定项。

### 3.14.6 ★ 复盘「是不是越来越慢」—— 没有回归，是两处配置读错

用户问「现在是越来越慢了吗」。用**同进程 + 空闲态**逐个环节对账（decode 7.7–8.1 ms 全程一致）：

| 环节 | §3.10（当时） | 复跑 e564543 源码 | 修复后 HEAD |
|---|---:|---:|---:|
| 单 token decode | 8.32 | **7.94** | 8.1 |
| drafter 链 3 深度 | 3.04 | **2.89** | 3.03 |
| T=4 验证 pass（SIMT，无图） | 17.20 | **16.99** | 15.94（带图） |

⇒ **三个环节都没有退化**，历史读数可复现。之前的「0.84×」由两个错误叠加而成：

1. **↑ 我把 int6 张量核门槛从 5 改成了 4**（依据是节流态读数）。空闲态同进程轮转 A/B 否掉它：

   | T | SIMT | mma | 判定 |
   |---:|---:|---:|---|
   | 4 | **16.66 ms** | 18.50 ms | T=4 留 SIMT（mma 慢 11 %） |
   | 5 | 22.13 ms | **19.23 ms** | T=5 起换 mma（快 13 %） |
   | 6 | 23.81 ms | **19.80 ms** | 快 17 % |

   已改回 `I6NM_MMA_MINB=5`，并把档位表写进函数文档。**T=4 的 16 行只填 4 行，解包摊不薄，
   张量核在这个形状上永远赢不了 SIMT**——这条与 §3.12 的原结论一致，中间那次「翻案」是错的。
2. **`I6NM_MMA_MINB=99` 被过滤条件吃掉后回落成默认值**，于是「SIMT 臂」其实跑的 mma，
   表现为「verify 17 → 19.5 = 变慢」。现在 env 值不过滤，`>16` 即明确「永不启用」。

顺带：mma 的 block 宽度取 **4 warp**（T=5/6：19.23/19.80 vs w2 的 19.61/20.64），已改默认。

**最终档位与端到端（空闲态，同进程交替 3 轮 × 64 token）**：

| K | 接受的草稿/步 | verify | drafter | E2E |
|---:|---:|---:|---:|---:|
| **3** | 1.95 | **15.94 ms**（SIMT + 图） | 3.03 ms | **1.14×** |
| 4 | 2.10 | 20.25 ms（mma） | 4.20 ms | 1.00× |
| 5 | 2.53 | 20.96 ms（mma） | 5.46 ms | 1.03× |

⇒ §3.14.5 的「K=5 最好」是建立在「T=4 走 mma」这个错误前提上的，**作废**；`MTP_K` 默认回到 3。

**到 1.5× 的下一刀（唯一现实路径）**：T=4 的 SIMT 批量 GEMV 只跑到 **155 GB/s**（decode 单流
288）。指令账：b=4 时每 4 个权重是「3 次逐字节载入 + 12 整数 + 4 cvt + 4 scale + **16 次 x 载入**
+ 16 FMA = 55 条」，b=1 是 31 条，55/31 = 1.77 ≈ 288/155 = 1.86，**发射受限**。四项 x 载入
（k = jj, 16+jj, 32+jj, 48+jj）不相邻，所以要用 `float4` 必须先把激活按
`perm(k) = 4·(k%16) + k/16` 重排进一份 x 副本（在 `seq_shift6` / `to_f16_six` 这两个已有的
生产节点里顺带产出，零新增 launch）。预期 55 → 43 条 ⇒ verify 16.0 → 12.5 ms；
再叠加 drafter int6 + draft 词表子表（3.0 → 1.3 ms）⇒ 一步 15.3 ms / 2.95 token = 5.2 ms/token
⇒ **1.56×**。

### 3.14.7 验证 pass 的两条提速路都被否掉（x 重排 + ksplit 重扫）

目标是「验证 pass 从 16.7 降到 ~12 ms」。按指令账（b=4 时每 4 个权重 55 条指令、其中 16 条是
x 载入；b=1 是 31 条）推断「把 x 载入压成 `float4` 能拿 1.28×」。做法：新增
`x_perm6`（把激活按 `dst[64c+4·(k%16)+k/16] = src[k]` 重排一份副本，一次 dispatch 处理 6 对）
+ `w_perm`（读重排副本的批量 GEMV），把它接到验证路径的 6 个主矩阵上。**实测失败**：

| 项 | XPERM=0 | XPERM=1 |
|---|---:|---:|
| T=4 验证 pass | 18.37 ms | 20.05 ms |
| 端到端（3 轮 × 64 token） | **1.13×** | 1.03× |
| 数值 | argmax 2、max\|Δlogit\|=3.6552 | **逐位相同**（重排是精确索引） |

拆开看：4 次 `x_perm6` launcher/层 = 128 次/整 pass，在这台 Windows 上**每次 ~20 µs**
（`cuLaunchKernel` 的宿主开销），合计 2.5 ms；而 `float4` 只省下 **0.8 ms**。
⇒ **「55→43 条指令」这条账在真实 GPU 上不成立**（那个核不是 x 载入发射受限），
且「一次 dispatch 处理 6 对」并不改变「每个生产节点各要一次小拷贝」的事实。代码已整体撤除。

同时重扫 split-K（空闲态、端到端）：`KSPLIT=3` **17.71 ms（1.13×）** / 2 → 20.69（0.96×）/
1 → 28.91（0.95×）⇒ **默认 3 仍然最优**（此前的结论在空闲态依然成立）。

**结论（第三次修正后的判断）**：验证 pass 的 155 GB/s 不是「指令数」或「split 粒度」造成的，
而是这条小批量取数路径的**内存访问形态**本身（32 B 行片段 + 16 个串行节点，decode 单流则是
一条连续流）。同一份权重在 b=1 上能跑到 288 GB/s、在 b=4 上只有 155 GB/s，而三次「按指令账
优化」的实验（tile mma、x 重排、split 粒度）**全部否掉**。⇒ 单请求 1.5× 在 2080 Ti + int6 +
本架构上**已无可挖的低垂果实**；要再上台阶只有两条路：① 服务端跨请求合批验证（上游 1.8× 的
真实来源，B×4 行一次前向）；② drafter 侧确定性收益（int6 + draft 词表子表，3.0 → ~1.3 ms，
端到端 1.14 → ~1.24 倍）。

### 3.14.8 drafter int6 化实测（默认关）+ 与上游差距的定量拆解

**做了什么**：`mtp/drafter.rs` 新增 `up_i6`（把 sidecar 的 f32 权重在加载期量化成 int6 N-major
平面，打包规则与 `i6nm_dot` 逐字节一致）+ `Lin::{F16,I6}` 分派，9 个 Linear 全部可切 int6
（`MTP_DRAFTER_I6=1` 开，默认关）。

**实测（空闲态、同进程）**：

| 项 | fp16（默认） | int6 |
|---|---:|---:|
| drafter 链 3 深度 | 3.26 ms | **2.93 ms**（−10 %） |
| 接受草稿/步 | 1.95 | 1.83 |
| 端到端 | **1.13×** | 1.11× |

权重字节数减半却只省 0.33 ms ⇒ drafter 的矩阵窄（m=512/2048/2560，k=2560，b=1），
`gemv_int6nm` 在这个形状上的效率远低于 `gemv_f16`（块数只有 16~80）。而 int6 的草稿略差
（1.95 → 1.83）把省下的 0.33 ms 吃掉。⇒ **默认关**，等 head 子表那一半一起做时再评估。

#### 与上游 1.8× 的差距到底在哪（全部用两边的公开/实测数对齐）

| 项 | 上游 2.9B int6（单卡 16 GB） | 我们（2080 Ti 11 GB） | 差 |
|---|---:|---:|---|
| 单 token decode | 4.17 ms（240 tok/s） | **8.1 ms** | **1.9×** |
| 验证 pass（T=4） | ≈8 ms（1.94 × decode） | 16.7 ms（2.06 × decode） | 2.1× |
| 每验证行的成本 | 2.0 ms/行 | 4.2 ms/行 | 2.1× |
| 接受草稿/步 | ≈2.5–3.5（1.8–1.9× 反推） | 1.95 | 1.5× |
| drafter 每步 | ≈1.0 ms（int6 68 MB/深度 + head 仅 16384 行 int8） | 3.0 ms（fp16 + 全词表 head） | 3× |
| 每步总耗时 | ≈10–11 ms / 3.5 token | 21 ms / 2.95 token | — |

三个结论：

1. **不是「同一件事他们做成了我们没做成」，而是我们的单 token 路径本身就慢 1.9×**
   （4.17 vs 8.1 ms）。验证 pass 的比值两边几乎一样（1.94 vs 2.06），我们差的绝对量是跟着
   decode 一起放大的。**比率上的真正差距只有两处**：接受数（1.95 vs ~3.0）与 drafter
   （0.37 vs 0.15 个 decode 步）。
2. 上游的 1.8× 反推需要 `tokens/step ÷ (verify + drafter 比值)` = 3.5 ÷ 2.09 = 1.67，
   再叠加图内采样/单次同步拿到 1.8。我们 2.95 ÷ 2.43 = **1.21**（实测 1.14，差在回滚/读回）。
3. 所以**要 1.5× 只有两条路**：① 接受数从 1.95 提到 3.0（=换/重训 sidecar，不在本仓库范围）；
   ② drafter 从 0.37 → 0.15（int6 + 16384 行 head 子表；本轮 int6 只兑现三分之一）。
   验证 pass 的 4.2 → 2.0 ms/行 需要**编译式整图**（上游 `RWKV_COMPILE=1` + Triton 融合核），
   即把 23 个节点压到 decode 那种 8 节点 —— 那是重写，不是调参；本机三次「按指令账优化」
   已全部被实测否掉（§3.14.3、§3.14.7）。

### 3.14.9 ★ head 子表落地：drafter 3.27 → 2.03 ms，端到端 1.13× → 1.20×

**问题**：head 是 `[vocab, C]` 量化矩阵（本模型 **int8**，65536×2560 = 168 MB），drafter 每步在
**每个深度**读一遍，而实际只用 `draft_vocab[:16384]` 这 16384 行 ⇒ 白读 3/4（每步 ~504 MB）。

**做法**（两个小内核 + 一处映射）：
1. `rwkv_i8_gather_rows` / `rwkv_i6_gather_rows`：按行号表把 3 个/2 个平面摘成子表
   （int8 的 idx 在 CUDA 上是**行主序** `[m][k/4]`——组主序只给 Vulkan，见
   `int8_idx_to_group_major`；第一版按组主序写，接受率直接掉到 0.00，是这个坑）。
2. `rwkv_map_index`：子表 argmax 得到的是**子表下标**，用 1 个线程 `tok = map[idx]` 映射回
   真实 token id（`idx`/`out` 是 f32 缓冲，按位重解释）。
3. `build_head_sub` 在 `enable_mtp` 时一次性建表；后端/模型不支持时返回 `None`，自动退回
   「全词表 + 掩码」，行为与之前逐位一致。子表命中时连掩码那次 256 KB 读写也省了。

**实测（空闲态）**：

| 项 | 改前 | 改后 |
|---|---:|---:|
| drafter 链 3 深度 | 3.27 ms | **2.03 ms**（−38 %） |
| 每深度 head 流量 | 168 MB | **31.5 MB** |
| 接受草稿/步 | 1.95 | **1.95**（逐位等价） |
| 接受长度（63 步） | 3.063 | 3.063 |
| 端到端 | 1.13× | **1.20×** |

**为什么数值完全不变**：子表只是把「argmax 在全词表上、其余位置掩成 −1e30」换成「argmax 在
这 16384 行上」——被比较的 16384 个值逐位相同，取 max 的结果与顺序无关。

**累计**：单流 MTP 1.14× → **1.20×**（这一步纯 drafter 侧，无风险、无数值影响）。

### 3.14.10 验证 pass 的三处「省 launch」优化：落地了，但收益只有 ~1 %（2026-11-09）

按 §3.14.7/3.14.9 的逐核归因（`PROF_CUDA_KERNEL`）挑出三处「纯开销」节点，逐项落地并逐项 A/B。
**结论先说**：三处都留下了（都是客观减工作量、零风险），但合计只值 0.1–0.4 ms（16.7 ms 的 1–2 %），
**远低于归因表预测的 3.4 ms**。原因见下面「归因为什么骗人」。

**① `SEQ_NORMSUM`（默认开）：`norm(y)` + `sum_rk_rk` 合成一个内核**
两者都按 (token, head) 分块、都读写 `sb.y_norm`，网格形状本来就同构（`rows×h`），
新核 `rwkv_norm_sum_rk_rk` 一次算完 mean/var + `sum(r*k_mod*r_k)` 再做一次归一化写出，
省掉 `y_norm` 的一遍读+一遍写与一个串行节点。非 CUDA 后端走默认实现（两次调用）。

**② `SEQ_COPY2`（默认开）：两层 token-shift 状态回写合成一次 launch**
`tmix_x` / `cmix_x` 的同名回写各自只搬 10 KB、31 µs/次（延迟受限），原先是每层 2 发。
新核 `rwkv_copy_token2` 单核双写，并把 `tmix_x` 的写出**移到本层 cmix shift 之后**
（那里同样已过读取点，且中间没有任何节点读 `tmix_x` ⇒ 无竞态）。

> 附带结论：`seq_shift6` 里那个 `state_out` 参数（把第 7 发并进 shift 核）**不能用**——
> block 0 读旧 state、block t−1 写新 state，同一 launch 内是实打实的跨块竞态。

**③ `LR2F16`（默认开）：低秩第二级 `w2/a2/v2/g2` 换 fp16 副本**
这四张 `[C, mid]` 矩阵的 fp16 副本**本来就在显存里**（prefill GEMM 用），换过去等于把
chain4 唯一的权重流量砍半、且不新增内存。解码与验证**必须同档**（共用一个门），
实现方式是「按张量 dtype 分派」：`gemv_lowrank_chain4` / `gemv_lowrank_chain4_f32`
各自多一个 `*_f16w` 核，权重 stride 由 `round_up(mid,64)` 推出（fp16 副本是补零的 padded 布局）。

| 项 | 预测（PROF 归因） | 实测（同进程轮转交替） |
|---|---:|---:|
| ① norm+sum 合一 | −1.0 ~ −1.7 ms | **−0.07 ~ −0.11 ms** |
| ② copy×2 → ×1 | −2.0 ms | **−0.1 ~ −0.2 ms**（+/− 噪声同号） |
| ③ 第二级 f16 | −0.4 ~ −0.5 ms | **−0.03 ms**（解码 −0.03 ~ −0.15） |
| 合计 | −3.4 ms ⇒ 13.3 ms | **≈ 16.6 ms（1–2 %）** |

接受率：E2E 平均接受 **1.83 草稿/步**（fp32 第二级档同为 1.83；63 步接受长度 3.063 不变）。

#### 归因为什么骗人（本轮最重要的方法论修正）

`PROF_CUDA_KERNEL` 会给每个内核插 `cuEvent` 对，**它使图捕获失效** ⇒ 量到的是「eager 模式
每发 31 µs」的 copy_token，而验证 pass 真正跑的是**图捕获档**：64 发 copy_token 在图里
只值 ~0.2 ms（≈3.5 µs/节点）。同一个数在两种模式下差 10 倍，逐核归因表若不当心就会把
「eager 的 launch 税」当成可回收的墙钟。

#### 新仪器：`MTP_AB_VERIFY=<门名>` + 图代次（这次留下来的东西）

原先的进程内 A/B 只能测「不改变 dispatch 序列」的门（`MTP_AB_INT6` 当年被迫配
`PREFILL_GRAPH=0`，否则重放上一臂捕获的图）。这次把**图代次**混进图 key
（`gpu_model::set_graph_arm_epoch`，key 高 4 位），仪表每次切臂 bump 一次 ⇒ 两个臂各自
捕获、各自重放，**图捕获档下也能做同进程 A/B**。同时报**最小值**与**中位数**（最小值抗热节流、
中位数抗顺序偏置），并紧邻量 16 步解码。

**仪器分辨率自检**（用一个什么都不影响的门跑同一套流程）：最小 Δ +0.12 ms、中位 Δ −0.17 ms
⇒ 分辨率 **~0.2 ms**。所以上面三处「−0.03 / −0.07」这类读数只能判「无回归」，不能判收益。

#### 所以单流还差什么

16.6 ms 里 6 个主 GEMV 的权重流量 ~7.1 ms（267 GB/s，已近打满）、剩 ~9 ms 是「4 行 × 32 层」
的算术与小核延迟。**再往下不是「少 launch」能到的**——三处合并一共只值 1–2 %，
继续在同一层里抠节点是零收益方向；要么动 GEMV 之外的数值档（风险已记账），要么走合批。

### 3.14.11 GEMV 之外的数值档：已经到底了（2026-11-09）

按上节的结论先试「GEMV 之外的数值档」。**结论：这条路上已经没有可回收的量**，
真正浪费的是两个微内核的**取数方式**（不是精度），改完也不到本机仪器的分辨率。

#### 先量「时间随 T 怎么长」——比逐核归因可靠

`mtp_probe` 在 K=1/2/3/5 下的因果 seq pass（同进程、8 次取均值）：

| T | seq pass | 相对 T=1 的增量 |
|---:|---:|---:|
| 2 | 11.34 ms | — |
| 3 | 13.38 ms | +2.04 |
| 4 | 16.74 ms | +3.40 |
| 6 | 18.83 ms | +5.45 |

线性拟合：**verify ≈ 7.6 ms（固定）+ 1.87 ms/token**。固定段 ≈ 每 pass 2.0 GB 权重流量
（63.4 MB/层 × 32 + head 168 MB）/ 270 GB/s = 7.5 ms ⇒ **固定段就是权重流量，一分不多**；
边际段是批量 GEMV 的**算术**（SIMT + int6 解包，实测约 1.3 TOPS 有效）。

#### 逐核消融（`ABLATE`，图捕获档，读数=移除上界）

| 内核 | 消融收益 | 它的流量下限 | 判读 |
|---|---:|---:|---|
| `gemv_lowrank_chain4_f32_f16w`（第二级） | 1.16–1.50 ms | 47 MB ≈ 0.17 ms | 取数方式问题 |
| `lowrank_mid1_w4`（一级四链） | 0.84–0.91 ms | 94 MB ≈ 0.35 ms | 权重被读 T 遍 |
| `dplr_seq_s16`（WKV 状态） | 0.46 ms | 168 MB ≈ 0.62 ms | **已到顶**（f16 + 带宽满） |
| `imma_gemm_batch …m65536`（head） | 0.41 ms | 168 MB ≈ 0.62 ms | **已到顶**（int8，309 GB/s） |

⚠️ 消融读数是**上界**：缺席的内核让下游读到陈旧值，部分下游会变快（§batch 段早有记录）。

#### 数值档盘点（全都已经是最低可行档）

- WKV 状态 `tmix_rnn`：f16（`WKV_STATE_F16` 默认开，2026-09-22 就翻了默认）
- head：int8，实测 309 GB/s ≈ roofline ⇒ 换 int6 最多省 0.15 ms（不值得引入新数值档）
- 低秩第二级 `w2/a2/v2/g2`：本轮已换 f16 副本（§3.14.10 ③）
- 低秩一级 `w1/a1/v1/g1`、mid、`y/y_norm` 等激活：f16/f32 混合，流量都在几十 MB 量级
- 剩余可动的只有 **主 GEMV 的权重位宽**（int6 → int4）与**合批**——即 §3.14.10 说的两条路

#### 本轮实际改了什么（结构性修正，收益在噪声下）

1. `lowrank_mid1`：旧写法「外层 batch、内层 k」⇒ 同一权重行被读 **T 遍**（T=4 时 4 倍流量）。
   改成「外层 k 载权重、内层 batch 累加」（`MID1_MAXB=8` 个独立累加器），权重行只读一遍；
   向量化（16 B/lane）与求和顺序保持不变 ⇒ 数值逐位不变。
2. `gemv_lowrank_chain4_f32_f16w` / `gemv_lowrank_chain4_f16w`：旧写法是 **2 B/lane** 的标量 half
   载入（warp 64 B/迭代 = 半个 sector）⇒ 实测仅 ~40 GB/s。改成 8 half（`uint4`）+ 2×`float4`
   激活一条 lane，**解码与验证同步改成同一累加顺序**（保证两档一致）。
   注意：累加顺序变了 ⇒ `max|Δlogit|` 3.6204 → 3.6266（可忽略），接受长度 3.063、E2E 接受 1.83 不变。

**实测（同进程 vs 上节）**：验证 pass 16.94 ms（改前 17.04）、seq pass 16.64（改前 16.25）、
解码 8.40（改前 8.15）——**全在 ±0.7 ms 的跨进程噪声里**。这两处只能算「按结构少读了 3–4 倍
权重」，收益被固定段的带宽上限盖住；要判它的净效果需要单核隔离基准（`kernel_bench` 尚未覆盖
chain4/mid1），已记为待补。

### 3.15 ★ 合批：先量「批量投机值不值」，再修批量路径的真病灶（2026-11-09）

#### 3.15.1 批量投机在现有内核上**不赚**

`forward_seq_batch_padded`（prefill 档）在 B=32 下量「投机验证形状」（每槽 T 行一次因果 pass）：

| T | 1 | 2 | 4 | 8 | 16 |
|---|---:|---:|---:|---:|---:|
| ms/步 | 645.6 | 697.8 | 688.9 | 656.3 | 680.0 |

**与 T 无关** ⇒ 全部是 prefill 档的固定成本：`m_pad` 补到 256 行、每层 dequant 成 fp16 再
GEMM。32 槽 × 4 行 = 128 行有效却按 256 行算，而 32 个单流 verify 只要 32×16.6 = 531 ms
⇒ **合批验证用 prefill 档比单流还贵**。

批量解码阶梯（同进程自循环，int6n 原档）也说明行成本近乎线性：B=1 9.6 / B=4 5.05 / B=8 3.78 /
B=16 3.23 / B=32 4.02 ms（每槽每 token）。投机每 token 要 1.38 行（4 行换 2.9 token）⇒
按线性外推，批量投机在现有内核上**净亏**。**所以合批的前置条件是先把批量路径的行成本压下去**。

#### 3.15.2 真病灶：int6 模型在宽批完全没有张量核

`ABLATE`（图捕获档，B=16，基线 311.2 tok/s）逐核读数：

| 消融内核 | tok/s | 占比 |
|---|---:|---:|
| `gemv_int6nm_rkv_w16`（r/k/v 投影） | **605.1** | **48 %** |
| `ffn_value_gemm_b64n64k64_g` | 442.1 | 21 % |
| `gemv_int6nm_mma_w4_s7_g0` | 351.4 | 6 % |
| `lowrank_gemm_*_s2` / `_s1` | 342 / 333 | 3 % / 3 % |
| head / 其余小核 | ≈311（无变化） | 0 % |

而**同参数 int8 模型**在同口径下是 **1027.7（B=16）/ 1743.9（B=32）tok/s** —— 大 3.3–7 倍。
差别只在一条：int8 的 r/k/v 与 ffn/out 走 `quant_x_i8` + `gemm_imma`（W8A8 张量核），
而 **int6 文件没有 int8 键 ⇒ 这些矩阵只能落回 SIMT GEMV**（`gemm_imma` 只吃 W8A8）。

#### 3.15.3 做法：加载期把 int6 重量化成 int8 副本，只给批量档用

`requant_i6_to_i8`（`ModelBuilder::build_layer`）：`dequant_int6` → 按 128 分组 min-max
非对称量化（`idx*scale+zero`，与 `unpack_int8_sz` 同约定）→ 上传 idx/sz。覆盖
`att.receptance/key/value` + `ffn.key/value` + `att.output`。
门：`I6_RKV_I8=0` 关 r/k/v 副本、`I6_FFN_I8=0` 关 ffn/out 副本、`RKV_I8_MINB=8` 定批量档下限。
**单流（batch < 8，含 MTP 投机步）仍走 int6 GEMV** —— `wq()` 优先 int6，MTP 的 17.3 ms / 1.95
接受是那一条档上量的，不换。代价：显存 +2.5 GB（模型加载后 4537 → **7012 MiB**），
加载期多约 3 s（6.3 亿权重走一遍 f32 往返）。

#### 3.15.4 实测（int6n 2.9B，同参数同会话）

r/k/v + ffn 两组副本（`att.output` 见下一条）：

| B | 改前 | 改后 | int8 参考 |
|---:|---:|---:|---:|
| 8 | 264.6 | **549.1**（×2.07） | — |
| 16 | 311.2 | **960.5**（×3.09） | 1027.7 |
| 32 | 248.9 | **1076.0**（×4.32） | 1743.9 |

单流不受影响：decode 116–118 tok/s、MTP 验证 pass 17.3 ms、E2E 1.16×、接受 1.95。
`cargo test --release` 96 项全绿。

**正确性证据（逐层隔离）**：三组副本各自单独开、B=16 贪心 16 token 落盘对拍：

| 开的组 | 结果 |
|---|---|
| 仅 r/k/v | **健康**，且与「全关（int6 档）」**逐 token 完全相同** |
| 仅 ffn key/value | **健康**，与 int6 档逐 token 相同 |
| 仅 `att.output` | ❌ 退化成周期性单/双 token |

#### 3.15.5 ⚠️ `att.output` 副本已知有问题（默认关，`I6_OUT_I8=1` 才建）

同一条 `requant_i6_to_i8` 喂 r/k/v / ffn 都正常，只有 `att.output` 坏。**已排除的假设（都有实测）**：

| 假设 | 判别实验 | 结论 |
|---|---|---|
| 宿主侧重量化算错 | layer 0 自检：max\|Δ\|=1.6e-3、max\|w\|=0.53、无 NaN、q 用满 0..255 | 排除 |
| `gemm_imma` 的 **op=1（累加）** 本身坏了 | int8 模型 + `VK_IMMA_OPS=out`（只让 out 走 imma，其余 SIMT） | **健康**，且 token 与 int6 档逐位相同 ⇒ 排除 |
| **prefill** 的 out 分支有问题 | 副本 + B=4（decode 的 rkv/ffn 仍 int6） | 仍崩 ⇒ 不是 prefill（prefill 的 out 走 `wq()`→int6，根本没用副本） |
| 编码约定不对（有符号 / 对称） | 三种约定（无符号+零点 / 有符号+中点 / 对称+128 偏置）逐一轮 | 全崩 ⇒ 排除 |
| 磁盘零点分布与官方不同 | 读官方 int8 文件的 `att.output.int8_sz`：scale 8e-5..3.3e-3、**zero −0.60..−0.009（全部非零）**、字节 0..255 | 与我的编码同类 ⇒ 排除 |
| 只是"分配了张量"的副作用 | `I6_OUT_BUILD_ONLY=1`（建完丢弃，不进 Gpulayer） | **健康**（与 int6 控制臂逐 token 相同）⇒ 确实是"被消费"才坏 |
| 是我的 int8 权重"算成了另一颗矩阵" | 把**官方 int8 文件的同名张量**塞进同一位置（`I6_OUT_FROM=<int8 模型>`） | **健康**，且与 int6 控制臂 **32/32 逐 token 相同** |
| 我的权重与官方差得离谱 | 宿主侧逐元素对拍（`I6_R8_STATS=1` + `I6_OUT_FROM`） | **不成立**：六颗矩阵（含已证明正确的 r/k/v、ffn）与官方的 `max\|Δ\|` **都约 47 % 满量程、约 76 % 元素相对差 >1 %** —— 这是 int6 与 int8 两次独立量化的正常噪声 |
| 该矩阵平面排布是 M-major | `I6_OUT_MMAJOR=1` 按 M-major 解 | 仍崩 ⇒ 排除 |

⇒ **当前圈定**：op=1/门控/prefill/编码/布局/零点分布**全部排除**；官方 int8 张量放进同一位置
完全正常，我这份在数值噪声内等价却崩。

**字节级对比（按 §3.15.5 的第一步做的）**：把两份 `att.output` 的 `idx`/`sz` 前 4 KB dump 出来比
（`I6_R8_STATS=1` + `I6_OUT_FROM`，落 `target/r8_{mine,off}_{idx,sz}.bin`）：

```
idx: mine c1 84 84 cf 9e 61 9a 77 …    off c6 89 88 cf a0 67 9c 7c …
sz : mine 6a 0a d5 a6 5e 0b 74 a7 …    off 8b 0a 28 a7 2e 0a 90 a7 …
```

**逐字节都"接近但不等"**（差值就是量化噪声量级），`sz` 的 f16 指数位完全对齐
⇒ 打包/排布（u32 词序、scale 低 16 位 / zero 高 16 位、行主序）**确认一致**。

⇒ 于是嫌疑收到最后一层：**不是张量内容，而是那块显存被写坏**。
依据：官方那份是在我的副本**之后**才分配的（地址不同）、且 `I6_OUT_BUILD_ONLY=1`（同一块显存
也被分配但不用）完全健康 ⇒ 只有"被 out 的 GEMM 当权重读"时才坏，指向**写越界/别名**
（某个内核对 6.55 MB 附近的区域越界写，或 `imma_partial`/`gemm_epilogue` 的尺寸口径）。

**换地址实验（`I6_OUT_PAD=1`，在副本之前多分配一块同尺寸缓冲）⇒ 仍崩**，即不是简单地址/别名。

**行为特征（重要线索）**：B=4 崩溃时的 token 流是 `12231, 16749, 12231, 16749, …` ——
**第一个 token 是对的**（与 int6 控制臂一致），之后进入 **2-周期**。这不像权重坏（那样第一个
token 就会错），更像**每步之间有状态被复用/多加**：例如 out 这条 GEMM 读到了上一步的
`y_norm`/`g`，或残差/门控被重复施加一次。下一步应沿这条查：
`bb.y_norm`/`bb.g` 在 imma 分支里是否被 `bb.xb_q`/`bb.xb_aux` 或 `bb.x` 别名覆盖，
以及 `gemm_imma(op=1)` 在 B≤4 时是否走 `gemv_int8_mul_add` 的 SIMT 分支（两条都要对拍）。
