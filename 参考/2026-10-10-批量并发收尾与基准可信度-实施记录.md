# 批量并发收尾与基准可信度 —— 实施记录（2026-10-10）

范围：本轮是「升级 rwkv-rsv 全面匹配新增的并发能力」的**残差补丁轮**。并发内核本身在上一轮已完成，
本轮只做八项收尾（改进项 1–8），并遵守两条口径约束：

- **rwkv-rsv 保持纯库**：不建引擎侧调度器、不加 HTTP 壳、不新增并发内核；请求合并留在消费方
  （client 会话池 / mytown 引擎）。
- **每项都要有真测试**：没有可复现证据的结论不写进 README。

## 2. 真实 bug：Vulkan `copy_range` 的同张量别名

`VulkanBackend::copy_range` 原先**先** `tensors.remove(&dst)` **再** `tensors.get(&src)`。
而它的主要用途就是同一张量内的区间拷贝（`State::slot_move` / 广播传的是
`copy_range(t, from*stride, t, to*stride, stride)`，`src == dst`）——于是自己把 src 查没了：
**Vulkan 上所有槽位拷贝恒定报 `copy_range: unknown src`**，即该路径此前从未工作过。

- 抓到它的方式：为改进项 6 新写的广播用例（`device_slot_broadcast_matches_host_roundtrip`）。
  在此之前 `slot_move` 只在 CUDA 上被真实调用过（CUDA 的 `lens` 是另一张表，无此症状）。
- 修法：在 `remove(dst)` **之前**取好 src 的只读句柄（F32/F16 两支），dtype 不匹配分支
  仍然把 dst 放回映射表再报错。

**教训**：一条「只有另一个后端会走」的路径，等于没有路径。跨后端等价性用例（而不是单后端冒烟）
才是抓这类 bug 的最低成本手段。

## 3. 真实 bug（测试层）：lib 单测并行时的进程级 GPU 竞争

现象（**先复现再修**）：`cargo test --release --lib` 并行跑随机挂 3–4 个用例，且**挂的集合每轮不同**
（实测两次分别挂 `{record_tokens, sample_batch, rkv_stage1_batch}` 与
`{quant_x_i8, record_tokens, lowrank_gemm, rkv_stage1_batch}`）；
把任一用例单独跑 → 绿；`--test-threads=1` 串行 → 77 passed。

根因不在 kernel 数值，而在**实例契约**：`CUDA_CTX_LOCK` 只串行化 `CudaBackend::new()` 的创建期，
文档写明多实例「同线程顺序使用」；但除此之外还有**进程级共享**的设备资源
（cuBLAS 句柄是 `OnceLock`、sampler 的 pinned 暂存区按行号寻址）。
lib 单测默认多线程，多个设备测试同时开跑就是并发使用多个实例 ⇒ 读到别人的数据。

修法：`crate::backend::gpu_test_guard()` 进程级串行锁，所有碰设备的用例先取锁
（CUDA 39 处 + Vulkan/Runtime 13 处）。加锁后并行两轮均 77 passed。

**为什么不改成「支持并发多实例」**：那是产品级设计变更（每实例独立 cuBLAS 句柄 + 独立 pinned 区），
收益只是让单测并行快 7 秒，与风险不成比例。契约写清楚 + 测试守契约即可。

## 4. 随机采样不可复现：实测确认，不修

`stochastic_reproducibility_repro` 以 `#[ignore]` 留在 CI 里作复现用例。实测（2026-10-10）：
`top_k > 0` 时同一路径两次跑逐 token 不同；`TOPK=8 STEP=1` 下自循环 `0xc91fa/0x6a92`
对逐步 `0xd12aa/0x33e8`，**第 0 步相同、第 ≥1 步起分叉**。
更关键：`SKIP_GRAPH=1` 时**同一路径跨进程也不复现** ⇒ 不是两条路径的口径差，而是归约顺序本身未钉死。
采样把罕见的单点翻转放大成后续序列分叉，故这不是正确性缺陷，但任何「随机采样可复现」的说法都不成立。
CI 断言因此只覆盖贪心（`top_k = 1`）。要恢复这条用例，先要把归约顺序钉成确定的。

## 5. 长度桶预热：代价是**搬走**的，不是省下的（改进项 8 与立项假设不同处）

立项假设：「首个请求在新长度桶上慢，预热可以消除」。实现后测出三点事实：

1. **`SeqBuffers` 是单槽缓存**（`seq_bufs` 只存一份，`take_seq_bufs` 在 `bt` 变化时
   `clear_cache()` + 释放重分配 45 个 `[bt, ·]` 缓冲）。所以预热列表里**只有最后一个桶**留在显存，
   前面的桶会被下一次重建顶掉 ⇒ 多桶预热是白付开销。
   API 文档已把这条 ★ 约束写明；真正跨桶抖动的解法是「固定 `pad_to`」或「按桶各留一个 `GpuModel`」。
2. `warmup_len_buckets` 只把重建从「用户等的那一次」挪到「启动期的一次」，**不减少重建次数**。
   `BUCKET_BENCH=1` 量的就是这四档：冷桶首请求 / 同桶重复 / 预热成本 / 预热后首请求。
3. 结果不变性是硬判据：`warmup_buckets_do_not_change_results` 断言预热过与没预热过的
   seeds 与贪心 token 序列**逐位一致**（预热用的 `t_pad` 与真实请求同宽 ⇒ 命中同一个 `bt`）。

实测数字：见 §12（`BUCKET_BENCH=1` 四档）。

## 6. 真实 bug：Vulkan 批量 >64 掉出张量核路径（改进项 5 抓出来的断崖）

`imma_ok()` 的批宽门写死 `(1..=64).contains(&batch)`（`gemm_imma.comp` 构建期只编 `IM_NST`
1/2/4/8 四档 ⇒ 一个波 8·NST=64 槽，当时没实现多波），于是 **B>64 静默回落 SIMT**。

**这条门到底关掉了什么（先说结论，因为很容易写错）**：`imma_ok` 有五个调用点——
head（gpu_model.rs:1620）、rkv（:2276-2277）、out（:2520）、key（:2567-2569）、val（:2623-2625）。
而 `imma_op_on(op)` 默认 `op != "rkv"` ⇒ **rkv 的张量核变体本来就不走**，所以掉出这道的代价
**不是**「rkv 回落 SIMT」，而是 **head/out/key/val 四条张量核 GEMM 一起关掉**，
其中 head = vocab 65536×2560，是单层最大的一块矩阵乘 ⇒ 吞吐直接塌到与 B=1 同量级的平台。
（早期草稿里那句「SIMT 的权重按批宽重复读 `batch/BGRP` 遍」描述的是 rkv 融合核的读放大，
与这道门的实际受害者不是同一批算子，已按调用点核对后订正。）

先复现再修（`bench/probe-imma.jsonl`，同会话、`SEGS=4 PAD_TO=512 NTOK=32 WARMUP=1`，
`rwkv7-3B-int8.st`）：

| 批宽 | 门控 | tok/s | 归因 |
|---:|---|---:|---|
| 64 | `VK_IMMA=1` | **934.4** | 张量核路径（波内） |
| 64 | `VK_IMMA=0` | 436.5 | SIMT 基线（同批宽对照） |
| 80 | 默认（旧门在） | 430.7 | 落 SIMT ⇒ 与 436.5 同档 |
| 96 | 默认（旧门在） | 429.2 | 同上 |
| 128 | `VK_IMMA=0` | 422.8 | SIMT 基线（强制） |

3 轮交错 A/B（17:26 那次会话，仍是旧门，`bench/ab-20261010-172659-90152.jsonl`）给出的
B=128 **428.4** / B=256 **426.2** tok/s 正是这个
平台 ⇒ **断崖 100% 由这条门造成**，不是驱动、不是显存、不是 kernel 数值。

修法与两处连带坑：

1. **门放开机**：`imma_ok` 的批宽条件改成 `batch >= 1`。多波本身**早就写好了**——
   `grid.z = batch.div_ceil(8·NST)`，shader 里装载用 `s0base + (i>>5) < BATCH` 守卫、
   写回用 `slot >= BATCH continue` 守卫。只是旧门让它从未被执行过。
2. **`WorkBuffers` 的 `bsz.min(64)`**（三处）：放开门后 B=128 立刻 `ERROR_DEVICE_LOST`。
   量化内核按**全局槽号**写满 `bsz` 行，`min(64)` 让第二波直接越界写。`xb_q` / `xb_aux`
   改为按 `bsz` 实配。
3. **`imma_partial` 不能按 `bsz` 配**：split-K 部分和是 `ks·batch·C`，而 `imma_ksplit`
   在 `ks·batch·m > cap` 时会主动缩小 `ks` ⇒ 固定 `8·64·max(C,FH)`（约 21 MiB）就够；
   按 `bsz` 预留会在 B=256 多要 63 MiB，那张卡此时已贴显存上限（实测 `ERROR_OUT_OF_DEVICE_MEMORY`）。

放开后（`bench/probe-after.jsonl`，同参数；**注意这是另一次进程运行，不是交错 A/B**，
所以只用来证明「断崖消失」，绝对值以 §13 的交错表为准）：B=96 **939.5**、B=128 **976.5**、
B=256 **996.9** tok/s —— 三档都回到与 B=64（934.4）同一量级，平台消失。
prefill 同样受益（同一次运行内的对照）：B=96 **33.3 s**（旧门/`VK_IMMA=1` 那次 46.5 s）、
B=128 **45.4 s**（`VK_IMMA=0` 的 SIMT 参照 49.1 s）。B=256 修前的 97.4 s 取自 17:26 那次交错会话，
**与 85.9 s 不同会话**，所以这一对只能读成「量级下降」，不能当同会话倍率引用（同会话数字见 §13）。

**一条有用的旁证**：修前修后同一批宽的 `prefill_seeds_sum` 完全相同（B=96 两侧都是
`0x14b0cb`、B=128 都是 `0x1b9664`），而 `batch_tokens_sum` 变了 ——
说明改动只换了 **decode 的数值路径**（SIMT → 张量核），prefill 一行没动。
指纹变化是路径切换的必然结果，不是回归。

守门用例：`tests/batch_parity.rs::slots_beyond_the_first_wave_match`（72 槽 × 8 步贪心，
全槽同 prompt 同 seed，零容差断言「第二波 == 第一波」，实测 `[WAVE] 72 槽 × 8 步贪心逐位一致
（首 token 10464）`）。这类 bug 的杀伤模式是「批宽 ≤64 全对、>64 后半槽静默错」，
只有跨波边界用例能钉住，吞吐基准看不出来。

## 7. 真实 bug：CUDA self-loop 图跨 State 复用（改进项 8 的守门用例抓出来的）

`warmup_buckets_do_not_change_results` 在 CUDA 上失败、Vulkan 上通过：预热过的臂与没预热的臂
**seeds 相同**，但贪心 token 序列是对方序列**平移约 4–5 个 token** 的样子
（左臂槽 2 `[…,13006,14486,13055,10325,…]` vs 右臂 `[13006,14486,13055,10325,…]`）。

根因：CUDA 的自循环已捕获图按 `selfloop_shape_key(kind, batch, n)` 缓存，
而**图里烘焙的是 State 各张量的设备指针**。用例先建的 `State` 被释放后，同形状的第二个
`State` 拿到同一个 key，于是**静默重放前一个 State 的图**——读的仍是旧指针位置，
恰好落在新 State 的另一段偏移上 ⇒ 看起来像「序列平移」而不是崩溃。

修法（bookkeeping + 失效，而不是把 uid 塞进 key）：
`State` 新增进程级唯一 `uid`（`STATE_UID: AtomicU64`），`SelfloopBufs` 记住当前
`state_uid`，`selfloop_key_for_state()` 在发现换 State 时先 `clear_selfloop_graphs(Some(kind))`
再返回 key。三处取 key 的调用点统一改走这个方法。

- **为什么不把 uid 编进 64 位 key**：key 已经是 `(kind<<62)|(batch<<32)|n`，再挤一个单调
  计数器必然撞位（撞了就又是静默复用）。后端侧 `clear_selfloop_graphs` 按 `k>>62` 解 kind，
  语义保持稳定。
- **代价（写进 doc）**：交替使用两个同宽度 `State` 会每段重捕获一次。真实消费方不受影响——
  `build_shared()` 给每个实例私有 State，一个进程里同一形状只有一个 `State` 在跑。
- Vulkan 侧无此症状（它不捕获图，n 轮记录进同一个 buffer 一次 submit）。

这条 bug 只有「预热不该改变结果」这类**跨请求状态不变性**用例才抓得到，单请求自循环基准
永远看不到——它是本轮两个「测试写出来才发现的真 bug」之二。


## 10. 用例自己踩掉的两条口径坑（写下来是因为它们都会骗人）

1. **`forward_seq_batch_padded` 的返回值是「各槽提示词的末 token」（解码种子），不是
   next-token 预测**。改进项 4 的用例初版拿它去比单流 argmax，两后端都「失败」
   （种子 `[11098,16417]` vs 单流 next `[19137,10080]`）——差得离谱，第一反应是
   「fp16 批量 prefill 在产出垃圾」。实际是用例口径错：种子本来就该等于提示词末位。
   **判据要换成状态**：批量 prefill 之后每槽状态与单流 `state_back` **逐位一致**
   （`to_bits` 全等，两后端实测 max_abs=0）。这条比种子强得多，它才真正钉住
   「pad 行不进 state」的契约。
2. **`Result::expect_err` 要求 Ok 侧实现 `Debug`**，而 `SelfloopTicket` 没有 ⇒ 编译不过。
   改成 `match` + `Ok(_) => panic!(...)`，报错信息反而更明确（「门控失效或被绕过」）。

**方法论**：断言失败先问「参照物是不是我选错了」，再怀疑被测物。这一条本轮救了两次——
一次是把 fp16 prefill 误判成垃圾（真判据是状态），一次是 §5 里「预热改变结果」的误判
（真因是 CUDA 图跨 State 复用，见 §7）。

## 11. 改进项 5 剩下什么（把判据算清楚，别留「以后再优化」这种话）

门放开后大批量**能跑张量核了**，但吞吐不随批宽线性涨。把 §6 的读数换算成「每步时间」
（`每 tok/s ÷ 批宽 = 每步 token 数` 的倒数，decode-only 口径）：

| 批宽 | 波数 = ⌈B/64⌉ | tok/s | 每步 ms | 每步 ms ÷ 波数 |
|---:|---:|---:|---:|---:|
| 64 | 1 | 934.4 | 68.4 | 68.4 |
| 96 | 1.5 | 939.5 | 102.2 | 68.1 |
| 128 | 2 | 976.5 | 131.1 | 65.6 |
| 256 | 4 | 996.9 | 256.8 | 64.2 |

**每步耗时几乎严格正比于波数**（每波那份「常数」64–68 ms 稳定），说明每起一波就把
int8 权重**整份重读一遍**——波与波之间不共享权重。所以改进项 5 还剩两个杠杆，都不小：

1. **让一波覆盖更多槽**：`build.rs` 现在只编 `IM_NST` ∈ {1,2,4,8}（一波 ≤ 64 槽）。
   加 16/32 两档 ⇒ B=128/256 各只用一波 ⇒ 按上表的比例，每步可省 1–3 次权重整读。
   代价是 shared memory / 寄存器压力随 NST 线性涨，sm_75 的 48 KB 上限要先算一遍形状。
2. **减少每步的 dispatch 条数**（既有实测：Vulkan 每步约 43 ms 落在 dispatch **之间**，
   见 README §9「Vulkan 没有批量张量核 GEMM」条）。这条与波数无关，是另一笔固定开销。

**为什么本轮不做**：两条都要新 SPIR-V 融合 kernel 或改构建期形状档位，与本轮口径
「不新增并发内核、只做残差补丁 + 测试」冲突。判据已量化到「一波 = 64–68 ms 的权重整读」，
下一轮可以直接按这张表验收（做完 1 之后，B=128 的每步应降到 ≈ 一波的 68 ms 量级）。

## 12. 长度桶预热四档实测（改进项 8 的量化）

`BUCKET_BENCH=1 SLOTS=8 PAD_TO=512`（3B int8，同一进程内四档相邻测量，所以可比），
新桶取 `pad_to + 128 = 640`：

| 后端 | ① 冷桶首请求 | ② 同桶重复 | ③ 预热该桶的成本 | ④ 预热后首请求 | 用户可见延迟省 |
|---|---:|---:|---:|---:|---:|
| CUDA | 1809.0 ms | 942.7 ms | 1845.3 ms | 944.8 ms | **864.1 ms** |
| Vulkan | 3641.0 ms | 2493.2 ms | 3623.4 ms | 2488.8 ms | **1152.2 ms** |

三点读法：

1. **④ ≈ ②**（944.8 vs 942.7 / 2488.8 vs 2493.2）⇒ 预热确实把首请求拉到了稳态水平。
2. **③ ≈ ①**（1845.3 vs 1809.0 / 3623.4 vs 3641.0）⇒ **总代价一点没省**，只是换了谁等：
   用户等的 864/1152 ms 变成启动期等的 1845/3623 ms。这就是 §5 说的「搬走，不是省下」。
3. 差值（① - ②）就是「换一个长度就整表重建 45 个 `[bt,·]` 缓冲」的代价，两后端都是
   **约 0.9 s / 1.1 s 量级**——比很多人以为的「几 ms」大两个量级，值得在服务端启动期付掉。

**另一条与桶无关的实测**（守门用例顺带产出）：`warmup_len_buckets` 本身在 3B 上预热 2 个桶
（71 tok + 108 tok 两档）CUDA **380.2 ms**（143.1 + 237.1）、Vulkan **492.0 ms**（176.6 + 315.4）。

四条结论（都要写进 README，一条都不省略）：

1. **默认口径下 Vulkan 每一档都落后**，比值从 0.87 单调降到 0.27 ⇒ 旧 §6.1 的
   「0.98×~1.03×、128/256 反超」两列作废（那是 SIMT 对口径，见 §10 与 README「口径」段）。
2. **每格同后端 3 轮指纹逐位复现（det=Y 全 16 格）**，所以跨后端分叉只来自后端而非时序——
   这条是「指纹差异 ≠ 不可复现」的证据，也是本轮基准可信度工作的正面成果。
3. **CUDA 自身在 B=32/64 离散度 12.6% / 19.4%**：改进项 1 的论点被自己的数据坐实——
   中位数之下必须同时报 spread，否则「CUDA 比 Vulkan 快 2×」这种句子在同参数下能差出 20%。
4. **B=256 相对 B=1 只 ×40.8（CUDA）/ ×12.5（Vulkan）**，Vulkan 从 B=64 起走平 ⇒
   「一次读权重算 B 份 ⇒ 吞吐 ≈ ×B」那句理想化表述已在 `submit_sample_selfloop_batch` doc 里
   换成实测倍率，机理见 §11 的波次成本表。
