# 2026-10-11 Vulkan：B=128 残余差距的内核级归因 + mid 投影臂向量化（S27–S29）

会话日期：2026-10-11。后端：Vulkan（RTX 2080 Ti，22 GB 改版，同时是显示适配器）。
模型：`rwkv7-3B-int8.st`（C=2560 / H=40 / N=64 / ffn_hidden=10240 / vocab=65536 / L=32）。
本轮起点：第五次 Vulkan/CUDA 成对复测（README §6.1）之后，B=128/256 还剩 ≈31 个百分点。

## 1. 目的与结论摘要

目的：把「剩下的大批量差距到底压在哪些核上」量出来，而不是继续猜。

三条结论：

1. **跨后端的分核对齐用现有两把仪器做不到**——`PROF_CUDA_KERNEL` 在它唯一能用的配置下
   把 host 发射间隙算进了内核时长（§2，已登记为死仪器路径）。
2. **Vulkan 自己的 dump 自洽**，并给出新的排序：`gemm_imma` 48.6 % /
   **mid 投影臂 `gemv_int8_rkv_stage1_batch` 18.8 %** / 状态核 13.8 %（§3）。
3. **mid 臂既不是带宽受限也不是「访存指令数」受限**：加大 `GEMV_BGRP` 省权重重读端到端 **−8.6 %**
   （§4，死路）；于是改内循环本身——四路 mid 投影由标量改 **vec4 + `dot`**（指令与载入条数 ÷4），
   同会话反序 A/B 端到端 **−6 ~ −9 %**（§5，死路，已回退）。**两根都死 ⇒ §3 的「剩下就是指令
   条数/延迟」这个判据被证伪。**
4. **CUDA 侧同一个核独立量到同一条机制**（§6）：它的 mid 臂同样是标量循环、同样只用 `BGRP=8`
   （`MID_GG=2/4/8` 实测 1.39/1.98/4.66 ms vs GG=1 的 1.03 ms），而它拿到的 2.5× 来自消除
   `xsrc[BGRP]` 指针数组落 local memory——**Vulkan 侧本来就是内联寻址，没有这个坑**。
   ⇒ CUDA 的 mid 臂形状与 Vulkan 几乎一致，「差距压在 mid 臂」这个归因**待验**。
5. 下一步（§7，任务 #53）：给 Vulkan 补一把与 CUDA 同名的 **`ABLATE=csv` 按名消融尺**
   （纯 host、`src/runtime.rs:1089` 一处），用它做同口径的跨后端逐核归因。

## 2. 跨后端分核对齐：仪器不可用（死路登记）

命令（同一会话串行，脚本 `C:/tmp/prof128both.sh`）：

- Vulkan：`PROF_GPU=1 SKIP_GRAPH=1 NTOK=1 SLOTS={64,128} SEGS=1 PAD_TO=512 PREFILL_SLOTS=8 TOPK=1`
- CUDA：`PROF_CUDA_KERNEL=1 NO_SELFLOOP_GRAPH=1 NTOK=4`（同尺同门控）

CUDA 侧读数不可用的三条独立证据（B=128）：

| 证据 | 读数 |
|---|---|
| 合计远超自身墙钟 | dump `SUM 6 249 ms`，而该次运行 decode 墙钟 ≈150 ms（4 步 × ≈38 ms） ⇒ **≈41×** |
| 分次 flush 而非按步 | 日志里 `SUM` 从 368 ms 一路涨到 6 249 ms，共 30+ 行（事件池填满即 flush） |
| 排名被发射次数压住 | `to_f16` 3 568 次 / `dequant_int8` 3 072 次 / `elementwise_sigmoid` 2 032 次，占据前列 |
| 批宽不敏感 | 同一个 `fuse_ka` 在 B=128 与 B=64 的 avg 分别是 1.169 / 1.205 ms——流量随批宽翻倍的内核不可能等价 |

机制：`backend_cuda.rs` 的事件对是**非同步**的（launch 前后各记一个 event，dump 时统一取）。
开 self-loop 图时内核不执行、计时全 0（所以必须 `NO_SELFLOOP_GRAPH=1`）；一旦关掉图，decode 变成
host 发射受限，队列一空，`begin` 事件立刻完成而 kernel 要等下一次提交才开工 ⇒
**每对事件量到的是「GPU 执行 + host 提交等待」**。这不是散布，是系统性偏大且按发射次数分配。

⇒ 跨后端归因要走**消融**（`ABLATE=`，`backend_cuda.rs` 注释里 CUDA 自己也说它「比
PROF_CUDA_KERNEL 可靠」）或 `PROF_GAPS`，不要用这两个剖析器相减。登记为死仪器路径。

| `fuse_ka_dplr_norm_s16` | 6.42 | 13.8 % | 0.2008 ms/层 = 83.9 MB / 0.2008 ms = **418 GB/s = 峰值 68 %**（已在屋顶，§6.10） |
| `gemm_imma_reduce` | 2.04 | 4.4 % | |
| `sample` | 1.91 | 4.1 % | |
| `gemm_f16_f32` | 1.64 | 3.5 % | |

| `norm_lerp6_batch` | 1.21 | 2.6 % | |

注：r/k/v 在 §6.3 之后默认已走 `gemm_imma`，所以 `gemv_int8_rkv_stage1_batch` 在这里
**只剩 mid 投影臂**（`v1/w1/a1/g1`，fp32 权重，`VM=64 / WM=96 / AM=96 / GM=320`，共 576 行），
dispatch = `(VM+WM+AM+GM, ceil(batch/BGRP))` ⇒ 每 block 一行。

- 带宽：5.9 MB/层 × ceil(128/8)=16 次重读 = 94 MB/层 ÷ 0.2739 ms = **343 GB/s**（实际可用 ≈560）
- 算力：2 × 576 × 2560 × 128 = 377 MFLOP/层 ÷ 0.2739 ms = **1.37 TFLOP/s**（fp32 峰值 13.5 的 10 %）

⇒ 既不是带宽受限也不是算力受限，剩下的就是**每 lane 的访存/算术指令条数与延迟**。

## 4. S28：`GEMV_BGRP` 16/32 在 mid 臂上是否可行 —— 死路

脚本 `C:/tmp/bgrp_probe.sh`，B=128、SEGS=1、NTOK=64、同尺门控，3 轮交错（第 2 轮反序）。
绑定标记 = 三臂 decode token 校验和 **`sum=0x690fa29 xor=0x6b23` 逐位相同**（BGRP 只改
「哪些槽落在同一 workgroup」，累加顺序不变）⇒ 下面所有位移都是纯结构差异，没有数值混淆。

| 轮 | BGRP=8 | BGRP=16 | BGRP=32 |
|---|---|---|---|
| 1 | 2360.7 | 2143.9 | 2147.3 |
| 2（反序） | 2305.0 | 2107.7 | 2142.1 |
| 3 | 2226.7 | 1991.9 | 2016.4 |
| 中位 | **2305.0** | 2107.7（−8.6 %） | 2142.1（−7.1 %） |

三轮的**同轮配对**里 8 都赢，且 16 与 32 彼此几乎相等 ⇒ 位移不是随槽组宽线性变化的
「流量」效应，而是**一过 8 就出现的台阶**。合理解释：这个 env 同时被
`gemv_lowrank_chain4_batch` 消费，后者的 `float acc[ROWS][BGRP]` 在 BGRP>8 时溢出到
local memory（§6.2① 已在 B=256 量过同一台阶：8→986.9、16→890.3、24→750.7、32→718.1）。

⇒ **死路登记**：想靠加大 BGRP 省 mid 权重重读是错的方向（它本就不是带宽受限）；
`GEMV_BGRP>8` 会被 chain4 的溢出拖回去，端到端净亏 ≈9 %。

## 5. S29：mid 臂标量内循环 → vec4 + `dot`

改动（`assets/shaders/src/gemv_int8_rkv_stage1_batch.comp`，spv md5
`9addb312…` → `827ba705…`）：

- `Params` 里 `in_v1/in_w1/in_a1/in_g1`、`in_xw/in_xa/in_xg` 由 `BufF` 改 **`InX4`**
  （同一 buffer_reference，8 字节槽位，**host 侧 `params` 数组一个字都不用改**）；
- 四路内循环由 `for k in index..C step BLOCK_SIZE` 标量取 4 B，改成
  `for k4 in index..XSLOT step BLOCK_SIZE` 取 `vec4`，累加写成
  `accM[s] += dot(w4, x4)`。迭代次数 **20 → 5**，访存指令数 **÷4**，每 lane 每指令搬 16 B
  （一个 warp 连续 512 B，仍完全 coalesced）。

⚠️ **数值口径变化（不是逐位不变）**：lane 内求和从「每 4 个 k 标量连加」变成
「一次 `dot` 合并 4 个乘积」，`dot` 的分量求和顺序由实现决定 ⇒ 换默认档必须过质量门：
`cargo test --release`、对 CPU fp32 基准的 logit 偏差（DIAG）、贪心逐 token 分叉率。

A/B 设计（`C:/tmp/mid4_ab.sh`）：两臂**都**走 `VK_SPV_DIR`（同一代码路径，只差目录），
OLD=`/c/tmp/spv-old-mid4`（改动前快照）/ NEW=`assets/shaders/spv`；先各跑一个不计时进程
（spec 常量按 batch 特化，重建后第一个进程会在计时区内编译 pipeline），再 3 轮交错、第 2 轮反序；
每臂打印它实际绑定的 stage1 spv md5 作为绑定标记，同臂跨轮校验和必须一致。

结果：**NEW 慢 6–9 %，弃用**（已 `git checkout` 回退，spv md5 回到 `9addb312…`；实验源码留在
`C:/tmp/mid4-vec4-experiment.comp`）。

| 轮（顺序） | OLD 标量 tok/s | NEW vec4 tok/s | NEW/OLD |
|---|---|---|---|
| 1 OLD→NEW | 385.7（弃） | 582.8（弃） | — |
| 2 **NEW→OLD**（反序） | 2324.9 | 2107.2 | **0.906×** |
| 3 OLD→NEW | 2243.7 | 2108.8 | **0.940×** |

- 绑定标记齐：每臂每轮都打印它实际绑定的 stage1 md5（OLD `9addb312` / NEW `827ba705`），
  同臂跨轮 decode 校验和逐位一致（OLD `sum=0x690fa29 xor=0x6b23`；NEW `sum=0x6938dbb
  xor=0x17c3`）⇒ 两臂差只是求和结合序，不是绑错目录。
- **第 1 轮整轮作废**：两臂 prefill 116.7 / 146.4 s（正常 26 s）——即便脚本已按同一 `SLOTS`
  各跑过一个不计时进程，**pipeline 编译仍落在计时区内**（spec 常量特化的变体集比预热跑的更宽）。
  轮 2 起 prefill 全部回到 25.7–26.4 s，读数和 §6.5 记的那条坑一致。**教训升级**：预热跑的
  `NTOK` 必须与计时跑**同档**，只提 `NTOK=1` 不够；否则第一轮必被污染。

- 静态确认改动确实生效（`spirv-dis` 两臂对比）：`OpDot` 1 → 5（四个 mid 循环 + rkv 段原有
  一处），循环体「2 次标量载入 + fmul + fadd」/k 变「2 次 `v4float` 载入 + dot」，每 lane
  trip count 20 → 5。**指令条数与载入字节数都按预期降了，却还是更慢。**

质量门：**不适用**（不采纳该改动 ⇒ 无数值口径变化需要把关；本轮 NEW 的校验和差异停留在探针里）。

## 6. 为什么慢：两个后端独立量到同一条机制（本记录的主要产出）

去读 CUDA 侧同一个核的 mid 分支（`backend_cuda.rs:2731-2812` + 启动器 `:8716-8745`），发现
**这两根杠杆它都试过并且都登记为负**：

1. **CUDA 的 mid 臂同样是标量循环**（`for kk = tid; kk < c; kk += blockDim.x:
   local_dot[gg][b] += w * xbase[s*c + kk]`），没有向量化 ⇒ 「÷4 指令条数」不是 CUDA 领先的原因。
2. **`MID_GG`（=每 block 槽跨度 `BGRP*MID_GG`，等价于 Vulkan 的 `GEMV_BGRP`）实测台阶**：
   GG=1 → **1.03 ms/次**，GG=2/4/8 → 1.39 / 1.98 / 4.66 ms，原话是「累加器变多又把寄存器压回
   溢出」。**与 S28（本仓 Vulkan，BGRP 8→16→32 净亏 8.6 %）同因**——两个后端、两套编译器、
   同一个台阶 ⇒ S28 里「被 `gemv_lowrank_chain4_batch` 的溢出拖累」这个混淆解释要让位给
   「**每 block 槽数 >8 本身就溢出**」，这条 env 本来就不该往 8 以上调。
3. **CUDA 在这个臂上真正的 2.5×（2.55 → 1.03 ms）来自消除数组化基址**：原先
   `const float* xsrc[BGRP]` 预存每槽基址被编译器落到 **local memory**，改成
   「单一 `xbase` + 常数偏移直接寻址」才拿回 2.5×。Vulkan 侧写法本来就是
   `params.in_xv.data[(slot0 + s) * XSLOT + k]` 内联寻址，**没有这个坑可消**——
   所以这根已在 CUDA 身上验证过的最大杠杆对 Vulkan 无效。

⇒ **mid 臂的定性判据要改写**：§3 的「既不贴带宽也不贴算力，剩下就是指令条数/延迟」在
「指令条数」这一半被本轮证伪（条数 ÷4 仍慢）。剩下的候选是**每 lane 在飞的载入条数**
（trip count 20 → 5 削掉了 4× 访存并行度）与 L2 侧按行×槽重读的字节，两者都不是「少发指令」
能碰到的。另外 CUDA 的形状与 Vulkan 几乎一致（同 576 行、同 1 行/block、同 BGRP=8、同样标量），
所以 §9「差距压在 mid 投影 SIMT 臂」这个归因**本身待验**——它可能两边同价。

## 7. 由此决定的下一步：把消融尺补到 Vulkan 侧（任务 #53）

S27 想做的「跨后端逐核归因」被 CUDA 那把 event-pair 尺判死（§2），而 Vulkan 侧只剩自家
`PROF_GPU`，两边不同尺 ⇒ 只能看单侧排名。CUDA 后端另有 **`ABLATE=csv`**（`backend_cuda.rs:1084-1117`
+ 跳过 launch `:741`，注释原文「比 `PROF_CUDA_KERNEL` 可靠」）：按名不启动某个 kernel，用**端到端
位移**度量它的代价。这把尺是跨后端可比的（同一个环境变量、同一个 bench、同会话交错），而 Vulkan
侧只有 `gemv_int8_rkv_stage1_batch` 一个核内的 `RKV_ABLATE` 位选，**没有通用的按名消融**。

⇒ 本轮的落地动作：给 Vulkan 补一把同名尺（Vulkan 的 dispatch 集中在 `src/runtime.rs:1089` 一处，
`shader_name` 就在手边，纯 host 改动、不动 shader、不进产品路径）。有了它，「差距压在 mid 臂」
这个待验归因可以用 4 臂同会话（base/ablate × cuda/vulkan）直接量出来，而不必再靠单侧 dump 猜。

## 8. S30：Vulkan 侧 `ABLATE` 尺建成 + 校准（B=128，与 §4/§5 同尺）

实现（`src/runtime.rs`）：`ablate_hit(shader_name)` 挂在 `record_kernel` 里唯一的
`cmd_dispatch` 上——命中的 kernel **只跳 dispatch 与它的两个 GPU 时间戳**，pipeline 创建、
uniform 池 slot、barrier、`cmd_bind` 全部照录 ⇒ 基线臂与消融臂在 host 侧逐字一致，唯一差别
是这条 dispatch 上不上卡。env 名与 CUDA 后端**共用 `ABLATE`**（同一个变量、同一个 bench、
同会话交错 ⇒ 跨后端可比）。

**第一个坑就撞上了 CUDA 文档里那条**：`record_kernel` 收到的是
`shaders/spv/<name>.spv`，而人和 dump 都写裸名 ⇒ 首跑四臂全部 `hit=NONE`、校验和与 base
**逐位相同**、tok/s 也在噪声内 —— 也就是「一处都不命中」的假零读数。区别只在于本次实现里
加了**每个名字首次命中打一条 `[ABLATE] 命中 <name>`**，日志没出现就等于没匹配，才没有把
「消融后没变化」读成「这个 kernel 不值钱」。修法是名字归一化（剥目录与 `.spv`）。

校准（修好后重跑，`C:/tmp/abl_cal.out`；每臂两轮、第 2 轮反序；臂内跨轮校验和一致：
base `0x690fa29/0x6b23`、mid `0x71a728/0xaf2c`、state `0x5a000/0x0`、imma `0xfdc027c/0x0`）：

| 臂 | r1 base | r1 消融 | 位移 | r2 消融 | r2 base | 位移 | dump 预测份额 → 折算吞吐 |
|---|---|---|---|---|---|---|---|
| mid 投影 `gemv_int8_rkv_stage1_batch` | 2389.3 | 2860.6 | **+19.7 %** | 2772.9 | 2319.1 | **+19.5 %** | 15.7 % ⇒ +18.6 % ✅ |
| 状态核 `fuse_ka_dplr_norm_s16` | 2389.3 | 2659.6 | **+11.3 %** | 2664.8 | 2319.1 | **+14.9 %** | 11.5 % ⇒ +13.0 % ✅ |
| int8 GEMM `gemm_imma_bm64_nst8` | 2389.3 | 1244.5 | **−47.9 %** | 1232.5 | 2319.1 | **−46.9 %** | 48.6 % ⇒ +94 % ❌ |

⇒ **两条与 dump 对上（mid 臂、状态核），这把尺在「消融后下游只读陈旧数据、不改变任何内核
工作量」的核上是可信的**。`gemm_imma` 那条是 CUDA 注释预告过的**反向失真**：被消融的生产者
不写输出 ⇒ 下游 `relu²` 拿到非零垃圾，稀疏 FFN 从「几乎免费」变回满密度，多出来的时间盖过了
被移除的 48.6 %。所以**imma 的份额只能用 `PROF_GPU` dump 读，不能用消融读**（登记进 §9 读数
纪律：消融读数只在「该核的缺席不改变其它核的工作量」时有效）。

### 8.1 同一把坑在 CUDA 侧也踩了一次（所以两边都加了命中日志）

CUDA 首轮（`C:/tmp/abl_cal_cuda.out`）用 `ABLATE=gemv_int8_rkv_stage1_batch /
fuse_ka_dplr_norm_batch / imma_gemm_batch` 四臂跑完：**全部与 base 逐位同校验和
（`0x6934e06/0x75b4`）、tok/s 也在噪声内** ⇒ 一处都没命中。根因是 CUDA 的消融按
**kernel 缓存键**匹配，而键带几何后缀（`fn kernel(key, src, entry)` 里
`register_kernel_name(func, key)`）。从 run 日志的 `compiling kernel <key>` 直接抄出来的真键：

| 角色 | CUDA 真键 | Vulkan 名 |
|---|---|---|
| mid 投影（低秩一级） | `gemv_int8_rkv_stage1_batch_g1` | `gemv_int8_rkv_stage1_batch` |
| 状态核 | `fuse_ka_dplr_norm_s16_w4` | `fuse_ka_dplr_norm_s16` |
| int8 张量核 GEMM | `imma_gemm_batch_b128n64l2s1p0d1k1e0v0_m65536k2560` 等 5 个（含 `_z3_*` 合并的 r/k/v） | `gemm_imma_bm64_nst8`（一个键跑全部形状） |
| 低秩两级 | `lowrank_gemm_1b64n16k128_2b64n64k64_s1` / `_s2` | 一级即上表 mid 臂；二级 `lowrank_epilogue_*` |

warn 一次请求集合，静默落空完全看不出来——它自己的文档注释写了这条坑，但没有配套日志）。

### 结论（改变了下一步的选点）

1. **CUDA 在 B≥32 的 decode 路径上不跑 SIMT mid 臂**：消融 hits=0 且校验和与 base **逐位相同**
   （`0x6934e06/0x75b4`）。这与接口注释的方向一致（`backend.rs:697/907`：`lowrank_gemm_batch`
   只有 CUDA 实现、Vulkan 的一级留在 SIMT），⚠️ 但注释里「两级都在一个 kernel 里」这句
   **措辞不准**（它是一对 kernel），已随 §9.5 一起就地订正。
2. ⇒ 两侧「同一条低秩链」的代价是 **CUDA ≈ 5.1 ms/步（一级+二级全包）** vs
   **Vulkan ≈ 8.9 ms（一级 SIMT）+ 二级（`PROF_GPU` 份额 ≈12 % ⇒ ≈6.5 ms）≈ 15.4 ms/步**。
   **差 ≈10 ms，占 17 ms/步总差距的 ≈60 %** ⇒ 残余差距的主战场是**整条低秩链**，
   而不是 §S27 说的「mid 臂单独一名」。
3. ⇒ **§9「一级 stays SIMT，实测 0.443 ms/层（TC）vs 0.274（SIMT）」这条决策是**错框**的**：
   它拿「只把一级搬上张量核」跟「SIMT 的一级」比，而 CUDA 的对照物是**一级+二级全在张量核上**
   ——键名 `1b64n16k128_2b64n64k64` 就是「一级 tile 64×16×k128、二级 64×64×k64」这一对几何。
   ⚠️ 但**不是**「一个融合核 / 一级瓦片留在 SMEM 直接喂二级」（那是本节初稿的说法，读源码后
   证伪，见 §9.5）。被优化的正确量是
   `Vulkan(一级 SIMT + 二级 TC + 4 个独立 epilogue)` vs `CUDA(一级 TC 四链合并 + 二级 TC 内联 epilogue)`。
4. **本轮脚本的失败也登记**：`abl_vk2.sh` 的 base 两轮漂到 61.7 / 56.1 ms（跨 4 分钟的热漂），
   于是它唯一新增的 `epi` 臂位移 7.51 / 0.17 ms 不可用。**教训**：一个脚本里 base 只出现在
   轮首与轮尾时，Δ 的可用性完全取决于这两点是否重合；**base 必须与消融臂在同一轮内紧邻**
   （下一轮脚本把顺序改成 base→abl→base 夹逼）。

### 9.5 零 GPU 成本的追读：CUDA 那一侧到底是什么形态（本节初稿曾写错）

归因把靶子指到「整条低秩链」之后，先读 CUDA 源码再动手——**初稿从键名 `1b64n16k128_2b64n64k64`
推出来的「一个融合核 / 一级的瓦片留在 SMEM 直接当二级的 A 算子」是错的**，实际是三次核、
两级之间经**全局** `mid16`（`[batch, Σ mid_pad]`，host 侧 `:8872` 的调用序注释 + `:8920` 的暂存切分）：

| CUDA kernel | 源位置 | 几何 | 关键点 |
|---|---|---|---|
| `cast4_f16` | `lowrank_gemm_batch` 内 | 4× `[batch,C]` f32→f16 | x 降位，不含 sigmoid（g 的 sigmoid 留给一级出口） |
| `lowrank_stage1_gemm`（`_s1`） | `:3188` | BM=64(批) × BN=16 × BK=128，`blockIdx.z` 选链 | ★ **四条链合并成一次 launch**（`LR1_MERGE`）。原话（`:3183-3186`）：分开发射时 v 链「**只用 16 个块去喂 68 个 SM**」，合并后 ≈160 个有效块一次铺开（≈5 波→≈3 波）。act（tanh/sigmoid）**内联**在累加器出口 |
| `lowrank_stage2_gemm`（`_s2`）×4 | `:3274` | BM=64 × BN=64 × BK=64 | 二级 GEMM **内联** `lr_chain_epi`（`:3165`：v 读改写 / w `exp(sc·sigmoid)` / a sigmoid / g 直出），没有独立的 epilogue kernel |

而 CUDA 的权重是**加载时已常驻的 `*_16` fp16 副本**（`gpu_model.rs:4978-4985`，两后端共用同一份
加载代码 ⇒ **Vulkan 侧这些 fp16 权重本来就在卡上**，一级上张量核不需要任何新的转换成本）。

**由此，#25 那条「一级不能上张量核」的旧结论要降级为待验**：`kernel_bench` 的 `lr1_w/lr1_v/lr1_g`
是**每个形状单独一档**（`examples/kernel_bench.rs:284-310`，`m` 直接就是 n_pad=64/128/320，`k=C`），
所以量到的 0.443 ms/层 = **0.4~0.6 TOPS** 是「块数极少」下的读数——`gpu_model.rs:2391` 自己写的
「coopmat 只有 2×1~3 个块」正是 CUDA 用 `LR1_MERGE` 专门避开的坑。Vulkan 侧从未试过
**四链合并 + 深 K 分块（split-K）**这一档：
- 合并：把 v/w/a/g 四条一级投影放进**一次 dispatch**（`grid.z = 链`），块数 ×4 级别地补回来；
- split-K：`gemm_imma` 一侧早就有 `imma_partial` + `gemm_imma_reduce` 与按全 grid 块数定 `ks`
  的规则（#38/S15），这是「窄 N 深 K」的对症药，与 S13 的 `pf_value` 是**同一个病**；
- 内联 epilogue：现有 `lowrank_epilogue_*` 四条是独立的 [batch, n_pad] 读写一遍，把它们并进二级
  coopmat 的累加器出口，一次省掉 4 条 dispatch + 4 个中间缓冲往返。

**所以 S31 的正确形态不是「造一个融合大核」，而是把 CUDA 这三处结构差别逐个搬过来**，并按
消融尺验收（一级 mid 臂位移应随 `gemv_int8_rkv_stage1_batch` 的 mid 段退休而消失）。

### 下一步（任务 #54，按 §9.5 修订后的选点）

顺序按「成本/收益」排：**① 一级四链合并 coopmat 档（先探针：`kernel_bench` 加一档 `lr1_merged`，
把四条链放进一次 dispatch 量 ms/层）** → ② 若仍打不过 SIMT 的 0.274 ms/层，再上 split-K（复用
`imma_partial`/`reduce`）→ ③ 把 `lowrank_epilogue_*` 内联进二级。任一档输了就停在那里并登记，
不许把三件事捆成一个改动去测。
判据 = 同尺 B=128/256 端到端，以及消融位移从 ≈15.4 ms 降到 ≈5-8 ms。
质量门 = `cargo test --release` + DIAG 对 CPU fp32 的 logit 偏差 + 贪心分叉率（fp16 存储/精度档
与 CUDA 一致，见 `LOWRANK_GEMM` 的「精度档与信天翁一致」）。

### 10.2 顺带钉死一条**静默零输出**的结构下界（潜在引擎 bug）

`gemm.comp` 的 tile-load 循环 trip count = `TILE_M*TILE_K/NUM_ELEMENT_VEC4/NUM_INVOKE_TILE`
（fp16 = `TILE_M*TILE_K/2048`），A/B 两侧都必须 `TILE_* × TILE_K ≥ 2048`，否则该侧**一片都不
载入**、累加器保持零并被原样写出，而 dispatch、 barrier、写回全都照常「成功」。
实测 (64,32,32)：`0.034 ms/次` 而 `sum(y)=0.0000` —— 若没有 `kernel_bench` 内建的带读回判据，
这就是一个 2.5× 的假胜利。`gemm_tile` 的共享内存兜底档 `(64,32,16)` 正好落在这条线下面
（`64×16=1024`），属于同一类。修法只有抬 `TILE_K`（抬 M/N 会破坏整除性）。

同理，`NUM_TILE_K = K / TILE_K` 是定长循环、无边界检查 ⇒ `TILE_K` 不整除 K 时是**静默丢尾**。
两者都写进了 `legal()`。

### 10.3 规则（`src/runtime.rs::gemm_tile_for`）

1. 整除收缩（原样保留，安全条件）；
2. **结构下界**：不合法就按 2× 抬 `TILE_K`（要求仍整除 K、仍放进共享内存），抬不动就
   `log::warn` 喊出来而不是静默出零；
3. **占用率**：`blocks = ⌈M/TILE_M⌉·⌈N/TILE_N⌋ < GEMM_MIN_BLOCKS`（默认 **32**，`0` 关掉）时，
   按 (64,32) → (64,64) → (128,32) 的顺序取**第一个仍整除形状且合法**的档，`TILE_K` 取
   「满足下界的最小档」（更大的 K 让每块 K 循环更深，实测更慢）。

★ 一并修掉一个**会错结果的耦合**：`gemm_grid` 过去用 `gemm_tile_for(app, m, n, 0)`（传 k=0），
旧注释的理由是「TILE_M/TILE_N 只依赖 M/N」。新规则里 `TILE_N` 受 `TILE_N*TILE_K ≥ 2048` 与
占用率档约束，**两个都依赖 k** ⇒ grid 与 spec 会分叉（表现为输出少写/多写若干列）。已把

## 11. S31 ①-b：一级 mid 臂整条搬上 coopmat fp16（`LOWRANK_GEMM1`）

### 11.1 落地形态（`src/gpu_model.rs`，门控三态）

- `lowrank_gemm`（CUDA 专有）→ `lowrank_stage2`（二级 coopmat，`batch>=32`）→
  **`lowrank_stage1 = lowrank_stage2 && LOWRANK_GEMM1≠0`**（一级 coopmat）。子集关系保证
  CUDA 一行代码都不会走到新臂。
- `WorkBuffers` 新增 **`lr_rows`（补长行数的唯一真源）** + `xw16/xa16/xg16`（A 操作数）+
  `v/w/a/g_mid_tc`（f32 累加器 `[lr_rows, mid_pad]`）。SIMT 臂的 `*_mid` 列维是真实 mid（不补长）
  ⇒ 两套不能复用，二级档的 `to_f16` 在一级档开启时改从 `*_mid_tc` 读。
  ★ 陷阱：`lr_rows` 在 `batch<16` 时等于 `batch` 而非 `round_up(batch,64)`，写侧就地算会越界——
  所以字段进结构体、所有写点一律 `bb.lr_rows`。
- 语义逐式对应 `gemv_int8_rkv_stage1_batch.comp` 头注：`w` 用 `gemm_tanh`（内联 tanh），
  `v/a/g` 用 `gemm`，`g` 的 sigmoid 仍在 f32 mid 上做（原本也在 chain4 里做）。
- 补长安全性：pad **列**的 `g_mid_tc` 会变成 `sigmoid(0)=0.5`，但权重 `g1_16` 的 pad 列恒 0 ⇒
  对二级贡献 0；pad **行**由 `lowrank_epilogue(..., batch)` 丢弃。
- SIMT mid 臂在一级档开启时**整条不发**（伪行数全 0）。注意不能靠「传 0 行」退役：
  `div_ceil(0,TILE)` 会让 grid 退化成 0 个工作组，Vulkan 非法 ⇒ 调用点加了显式 guard。
- 顺手关掉一个既有泄漏：`WorkBuffers::free` 从来没释放 `xr16/xk16/xv16`。

### 11.2 探针教训：v1 两臂全跑在 CUDA 上（登记为死探针路径）

v1 读数（`C:/tmp/s31b_probe.sh` 旧版）：两臂 `DUMP_LG` **逐字节相同**（md5 一致、`mean|Δ|=0`、
argmax 分叉 0/128），而日志里 **`GEMM 瓦片` 行数为 0**，聚合吞吐 **3553 tok/s**（§6.1：Vulkan
B=128 = 2296，CUDA B=128 = 3329.9~3600）。⇒ 三条独立证据同指一件事：**根本没在 Vulkan 上跑**。

根因：`cargo run` + 没设 `BACKEND=vulkan` ⇒ `detect_backend()` 选中 CUDA；而 CUDA 侧
`lowrank_gemm=true` ⇒ `stage2/stage1` 恒 false ⇒ `LOWRANK_GEMM1` 这个开关在它身上不可能有效。
「两臂相同」在这里不是「改动无害」的证据，是「改动没被执行」的证据。

修法（三样，全部与性能无关）：① 脚本显式 `export BACKEND=vulkan`；② 跑编译产物 exe 而不是
`cargo run`（bench 期间禁止编译，纪律 5）；③ 加**门控绑定标记** `PROF_LOW=1`，每次 forward 的
第 0 层打一条 `gemm/stage2/stage1` 三个 bool + `lr_rows`，并在脚本里当场回显瓦片/标记行数——
门没开就别往下读。

### 11.4 质量：三档同尺对拍（B=128，`PAD_TO=512` 分块 prefill + 贪心单步）

单看 B↔C 的 `mean|Δ|=0.837` 分不清「fp16 舍入级扰动」还是「前向算错」——一级 fp16 与 SIMT fp32
本来就不该逐位一致，而这个量级又远超单次 K=2560 点积的舍入。于是补一臂**全 SIMT**
（`LOWRANK_GEMM2=0`，即 #6.9 之前的已验收形态）当尺子：

| 对 | `mean|Δ|` | `max|Δ|` | argmax 分叉 |
|---|---|---|---|
| A（全 SIMT）↔ B（当前默认 = 二级 TC） | **0.8607** | 6.10 | 1 / 128（slot22） |
| A ↔ C（新增一级 TC） | **0.8137** | 5.48 | 1 / 128（slot22，同一个槽） |
| B ↔ C | 0.8368 | 6.37 | **0 / 128** |

读法：**≈0.8 是这把尺子的噪声地板**，不是新臂的缺陷特征——已上线的默认路径（B）与 A 的偏离
就是 0.86，而 C 与 A 的偏离（0.81）还略小一点。机制上这个量级来自「A 步之前已经跑过若干条
臂不同的 decode 步（`WARMUP` + 计时段），误差沿递归状态放大」，所以它只能做**同尺相对判据**，
不能读成单步误差。三档 slot0 的 top1 都是 `10080`、top3 集合一致 ⇒ 采样链路无恙。
真正的绝对判据用 bench 自带的**贪心 token sum/xor 指纹**（`TOPK=1` + 固定 seed 时与路径无关），
见 §11.5。

外部佐证（同一把尺子的历史读数）：§6.9 二级档入库时的质量门就做过同样的对照
（README.md:1096，`calibration control: base vs LOWRANK_GEMM2=0`，logit **rmse 1.103 = 6.558 %**），
所以「已上线的张量核档相对全 SIMT 偏离 ≈1 量级」不是我这次自己给的免责解释，是记录里已有的数。
⚠️ 口径差别：那条是 rmse，我这里是 mean|Δ|（不同统计量，不能直接比大小），所以判据只取
**同会话同脚本的三档互差**（上表），跨会话的历史读数只当方向性佐证。

### 11.5 端到端（B=128，`SEGS=1 NTOK=64`，只翻 `LOWRANK_GEMM1`）

**先记一条仪器教训（比收益更重要）**：这一版脚本为了省 prefill 墙钟把 `PREFILL_SLOTS` 从 8 提到
16，结果**解码被整段拖慢 ≈1.9×**——B=128 的 off 臂在 16 档是 6631/7158/7034 ms，在 8 档只有
3712 ms（同二进制、同会话、相邻时间）。机制：`SeqBuffers` 按**最大 chunk 行数**定容，
16 槽 × `PAD_TO=512` = 8192 行 ⇒ 光 `ffn_mid` 就是 8192×10240×4 B ≈ 335 MB（8 槽档 167 MB），
这些缓冲常驻之后解码就掉档。⇒ **跨批宽的门限测量必须钉死 `PREFILL_SLOTS=8`**，否则绝对值对不上
§6.1，而且两臂的相对位移会被热漂压成噪声（16 档三对确实从 +13.5 % 一路收敛到 +2.0 %）。

| 口径 | off（`LOWRANK_GEMM1=0`，= 已上线形态） | on（`LOWRANK_GEMM1=1`） | 位移 |
|---|---|---|---|
| **干净（`PREFILL_SLOTS=8`）** | prefill 32.3 s \| decode 8192 tok **3712 ms = 2206.6 tok/s**（58.0 ms/步） | prefill 25.9 s \| decode **3290 ms = 2489.4 tok/s**（**51.4 ms/步**） | **+12.8 %**（−6.6 ms/步） |
| 污染（`PREFILL_SLOTS=16`）r1 | 6631 ms = 1235.2 | 5844 ms = 1401.8 | +13.5 % |
| 同上 r2 | 7158 = 1144.4 | 6855 = 1195.0 | +4.4 % |
| 同上 rev | 7034 = 1164.6 | 6897 = 1187.7 | +2.0 % |

读法：干净档的 off 绝对值 **2206.6** 对上 §6.1 记的 Vulkan B=128 = 2296（差 −3.9 %，在会话漂移内）
⇒ 口径已归位；**+12.8 %（−6.6 ms/步）与 §10.6 的预测 4.5 ms/步同级**，比 §10.4 的
「0.274 → 0.118 ms/层 = 省 0.156 ms/层 = 5.0 ms/步」也吻合。污染档三对**全部 on 胜出**（符号一致），
只是幅度被热漂吃掉——它只能当旁证，不能当结论。

token 指纹（同一进程内可重现，跨臂分叉）：off `sum=0x690fa29 xor=0x6b23`、
on `sum=0x69260c3 xor=0x18cd`（各档三次逐位重现）。⚠️ 这条与 §6.9 二级档入库时「四臂多步指纹
逐位相同」**不同**：一级是 fp32 权重→fp16 权重（`*_16`），二级不是，所以贪心流从这里开始分叉。
分叉本身不是否决判据（跨后端指纹从 B=8 起就全部分叉，§6.1 已经写明），但它意味着这条臂的
准入依据是 §11.4 的**同尺对照**（与已上线档同一量级），而不是「逐位不变」。

## 12. S31 ②：一级 coopmat 接 split-K（解 4/8/20 块饥饿）

### 12.1 落地形态

- **两条新 shader**（不动 `gemm.comp`，一级臂以外的所有 coopmat 消费者零风险）：
  - `assets/shaders/src/gemm_splitk.comp` = `gemm.comp` 的窄形状兄弟，只改三处：
    ① `constant_id=42` `SPLIT_K`，`grid.z = ks`（批维恒 0），本块只算 K 的第
    `slot % ks` 段，段长 `CHUNK_TILE_K = NUM_TILE_K / SPLIT_K`；
    ② **输出不施加 op**，写进 `partial[ks][M][N]`（`STRIDE_C_BATCH` 被复用成「一个槽的元素数
    M×N」，槽号 = `gl_WorkGroupID.z` 原值）；③ 类型写死 fp16 进 / fp32 出，只出一条 spv，
    不进 `gemm` 的变体矩阵。
  - `assets/shaders/src/gemm_splitk_reduce.comp`：按 ks **升序**求和（固定顺序 ⇒ 结果确定），
    求和之后才施加 `op`（0 = 覆盖写、1 = tanh）。这是它与「每段各自 tanh 再相加」的本质区别
    ——`w` 链的 tanh 必须作用在完整和上。
- **`Runtime::gemm_splitk(a,b,partial,c,m,n,k,op)`**：`ks` 由形状自己定；`ks == 1` 时**整条退回**
  `gemm`/`gemm_tanh`（连 reduce 都不发），所以这一档在不需要加块的形状上是零成本的。
- **`ComputeBackend::gemm_splitk`** 是**带默认实现**的 trait 方法（默认 = `gemm`/`gemm_tanh`，
  语义等价 `ks=1`）⇒ CUDA 后端一行不用改，新臂天然只归 Vulkan。
- **定档规则** `gemm_splitk_ks(blocks, nk)`（最终形态 = **默认关，只认显式档**）：
  `GEMM_SK` 未设或 ≤1 ⇒ `ks=1`；设了 `n` 还要过三道闸才加块——`blocks < 32`
  （`gemm_tile_for` 的占用率档已经把能切的 M/N 切过了，再切只多一趟 partial）、`nk ≥ n`、
  `nk % n == 0`（不整除 = 尾 k-tile 静默丢）。任一道不过 ⇒ 退回 `ks=1`。
  - 中间曾试过**按形状自动取档**（`{8,4,2}` 里最小的、要求 `blocks × ks ≤ 64` ≈ 本机 SM 数），
    §12.3 表里标「自动档」的读数来自它，绑定读数：
    `N=64 块 2 ⇒ ks=8 = 16 块`、`N=128 块 4 ⇒ ks=8 = 32 块`（a/g 两链同形状，一条 op=0 一条
    op=1）、`N=320 块 10 ⇒ ks=4 = 40 块`。定档被证伪后这条规则一起撤了，改成手动 `GEMM_SK=n`。
- **暂存缓冲**：`WorkBuffers::lr_pk`（`ks 上限 8 × 最宽 mid_pad × lr_rows` ≈ 1.3 MB），
  四条链**串行共用一张**——GEMM 写完立刻被归约读走，同一队列线性顺序 ⇒ 复用安全。
  没有复用 `imma_partial`，是为了让 int8 臂与 fp16 臂能各自独立关掉。

### 12.4 判定：作为吞吐杠杆**证伪**，只留作被抢占慢窗的档位保险

1. **「4/8/20 块饥饿 ⇒ split-K 能把 B=64 从打平变赢」这个假设被证伪。** 安静窗同会话交错
   三对，B=64 与 B=128 都只有 +2.6~2.8 % 的合池位移，落在 base 复测极差之内，符号不
   一致；`ks=2` 只有 +1.2 %。⇒ §11.7 预期的「关键一环」不成立。
2. **为什么赚不到**：块数从 20 抬到 40~80 确实填了 SM，但代价同时来了——每步多 4×32 = 128 次
   dispatch（每条 reduce；按代码路径算的算术，不是 PROF 读数）加上 `partial` 的
   `ks·M·N·4 B` 写+读往返（B=128 强制 `ks=4` ≈ 84 MB/步，对 48 ms 的步时只有零点几个百分点）。
   两头都不大 ⇒ 净位移自然也只有噪声级：窄 N 的 K=2560 单块串行本来就接近带宽上限，把 K
   切开只是把「一条链的计算」换成「一条链的计算 + 一份全量中间量」，省下的串行时间被
   自己吐出的 partial 抵消。
3. **唯一实测收益是抗抢占**：重抢占窗里 `ks=4` 在退抢占沿上赚 **34~41 %**，自动档在 B=64 赚
   19.6 %。道理是把每条链切成更多、更短的块 ⇒ 被外界抢占时切片间隙更碎、单块排队更短。
   这是**保险**而不是**吞吐**。
4. **默认关**：`gemm_splitk_ks` 在 `GEMM_SK` 未设时返回 `ks=1`（= 上一发货形态，逐位相同的路径，
   连 reduce 都不发）。`GEMM_SK=n` 手动加块 = 已知在别的程序占卡时有用的档位；
   `LOWRANK_MIN`（默认 64）留给下一轮把 B=32/48 收进来时免重编。
5. **留给 ③**：真要动这一档的收益，方向不是加块而是**减 dispatch**（`lowrank_epilogue_*` 内联），
   以及重测一级档的份额表（任务 #56）。**split-K 这条别再回头补测**，除非会话长期处于被抢占态。

## 16. 「锁到最高频」锁到的其实是 1860 MHz：B=1 的回落与成对表的跨会话漂移都由它解释（2026-10-11 深夜）

起因是第七次成对复测（会话 `20261011-225925-17792`，锁频后，六档 × 3 轮）里 **B=1 的 Vulkan
读数从第五次的 80.6 掉到 76.9**，用户问「单线怎么还掉下来了」。用 1 Hz 采样 SM 时钟直接量了
一次（`/c/tmp/clk32.sh`，Vulkan B=32 单档跑，48 个样本）：

| 量 | 读数 | 说明 |
|---|---|---|
| `clocks.max.sm` | **2100 MHz** | 这张改过的 2080 Ti 的上限档 |
| 空闲时 `clocks.sm` | **1860 MHz**（48 样本里 37 个正好 1860） | ⇒ 锁频把时钟**钉在 1860**，不是 2100 |
| 重负载段（分块 prefill） | 掉到 **1755~1845**，功耗 **251~253 W**，温度 63~66 °C | 撞 **250 W 功耗墙**，时钟被压 |

⇒ 三条结论，全部用绝对数：

1. **B=1 没有相对掉**。同会话独立单档（各两次，同一份 exe、同一锁频档）：
   Vulkan **77.1 / 73.4 tok/s**（12.97 / 13.62 ms/step），CUDA **85.8 / 84.2**（11.66 / 11.88 ms/step）
   ⇒ 比值 **0.88×**；第五次未锁频是 80.6 / 89.5 = **0.90×**。两个后端各自都比第五次低约 **5 %**，
   与 2100→1860 的 **−11 % 时钟差**同向（B=1 每步 12~14 ms 里 GPU 大多在等提交，所以它只吃了
   一部分时钟差）。**掉的是绝对刻度，不是 Vulkan 的地位**；而 68.6 那一读是该档三轮里最差的一轮
   （68.6 / 76.9 / 80.6，17.4 % 带内），且它是整场第一个 Vulkan 臂、紧跟在 CUDA B=256（prefill 41 s
   全程撞功耗墙）后面。三次读数里最好的一次恰好复现第五次的 80.6 ⇒ 「回落」是**噪声 + 时钟档**，
   不是我这轮两个 commit 的副作用（`LOWRANK_GEMM1` 门 `batch>=64`、`LOWRANK_GEMM2` `batch>=32`、
   `GEMM_SK` 默认关 ⇒ B=1 一条都碰不到；三轮指纹 `0x1a747c` 完全一致 = 同一代码路径）。
2. **成对表里 B=32 那一格被时钟档放大了**。第七次（锁频、六档轮转）Vulkan B=32 中位 **1239.3**
   （25.82 ms/step）；同一份代码、同一天深夜**独立单档 1414.2**（22.62 ms/step）、
   同会话成对（只跑 B=32、cuda→vulkan 紧跟）**1380.6 / 1346.5**；第五次未锁频 **1427.6**。
   ⇒ 同一把尺内「轮转越宽、越靠后的臂越慢」+「锁到 1860」两件事叠在一起，让 1239 比 1428 低
   **13 %**，而 CUDA 那一格两次几乎不动（1731.5 / 1732.8）——因为 CUDA 在 B=32 撞的是带宽/张量核
   占用，对 SM 时钟的敏感度低于 Vulkan 的 SIMT mid 臂。**教训：跨会话比值的漂移里有一部分是
   「这场轮转了多少档」，不是纯噪声；要定某一格的账就在同会话里只跑那一格。**
3. **哨兵判据要补一条**：§15 里「四臂 token 校验和相同却出现 +10 % 单读离群」现在有了具体机制
   ——撞功耗墙时同一次运行内的时钟是 **1755~1860 波动**，所以「校验和相同 ⇒ 读数该相同」不成立；
   离群读数应当先查它落在时钟采样的哪一段（prefill 撞墙段 vs decode 空载段），再谈副作用。

**顺带量了「每次重加载模型」的代价**（用户问能不能不重载）：按 jsonl 时间戳与每档自己打印的
`prefill + decode` 之差拆开，**重载 + 管线编译 = 每档 8.2~9.2 s（中位 ~8.5 s）**，35 个档间
**合计 267 s**；整场墙钟 ≈ 1 018 s ⇒ 重载占 **27 %**，剩下 73 % 是 prefill+decode 本身
（B=256 单档 prefill 就 41.5~49.5 s，是真正的大头）。为什么现在非要重加载：`AB_SLOTS` 的注释
写着「每档一个子进程」，因为同进程内混批宽会把共享缓冲按**最宽档**撑大、污染窄档读数
（与 `PREFILL_SLOTS=8` 那条纪律同一个机制）。**能省的是另一件事**：`LOWRANK_MIN` /
`LOWRANK_GEMM1` / `GEMM_SK` 是**每次 forward 现读**的环境门（`src/gpu_model.rs:2453-2461`），
所以**同一批宽内的开关 A/B 根本不需要重加载**——一次加载、在测量阶段之间翻转环境变量即可。
下一个仪器步骤就是把这条做成 bench_ab 的一种模式（跨批宽仍开子进程，同批宽换档留在进程内）。

可覆盖（`-DSAMPLE_BLOCK=N`，**默认 256**，重编译后与已发货 `sample.spv` **逐字节相同**：
`3e9de68f…`），三档 256/512/1024 同会话轮换 A/B 正在跑。烟雾测试：1024 档 `sample` 0.574 → 0.224 ms

prefill 1430 → 3308 ms ⇒ **单读不可信**，必须看轮换序的多轮。

## 21. `sample` 的 workgroup 宽度：分核表推翻了「512 涨 10 %」的读数，顺带挖出一个**每进程交替**的时钟伪影（2026-10-12 01:36–01:50，300 W 档）

起因是 §20 判读 3：`sample` 每次 0.574 ms 且**与批宽无关**（B=1 与 B=8 逐位同耗时），因为
grid 是 `(1, batch, 1)` —— 一个 workgroup 只服务一个槽，所以它的成本是「单槽串行链」的长度，
加批宽只是加块数。块宽因此是单槽延迟的唯一杠杆，B=1 时它占整步 GPU 的 5.3 %。
探针：把 `sample.comp` 的 `BLOCK_SIZE` 改成编译期可覆盖（`-DSAMPLE_BLOCK=N`），
默认档编出来的字节与已发货的 `sample.spv` **逐字节相同**（md5 `3e9de68f…` 复核过），
所以三档目录只差这一个文件。第一轮三臂（256/512/1024 + 反序）端到端读出「512/1024 更快
（B=128 +10 ~ +21 %）」，幅度远超 `sample` 自身占比 ⇒ 用分核表逐臂核对。

**分核归因（`PROF_GPU=1 SKIP_GRAPH=1`，每臂两个 dump，取最后一个表）**：

| 臂 | `sample` ms/步 @B=1 | `sample` ms/步 @B=128 | GPU SUM 排序 |
|---|---:|---:|---|
| 256（发货字节） | 0.575 (r1) / 1.04 (r2) | 0.74 | r1: 512 < 256 < 1024；**r2: 1024 < 256 < 512** |
| 512 | 0.334 / 0.341 | 0.64 | 两轮**互换** ⇒ 排序不可信 |
| 1024 | 0.223 / 0.228（另有一次 1.887） | 0.64 | — |

⇒ 只有 `sample` 自己的那一条在两轮的六个 dump 里方向一致（256→512 约 1.7×，→1024 约 2.5×，
B=128 只到 0.64 就饱和 —— 128 槽 × 512 线程已经把机器填满，再加宽不增加驻留 warp）。
其余全是仪器噪声：**同一批 dump 里 `record_token` 从 0.24 跳到 3.60 ms、`gemm_imma` 从 13.1 到
15.9 ms、B=1 的 `gemm_imma_reduce` 从 4.02 掉到 0.71 ms** —— 这三个核都碰不到改动，
所以「SUM 差 3~9 ms」不是被改出来的。⇒ **教训（写死）：`SKIP_GRAPH=1 + PROF_GPU=1` 的 dump
只能用来回答「某个核自己值多少」，不能用来归因 5~15 % 量级的步时变化**；这个模式的
GPU SUM 在**同臂两轮之间**就能差 10~15 %。

**新伪影：每进程交替的时钟状态。** 于是改设计做严格 ABBA（`w1 p1=256,512 / p2=512,256 /
p3=256,512 / p4=512,256`，每对内两臂相邻、起始臂轮换），发货口径、无 PROF：

| 对 | 256 decode ms | 512 decode ms | 配对差 |
|---|---:|---:|---:|
| p1 | 1902 | 1630 | −272 |
| p2 | 1642 | 1913 | **+271** |
| p3 | 1945 | 1699 | −246 |
| p4 | 1857 | 1862 | +5 |

八臂的 decode 时间按**位置**严格交替（奇数臂 1902/1913/1945/1862 = 1905 均，偶数臂
1630/1642/1699/1857 = 1707 均），而**与臂身份无关**（256 的最好成绩 1642 与 512 的最好成绩
1630 只差 0.7 %）。更关键的证据：**prefill 墙钟与它同相位**（1201/1157/1128/1253 对
1027/1071/1074/1092）—— prefill 是 GEMM 密集的，跟 CPU 提交路径无关，所以交替来自
**整卡时钟状态**，不是进程放置或显存布局。指纹八臂逐位相同（`0x1a747c / xor 0x672e`）
⇒ 数值与块宽无关这一点是**硬证据**（顶多说明 radix/softmax 的块内归约形状换了没改结果）。

**B=128 的 ABBA（同一批四对，口径同上：16384 tok = 128 步 ⇒ ms/步 = decode ms / 128）**：

| 对 | 256 ms/步 | 512 ms/步 | 配对差 |
|---|---:|---:|---:|
| p1 | 50.66 | 58.77 | **+8.11** |
| p2 | 55.10 | 58.65 | +3.55 |
| p3 | 54.66 | 59.48 | +4.82 |
| p4 | 57.31 | 53.70 | −3.61 |

⇒ **B=128 上符号很清楚：4 对里 3 对说 512 慢 3.55~8.11 ms/步（+6~16 %），只有 p4 反向 −3.61。**
位置论在这里站不住（p1 与 p3 的 512 都在偶数位、都慢；p2 的 512 在奇数位、也慢），
所以这是**臂身份**效应。发货字节没被污染：**三个探针目录与 `assets/shaders/spv/` 逐文件 md5
对拍过（153 个文件），256 目录 0 处不同 = 已发货字节，512/1024 各只差 `sample.spv` 一个文件**。

**判读（结案）**：
1. `sample` 自己的 GPU 时间确实随块宽下降（0.575→0.334→0.223 ms/次 @B=1；0.74→0.64→0.64 @B=128），
   机制也讲得通（一块一槽）。
2. 但端到端**方向相反**：B=1 的预测收益 (0.575−0.334)×128 步 = 31 ms / 1902 ms = **1.6 %**，
   在本机 ±8~17 % 的每进程交替噪声之下不可判；B=128 却付出 **~4 ms/步（+8 %）**，3/4 对同号 ——
   而该核在 B=128 只值 0.1 ms/步。**⇒ #59 证伪：块宽加不得，`BLOCK_SIZE` 保持 256（发货字节不变）。**
3. ⚠️ 那条 0.1 ms/步的核改动换来 4 ms/步 的整步变慢，**机制还没查清**（时间戳里确实能看到不相关的核
   被带着变：r2 B=128 的 `gemm_f16_f32` 5.71→8.42、`fuse_ka_dplr` 9.84→11.45）。两个候选：
   宽块改变了卡上的**功率曲线**从而在 300 W 档把持续时钟压低（与 §18 判读 2「大档撞热不撞功耗墙」
   同族），或驱动对非 256 档的 specialization 走了另一条码路。要分辨只需一次 1 Hz 采样时钟的配对复测
   —— 但**这个结论（保持 256）不依赖机制**，所以没继续花卡时。
⇒ **方法学入册（本条比 #59 本身值钱）**：
   ① 三臂轮换（A,B,C / C,B,A）**不能**分辨 <10 % 的档 —— 它把「臂身份」和「时间位置」混在一起；
   必须做**严格 ABBA**（每对内两臂相邻、起始臂轮换），并看**配对差的符号一致性**而不是均值。
   ② 本机 decode 墙钟有一个**每进程交替**的 ±8~17 % 状态（B=1 八臂奇偶位 1905 vs 1707 ms，
   prefill 同相位 ⇒ 整卡时钟状态，不是进程放置/显存布局）。小于它的收益一律不许写端到端数字。
   ③ 探针目录在读数前必须与发货 spv **逐文件 md5 对拍**，不能只比探针目录之间。


## §22（2026-10-12）进程内换档 A/B 建成，但它的第一次读数是一个**假杠杆**——由此量出本机噪声的真正机制

### 22.0 起因：进程外四臂判不动「B=128 整步有多少时间不在内核里」

按 §20 判读 4 的算术（GPU 时间戳 SUM ≈42.3 ms/步 vs 墙钟 47~60 ms/步），残余可能有 10~28 % 在
内核之外 —— 若真，它比任何单核优化都值钱。第一次尝试是**进程外** ABBA
（`/c/tmp/ga.sh`，图开/图关各两臂，同会话轮转换序）：

| 臂 | 墙钟 ms/步 | prefill ms |
|---|---|---|
| r1 on | 47.13 | 24005 |
| r1 off | 50.01 | 23293 |
| r2 off | 52.40 | 24260 |
| r2 on | 57.35 | 24430 |

四臂**单调变慢**（47→50→52→57），而**同为 off 的两臂相邻差 4.8 %** ⇒ 配对差里只剩会话漂移，
符号在两轮之间翻转（on 第一臂时快 2.9 %、on 第二臂时慢 9.4 %）。这一轮**不出数**。
唯一可信的收获是 `PROF_GAPS`：2047 条 dispatch 间隙合计 0.537 ms ⇒ **每步 0.39 ms**，
即**提交间隙不是那 10~28 % 的去处**（与既有 1.3~1.8 µs/条 一致）。

⇒ 结论：进程外形态在本机测不动 3~10 % 的杠杆，需要**同进程内**换档（顺带满足用户
「测试不用每次重新加载模型」的要求）。

### 22.1 仪器：`examples/batch_decode_bench.rs` 的 `AB_*`（一次加载、一次 prefill、按段交替）

`AB_VAR=<环境变量名> AB_A=<值A> AB_B=<值B> [AB_ROUNDS=6] [AB_SEGS=1] [AB_WARM=1] [AB_RESTART=0]`：
每轮两档各跑 `AB_WARM` 段（丢弃，让图/缓存回暖）+ `AB_SEGS` 段（计时），**奇数轮反序**；
换档就是 `set_var`/`remove_var`（空串 = 撤销该变量走默认），当场回读并打印当绑定标记；
每档打印 ms/步与该档的 token 指纹。`AB_RESTART=1` 时两档各自 `reset+重 prefill` ⇒ 从**同一状态**
出发，此时指纹才是数值门（默认只量吞吐，指纹不可比 —— 状态在两档之间连续推进）。

### 22.2 假杠杆：`SKIP_GRAPH=1`「比发货档快 8.3 %」，6/6 同号

第一次用它测的是「自循环走图 vs 不走图」，B=128、6 轮、每臂 2 段：

```
A（不设 SKIP_GRAPH）55.25 51.27 58.11 58.62 60.02 61.98   中位 58.36
B（SKIP_GRAPH=1）    52.76 50.11 52.37 54.26 54.42 54.85   中位 53.51   ⇒ −8.31 %，6/6 同号
```

看着是「关掉图捕获白捡 8 %」。但读代码即可证伪：**Vulkan 上根本没有图路径** ——
`gpu_model.rs:3168` 的 `graph_ok = backend.supports_graph_capture() && !skip_graph && …`，
而 `supports_graph_capture()` 在 `backend.rs:163` 默认 `false`，**只有 `backend_cuda.rs:8082` 覆盖**
（`runtime.rs` 无覆盖）。`&&` 短路 ⇒ 两档都不进 `ensure_selfloop_graph`，**逐行执行完全相同**。
⇒ 这是一次**空档对照**（两档同一段代码），却读出 −8.3 % 且 6/6 同号。

### 22.3 机制：SM 时钟在负载下是**准静态台阶**，一次台阶维持几十秒

同窗口 1 Hz 采样（`nvidia-smi dmon -s pucm -d 1 -c 75`，与 bench 并发）：功率 251~254 W、
核心 81 ℃、**SM 时钟在 1695~1830 MHz 之间成段跳变**（分布：1830×22、1815×13、1725×12、1710×8…），
`1830/1710 = 1.070` ⇒ 一次台阶就是 **7 %** 吞吐。
任何「每臂几秒」的配对，其差值由**台阶落在哪一臂**决定；轮转换序只能抵消*线性*漂移，
抵消不了这种*成段*的台阶 —— 所以会出现 6/6 同号的空档读数（§21 里那条「臂身份效应」
和「0.1 ms/步的核改动换来 4 ms/步」的谜，最自然的解释也是它，而不是码路/功率曲线玄学）。

### 22.4 修法：配对统计量从「每档中位」改成**每档多轮最小值（Δmin）**

两档各取自己最好时钟态下的读数再比 ⇒ 台阶被 `min` 挑掉。空档对照复测（同一批数据两种统计量）：

| 批宽 | 轮数/每臂段数 | Δ中位（空档） | **Δmin（空档）** |
|---|---|---|---|
| 8 | 6 / 2 | −2.27 % | **−0.6 %** |
| 32 | 5 / 2 | −9.74 % | **−2.2 %** |
| 64 | 5 / 2 | −3.99 % | **+1.6 %** |
| 128 | 6 / 2 | −8.31 % | **−2.3 %** |
| 128 | 12 / 1 | −3.72 %（逐轮极差 −13.1/+12.4） | **−1.64 %** |
| 256 | 3 / 1 | −0.23 % | **−0.2 %** |

⇒ **底从 ±8~10 % 降到 ±2 %**，B=128 第一次有了能判 3~5 % 杠杆的仪器。汇总行现在打印
`Δmin` 为主、`Δ中位`+逐轮散布为辅（后者是时钟态/热的诊断，不是效应量）。

### 22.5 顺带订正两条旧账

1. ⚠️ **`gemm_imma取数结构` §5.5 那条「B=1 图开 796 ms vs 图关 798 ms ⇒ B=1 不是提交受限」是空档对照**，
   它测量的是同一段代码，**不能作为该结论的证据**。该结论本身仍然成立，但支撑换成另外两条：
   `PROF_GAPS` 实测每步间隙 0.39 ms（22.0），以及强制 `VK_IMMA_KSPLIT=1` 每层少排 3 条反而更慢。
2. ⚠️ **README/注释里「自循环走图捕获」对 Vulkan 不成立**（图捕获是 CUDA 独有）。
   过去所有用 `SKIP_GRAPH=1` 做的分核 dump 与发货路径**是同一条码路**（好消息：dump 无需订正），
   但它从来不是「降级 vs 发货」的对照，以后别再这么称呼它。
3. §20 判读 4 留的「10~28 % 残留在内核之外」**在本条关门**：间隙只值 0.39 ms/步，而 SUM 与墙钟
   的差在 7 % 时钟台阶面前不构成证据 ⇒ 大批量的差距按**内核内部**处理，不再找提交侧 Reserve。

### 22.6 修好的仪器第一次用在真门上：`SELFLOOP_CHUNK` 三档全部落在底噪内（死路入册）

`gpu_model.rs:3189` 那条注释挂着「超长 command buffer 上每步耗时超线性增长」，而发货档是
`chunk=0`（整段 NTOK 轮录进**一条** command buffer；B=128 时 32 轮 × ≈1477 条 ≈ 47k 条 dispatch）。
用 Δmin 配对（进程内、12 轮、每臂 1 段、奇数轮反序）测「切段 vs 不切」：

| 批宽 | 对照 | A=chunk 0 | B=chunk k | **Δmin** | Δ中位（同一批数据） |
|---|---|---|---|---|---|
| 128 | 0 vs 8 | 52.91 | 53.12 | **+0.39 %** | −1.65 % |
| 128 | 0 vs 16 | 56.76 | 56.46 | **−0.53 %** | −0.22 % |
| 32 | 0 vs 8 | 24.36 | 24.17 | **−0.77 %** | **−8.54 %** |

⇒ 三档全在 ±2 % 空档底之内 ⇒ **切段在 NTOK=32 的段长上没有可测收益**（每 k 轮多付一次
`end_batch/begin_batch` 的等待，正好抵掉「短缓冲」的理论好处）。
⚠️ 第三行的 **Δ中位 −8.54 %** 是活教材：不换成 Δmin，这一档会被当成「切 8 轮一段白捡 8.5 %」

所以这一格即便翻案也不影响发货形态。⇒ 任务：不再作为待办，除非有长段实测。

## §23（2026-10-12）修好的仪器第一次判「真杠杆」：一级 coopmat 在 B=64 打平、在 B=256 赚 15.8 %

§22 把判据换成 Δmin、并量出本机空档底 ±2 % 之后，第一件事就是回头判那两格**一直悬着的发货门**
`LOWRANK_MIN`（默认 64，即 `batch >= 64` 才把低秩一级搬到 coopmat fp16）：

- **B=64 就是门限那一格**。§19 当年的说法是「两负一正、臂内散布 9~10 % > 信号 ⇒ 既不确认也不推翻」。
- **B=256 从来没单独判过**：§15 记的 +12.8 % 只在 B=128，门限以上的更宽档是外推。

### 口径与绑定

`AB_VAR=LOWRANK_GEMM1 AB_A=1 AB_B=0`（A = 发货档「开」，B = 显式关，回到 SIMT mid 臂）。
B=64 跑 12 轮 ×（每臂 1 段 × `NTOK=32`），B=256 跑 6 轮（单轮 8192 tok ≈3.2 s，预算所限），
`AB_WARM=1`、奇数轮换起始臂。其余按发货口径：`PROMPT_REPEAT=6 PAD_TO=512 TOPK=1
PREFILL_SLOTS=8 BACKEND=vulkan`，`power.limit` 300 W。
绑定证据 = 每轮日志**回读** env（`[AB rN A] LOWRANK_GEMM1="1"` / `[AB rN B] LOWRANK_GEMM1="0"`
逐臂成对出现，两档各自的 A/B 轮数 6/6、12/12 全对）+ `PROF_LOW=1` 的 `stage1=true/false`
（B=64：832 / 768 行，B=256：448 / 384 行 ⇒ 两臂都真跑到那个分支）。

### 读数

| 批宽 | A（开）ms/步 | B（关）ms/步 | **Δmin** | Δ中位 | 逐轮配对差 | 判定 |
|---|---|---|---|---|---|---|
| 64 | 31.36 | 31.02 | **−1.06 %** | −3.40 % | 12 对里 11 负，极差 −9.4 % ~ +7.1 % | **打平**（\|Δmin\| 在 ±2 % 空档底内） |
| 256 | 96.81 | 112.09 | **+15.77 %** | +16.02 % | 6 对全正，+13.7 % ~ +17.2 % | **确认赚**（两口径相符、无一 Against） |

两格合起来正好把 §22 的教训演了一遍：
- B=64 的 **Δ中位 −3.40 %** 会被读成「在门限上关掉反而快 3.4 %」⇒ 进而把默认门限往上抬。但它的
  逐轮散布（−9.4 % ~ +7.1 %）比信号本身大一个量级，**Δmin 只有 −1.06 %** ⇒ 这一格什么也不能说，
  只能钉成「打平、不亏」。
- B=256 的 Δmin 与 Δ中位 **相符**（+15.77 vs +16.02）且 6 对全同号 ⇒ 这个才是量到的，不是撞到的。

### 判定与后果

1. **`LOWRANK_MIN` 默认 64 不动**。B=64 现在有结论：**不是赚也不是亏，是打平**；把门限抬到 128
   最多在这一格捡回 ≤1.1 %（低于判据下限），却要在 B=256 上少赚 15.8 % 的同类收益 ⇒ 不换。
   往下放到 32 依旧没有证据（§19 已实测 B=32 净亏）。⇒ 64 是「不亏的最高覆盖点」，发货档正确。
2. **门限以上的收益比 §15 记的更大**（B=128 +12.8 % → B=256 +15.8 %），所以大批量那一侧的低秩一级
   不再是「搬过去了但没在宽批上验过」。§6.1 的 B=256 格里，低秩一级的贡献到此**结帐**。
3. **仪器的分辨率定下来了**：进程内换档 A/B 能判的下限 ≈**2~3 %**（B=128 空档底 ±2 %；批宽越大
   单轮越长、噪声越紧，B=256 六对的极差只有 3.5 %）。⇒ 以后**机制预测收益 <3 % 的杠杆不要用端到端
   A/B 判**，直接上内核级 GPU 时间戳 + 逐位指纹，或者干脆放弃 —— 否则只是把噪声换成结论。

**边界**：两档都是**同进程、状态不重启**（`AB_RESTART=0`）⇒ 本条**只量吞吐**，不提任何质量结论；
数值等价性仍由 `tests/batch_parity.rs` 那条链钉。B=256 只 6 轮，但全同号 + 双口径相符，在本机
历史上属于最干净的一档。

   而它头上**三根杠杆都已被证死**（跨瓦片流水/`IM_NBUF`/`IM_PIPE`、split-K 作吞吐、权重片段直取 global）。
   ⇒ 下一根必须有**新的内核级假设**，不能再拿旧三条换批宽重测。
   ⚠️ 本表的绝对值**不能与 §20 跨会话比**（第 2 轮同会话就差 41.77 vs 46.19 = 10 %）；
   能比的是「份额结构」与「某一核在不在表里」这两类**结构**结论。

## §25（2026-10-12）第一次用 Δmin 做 Vulkan/CUDA 成对基线：它给出的不是「进步」，而是**第八次那张表的统计量偏差**

第八次复测（README §6.1，会话 `20261012-004236`，250→300 W 换档那一轮）用的是**每臂 3 轮取中位**。
§22 把本机噪声机制量清楚之后，同一份发货代码重跑一次成对，唯一变化 = **判据换成 Δmin**、
两后端同会话交错、第 2 轮反序、`power.limit` 300 W（起测 48 ℃）。

| 并发 | CUDA tok/s（两轮） | CUDA ms/步 | Vulkan tok/s（两轮） | Vulkan ms/步 | **Δmin 比值** | 第八次的中位比值 |
|---:|---|---:|---|---:|---:|---:|
| 128 | 3 566.9 / 3 270.1 | **35.89** / 39.14 | 2 659.2 / 2 320.1 | **48.13** / 55.17 | **0.746** | 0.690 |
| 256 | 3 472.6 / 3 455.5 | **73.72** / 74.08 | 2 730.7 / 2 646.5 | **93.75** / 96.73 | **0.786** | 0.762 |

prefill（同一批日志，同一口径）：B=128 Vulkan 23 926 vs CUDA 21 532 ms ⇒ **0.900×**；
B=256 48 240 vs 41 441 ms ⇒ **0.859×** ⇒ 与第八次的 0.89 / 0.86 **对得上**（prefill 单档跑 20~48 s，
时钟台阶被时间平均掉了，所以它本来就比 decode 稳）。

### 这条读数最重要的一句：**代码一行没变**

四个 decode 指纹与第八次**逐位相同**（Vulkan B=128 `0xd2150da` / B=256 `0x1a45b4d4`，
CUDA B=128 `0xd21f638` / B=256 `0x1a49f841`），而中间那三次提交只动了 `sample.comp` 的**编译期可覆盖**
（默认档 = 发货字节，md5 对拍过）与文档/基准 example ⇒ **跑的 kernel 完全同一份**。
所以 0.690 → 0.746（B=128）**不是 +8 % 的收益**，而是：

1. **统计量换了**：中位配对里 CUDA 与 Vulkan 各自被时钟台阶污染的程度不同（台阶在时间轴上成段持续，
   谁落在哪一段是轮转决定的）；Δmin 两边都往下走，但**不等量** ⇒ 比值自己就会动。
2. **会话环境本来就不许比**：纪律第 2 条（跨会话绝对值不可比）在这里第二次应验，而且这次连**比值**
   也不可比 —— 只有同会话双臂才有资格说话。
3. 轮内散布仍然大：Vulkan B=128 两轮 48.13 / 55.17（**14.6 %**）、CUDA 35.89 / 39.14（9.1 %）
   ⇒ 2 轮的 min 仍可能被一次「异常低的轮」抬高。**Δmin 成对基线要 ≥4 轮**才算稳。

### 判定

- **不要**把 §6.1 的 0.690 / 0.762 替换掉：那是中位口径的历史基线，换了就没法与它上面所有行对话。
  正确做法是**并排记下 Δmin 口径的第一组数**，并声明：**今后成对复测一律 Δmin + ≥4 轮**。
- 由此得到一个新的、可用的量级感：B=128 同会话 Δmin 下 Vulkan 比 CUDA **慢 12.24 ms/步**
  （48.13 vs 35.89）、B=256 慢 **20.03 ms/步**。这两个「绝对差额」比比值更适合排任务：
  §24 的 B=128 分核表里 `gemm_imma` 一家 23.90 ms ⇒ **整步差距（12.2 ms）比 gemm_imma 的份额小**，
  也就是说差距**不需要**在多个核上分摊解释，一个 `gemm_imma` 就够。

## §26（2026-10-12）`gemm_imma` 最后一根「换列」杠杆的两条证伪：宽列档 BN=16 与 epilogue 落盘换序

§24 的分箱表把 B=128 的 `gemm_imma` 份额定在 23.90 ms（整步差距 12.2 ms 的另一倍），并留下两条
「看起来像杠杆」的结构性观察：**(a)** 每 warp 的 B 片段 `coopMatLoad` 调用数可以减半（BN 8→16，
每 lane 摊 2 列组）；**(b)** epilogue 全局写 `o = slot*M + r` 每条指令只发 8 × 16 B 碎片 ⇒
扇区利用率 50 %。两条**都测了，都死**，而且 (b) 还顺手第二次验证了 §22 的假杠杆机制。

### 26.1 读数口径与绑定

仪器 = `examples/kernel_bench.exe`（**不加载模型**）+ `VK_SPV_DIR` 热换 `gemm_imma_bm64_nst8.spv` 的字节，
`BACKEND=vulkan`（默认 auto 会选 CUDA，那边 `supports_int8_imma()=false` ⇒ 整表跳过），
`KB_BATCH=128`（另有一组 256）、`KB_REPEATS=8`、同进程内臂序每轮奇偶反转为双臂 A/B。
绑定 md5：发货 = `a16e91789c…`（= 当前 `assets/shaders/spv/`，本轮结束时再次对拍未变）。

### 26.2 死路一：BN=16「宽列」档 —— 片段调用数减半，代价 +6 ~ +39 %

做法：`build.rs` 加第三档 `IM_BN => [def(16,"bn16")]`，kernel 里 `SLOT = BN·NST`、
flush 的 `coopMatStore` 步长、epilogue 的组循环全部走 `IM_BN`；发货档用 `#if IM_BN == 8`
**逐字保留历史文本**。

**一个必须记住的编译器事实**：把 acc 写成通用的 `acc[RPG][IM_BN/8][4]` 会让**发货字节也变**
（18 316 B → 19 308 B）—— glslang **不会**把 trip-count=1 的常量循环折叠掉。
所以「只加一档、不动老档」必须靠 `#if` 分支而不是靠循环边界，改完要 13/13 个发货臂 md5 对拍。

实测（Δmin，B=128 / B=256；`imma_head sum(y)=20024912.0000` 各臂逐位相同 ⇒ 数值精确）：

| 臂 | 几何 | head | key | value | out |
|---|---|---:|---:|---:|---:|
| a4 = `BN=16 NST=4` | SLOT=64 = **与发货同几何**（同 grid、同 ksplit） | **+9.2 %** (1.3438 vs 1.2303) | +9.2 % (0.2380 vs 0.2179) | +6.5 % (0.2701 vs 0.2536) | +12.1 % (0.0944 vs 0.0842) |
| a8 = `BN=16 NST=8` | SLOT=128 ⇒ smem ≈38 KB/块，**占用减半** | +37.6 % | +39.1 % | +25.7 % | +19.2 % |
| a4（B=256，2 轮） | 同上 | +8.5 % (2.6701 vs 2.4613) | +10.3 % | +9.9 % | +2.9 % |
| a8（B=256，2 轮） | 同上 | +33.8 % (3.2941 vs 2.4613) | +27.4 % | +27.0 % | +23.6 % |

**结论 = 上一轮 p14 探针给出的「12.7 ~ 15.2 % 归因给 B 片段取数」是错的读法**：把调用次数减半而
**字节数不变**，得到的不是收益而是回退。真正的成本是**每字节的 LDS/ILP**（宽列把一次 mma 后串起来的
回读宽度从 8 列拉到 16 列，行主序 `tile` 的 bank 冲突面变大），以及**每 warp 独立 mma 链从 4 条掉到 2 条**
（延迟隐藏变差）。占用减半的 a8 档是第二重惩罚。⇒ `IM_BN` 分支、`build.rs` 第三档、runtime 的
`imma_bn/imma_spv` 管道**已全部回退**（`git checkout --`），spv 字节对拍一致。

### 26.3 死路二：epilogue 落盘换序 —— 探针的 −8 % 是假读数，一致的换法只剩 ≤1 %

先说机制，这是本轮真正的收获：`tile` 是 `coopMatStore` 写进 smem 的行主序块，行步长 = `BN` = 8 int。
发货映射 `fcol = lane & 7 / frow = lane >> 3` 让回读地址 = `lane + 32i` ⇒ **无冲突**；
而任何「一条指令发 16 个连续 r」的换序，等价于按 `lr = lane>>1, lc = (lane&1)*4` 这类映射重排 lane，
于是**回读从 32 个不同行退化成 4-way bank 冲突**。写侧省下的扇区，读侧原样吐回去。

- **p16（store-only 探针，数值故意错）**：只改全局写地址（`slot = … + 2i + (lane>>4)`），**保留**无冲突回读
  ⇒ 这是数值一致的内核**拿不到的组合**，纯属时序上限。
  单次读数曾给出 **−8.4 % head / −9.5 % key**；同脚本 4 轮 Δmin 复测 = **−0.1 % / −1.2 %**，
  6 轮再复测 = **−0.6 % head / −3.1 % key / −1.9 % value / −3.6 % out**（base head min 1.1005，spread 3.6 %）。
  ⇒ **−8 % 不可复现，是 §22.3 那个准静态时钟台阶**（谁的轮落在哪一段是轮转决定的）。
  `sum(y)` 也与 base 不同（20010203 vs 20024912）⇒ 按纪律它连「候选」都算不上，只是**禁读数**。
- **c1 / c2（数值一致的两种换列）**：单次读数 ≈ **+17 %**（明显回退，未做 ≥4 轮，不入表）。
- **c3（第三种换列：`lr = lane>>1`、`lc = (lane&1)*4`，flush / `szs` / `xas` / epilogue 四处同步改）**：
  6 轮双臂配对，`sum(y)` 与 base **逐位相同**（head 20024912.0000、key 97899683840.0000、
  value 480213768.0000、out 59992149.0000）⇒ 数值零风险，但收益 = **head −1.1 %（1.1970 vs 1.2108）/
  key −2.0 % / out −5.2 % / value +0.2 %**，`szs` 少 3 条与 `xas` 多 3 条正好抵消。

**判定**：−1 % 量级低于内核级立项门槛（≥3 %），更低到 §22.5 定的**端到端 2 ~ 3 % 分辨率下限**以下；
而唯一看起来更大的 −8 % 是一个物理上拿不到的组合。**「落盘扇区利用率」不是可用杠杆 —— 写侧与 smem 读侧互相锁死。**

### 26.4 由此剩下的唯一解释（也是下一根的边界）

`gemm_imma` 在 B=128 的 Vulkan/CUDA TOPS 差（34.8 vs 50.9，同形状）不是**取数指令数**、不是**取数段长**、
不是**落盘时序**，而是 **accumulator 必须绕 smem 一圈**：GLSL 的 coopmat 片段归属对 lane 不透明，
`coopMatLoad/Store` 是唯一入口，而 nvcc 直接持有 mma fragment 寄存器 —— 去量化/写回都发生在寄存器里。
`subgroupShuffle` 也搬不动它（源寄存器下标随 lane 变，不是 uniform）。
⇒ 这条差距要动就得动**编译器/接口层**（SPIR-V 片段直取、或换 `vkCmdDraw` 级别的自有 tile 约定），
在 GLSL 内核里继续调度的空间**已经用尽**；下一批任务应回到 §4/§5 里那些**还没测的臂**（`pf_value` 深 K 窄 N、
SIMT gemv 组主序取数段长、rkv 三链合并），而不是继续磨 `gemm_imma`。
