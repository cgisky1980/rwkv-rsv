## 0. 为什么是 IMMA

同机基线（2080 Ti / RWKV-7 2.9B / B=256）：Albatross **2874.3 tok/s** vs 我们 **419.2**（6.86×）。
按 FLOP 口径：上游 **17.1 TFLOPS**（fp16 张量核）vs 我们 **2.42 TFLOPS**（fp32 SIMT）——
**差距就是计算单元档位**（详见基线文档 §3）。

Turing 的 int8 TC 峰值 **215 TOPS**（是 fp16 TC 107 TOPS 的 2×），
且我们**本来就把权重存成 int8**（`w = scale[m,k/128]*idx + zero[m,k/128]`）
⇒ 选 `mma.sync.aligned.m8n8k16.s8`，保住 D1 的「int8 常驻 / 8GB 下限」。

## 1. ★ 可行性已证（2026-09-21，一次通过）

临时探针 `backend_cuda::tests::imma_m8n8k16_probe`（合成小 GEMM，int32 逐位对 CPU 参考）
在 2080 Ti 上**通过**。一次同时证了四件事：

1. **NVRTC 能出该指令的 PTX**；
2. **sm_75（Turing）能 JIT 并执行 `mma.m8n8k16.s8`**；
3. 下面这套**片段↔线程映射与我的假设逐位一致**：
   - `groupID = lane >> 2`，`tig = lane & 3`
   - **A（row-major 8×16）**：线程持 `row = groupID`、`col = tig*4 + {0,1,2,3}` ⇒ **恰好一个 `u32`**
   - **B（col-major 16×8）**：线程持 `k = tig*4 + {0,1,2,3}`、`n = groupID` ⇒ **恰好一个 `u32`**
     —— 本工程权重是 `[m][k]` 行主序，**天然就是 col-major 的 B**，零转置
   - **D（8×8 int32）**：线程持 `row = groupID`、`col = tig*2 + {0,1}` ⇒ 2 个寄存器
4. 语义 `D[batch, n] = Σ_k xq[batch,k] * wq[n,k]`（int32 精确累加）与 CPU 参考**完全相等**。

### 1.1 ★ 顺带修掉的一个真 bug：Turing 的 NVRTC 架构选错了

原来 `backend_cuda.rs` 的 arch 选择是：

```rust
let arch = if maj >= 8 { "compute_80" } else if maj == 7 { "compute_70" } else { ... };
```

**cc=7.5（Turing）被归到 `compute_70`**。而 `mma.m8n8k16.s8` 是 **sm_75 起**才有的指令，
PTX 的 `.target` 低于指令要求 ⇒ `cuModuleLoadDataEx failed: **218 a PTX JIT compilation failed**`，
**报错完全不像"指令不支持"，极易误判**。

修法（已落地）：

```rust
let arch = if maj >= 8 { "compute_80" }
           else if maj == 7 && min >= 5 { "compute_75" }
           else if maj == 7 { "compute_70" } else { ... };
```

`sm_75 ⊃ sm_70`，细分不丢兼容性；**全量回归 60 passed / 0 failed**（codegen 会变，已验过）。

## 2. 数学口径：非对称分组量化的正确处理

现有量化：`w[m,k] = s[m,g]·wq[m,k] + z[m,g]`，`g = k/128`。
目标 `y[b,m] = Σ_k x[b,k]·w[m,k]`。把它拆成两项：

```
y[b,m] = Σ_g [ sx[b,g] · s[m,g] · IMMA_g(b,m) ]  +  Σ_g [ z[m,g] · rowsum_x[b,g] ]
                    └── 主项（张量核）──┘             └── 零点修正（G=K/128，可忽略） ──┘

IMMA_g(b,m) = Σ_{k∈g} xq[b,k] · wq[m,k]        （int32，m8n8k16 精确）
rowsum_x[b,g] = Σ_{k∈g} x[b,k]                 （每 token 一次，batch×K 次加）
```

要点：

- **必须按 128 组逐组 flush**：`sx[b,g]·s[m,g]` 依赖 (b,g) 与 (m,g) 两者，
  不能提出 k 求和之外。好在一个 k 组 = 8 个 mma k-step（128/16），
  组内 int32 累加、组末乘系数并入 fp32 累加器即可。**每组每输出 1 次 fp32 FMA**，
  以 ffn_key(B=256) 计 = 256×10240×20 = 52M 次 ≈ **可忽略**。
- **zero 修正是一次小 GEMM**：`rowsum[b,G] × z[G,M]`，G=20 ⇒ 每输出 20 MAC，
  相对 K=2560 是 **0.8%** 的工作量，可放进 epilogue 或独立小内核。
- ⇒ **量化分组（128）反而成了优势**：flush 粒度天然对齐 mma 的 k-step。

### 2.1 待定：激活的量化粒度

`xq` 需对称量化。粒度决定 `sx` 的维度与 IMMA 利用率：

| 方案 | `sx` | 代价 |
|---|---|---|
| per-tensor | 标量 | 最省，但 RWKV 逐层激活动态范围大，精度风险高 |
| **per-(token, k组)** | `[batch, G]` | 与权重分组同构、精度最好；组末 flush 已按组进行 ⇒ **天然契合**，推荐 |
| per-token | `[batch]` | 折中；但 flush 仍须按组（因为 `s[m,g]` 逐组变） |

**倾向 per-(token, k组)**，与既有的 128 分组完全对齐。

### 3.1 激活量化（`QUANT_X_I8_SRC`）

- 粒度 **per-(token, k 组)**，组宽 128（与权重 `s[m,k/128]` 同构）。
- 输出 `xq`（u32 打包 int8，byte i = k%4==i，与 `aidx` 同布局）+ `xaux[b,g] = float4{sx, 128·sx·colsum_xq, rowsum_x, 0}`。
- grid = (G, ceil(rows/8))、block 256（8 warp 各吃一个 (b,g) 组），组内 amax 用 `shfl_xor` 归约。

### 3.2 ★ 关键技巧：无符号 byte 怎么喂给只吃 s8 的 IMMA

磁盘上的 `idx` 是 **0..255 无符号**，而 IMMA 的 A/B 都是**有符号** s8。做法：

```
q_s = q_u ^ 0x80          // 每条 32 位权重 1 条 XOR（落 smem 时顺手做）
signed(q_s) ≡ q_u - 128
```

补偿项 `Σ xq·128 = 128·colsum_xq[b,g]` 在量化阶段预先乘好 `sx` 存进 `xaux.y`，
于是 flush 只需
`y[b,m] += s[m,g]·(sx·S_g + aux.y) + z[m,g]·rowsum_x[b,g]`
（`S_g` = IMMA 的 int32 输出；零点项用**精确** rowsum 而非 `sx·Σxq`，量化误差相消且省一次 rank-1 修正）。

### 3.3b ★ 第四代：r/k/v 也改走 IMMA（`gemv_int8_rkv_stage1_batch`）

第一轮 IMMA 上线后重扫消融，头号瓶颈变成 **`gemv_int8_rkv_stage1_batch`（43%）**。
它内部每层含 3 个 `[c,c]=[2560,2560]` 的 int8 投影（r/k/v，与 `mul_add` 同形状），
仍是 int8 SIMT + `hfma2`——**而同形状隔离计时 IMMA 有 7.18× 空间**。

做法（改动很小）：

1. `imma_gemm_batch` 增加 **`op=4`**：覆盖写但落 **fp16**（`out_v` 是 fp16 语义，
   与 SIMT 路径的 `__float2half` 同舍入）；
2. `gemv_int8_rkv_stage1_batch` 增加参数 **`crows`**（r/k/v 伪行数）：传 0 即整段跳过，
   `grid.z` 也退化为 1；`mid_idx = flat - crows` 保持 mid 投影的索引不变；
3. host 侧 `GEMV_IMMA=1` 且 `batch ≥ 16` 时发 3 个 `imma_gemm_dispatch`
   （r/k fp32 覆盖 op=3、v fp16 op=4），并**顺带省掉 `cast3_f16` 那次降位 launch**。

**实测**：端到端 `577.5 → 767.3 tok/s`（再 1.33×）；每步 443.3 → 333.6 ms。
**累计相对 SIMT 基线 = 400.9 → 767.3 = 1.91×。**

### 3.5 踩坑留档（省一小时）

写数值门禁时把 fp16 的 scale/zero 打包成 `sz` 时写成了
`f16::from_f32(v).to_f32().to_bits()` —— **中间 `.to_f32()` 让 `to_bits()` 取到的是 f32 位型**，
于是内核读到的 `scale` 是垃圾（实测变成 2⁻⁷），门禁一路报"公式错"。
正确写法是保留 `f16` 再 `.to_bits()`（见既有 `make_int8_weights`）。
**教训：内核没错之前先怀疑门禁的位型构造。**

### 3.3d ★ 第五代：ffn 稀疏累加去掉全局原子（`ffn_value_sparse_add_batch`）

第二轮 IMMA 之后重扫消融，`ffn_value_sparse_add_batch` 升到 **33%（#2）**。读源码发现结构问题：

- 旧 grid = `(fh/128, c/256, batch)` = **204800 个 block**，每块只算 128 个 f；
- 于是同一 `(b,c)` 被 `fh/128 = 80` 个 block **用 `atomicAdd` 争抢**：
  **52.4M 次/层、1.68G 次/步**。

改法：**每个 (slot, c 分块) 一个 block 吃掉整段 fh**，块内按 F_TILE=128 分轮
（`__ballot` 压实非零 → smem 列表 → 累加），每个 (b,c) 只被一个块触及 ⇒ 原子数 = 0，
累加顺序固定 ⇒ 顺带把结果变回**确定性**。

★ 坑（吃了一次"输出变乱码"）：**「f 索引」与「c 索引」是两个正交维度**——
线程 `tid` 固定持有 c 对 `(c0, c0+1)`，必须对**组内每一个非零 f** 都累加；
第一版写成"线程 tid 只加自己读到的那个 f"，数学上等价于把矩阵算成了对角，输出立刻崩。
（该内核此前**没有 batch 版数值门禁**，是这次才暴露的。）

小 batch 会因块数骤降而掉速 ⇒ 加 `nf`（f 维分块数）：`batch ≥ 64` 取 `nf=1`（零原子），
更小则 `nf = clamp(512/batch, 1, fh/128)` 换并行度（此时争抢方只有 nf 个）。
可用 `FFN_NF` 覆盖。

### 3.4b ★ 一次「把火把点起来」的诊断投资（`PROF_CUDA_KERNEL` 重做 + `PROF_CUDA_COUNT`）

前面几轮都在用 `ABLATE` 消融猜占比，**信噪比不够**（去掉一个内核会连带改变下游数据，
读数系统性偏高）。这次把两件工具补齐了：

- **`PROF_CUDA_COUNT=1`**：只数「内核被启动了几次」，**不加同步、捕获期也照数**，
  图捕获那一趟走完 `launch_smem` 就等于把图的内容抄了一遍。
  实测 self-loop 图**一步只有 519 次启动**（每层 16 个）。
- **`PROF_CUDA_KERNEL=1` 改成非同步**：launch 前后各记事件**不 sync**，
  排空时一次性 `cuStreamSynchronize` 再批量取 elapsed ⇒ 不破坏流水，测到的是真 GPU 时间。
  必须配 **`NO_SELFLOOP_GRAPH=1`**（捕获期的内核只被记录、不执行，计时全是 0）。

**B=256 每步（32 层）的真实账本 —— 各内核时间之和 287.3ms 与实测步时间 288.5ms 吻合：**

| `gemv_int8_rkv_stage1_batch`（mid 投影） | 2.59 | 83 ms | 29% |
| `ffn_value_sparse_add_batch` | 2.02 | 65 ms | 23% |

> `fuse_ka_dplr_norm` 0.75ms = 336MB/层 ⇒ 450GB/s，**已经贴着 roofline**（WKV 状态是硬成本）。

### 3.4c ★ 一个 local-memory 溢出，值 1.25×

按上面的账本去啃 `gemv_int8_rkv_stage1_batch` 的 mid 分支，发现它内层写的是：

```cuda
const float* xsrc[BGRP];          // 每槽一个基址指针
for (b < bcnt) xsrc[b] = xv + (b0 + b) * c;
... local_dot[b] += w * xsrc[b][kk];   // ← 指针数组被落到 **local memory**
```

指针数组 + 运行期下标 ⇒ 编译器把 `xsrc[]` 放进 local memory，
内层每次访存都变成 local 读写。**改成「基址 + 常数偏移直接寻址」后 2.59ms → 1.03ms（2.5×）**，
端到端 `850 → 1045 tok/s`。

反例留档（同一次实验）：顺手把「每 block 槽跨度」从 8 放大到 16/32/64（想换 x 复用）
**全部更慢**（1.39 / 1.98 / 4.66 ms）——累加器变多又把寄存器压回溢出。**`MID_GG=1` 即最优。**

同样试过的反例（`gemv_lowrank_chain4_batch`）：把它改成「slot 进块内循环」削流量
（717MB→47MB）反而 1.99 → 2.82ms —— block 数从 4608 掉到 288，**并行度塌了**；
该内核在原结构下已是带宽受限（360GB/s）。**已回退并留档「结构不要动」。**

### 3.4e ★ fp16 张量核套到 lowrank chain 是负收益（2026-09-21 反例）

用户建议「你也用 FP16 / 更低精度」。对 lowrank chain4 试了 `mma.m16n8k8.f32.f16.f16.f32`（`CHAIN4_FP16=1`），
**实测 2.03 ms → 6.52 ms（3.2× 更慢）**，默认关闭。根因：

- 本 kernel 的 K 维只有 96/96/64/320（低秩），每链每 block 只有 **1~40 次 mma**，
  mma 本身的吞吐红利摊不薄；
- 实现上每元素要做 fp32→fp16 转换 + 标量 mma（`d[0]` 标量累加），转换 + mma 发射开销
  反而把 SIMT 的流水线打断了；
- 真正瓶颈是**带宽**（360GB/s，已贴顶），不是算力档位 ⇒ 上张量核改变不了带宽受限的本质。

**结论**：剩下那几个 fp32「按行归约」内核（lowrank / ffn 稀疏 / mid 投影）之所以慢是**带宽受限**，
不是算力受限；fp16 mma 帮不了它们。要再压，方向是**削流量**（lowrank 的 717MB/层），
但前面「slot 进块内循环」的反例已证**削流量会塌并行度**——本机这平衡点已经被原结构占住了。

> 即：当前 B=256 ~1000 tok/s 已接近「fp32 状态 kernel 带宽受限 + int8/fp16 线性层已 IMMA」
> 的**结构性上限**。要真正压过 2874，得换一整个维度（比如把 WKV 状态与 ffn 稀疏那批
> 重写成张量核友好的 batch 形式 + 状态走 fp16/bf16），那是动数值口径 + 动状态机的大改。

## 3d. ★ Phase 2-1：低秩链两级 → fp16 张量核 tiled GEMM（2026-09-22）

**结论先行：端到端 B=256 `1025.5 → 1597.5 tok/s`（1.56×，249.6 → 160.3 ms/步）；
低秩链本身 `97ms → 17.7ms/步`（5.5×）。**

### 3d.1 病根不是算力档位，是**分块结构**

§3.4e 曾判「fp32 按行归约内核是带宽受限、fp16 mma 帮不了」，并把 `CHAIN4_FP16`
（6.52ms，比 fp32 还慢 3.2×）当作 mma 无效的证据。**这个结论错了一半**：

- `CHAIN4_FP16` 之所以更慢，是因为它把 mma **套在旧分块里**——仍旧「按 slot 分块、
  每块重读权重」，权重被读 ~20 遍，而 fp16 mma 的算术强度优势完全没兑现；
- 真正的病根是**权重没进 smem、整 batch 没流过**。旧 chain4 的流量账：
  权重 `[C, mid_pad]` 被 `batch/BGRP = 64` 个块各读一遍 ⇒ 717MB/层 @360GB/s。

改法 = **真 tiled GEMM**：权重 tile 进 smem 一次，整 batch 流过；A/B 都是 fp16
（`mma.m16n8k8.row.col.f32.f16.f16.f32`），D 走 fp32 累加。

### 3d.2 落地清单（全部在 `backend_cuda.rs` + `gpu_model.rs` 一处调用点）

| 件 | 落点 | 说明 |
|---|---|---|
| `cast4_f16` | 新增 | xw/xa/xv/xg `[batch,C]` fp32 → fp16（**纯降位，不含 sigmoid**） |
| `lowrank_stage1_gemm` | `LOWRANK_GEMM_SRC` | `mid[b,j] = act(Σ_c x·W1_16[j,c])`，act∈{无,tanh,sigmoid}，出 fp16 |
| `lowrank_stage2_gemm` | 同上 | `out[b,m] = epi(Σ_j mid16·W2_16[m,j])`，epilogue = chain4 逐字语义 |
| `lr16_base` | 新增 | 暂存池（捕获前预建，图安全）：`4×[batch,C]` fp16 + `[batch,Σmid_pad]` mid16 |
| `lowrank_gemm_batch` | 新增 dispatch | `cast4_f16` → 4×stage1 → 4×stage2 |
| `gpu_model` 接线 | `forward_batch_layer` | `lowrank_gemm` 时 mid 伪行数传 0 ⇒ 旧两内核整段跳过 |

**权重零成本**：`w1_16/w2_16/a1_16/a2_16/v1_16/v2_16/g1_16/g2_16` 在模型加载时**已常驻**
（prefill 的 cuBLAS GEMM 在用，`gpu_model.rs` GpuLayer），decode 直接复用。

**g 链的 sigmoid 前移**：旧 chain4 在**内层 k 循环**里对 `xg` 逐元素做 sigmoid
（`sigmoid(xg)·G2`）；新结构把它移到 stage1 的 epilogue（作用于 `mid_g`），
数学等价（sigmoid 是逐元素函数，与线性组合可交换次序）但省掉 k 循环里的逐元素 exp。

### 3d.3 ★ 踩坑：`kernel()` 缓存只按 key 索引、不校验 entry（省两小时）

`CudaBackend::kernel(key, src, entry)` 的缓存是 `HashMap<key, (module, func)>`，
**命中时直接返回 func，不比对 `entry`**。于是：

```rust
let f1 = self.kernel(&kkey, &src, "lowrank_stage1_gemm")?;  // 编译并缓存
let f2 = self.kernel(&kkey, &src, "lowrank_stage2_gemm")?;  // ← 直接命中，返回 **stage1 的句柄**！
```

后果极具误导性：stage2 的 launch 实际执行的是 stage1，于是 stage1 按 stage1 的形参表
去读 stage2 的实参——**把指针当 int 读**（`n_pad` 读成 0x0B24xxxx ≈ 186887168），
地址算飞 1GB 外，`cuStreamSynchronize` 报 **CUresult 700（非法地址）**。
compute-sanitizer 只报「Invalid __global__ read at lowrank_stage1_gemm+0x1660」，
完全看不出是"拿错了函数"。

**修法**：两个入口用不同 key（`{kkey}_s1` / `{kkey}_s2`）。
**教训**：同一个源码里取多个入口时，key 必须逐个入口唯一。

### 3d.4 一级 tile：`BN=64 → 16`（1.44×）

一级的 `n`（各链 mid_pad）只有 64/128/128/320，而 `BN=64` 时 `grid.y = n_pad/64 = 1`
⇒ 整个 launch 只有 `batch/BM = 4` 个 block（68 个 SM 上跑 4 个块，**并行度塌**）。
扫 `LR1_BN`（B=256，8192 次启动）：

| LR1_BN | ms/次 | grid（v/w/a/g 链） |
|---|---|---|
| 64（原默认） | 0.1292 | (4,1) |
| 32 | 0.0968 | (4,2) |
| **16（新默认）** | **0.0900** | (4,4)~(4,20) |

代价是 x 片被重读 `n_pad/BN` 遍，但一级 k=2560 很长、n 很短 ⇒ **并行度远比这点重读值钱**。
（与 §3.4c 的「削流量塌并行度」反例同源，只是方向相反：这次是**加并行度、接受重读**。）

### 3d.5 质量代价（已获用户拍板：默认开）

权重从 fp32 变 fp16 是**真精度变化**（不像 W8A8 那次贪心逐位一致）。
`TOPK=1` 贪心对拍（64 槽 × 64 步 = 4096 token，`DUMP_TOK` 逐 token 比）：

| 指标 | 值 |
|---|---|
| 不同 token 数 | **581 / 4096 = 14.18%** |
| 首处分叉 | 第 63 步（槽 0） |

比 W8A8 的 6.44% 高一档（6.44% 是 top50 采样口径、256 token 样本，两者不完全可比）。
**拍板依据**：信天翁本身就跑 fp16 张量核（基线文档记它 17.1 TFLOPS 就是 fp16 档），
追它就得在同一精度档；且 prefill 早已在用这批 fp16 权重，现在 decode 与 prefill 反而更一致。
`LOWRANK_GEMM=0` / `GEMV_IMMA=0` 可随时回退（两个开关**均已翻默认开**，见 `env_on()`）。

### 3d.6 ★ 新账本（B=256 / 32 层，`PROF_CUDA_KERNEL` + `NO_SELFLOOP_GRAPH`，160.3ms/步）

| 内核 | 每步 | 占比 | 变化 |
|---|---|---|---|
| `ffn_value_sparse_add_batch` | **67.5ms** | **38%** | 不变（新头号） |
| `imma_gemm_batch`（161 次/步） | 42.3ms | 24% | 不变 |
| `fuse_ka_dplr_norm`（WKV 状态） | 24.9ms | 14% | 不变（已贴 roofline） |

| `rwkv_sample_batch`（1 次） | 11.0ms | 6% | 采样本身 |

## 3e. ★ Phase 2-3：ffn_value 稠密 fp16 张量核 GEMM（2026-09-22）

**结论：B=256 `1568.3 → 2005.1 tok/s`（1.28×，160.3 → 127.7 ms/步），
且显存**反而降了 1.6GB**（模型加载后 6747 → 5147 MiB）。**

### 3e.1 判据：大 batch 下「稀疏」是负资产

旧 `ffn_value_sparse_add_batch` 的逻辑是「按 r2 的非零列 gather 权重行」。
它在**单 token 解码**下是对的（只读 4% 权重），但在 B=256 下：

```
权重流量 = 非零率 × fh·C·2B × batch = 0.23 × 52.4MB × 256 ≈ 13.4 GB/层
```

而**稠密** tiled GEMM 把权重整 batch 只读 `batch/BM` 遍（BM=128 ⇒ **2 遍**）：

```
权重流量 = 52.4MB × 2 ≈ 105 MB/层      ← 两个数量级之差
```

稠密多算的 FLOP = `batch·C·fh·2 = 13.4 GFLOP/层`，在 fp16 张量核上只有
`13.4e9/107e12 ≈ 0.125 ms/层`（32 层 = 4ms/步，峰值口径）——**大 batch 下
「算」是免费的，「读」才要钱**。稀疏的价值随 batch 增大而单调消失。

### 3e.2 落地（复用 P2-1 的全部机器）

| 件 | 说明 |
|---|---|
| `ffn_value_gemm` | 3rd entry in `LOWRANK_GEMM_SRC`：`x[b,m] += Σ_j r2_16·W[m,j]`，**就地累加** fp32 |
| `cast_f16` | r2 `[batch,fh]` fp32 → fp16（新 `ffn16_pool` 暂存，捕获前预建） |
| `LR3_BM/BN/BK` | 128 / 64 / 64（smem `(128+64)·(64·2+16)=27.6KiB`；BK=128 会到 52KiB 超限） |
| `ffn_value_dense16` | GpuLayer 新字段：`[C, fh]` fp16 常驻权重 |

### 3e.3 ★ 显存**净减** 1.6GB（顺带缓解 8GB 下限压力）

`load_ffn_value_tiled` 本来就先把 int8 权重反量化成 `oriented`（`[C, fh]` **行主序**），
再逐元素重排成 tiled 布局。而稠密 GEMM 要的 B 操作数**正是 `oriented` 本身**
（`[n][k]` 行主序 = mma 的 col-major B，与 P2-1 同一约定）⇒ 直接把 `oriented`
上传成 fp16 即可，**整块 tiled 构建与重排全部省掉**。

两者体积相同（52.4MB/层）但**互斥**：`FFN_VALUE_GEMM` 开时 `ffn_value_tiled = None`。
实测省下 1.6GB（含原来那份 f32 中间体的生命周期效应）。

### 3e.4 门禁与质量

- **数值门禁** `ffn_value_gemm_matches_cpu`（c=128/fh=256/batch=40，非 tile 整数倍）：
  CPU 走 fp64 累加以隔离「顺序差异」，只比 fp16 输入舍入本身的误差，容差 `2e-3·max(1,|ref|)`。
- **质量**（TOPK=1 贪心，64 槽×64 步，隔离对比）：稀疏 vs 稠密 **19.19%** 分叉。

### 3e.5 累计战果与剩余账本

| 档 | B=256 tok/s | B=64 tok/s |
|---|---|---|
| 起点（IMMA/lowrank/ffn 全关） | 1025.5 | 458.8 |
| P2-1 后 | 1597.5 | — |
| **P2-3 后（当前默认）** | **2005.1**（1.96×） | **1052.0**（2.29×） |

**B=256 每步 127.7ms 的新账本**：

## 3f. Phase 2-4：tile 几何扫描（2026-09-22）——**结论受噪声限制**

| 扫描项 | 各档 ms/次 | 采用的默认 |
|---|---|---|
| `IMMA_BM`（relu2 10240×2560，`kernel_bench` 5 轮取最小） | 64 → 0.6604；**128 → 0.5774** | **128** |
| `IMMA_BN` | 64 → 0.2295；128 → 0.5412；256(BM=64) → 0.9304 | **64** |
| `LR3_BM`（ffn_value_gemm） | **64 → 0.8471**；128 → 0.9983；256 → 1.5212 | **64** |

**共同规律（第三次出现）**：**并行度 > 流量**。BM 越小 ⇒ block 数越多 ⇒ 越快，
即使权重被多读 `batch/BM` 遍。这与 §3d.4（一级 BN 16 优于 64）同源，
与 §3.4c 的「削流量塌并行度」是同一枚硬币的两面。

⚠️ **必须记住的测量纪律**：本机（2080 Ti 兼作桌面显示）**同一配置跨运行可差 ±17%**
（`imma_gemm_batch_b128n64l2` 两次 PROF：0.2295 / 0.2689 ms）。
- 端到端差异 **<5% 不可作 A/B 结论**（本次 tile 改动端到端落在噪声内，故未观察到增益）；
- 单内核调参**必须**用 `kernel_bench`（repeats 取最小）并看「抖动」列，>10% 的行弃用。

## 3g. Phase 2-2：WKV 状态 fp16（2026-09-22）——**已翻默认开**

### 3g.1 做法

`tmix_rnn`（`[batch][H][N][N]`，B=256 时 168MB/层、读写 336MB）改 fp16 存储，
**计算全程仍 fp32**，只在载入/回存降位。三处状态内核
（`fuse_ka_dplr_norm` / `dplr_seq_batch` / `dplr_seq`）用 **typedef 双变体**：

```cuda
#ifdef WKV_S16
typedef __half stype;  st_ld/st_st = half2float/float2half_rn
#else
typedef float  stype;  st_ld/st_st = 恒等
#endif
```

host 侧 `any_ptr()`（fp32/fp16 同取裸指针）+ `dplr_variant()`（按状态张量 dtype 注入
`#define WKV_S16 1` 并**换 key**——§3d.3 的教训已内化：`kernel()` 缓存不校验变体）。
状态持久化（`download`/`upload_part`/`download_part`/`copy_range`）**本就支持 f16，零改动**。

### 3g.2 收益（B=256，同会话背靠背 A/B）

| | tok/s | 每步 ms | 登记张量 |
|---|---|---|---|
| fp32 状态 | 2241.4 | 114.2 | 11554 MiB |
| **fp16 状态（当前默认）** | **2350.3（+4.9%）** | **108.9（−5.3）** | **8904 MiB（−2.6GB）** |

实测只省 5.3ms 而非预算的 12ms（流量减半 168MB/层 ⇒ 理论 10.7ms）⇒
本内核并非纯带宽受限，减字节只兑现了一半。

### 3g.3 ★★ 翻默认的**真正依据**：信天翁的默认档就是 fp16 状态（且运算也是 fp16）

**这一步最初被判「门禁不通过」，是把尺子拿错了**——门禁的参照是"我们自己的 fp32"，
但目标是**追上信天翁**。查上游源码：

```python
# rwkv7_fast_v3a.py:14   DTYPE = torch.float16
# rwkv7_fast_v3a.py:24   WKV_MODE = "fp16"          ← 上游**默认值**
# rwkv7_fast_v3a.py:2404 wkv.append(torch.zeros((B,H,N,N),
#     dtype=torch.float32 if WKV_MODE == "fp32io16" else DTYPE, ...))
# CLI 默认也是 fp16（L1594，注释写 "# fp32io16 is more accurate"）
```

```cuda
// cuda/rwkv7_wkv_fp16_v2.cu —— 上游 fp16 档**连状态运算都是 fp16**
half2 state[CLONE_N / 2];                    // L126 状态寄存器 half2
sa2 = __hfma2(a[j], state[j], sa2);          // L153 fp16 FMA 累加
half sa = sa2.x + sa2.y;                     // L155 fp16 求和
const half2 product = __hmul2(state, av);    // L288 fp16 乘法
```

| 实现 | 状态存储 | 状态运算 |
|---|---|---|
| 信天翁默认（`fp16`） | fp16 | **fp16** |
| 信天翁 `fp32io16`（我们测的 2874.3 基线） | fp32 | fp32 |
| **我们（fp16 存 + fp32 算）** | fp16 | **fp32** |

⇒ **我们比上游默认档更准**（同存储、更高精度运算）⇒ 翻默认**有据**。

⚠️ 顺带一个重要口径事实：**2874.3 是上游 `fp32io16`（它更准的那档）的成绩**，
而 fp16 档在 sm_75 上**编不出来**（用 `cp.async`，全目录零 `__CUDA_ARCH__` 守卫）
⇒ 上游默认档的真实速度本机测不到，只能确定**比 2874.3 更快**。
**即我们追的是一条偏难的线。**

### 3g.4 精度实测（如实留档）

`TOPK=1` 贪心逐 token 对拍 fp32 状态：

| 配置 | 样本 | 分叉率 | 首处分叉 |
|---|---|---|---|
| **B=8** × 512 步 | 4096 token | **0 / 4096 = 0%** ← **假阳性** | 无 |
| B=256 × 64 步 | 16384 token | 2898 / 16384 = **17.69%** | — |
| B=64 × 512 步 | 32768 token | 7621 / 32768 = **23.26%** | slot 1 第 0 步 |

**★ 教训（方法论）**：B=8 的「0% 完美通过」是**假阳性**——batch<16 时线性层走 int8 SIMT，
不走 IMMA/fp16 低秩/稠密 ffn，喂给状态的输入值不同，恰好落在"fp16 舍入不改变 argmax"
的窄区里。**⇒ 长程数值门禁必须在生产批量档（≥64）上做，小 batch 的结论不可外推。**

**★ 教训（尺子）**：门禁阈值必须锚定**参照实现的精度档**，不能锚定自己的上一版。
本次若只看"vs 自己 fp32 = 23% 分叉"就会误杀一个比上游默认更准的选项。

## 3h. Phase 2-②：采样内核 —— **瓶颈已定位（smem/占用率），修法已设计，未落地**（2026-09-22）

`rwkv_sample_batch` 单次 ~10.3ms（B=256，占整步 9%）。**已排除**：不是 top-k/top-p 选择
（`TOPK=0` 10.27ms vs `TOPK=50` 11.48ms，两条路径同量级）⇒ 瓶颈在**共同前缀**：
对 65536 词表做 ~3 遍流式读写（载入 logits → 惩罚 → temperature），流量 ~400MB/步
⇒ 实测仅 **39GB/s（8% 带宽）**。

**根因（已用诊断实验证实）**：`__shared__ float s_val[112][50]` + `int s_idx[112][50]`
= **44.8KB/块** ⇒ Turing 64KB smem/SM **只驻留 1 块 = 4 warp = 6.25% 占用率**；
而本内核是纯流式扫描，靠**内存级并行**喂饱 DRAM（需 ~20 个在飞 warp-load/SM，实际只有 4~8）。

| 诊断 | smem/块 | 单次耗时 |
|---|---|---|
| `MAXK=50`（现状） | 44.8KB | 10.42ms |
| `MAXK=8`（仅诊断，破坏 top_k>8） | 7.2KB | **5.41ms（−48%）** |

**⚠️ 不能简单调小 `MAXK`**：快路径被 `K <= MAXK` 挡掉后会落到兜底路径，而兜底路径是
**K 轮全词表扫描**（top_k=50 ⇒ 50×585 次迭代/线程）⇒ 会慢几十倍。
**也不能按 top_k 做 host 侧变体分发**：self-loop 图捕获后 kernel 变体即被烘死，
而 sampler 参数（含 top_k）是逐轮异步更新的 ⇒ 换 top_k 的请求会跑到错档。

**修法（待落地）**：把「线程私有 top-K 候选表」移出 smem——
① 每线程的 top-K 放 **local memory**（不占 smem）；② 扫描结束做**warp 内 K 路归并**
（shfl 比较 32 个表头，K 轮）；③ 只把 8 个 warp 的表（`8×K×8B = 3.2KB`）落 smem；
④ 块内 tid==0 归并 8 个表。smem 44.8KB → 3.2KB（**14×**），占用率随之解锁。
正确性对任意 top_k 成立，无需 host 分发、无图捕获隐患。
验收：`TOPK=0` 与 `TOPK=50` 双档单次 ≤6ms，且采样结果与现版逐 token 一致。

## 3i. Phase 2-② 采样内核：**只做趟数融合 + 依赖链截断，10.45 → 8.09ms（2026-09-22）**

上面 §3h 的「smem/占用率」诊断**方向对，但修法走不通**——实测数据把病因指向了别处。

### 3i.1 三条实测结论（把病因钉死）

| 实验 | 单次 ms | 结论 |
|---|---|---|
| 基线（7 趟全词表） | **10.45** | — |
| 只融合趟数：7 趟 → 3 趟（载入+惩罚+温度 一趟、掩码+exp+sum 一趟、归一化只做 top-K 那 K 个） | **10.16（−2%）** | **不是带宽/趟数受限**（3 趟共 335MB/10.16ms = 33GB/s，只有 8% 带宽） |
| 再把「缩放值不物化、两趟都从 logits 现算」压到 2 趟 | 9.62（**反慢**） | 去掉流量、加回 ALU ⇒ 净亏。**已回退，勿重试** |
| ★ 把表内最小值 `thr` 从 smem 镜像到**寄存器** | **8.05（−21%）** | **真凶是主循环的依赖链** |

**根因**：旧版主循环写成 `if (v > s_val[tid][K-1])` —— 每轮都要读一次 smem 再拿它做
分支判据，**smem 读落在关键路径上**，编译器无法把后续全局载入提前发出（本内核只有
4 warp/SM，全靠内存级并行掩盖延迟）。改成 `float thr` 寄存器镜像后，主循环变成
「纯载入 + 比较」，只有真正插入时才触碰 smem。

**三条否定结论已写进内核注释**（防后人重蹈）：趟数融合、不物化 temp、加大并行度
的 tile 调整都无效；**这个内核要的是「砍依赖链」而不是「砍流量」**。

### 3i.2 落地内容（`SAMPLE_BATCH_SRC`）

1. **`sample_scaled1()`**：把「惩罚 → temperature」抽成 `__device__ __forceinline__` 函数，
   供两趟复用（同一表达式算两次逐位相同）。
2. **7 趟 → 3 趟**：`载入+惩罚+温度` 合一；`掩码+exp+sum` 合一（`m` 直接取 top-K 归并的
   `s_sorted[0]`，不必再扫一趟 max；低于阈值当场取 0，等价于 `exp(-1e30-m)`）；
   **归一化只做 top-K 那 K 个索引**（§8 快速分支与 §9 都只读这 K 个）。
3. **寄存器阈值 `thr`**（见上）。
4. `s_maxkeep` / `fast_k` 两个中间量；`need_full_norm` 保证 §8 **兜底分支**
   （`sample_top_candidates` 按概率累计到 top_p）仍拿到整表归一化值。

**验收**：`TOPK=0` 与 `TOPK=50` 双档 token 指纹 `sum=0xd182bf8 xor=0x7c02` **与改前逐位一致**；
64 单测 + doctest 全绿。

⚠️ **仍未落地**：smem 从 44.8KB 降下来（values-only 表 22.4KB ⇒ 2 块/SM，或
warp 内 K 路归并 ⇒ 3.2KB）。按 §3i.1 的结论，**收益上限约 −2.7ms**，且需要
「索引二次恢复」或「分层归并」的额外复杂度 ⇒ 优先级排在 IMMA 重构之后。

## 3j. Phase 2-5：ffn_value 稠密 GEMM 从 fp16 换成 **int8 IMMA**（2026-09-22）

### 3j.1 为什么能直接换（零新内核）

`imma_gemm_dispatch` 本来就是「A 侧量化（`quant_x_i8`）+ int8 权重 + mma」，
而 ffn_value 的形状恰好完全吻合：

| 项 | ffn_value GEMM |
|---|---|
| 语义 | `x[b,c] += Σ_f r2[b,f]·W[c,f]` |
| `m` / `k` | `m = c = 2560`（输出行）、`k = fh = 10240`（归约维） |
| 权重 | `{key}.int8_idx` **本身就是 `[c, fh/4]` u32**（`load_linear(..., c, fh)`）⇒ **零转换** |
| 输出 | `bb.x`（fp32）⇒ `op=1`（就地累加） |

⇒ 只需 ① `backend.rs` 加一个 trait 方法 `ffn_value_imma_batch`（默认 Err）；
② `backend_cuda.rs` 实现（3 行，转发到 `imma_gemm_tiled`）；③ `gpu_model.rs` 调用点优先走它。

### 3j.2 两条收益

1. **权重字节减半**：fp16 常驻 52.4MB/层 → int8 26.2MB/层，且重读 `batch/BM` 遍
   ⇒ 210MB/层 → 105MB/层。
2. **A 侧改由 `quant_x_i8` 在核内量化** ⇒ **`cast_f16` 整段省掉**（10.5MB 读 + 5.2MB 写/层）。

### 3j.3 实测（B=256，交错 A/B，2 轮各 2 次）

| `FFN_VALUE_IMMA` | tok/s | 每步 ms |
|---|---|---|
| `0`（fp16 dense，P2-3 版） | 2294.6 / 2290.9 | 111.5 / 111.7 |
| **`1`（int8 IMMA，当前默认）** | **2422.1 / 2447.6** | **105.7 / 104.6** |

⇒ **+5.8%**；`ffn_value_gemm_b64n64k64_g` 0.845 → `imma_gemm_batch_b64n64l2` 0.639 ms/次
（32 次/步 ⇒ **27.0 → 20.4ms/步**）。

**新增 tile 旋钮** `FFN_IMMA_BM` / `FFN_IMMA_BN`（默认 64/64）：全局 `IMMA_BM=128` 时
本形状 grid 只有 `(2560/128)×(256/64) = 80` 块，喂不满 68 个 SM；BM=64 抬到 160 块。
`IMMA_LB2` 2→3 实测无增益（2416/2465 抖动内），保持 2。

### 3j.4 质量（这是本次最关键的判据）

固定 seed、`SLOTS=64 SEGS=2 NTOK=32 TOPK=1`（贪心）逐 token 对拍：

| 对比 | 分叉率 | 首处分叉 |
|---|---|---|
| sparse（fp16 平铺，P2-3 之前的参照） vs **fp16 dense** | 18.51% | @128 |
| sparse vs **int8 IMMA（本次）** | **16.89%** | @128 |
| fp16 dense vs int8 IMMA | 13.92% | @320 |

★ **结论：int8 IMMA 相对 sparse 参照比现行 fp16 dense 更准**（16.89% < 18.51%），
因为它把**权重**保持在模型原生的 int8 上、只对激活做 per-(token,128 组) 对称量化，
而 fp16 dense 是「把 int8 权重反量化成 fp16 再算」。⇒ 换掉是**净收益**，不是净损失。

## 3k. Phase 2-6：**交换 IMMA 的 grid 维序**（L2 复用），+4.1%（2026-09-22）

### 3k.1 先建一把「解码专用账本」的尺子（本次方法论收获）

`PROF_CUDA_KERNEL` 的 `avg` 是**整轮（prefill + decode）的均值**，而 prefill 每步处理的
token 多得多 ⇒ 混用内核的 avg 会把解码成本高估 3 倍以上（曾据此得出「imma 110ms/步」的
荒谬结论）。**正确做法：跑两次只改 `NTOK`（8 与 72），把两份 PROF 的 `total` 相减再除以
步数差**（本例 192 步）⇒ 得到纯解码账本：

| 内核 | ms/步 | 占比 |
|---|---|---|
| `imma_gemm_batch_b128n64l2`（r/k/v/o + ffn_key，160 次） | **36.92** | 34% |
| `imma_gemm_batch_b64n64l2`（ffn_value，32 次） | **21.52** | 20% |
| `fuse_ka_dplr_norm_s16`（WKV 状态） | 17.94 | 17% |
| `lowrank_gemm_1b64n16k128_2b64n64k64_s1`（128 次） | 10.78 | 10% |
| `rwkv_sample_batch` | 8.09 | 7% |
| `lowrank_..._s2` | 3.72 | 3% |
| `quant_x_i8`（192 次） | 3.34 | 3% |
| `norm_lerp6_batch` / `cmix_norm_lerp_batch` / `cast4_f16` | 5.90 | 5% |
| **合计** | **108.6** | |

⇒ **两个 IMMA kernel 占整步 54%**，是唯一值得动的大头；WKV 已贴 roofline（268MB/层
@ ~516GB/s）无空间。

### 3k.2 改动与依据

CUDA 的线性块号是 `x + y*gridDim.x`。原维序把 **batch 槽块放在 y**（慢变）、权重行块放在 x
⇒ **连续块各读不同的权重 slab，权重被 `batch/BN=4` 重读时零 L2 复用**。
把两维对调（`#define IM_SWAP 1`，host 同步换 grid 元组）后，**连续 4 个块共享同一份权重
slab**（只是槽块不同）⇒ 重读命中 L2（slab = `BM·K·1B`，BM=128/K=2560 时 328KB，
34 个 slab 组 ≈ 11MB，L2 5.5MB 部分命中）。

### 3k.3 实测（B=256，3 轮交错 A/B）

token 指纹 `sum=0xd182bf8 xor=0x7c02` **逐位一致**（纯调度变化，零数值影响）。

**翻默认后重扫 tile**（`IMMA_BM/IMMA_BN`，SWAP=1）：`128/64` **2561.0** · `64/64` 2373.8 ·
`64/128` 2234.3 · `128/128` 1722.9 ⇒ **仍以 128/64 最优，tile 不变**。
`IMMA_LB2` 2→3 亦无增益。

## 3l. Phase 2-7：`imma_gemm_batch` 的 flush 改为 **smem 取 `xaux`**，+6.1%（2026-09-22）

### 3l.1 先排除「软流水」（重要反例）

按 §3k.1 的账本，IMMA 已占 54%，先试了教科书解法——**k-tile 软流水**
（每线程把下一块的 W/X 预取进 24 个 u32 寄存器，与 mma/flush 重叠）：

| 配置 | tok/s |
|---|---|
| `IMMA_PIPE=0` | 2550.3 / 2527.4 |
| `IMMA_PIPE=1` | **1636.3 / 1614.2（−36%）** |
| `IMMA_PIPE=1` + 换轻寄存器几何 `BM=64`（累加器 64 → 16 个） | 2379.0（对 `BM=64/PIPE=0` 的 2372.0 **无差异**） |

★ **两条结论**：
① `BM=128/BN=64` 时累加器已占 `NT×NST×4 = 64` 个寄存器，再加 24 个预取寄存器直接
溢出到 local memory ⇒ −36%。**本内核寄存器是硬约束，「用寄存器换延迟隐藏」走不通。**
② 换成轻寄存器的 `BM=64` 后软流水**完全无效**（2379 vs 2372）⇒ **本内核也不是
k-tile 载入延迟受限**。⇒ 排除「延迟」这条线，转向「流量」。

### 3l.2 真凶：flush 里的 `xaux` 全局读

```cuda
// 旧版（每 k-tile、每线程）
for (int rg = 0; rg < NT; rg++)
  for (int st = 0; st < NST; st++) {
      const float4 au = xaux[min(col0 + st*8 + gID, batch-1) * G + gr];   // ← 全局读
      ...
  }
```
`NT×NST = 16` 次/线程（CSE 后 8 次）⇒ 每块每 k-tile **32KB**、每块 **640KB**、
全步 **13GB** —— **比 W/X 的 staging 流量（10GB）还大**，而它只是同一列 `xaux[sb][gr]`
被 16 个 `(rg,st)` 反复取。

**改法**：与 W/X 同一趟把**本 k 组的 `xaux` 列**（`BN` 个 float4 = **1KB**）搬进 smem，
flush 改读 smem。全局读从「每块每 k-tile 2048 次 float4」降到 **64 次**。

### 3l.3 实测

| | tok/s（3 轮） | 均值 |
|---|---|---|
| 改前 | 2713.9 / 2706.3 / 2707.4 | 2709.2 |
| **改后（当前默认）** | **2709.1 / 2712.1 / 2720.0** | **2713.7** |

⚠️ 注意：**交错 A/B 显示 +6.1%**（2553.7 → 2709.2，见 §3l.4），但**改前那 3 轮已是
改后代码**——两次测的都是同一份代码，差异来自机器漂移。**唯一可信的是改前基线
（`IMMA_XA_SMEM` 不存在时的 2553.7 / 2550.3 / 2527.4）与改后的 2709~2720。**

**新解码账本（同 §3k.1 的差减法，97.2ms/步）**：

|---|---|---|
| `imma_gemm_batch_b128n64`（160 次） | 36.92 | **28.31** |
| `imma_gemm_batch_b64n64`（ffn_value，32 次） | 21.52 | **18.91** |
| `fuse_ka_dplr_norm_s16` | 17.94 | 17.83 |
| `lowrank_..._s1` | 10.78 | 10.79 |
| `rwkv_sample_batch` | 8.09 | 8.07 |

### 3l.4 顺手做的一个反例：`asz` 不要搬 smem

`asz[r0*G+gr]` 每线程每 k-tile 只有 2 次（天然命中 L2）⇒ 照 §3l.2 搬进 smem 后
**端到端 −2.7%**（2713.9 → 2634.8）。原因：搬它需要 128 个线程做 **80B 跨步的未合并读**
+ 多一次同步。**判据：只有「每线程多次重复读同一地址」才值得搬 smem**（xaux 是 16 次，
asz 是 2 次）。

**关键方法论**：本机端到端跨时段可漂 **>5%**（本次会话内 prefill 从 29.1s 掉到 27.7s），

## 3m. Phase 2-8：低秩一级 **4 链合并成一次 launch** ⇒ ★ **反超信天翁**（2026-09-22）

### 3m.1 病灶：4 次串行 launch 的 grid 太小

`lowrank_stage1_gemm` 原本**每条链一次 launch**，四条链的 `n_pad` 是 **64/128/128/320**
（BN=16 ⇒ grid.y = 4/8/8/20），乘上 grid.x = `batch/BM = 4`：

| 链 | grid | 块数 | 波数（68 SM） |
|---|---|---|---|
| v（n_pad=64） | 4×4 | **16** | 1（**52 个 SM 空转**） |
| w（128） | 4×8 | 32 | 1 |
| a（128） | 4×8 | 32 | 1 |
| g（320） | 4×20 | 80 | 2 |
| | | | **合计 5 波** |

而该内核实测只有 **193GB/s**（65MB/层 ÷ 0.337ms）——**39% 带宽**，说明**不是带宽受限，
是并行度受限**（与 §3k.3 / §3l 的「流量 vs 并行度」是同一枚硬币）。

### 3m.2 改法

把一级改成 **一次 launch 跑四条链**：kernel 增加 `blockIdx.z` 选择链，
参数收成 4 组 `(W, X, mid, n_pad, act)`；grid = `(batch/BM, max_pad/BN, 4)`

## 3p. Phase 2-11：**split-K**（小 batch 加块的唯一手段）⇒ ★ **全档位明确反超**（2026-09-22）

### 3p.1 先把「按形状分解的账本」这把尺子建起来（本次最关键的方法论）

`PROF_CUDA_KERNEL` 原本**按几何名分桶**（`imma_gemm_batch_b64n32l2s1p0d1`），
于是 `rkv` / `ffn_key` / `head` 三个形状全挤在一个桶里，小 batch 的账本无法分解。
改法：**kernel cache 的 key 里带上 `m`/`k`**（源码与几何无关，形状只有个位数，
多编译几次可忽略）。另外 `imma_gemm_dispatch_z3` 的 key 加 `z3` 前缀，避免与单链同名。

同时确认了剖析器**必须用「同一次运行内 dump2 − dump1」**：`dump_prof` 每次 `end_batch`
打印且**不清零**，warmup 用的是同一个 `ntok` ⇒ 跨运行相减会多算一份 warmup（差 2 倍）。

**B=64（无图路径，34.5 ms/步）的真实账本 —— 每 block 吞吐被钉死在 ~90 GMAC/s：**

| 形状 | 块数 | 每块 W 字节 | 每块 MAC | 实测 per-launch | 推出 per-block 吞吐 |
|---|---|---|---|---|---|
| `att_output` (2560,2560,BN=32) | 80 | 164 KB | 5.24 M | 60.2 µs | **87 GMAC/s** |
| `ffn_key` (10240,2560,BN=64) | 160 | 164 KB | 10.5 M | 143.3 µs | **87 GMAC/s** |
| `ffn_value` (2560,10240,BN=32) | 80 | 655 KB | 21.0 M | 227.3 µs | **92 GMAC/s** |

⇒ **每 block 吞吐与形状无关（~90 GMAC/s）**，而**聚合吞吐随并发块数单调上升**：
80 块 → 102、160 块 → 172、1024 块 → 232 GMAC/s/SM。
小 batch 时 `grid.y = batch/BN = 1`，块数只剩 `M/BM`（M=2560 ⇒ 只有 40~80 块，68 个 SM 大半空转）
⇒ **加块 = 提速**，而 split-K 是**唯一不增加流量的加块手段**。

### 3p.2 落地

- **内核**：`IM_KSPLIT` 宏；`blockIdx.z` 语义变为 `z = chain·IM_KSPLIT + ksp`
  （`IM_KSPLIT == 1` 时退化为原来的 `z = chain`，源码逐字等价）；k 循环改成
  `for (kt = ksp·kb; kt < (ksp+1)·kb; kt += BK)`；epilogue 在 `ks>1` 时**只写部分和**
  （`yp = y + ksp·batch·m`，布局 `[ksplit][batch][m]`），`op` 交给归约内核。
- **归约内核** `imma_gemm_reduce`（独立源码，只编这一条）：按 **ksp 升序**逐项相加
  ⇒ **确定性**（刻意不用 `atomicAdd`，项目要求 token 指纹可复现），再施加原 `op`
  （`0`=relu²、`3`=覆盖、`4`=覆盖落 fp16、其余=`+=`）。
- **暂存**：新开 `ipart_pool`（f32，`nchain·ksplit·batch·m`），在 `begin_batch` 预建
  （图安全，与 `xq`/`xaux` 同规矩）。

### 3p.3 ★★ 途中挖出的一个**真 bug**：`cuGraphInstantiate` 解析到了 v1（五参数）符号

加 split-K 后 `batch_decode_bench` 开始**在 `cuGraphInstantiate` 内部确定性 `0xC0000005`**
（`STATUS_ACCESS_VIOLATION`，8/8）。逐步排除：

| 实验 | 结果 |
|---|---|
| `IMMA_KSPLIT=0`（关） | **0/6 崩溃** |
| `NO_SELFLOOP_GRAPH=1`（不走图） | **0/6 崩溃** ⇒ 与图有关，不是 kernel 内存错误 |
| 跳过归约内核、只留 split 的 GEMM | **6/6 崩溃** ⇒ 不是归约内核，是 **GEMM 变体/图内容** |
| 在 `cuStreamEndCapture` 前后、`cuGraphInstantiate` 前后各打一行日志 | 稳定停在 **`before cuGraphInstantiate`**（8/8） |

根因在**符号解析顺序**：

```rust
sym(&lib, "cuGraphInstantiate", &[b"cuGraphInstantiate\0", b"cuGraphInstantiate_v2\0"])
```

本工程用的 typedef 是**三参数** `(CUgraphExec*, CUgraph, flags)`（= v2 / WithFlags 的签名），
但**优先解析到的却是 v1 的 `cuGraphInstantiate`（五参数）**：
`phErrorNode`/`errorString` 是第 3/4 个形参 ⇒ 第 3 个实参 `0` 被当成 `phErrorNode`（写 NULL），
第 4/5 个形参是**寄存器垃圾**当 `errorString` ⇒ 驱动里踩空指针。

**修法**：优先取 `cuGraphInstantiateWithFlags`（三参数，语义完全一致），再退 `_v2`，最后才 v1。
**修后 8/8 → 0/8**（后续 18 次连跑 0 失败）。

> 这条同时解释了文档里长期挂着的两条「未定位」记录：§3l 的「偶发退出崩溃 0xC0000005，
> 发生在结果打印之后（约 10 次 1 次）」与 backend_cuda.rs 里「高频 instantiate 触发驱动崩溃」
> ——**同一个 ABI 错配**，只是触发概率随图大小/时序变化。

### 3p.4 参数标定（全部同会话交错 A/B）

**① 目标块数**（B=64，tok/s 越大越好）：

| `IMMA_KSPLIT_TARGET` | 136 (2×SM) | 272 (4×SM) | **400 (6×SM)** | 544 | 800 |
|---|---|---|---|---|---|
| B=64 | 2164 | 2219 | **2234** | 2185 | 2144 |

⇒ **400 是峰值**（再多则部分和流量 + 归约开销反超并行收益）。`IMMA_KSPLIT_MAX` 取 **5**。

**② 闸门一：`batch/BN > 2` 不切**。`batch/BN` = 「同一份权重 slab 被几批 batch 列块重读」，
≥3 时 grid 的 batch 维本身已够块数。实测 B=256 的 `att_output`/`ffn_value`
（`batch/BN = 4`、80 块）：**3250.4 → 3244.8（−0.2%）**。加闸门后 B=256 回到 3307。

**③ 闸门二：多链合并的 launch（`z3`）不自动切**。`imma_gemm_dispatch_z3` 已用
`grid.z = 3` 把 r/k/v 并成一次 launch（块数 ×3），再切 K **收益小、代价是 3 份**
（每条链一次归约）。实测 B=64：全切 **2090** vs 只切 `att_output`/`ffn_value` **2131**
⇒ **r/k/v 那一刀净亏约 2%**。

**④ 成本账（B=64 无图路径，ms/步）**：

| 项 | Δ |
|---|---|
| `ffn_value`（ks 1→5） | **−1.690** |

### 3q.2 已落地：`IMMA_MIN_BATCH` 8 → **1**

`gemv_variant_dispatch` 本来就有 IMMA 分支，只是被 `batch >= imma_min_batch()` 挡住。
把阈值降到 1 之后 **batch=1 也走 W8A8 张量核**：

|---|---|---|---|
| 批量路径 B=1 | 65.1 / 67.5 | **78.8 / 78.8** | **+18%** |
| 单流 selfloop（同一条 dispatch 的 batch=1 分支） | 75.4 | **80.4** | **+6.6%** |

机理：小 batch 的瓶颈是**每 block 摊到的权重流量**，不是张量核利用率 —— `BN` 由
`small_batch_bn` 保证 ≥8，**槽位浪费不影响权重读取量**（每 block 读的 W 字节与 BN 无关）。
单流 prefill（`forward_seq_with_state`）`WARMUP=0` 隔离实测**在噪声内**（首段多出的 ~200ms
是一次性图捕获，多编了几个 batch=1 变体）。

⚠️ **连带的门禁修正**：`gemv_variant_int8_matches_cpu` / `gemv_int8_plain_matches_cpu`
压的是 **int8 SIMT** 内核（容差 2e-2 按 fp16 激活标定），阈值降到 1 后 batch=2 会被
IMMA（W8A8，误差更大）接走而越界。修法：给 `CudaBackend` 加**每实例**字段
`imma_min_batch_override`（不用全局环境变量，避免测试串扰），两个门禁置 `Some(8)`。
另外 `imma_gemm_matches_cpu` 扩到 7 组（batch=1/3 + `BN=8` 的档位，覆盖 mma n 维刚好填满）。

  - `BN` 变大换 ILP（`NST` 1→2/4/8）：8 → 16 持平、32 −5%、64 −18%（**BN=8 最优**）；

- ⇒ 剩下的怀疑点是**每 k-tile 的固定开销**（每 k-tile 实测 ~3.8µs = 5700 cycle，
  而 8KB 的载入在 600ns 延迟下只该 ~600 cycle）。已排除「指令数」（uint4 无效）与
  「延迟隐藏」（`IM_PIPE`/`IM_NBUF` 都无效）⇒ 更可能是 **barrier 与
  `asz`/`xaux` 全局载入的串行点**。**下一步：BK 128 → 256**（flush 仍按 128 组做两次）
  以把 barrier 与 s/z 载入的**次数减半**；这是目前唯一还没试的方向。
- ★ **再补一个关键的定量结论（按块折算）**：把各形状的「每块权重字节 / 每块时间」算出来，

  ⇒ **每 SM 只有「1 个块」的带宽在真正流动**（`IM_LB2=2` 名义 2 块/SM，但第二块不产生
  额外吞吐）；而 §1.1b 的纯权重读探针每 SM 能到 **7.8 GB/s**（528 GB/s ÷ 68）。
  **差的就是这 1.8×**，且它与 BM/BN/占用率/split 全部无关 ⇒ 瓶颈在**单个块的
  访存流水线内部**（每 k-tile 一次「载入→barrier→算→flush→barrier」的串行链）。
  `BK=256` 正是针对这条链的「每字节串行次数」减半。
- **另测**：`IMMA_BM_SMALL=64/128/256` 在 batch=1 **完全无差异**（78.9~80.6）——

### 3q.4 ★ 单流采样器：结构上明显低效（下一个确定收益点）

`rwkv_sample`（**单流专用**，`SAMPLE_SRC`）与已优化的 `rwkv_sample_batch`
（`SAMPLE_BATCH_SRC`，§3i 把 7 趟融成 3 趟）**是两份源码**。单流版的病灶：

- **`grid=(1,1,1)`、`block=(112,1,1)`** —— 整段 65536 词表的采样只有 **1 个块 112 线程**；
- 每个 pass 都是 `for (int i = tid; i < n; i += BS)` ⇒ **585 次/线程的串行访存**
  （无 ILP，每轮 ~600 cycle 延迟），而这样的 pass 有 **~9 个**
  （copy → temperature → mask 清零 → top-p 候选扫描 → softmax 的 max/exp+sum/normalize
  → cutoff 清零 → 采样扫描）⇒ 585×9×600 ≈ 3.2M cycle ≈ 2.1ms，**实测 1.74ms 吻合**。
- 实测两条采样路径（`TOPK=0` 兜底 / `TOPK=50` 快速）**代价相同**（76 / 74 tok/s）
  ⇒ 瓶颈是**共享的全量扫描趟数**，不是 top-K 选择本身。

**修法（已落地）**：把每个扫描趟按 4 个元素/线程展开（`SAMP_SCAN4` 宏，保持
「同一元素→同一 lane、同一顺序」⇒ **语义逐位不变**；尾部用标量循环收尾）。
⚠️ 注意 `s_val[tid][j]`/`s_idx[tid][j]` 与 `block=(112,)` 是**绑死的**
（host 注释：tid≥112 会越界 → sticky error 700），所以只能改**循环展开**，
不能简单加大 block。

**实测（`rwkv_sample` ms/32tok，同会话剖析）**：

| 版本 | `rwkv_sample` | 单流内核总和 |
|---|---|---|
| 原始 | 69.640（2.176 ms/token） | 609.34 |
| 4× 展开（守卫写在展开体内） | 69.218（**−0.6%，等于零收益**） | 602.37 |
| **4× 展开（无守卫主循环 + 尾部标量）** | **65.306（−6.2%）** | **601.61（−1.3%）** |
| 端到端单流 | — | 75.9~76.1 → **77.2~78.4 tok/s（+2%）** |

⇒ **结论修正**：采样器**不是**纯「扫描趟延迟」受限 —— 4× 展开只拿到 6%，远低于
预测的 4×。剩下的成本应在 `expf`（65536 次/112 线程）、O(BS²) 定秩、以及末尾
**单线程** 65536 次前缀扫描上。⇒ **单流采样器的进一步优化收益有限，优先级下调。**

  （全在噪声内）；`IMMA_BN_SMALL` 8/16/32/64 → 94.5/93.4/87.0/75.0（8 最优，与批量侧一致）。
- **IMMA 路径 vs SIMT 回退在同一形状**：`IMMA_MIN_BATCH=1/8/64/256` → 90.9/84.3/84.0/83.8
  ⇒ IMMA 在 B=1 仍明显更优（但 `gemv_int8_rkv_stage1` 的 r/k/v 段本身已 ~511 GB/s）。

### 3r.4 验收（同机同刻，多轮交错）

单流 B=1 交错 3 轮（每轮：先测我们、立刻测 Albatross）：

| 轮 | 我们 | Albatross |
|---|---|---|
| 1 | 96.8 | 94.2 |
| 2 | 94.1 | 96.4 |
| 3 | 94.6 | 98.2 |
| **均值** | **95.2** | **96.3（1.012×）** |

⇒ **统计持平**（Albatross 的 B=1 跨轮漂移 94.2~99.0 达 5%，我们的 94.1~97.2 为 3%）。

## 4. 关键路径预算（ffn_key，B=256，M=10240 K=2560）

| 项 | 值 |
|---|---|
| MAC 总量 | 10240×2560×256 = 6.7 GMAC = 13.4 GOP |
| int8 TC 峰值 | 215 TOPS ⇒ **0.062 ms**（vs 现状实测 4.374 ms） |
| 权重字节（int8） | 27 MB ⇒ 0.054 ms @500GB/s |
| x 字节（int8） | 256×2560 = 0.66 MB（**比 fp16 又减半**） |
| x 重读（块覆盖 BM 行） | `(M/BM)×batch×K×1B`，BM=256 ⇒ 26 MB |
| 权重重读（块覆盖 BN 槽） | `(batch/BN)×M×K×1B`，BN=32 ⇒ 216 MB |

⇒ 取 **BM≈256 行 / BN≈32 槽** 的块划分，总量 ~242 MB ⇒ **0.48 ms**，相对现状 **9×**。
（IMMA 下寄存器不再是绑缚：一个 `m8n8k16` 吃 8×8×16 = 1024 MAC，
而 SIMT 时代每线程 32 个 `half2` 累加器只换来 64 MAC/轮。）
