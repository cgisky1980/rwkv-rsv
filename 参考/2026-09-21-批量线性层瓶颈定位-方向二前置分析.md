# 2026-09-21 批量线性层瓶颈定位（「方向二：对标 rows_cutlass 上 tensor core」前置分析）

> 目的：在动手改批量线性层内核前，先用**可信的测量**确定瓶颈，避免优化错方向。
> 环境：RTX 2080 Ti（理论带宽 ~616 GB/s、fp16 ~13.45 TFLOP/s）/ RWKV-7 3B int8 /
> g1j 量化（`w[m,k] = scale[m,k/128]*idx[m,k] + zero[m,k/128]`，idx 4×uint8 打包进 uint32）。
> 基准：`cargo run --release --example batch_decode_bench`（SLOTS=8 SEGS=2 NTOK=32 TOPK=50）。
> 基线：**批量 B=8 decode 259.7 tok/s 聚合 ≈ 30.8 ms/步（8 token）**。

---

## 1. 先修测量方法：`PROF_CUDA_KERNEL=1` 的数字不可用

`CudaBackend::launch_smem` 的 per-kernel profiling 在每个 kernel 后
`cuEventSynchronize`，完全序列化且把同步开销计入 kernel 时间。实测 batch 段：
内核数 ≈ 14400，各 kernel 累计"耗时"总和 3138ms ≈ 与"14400 × 单次同步开销"同量级
——**测到的主要是同步开销，不是内核**。据此得出的占比（如 dequant_int8 61%）会严重误导。

**新增诊断设施：消融探针 `ABLATE=<kernel名逗号分隔>`**（`backend_cuda.rs::ablate_hit`）。
命中则**不启动**该 kernel，其余流水/图重放完全不变 → 总步时间差 = 该 kernel 的关键路径贡献。
只在设了环境变量时生效，平时零开销（`ablate_hit` 先查 `OnceLock`）。

> 注意：消融会让下游读到陈旧数据，**部分内核会因此变快**（如 r2 全零时稀疏 FFN 几乎免费），
> 所以读数应理解为「移除收益上界」，不是干净份额。

---

## 2. 消融结果（B=8，512 token；基线 decode 2414ms）

| 消融的 kernel | decode | 移除收益 | 说明 |
|---|---|---|---|
| （无） | 2414 ms | — | 基线 |
| `gemv_variant_mb` | 1204 ms | **-1210 ms** | 批量线性（att_output / ffn_key / head） |
| `gemv_int8_rkv_stage1_batch` | 1535 ms | -879 ms | 批量 r/k/v + mid 投影 |
| `cmix_norm_lerp_batch` | 1897 ms | -517 ms | 元素级 |
| `ffn_value_sparse_add_batch` | 1922 ms | -492 ms | 稀疏 FFN down |
| `rwkv_sample_batch` | 1926 ms | -488 ms | 采样（单次调用 ~7.6ms/轮！） |
| `gemv_lowrank_chain4_batch` | 1993 ms | -421 ms | 低秩链 |
| `norm_lerp6_batch` | 2063 ms | -351 ms | 元素级 |
| `fuse_ka_dplr_norm_batch` | 2364 ms | -50 ms | 仅 2% |
| `dplr_seq_batch` | 2368 ms | -46 ms | 仅 2% |

**两个线性内核合计移除收益最大（-1210 / -879ms）→ 方向二（线性层）本身是对的。**
`fuse_ka_dplr_norm_batch` / `dplr_seq_batch` 几乎免费（与旧文档"状态更新占大头"的猜测相反）。

## 3. 隔离计时：内核本身到底多快

用 crate 内临时测试直接调用 `gemv_int8_relu2`（= `gemv_variant_mb` 路径）300 次取均值：

| 形状 | B=1（走单流 `gemv_variant`） | B=8（走 `gemv_variant_mb`） |
|---|---|---|
| att_output [2560,2560] | 0.031 ms / 218 GB/s | 0.070 ms / 97 GB/s |
| ffn_key [10240,2560] | 0.081 ms / **333 GB/s** | 0.252 ms / 107 GB/s |
| ffn_value [2560,10240] | 0.109 ms / 249 GB/s | 0.217 ms / 125 GB/s |

按 FMA 折算（B=8）：ffn_key 209.7M MAC / 0.252ms = 832 G MAC/s = **仅 12% 峰值**；
att_output 52.4M MAC / 0.070ms = 749 G MAC/s = 11%。

**即：B=8 的批量线性内核在带宽（~35%）与算力（~12%）两端都远未饱和 ⇒ 延迟 / 内存级并行不足。**

## 4. 三次几何实验都否掉了"权重带宽受限"

| 实验 | 预期（若带宽受限） | 实测 |
|---|---|---|
| `BGRP` 4→8（权重读 2 遍 → 1 遍） | 步时近 2× 改善 | **无改善**（252.4 vs 259.7 tok/s） |
| `ROWS`=4→2 且 `BGRP`=8（流量减半、每线程 FMA 不变、block 数不变） | 近 2× 改善 | **无改善**（ffn_key 0.252 vs 0.247ms） |
| blockDim 128→256（线程数翻倍） | 延迟更易隐藏 | **更差**（217.1 vs 259.7 tok/s） |
| B 8→16 | 吞吐近 2× | **仅 +5%**（238.9→250.5）；每 slot 成本几乎不变 |

**结论：既不是权重带宽受限，也不是 FMA 受限，也不是单纯占用率不足。**
共性是「换几何 / 加线程都不动」——典型的**每 kernel 延迟主导 + 内存级并行不足**：
B=1 走单流内核可达 333 GB/s（54% 峰值），说明相同的权重访问模式**本身能跑快**；
批量内核因为每线程要同时维护 ROWS×BGRP 个累积器、指令流更长，未能把访存延迟盖住。

## 5. 对「上 tensor core」的判断

- tensor core 解决的是**算力**问题；实测算力只用到 12%，**不是瓶颈**。
- 但 Albatross `rows_cutlass` 真正的价值不在 mma 指令，而在 **CUTLASS 的
  `Stages=3` + `cp.async` 多级流水**——那正是对症「内存级并行不足」的结构。
- 因此方向二的正确形态是：**给批量线性层做 cp.async 多级流水的 GEMM 结构**
  （tensor core 可作为顺带收益，但不是目的）。
- 硬约束：本项目的 CUDA 内核全部由 **NVRTC 运行时编译**（内嵌源码字符串），
  **无法直接使用 CUTLASS**（重模板 + 头文件依赖，NVRTC 不可行）。要落地必须
  手写 `cp.async`（`__pipeline_memcpy_async` / `cp.async.commit_group`）+
  可选 `mma.sync` 的内核。

### 建议的下一步（按性价排序）

1. **`rwkv_sample_batch` 多 block 化**（消融显示单次 ~7.6ms/轮，占步时约 20%）：
   现状 `grid=(1, batch, 1)`、每 block 112 线程单块扫 vocab=65536 → B=8 只用 8 个
   block（68 个 SM 闲置 60 个），实测 ~0.26 GB/s，是全链路最明显的一处病态。
   代价中等（top-K/top-p 归约需跨 block 化），收益明确。
2. **批量线性层 cp.async 流水化**（本文件 §5）：先只改 `gemv_variant_mb`
   （消融收益最大），作出 A/B 再推广到 rkv/chain4。
3. 元素级内核融合（`cmix_norm_lerp_batch` + `norm_lerp6_batch` 等，各占 15-21%）。

## 6. 本次附带修复

- **`gemv_variant_mb` 共享内存越界（真 bug）**：`__shared__ float partial[4][4][BGRP]`
  硬编码 4 warp，blockDim 改 256（8 warp）时 `partial[4..7]` 越界写 → 访问违例
  （实测 `0xC0000005`，exit 3221225477）。已改为按 8 warp 开数组 + 运行时
  `nwarp = blockDim.x >> 5` 作求和上界。当前 blockDim=128 不触发，属潜在缺陷。
- **`ABLATE` 消融探针**（见 §1）：新增长期可用的诊断设施。
- `register_kernel_name` 改为恒注册（原来只在 PROF_CUDA_KERNEL=1 时注册，
  消融探针需要 func→name 反查）。

## 7. 排查教训

1. **先验测量工具本身**：`PROF_CUDA_KERNEL` 的同步开销把数字淹没了，我据此误读了一轮
   （"dequant_int8 占 61%" 实为 prefill GEMM 的假象）。发现"总和 ≈ kernel 数 × 同步开销"
   这个巧合才识破。
2. **消融比逐 kernel 计时更可靠**：保留完整流水，只让一个内核缺席。
3. **别用"加线程/换几何"猜延迟问题**：三次实验都不动，说明症结在指令级并行/访存
   在途量，需要结构性改造（多级流水），而非参数调整。
4. **B=1 与 B=8 走的是两个不同内核**（`gemv_variant` vs `gemv_variant_mb`），
   比较两者差异时不能当成纯 B 标度。
