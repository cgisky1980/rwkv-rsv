# Vulkan 状态核：访存宽度（列对）+ 行交错 实施记录（2026-10-11）

目标杠杆：`fuse_ka_dplr_norm{,_s16}`（RNN 状态更新 + 融合 fuse_ka/dplr/group_norm/sum_rk_rk）。
它在 B=128 批量 decode 里 per-layer **0.2751 ms**，占分核窗口的 **17.7 %**，仅次于
`gemm_imma`（44.4 %），是 §6.9 之后 Vulkan 侧第二大单核。本轮做两件互相独立的事，
各自的证据链分开记：

1. **行交错**（两行延迟链重叠）—— 数值零风险，先单独实测；
2. **列对访存**（每 lane 一次 4B 取两个相邻元素）—— 改变 `subgroupAdd` 的求和划分，
   必须过逐元素误差门。

内核本体：`assets/shaders/src/fuse_ka_dplr_norm.comp`；两条路径（单 token 与 batch）
共用同一个 spv，只有 dispatch 的 grid.z 不同（`runtime.rs:3320` / `:3398`），
所以一处改动覆盖两处。

**结论（先看这条）**：两处改动都已装上，**数值逐位不变**（含正向标定对照），但收益比预期
小一个量级——同会话四轮反序对照给出列对 **−0.98 %**（f16 档）/ −2.18 %（f32 档），交错同号
且更小。原因是这个核 **本来就贴着带宽屋顶**：f32 档搬 2 倍字节慢 1.77 倍 ⇒ 时间随字节线性，
f16 档 83.9 MB / 0.1876 ms = **447 GB/s = 峰值 616 的 72.5 %**，剩余空间 ≤15 %，摊到解码窗口
（状态核现占 ~12.5 %）是 **≤2 %** 的端到端上限。**这根杠杆到此为止**，下一根是
`gemm_imma`（窗口 ~48 %，仍在 14-22 TOPS 档、int8 峰值 ~107 TOPS）。
顺带把测量口径钉死：`PROF_GPU` 的 per-avg **跨进程批次散布 ±4~10 %**，所以本记录里
所有「跨批次相减」的读数（§2.2、§3.3）都降级为方向性证据，只有 §4.1 的同会话反序配对可作口径。

## 一、诊断：假设「这个核卡在每条访存指令搬多少字节上」（**已被 §4.2 证伪**）

### 1.1 字节核算（手工，不依赖 profiler 的 est/bw 列）

每 dispatch（= 一层 × 一步 × 整批）状态流量：
`B × H(40) × N(64) × N(64) × 2B × (读+写) = B × 655,360 B`。

本会话 batch 标度探针（`C:\tmp\stbatch.sh`，口径 `SEGS=1 NTOK=2 PREFILL_SLOTS=8
SKIP_GRAPH=1 SKIP_SINGLE=1 PROF_GPU=1`，取末个 decode dump 的 per-avg）：

| B | per-avg | 每 dispatch 字节 | 有效带宽 | 占 616 GB/s 峰值 |
|---:|---:|---:|---:|---:|
| 8 | 0.0244 ms | 5.24 MB | 215 GB/s | 35 % |
| 32 | 0.0775 ms | 20.97 MB | 271 GB/s | 44 % |
| 128 | 0.2766 ms | 83.89 MB | 303 GB/s | 49 % |
| 256 | 0.5659 ms | 167.77 MB | 297 GB/s | 48 % |

两点结论：

- **时间对 B 近线性、带宽在 B≥128 就平头**（300 GB/s 上下），所以大批量下它**不是**
  「块数太少/并发不足」——CUDA 侧那个 B=1 病灶（`KAW` 提块内 warp 数）在这里不适用。
- 与 fp32 状态档对照**看起来**指向「访存指令条数」：同口径 B=128 的 fp32 档 per-avg
  0.3559 ms（=167.8 MB ⇒ 471 GB/s），fp16 档 0.2766 ms（=83.9 MB ⇒ 303 GB/s）——
  访存指令条数相同、字节少一半的档反而带宽效率更低。
  ⚠️ **但这个读数是跨进程的，而本轮实测到 `PROF_GPU` 的 per-avg 跨进程批次漂移可达
  ±25 %**（同一个 spv `F255BA09` 在两个批次里分别读出 0.2131 ms 与 0.1982 ms），
  所以上面这条只够当**假设**，不够当结论。判定改到四臂同批次交错实验（§4）。

### 1.2 为什么 CUDA 的反例不适用于 Vulkan

`src/backend_cuda.rs` 里同一内核留着一段 **反例（勿重试）**：把列映射改成
`j0 = 2·lane / j1 = j0+1` 以便 `half2` 向量化，端到端只 **+0.55 %**（2923.2 → 2939.4），
还改了蝶形归约的求和顺序 ⇒ 已回退。

那条结论的前提是 CUDA 的窄映射**已经**跑到 450 GB/s（同一注释里 B=256 的读数），
即它本来就在带宽附近，向量化自然没肉。Vulkan 的窄映射只有 300 GB/s（同一批次内的
读数），所以「向量化有肉」在 Vulkan 侧是**待验证假设**而不是既成事实。本轮把它验证掉了：
**不成立**——列对在 f16 档只买到 −0.4~−0.9 %（§4.1），CUDA 那条 +0.55 % 的反例在 Vulkan
这边同样成立，因为这个核和 CUDA 版一样贴着带宽屋顶（§4.2）。

## 二、改动一：两行交错（数值零风险）

### 2.1 做法

CUDA 版同一内核用 `#pragma unroll 2` 让两行独立的蝶形链交错。Vulkan GLSL 没有
`#pragma`，这里直接把行循环改成**一次迭代处理 `row` 与 `row + NUM_SUBGROUPS` 两行**：
两套 `sreg`、两条 `sa` 部分和、两次 `subgroupAdd`、两个存回。每行的算术表达式、
列划分、归约结构**逐字未动** ⇒ 只改调度。N=64、`NUM_SUBGROUPS = BLOCK_SIZE/SUBGROUP_SIZE = 4`
时每 subgroup 16 行 = 8 对，无尾部；仍留 `hasB` 兜住 `N % (2*NUM_SUBGROUPS) != 0`
的通用形状（尾部第二行只算不写）。

### 2.2 实测（同会话交错，spv 文件在两档间热替换）

口径：`SLOTS=128 SEGS=2 NTOK=64 PREFILL_SLOTS=8 SKIP_GRAPH=1 SKIP_SINGLE=1 TOPK=1`，
脚本 `C:\tmp\stilv.ps1`（预热各 1 轮 + 交错 3 轮 + 分核各 1 次 + logits dump 比对）。

| 轮 | 交错前 | 交错后 |
|---:|---:|---:|
| 1 | 2364.6 | 2354.2 |
| 2 | 2334.6 | 2333.5 |
| 3 | 2326.7 | 2327.4 |

- **端到端**：均值 2341.97 → 2338.37 tok/s，**−0.15 %（噪声内）**。
- **内核 per-avg**：0.2219 → **0.2131 ms（−4.0 %）**；窗口 SUM 77.587 → 76.973 ms（−0.8 %）。
  ⚠️ 本会话内核 per-avg（0.2219）比 1.1 的探针（0.2766）低 20 %，是跨进程的剖析器
  开销/驱动状态差异，**不是**改动效果——所以两档必须在同一进程批次里比。
- **逐位性（这条改动的全部风险所在）**：6/6 轮的 token 指纹都是
  `sum=0xd2acfd0 xor=0x19fe`；另外 `STEP=1 PROBE=1 DUMP_LG`（SLOTS=8）的 logits dump
  两档 md5 逐位相同（`8303A7D9…`，9,859,048 B）。
  ⚠️ 口径要说清：`DUMP_LG` 落的是 `forward_seq_batch_padded`(prefill) 之后**再走一步
  `batch_step_logits`** 的那一行 logits ⇒ 它**确实经过了解码态状态核**（8 槽 × 32 层），
  但只有**一步**；多步演化靠 token 指纹（本档 16,384 token × 2 档逐位相同）兜。

### 2.3 结论

内核自己 −4 %，但状态核只占步时间的 ~15 %，−4 % 摊到端到端是 −0.6 %，落在本机的
噪声带（±0.5~1 %）里。保留的理由是它**零数值风险**且方向为正，并且是列对改动的
载体（两者叠加后才好测）。单靠它拿不到可引用的吞吐结论。

## 三、改动二：列对访存（`f16vec2` / `vec2` 视图）

### 3.1 做法

`BufS` 的 buffer_reference 块从标量视图换成**列对视图**：

```
#ifdef WKV_S16
#define S_TYPE float16_t
#define S_VEC  f16vec2      // fp16 档：一次 4B 取两个相邻 half
#else
#define S_TYPE float
#define S_VEC  vec2         // fp32 档：一次 8B 取两个 float
#endif
layout(buffer_reference) buffer BufS { S_VEC data[]; } buf_s;
```

列↔lane 的对应由「lane 拥有列 `sgid`、`sgid+32`」变成「lane 拥有**列对** `2p, 2p+1`，
`p = sgid + m*SUBGROUP_SIZE`」⇒ 每行的载入/存回**指令条数减半**，且 warp 一条指令
覆盖 128 B 连续（旧的是 64 B）。对齐前提：`N` 为偶（64）且行首元素索引
`s_base + row*N` 为偶（`N*N=4096`、`N=64` 都是偶数）⇒ fp16 档 4B 对齐、fp32 档 8B 对齐成立。
两档 spv 都过 glslangValidator（`--target-env spirv1.3 -V`，带/不带 `-DWKV_S16`）。

⚠️ 数值口径：求和划分变了 ⇒ `sa[row]`、`y[row]` 的 fp32 加法结合顺序与上一版不同，
**不逐位**。判据用逐元素 logits rmse，并拿一个**已上线**的扰动（`LOWRANK_GEMM2=0`
即低秩二级张量核↔SIMT）作标定对照——理由与 §6.3 split-K 那次一样：贪心分叉率会饱和，
只有逐元素误差能分开「舍入级扰动」与「算错」。

### 3.2 吞吐（同会话交错，脚本 `C:\tmp\spin.ps1`）

口径同上（`SLOTS=128 SEGS=2 NTOK=64 … TOPK=1`，预热各 1 轮 + 交错 3 轮；
base = 只交错不向量化 `F255BA09`，pairs = 交错 + 列对 `EC23C548`）：

| 轮 | base | pairs |
|---:|---:|---:|
| 1 | 2389.2 | 2382.9 |
| 2 | 2313.2 | 2372.4 |
| 3 | 2351.9 | 2363.3 |
| 均值 | 2351.4 | **2372.9（+0.91 %）** |

### 3.3 内核 per-avg 与误差门

- **per-avg（B=128，50 次 dispatch）**：base 0.1982 ms → pairs **0.1889 ms（−4.7 %）**;
  窗口 SUM 76.262 → 75.827 ms（−0.57 %）。
  ⇒ 列对方向为正，但幅度是 **~5 %**，不是「指令数减半 ⇒ 时间减半」的那个量级。
- **误差门（这条改动的准入条件）**：`STEP=1 PROBE=1 DUMP_LG`，`SLOTS=32`（状态核走
  batch 路径，8 槽换成 32 槽是为了同时满足低秩二级张量核的 `batch>=32` 门限，让标定
  对照真的有扰动）：

  | 比较 | 元素数 | rmse | 相对 rmse | 逐位相同 |
  |---|---:|---:|---:|---:|
  | pairs vs base | 2,097,152 | **0.000e+0** | **0.0000 %** | **100.00 %** |
  | 标定对照：base vs `LOWRANK_GEMM2=0` | 2,097,152 | 1.103e+0 | 6.558 % | 0.00 % |

  两档 logits dump 的 md5 **完全相同**（`F47EBB40…`，40,878,897 B）。标定对照那一档
  证明这套探针**能**看见「已上线的求和口径扰动」量级（6.6 %），所以这里的 0.000 %
  是实测而不是探针坏了。解释：`sa`/`y` 的结合顺序差在 fp32 的最后一两个 ulp，而状态
  矩阵本身按 **fp16 存回**，扰动在舍入处被吸收掉。
- **多步解码**：3+3 轮 × 16,384 token 的指纹在两档**逐位相同**（`sum=0xd26732a
  xor=0x7004`）⇒ 扰动没有随状态演化放大。

### 3.4 结论

列对与两行交错**都保留**，但收益口径以 §4 的同会话反序四臂为准：**f16 档 −0.98 %**
（列对），交错同号且更小。本节 §3.3 的 −4.7 % 与 §2.2 的 −4.0 % 都是跨进程读数，
已被 §4.3 的漂移测量降级为「方向为正、幅度不可单独引用」。端到端 §3.2 的 +0.91 %
在噪声带内，不作收益声明。

准入条件仍然满足并且很强：**数值逐位不变**（含正向标定对照，§3.3），state 格式/序列化
不变，prefill 不动，两档 spv 都能编译。它**不是**原来预期的那根 2× 杠杆——状态核的
剩余瓶颈**是字节数而不是访存指令条数**，判定见 §4.2：f32 档相对 f16 慢 ≈1.8 倍，
f16 档已跑到峰值带宽的 73 %。

## 四、位宽 × 映射 四臂分解（判定剩余瓶颈到底是不是带宽）

§1.1 那条「指令条数受限」的假设用的是跨进程读数，而 §2.2/§3.3 之间暴露出 per-avg 跨
进程批次漂移有 ±25 %（同一 spv 读出 0.2131 与 0.1982），所以必须把两个因素放进**同一
批次的交错实验**：`{base, pairs} × {fp16, fp32}` 各 2 轮，`PROF_GPU` 只取状态核 per-avg。
脚本 `C:\tmp\spdec.ps1`。

（读数待填：判定标准是——若 fp32 档相对 fp16 的时间**接近 2 倍**，说明字节数就是瓶颈，
我们已经贴着带宽屋顶，列对那 5 % 是最后一点肉；若 fp32 只慢一点点，说明核内还有
与字节数无关的开销，得另找方向。）

### 4.1 读数（同会话四臂，每臂 per-avg；`bound=` 是该轮实际绑定的 spv md5 前 8 位）

脚本 `C:\tmp\spdec.ps1`，`SLOTS=128 SEGS=1 NTOK=2 PREFILL_SLOTS=8 SKIP_GRAPH=1 SKIP_SINGLE=1
PROF_GPU=1`。同一会话共 4 轮，**前两轮 pairs 先跑、后两轮 base 先跑**（反序是为了让「批内
单调漂移」在两个方向上各偏一次，而不是只偏一边；本轮确实观察到漂移：同一臂跨轮散布
f16 ±4 %、f32 ±8 %）。`bound=` 是该轮实际绑定 spv 的 md5 前 8 位（性能无关的绑定标记）：
base=`F255BA09`/`47F25235`（f16/f32），pairs=`EC23C548`/`171B91A3`。四轮里状态核的**解码指纹
逐位相同**（f16 档恒 `sum=0x32c026 xor=0x18ea`，f32 档恒 `sum=0x32a50a/0x18ea`）⇒ 列对没有
挪动任何一步的输出。

| 轮（顺序） | base f16 | pairs f16 | base f32 | pairs f32 |
|---|---:|---:|---:|---:|
| r1（pairs 先） | 0.1854 | 0.1838 | 0.3387 | 0.3241 |
| r2（pairs 先） | 0.1888 | 0.1880 | 0.3531 | 0.3312 |
| r1（base 先） | 0.1935 | 0.1889 | 0.3310 | 0.3307 |
| r2（base 先） | 0.1901 | 0.1897 | 0.3232 | 0.3306 |
| **均值** | **0.18945** | **0.18760** | **0.33650** | **0.32915** |
| **Δ(pairs vs base)** | | **−0.98 %** | | **−2.18 %** |

位宽比（同臂 f32/f16）：base 1.776，pairs 1.754 ⇒ **≈1.77 倍**。

### 4.2 判定：字节数就是瓶颈，这个核已经贴着带宽屋顶

- **f32 相对 f16 慢 ≈1.77 倍**，而它恰好搬 2 倍字节 ⇒ 时间几乎随字节线性 ⇒
  **DRAM 带宽受限**，不是访存指令条数受限。§1.1 那条「指令条数」假设就此**证伪**
  （它用的正是跨进程读数）。
- 反过来印证：列对（每 warp 一条指令覆盖 64 B→128 B）在 f16 档只买到 **−0.98 %**，
  f32 档 −2.2 %。注意 −2.2 % 里有顺序效应：pairs 先跑的两轮给出 −4.3/−6.2 %，base 先跑
  的两轮给出 −0.1/−2.3 % ⇒ 反序那两轮的均值把虚高削掉了。**取 4 轮均值 −1 %/−2 % 为口径。**
- 绝对位置核算：每 dispatch 状态字节 = `B×H×N×N×2×2 = 128×40×64×64×2B×2 = 83.9 MB`
  （profiler 的 `est` 列不计 `buffer_reference` 流量，所以它显示 0.1 MiB，别看它）。
  f16 档 0.1876 ms ⇒ **447 GB/s = 峰值 616 的 72.5 %**；f32 档 0.3292 ms ⇒ 510 GB/s = 83 %
  （字节翻倍而时间只翻 1.77 倍，就是这一行的来源）。Turing 上纯 read+write 串流
  能做到的量级就在 80-85 %，所以**剩余空间 ≤15 %**，摊到解码窗口（状态核占 ~12.5 %）
  是 **≤2 %** 的端到端上限。
- ⇒ **这根杠杆到此为止**。两行交错（§2）与列对（§3）都保留——同号、逐位不变、且是后续
  任何改动的正确起点——但下一步该去 `gemm_imma`（同一次 dump 里 36.05 ms / 窗口 ~48 %）
  而不是继续磨状态核。

### 4.3 对本记录前两组读数的口径降级（同一次漂移测量逼出来的）

同一份 `F255BA09`（只交错、未列对）跨批次读出 **0.2219 / 0.2131 / 0.1982 / 0.1854 /
0.1888 / 0.1935 / 0.1901 ms** ⇒ 散布 ±12 %，比 §2.2 的 −4.0 % 与 §3.3 的 −4.7 % 都大。所以
那两条要降级为：**方向为正、幅度落在跨进程漂移带内，不可单独引用**。§4.1 的同会话反序
配对才是口径。

整根杠杆的诚实上限因此也很小：状态核在今日 dump 里是 9.19~9.68 ms / SUM 73.8~76.8 ms
= **窗口的 12.3~12.6 %**。就算交错+列对真有 −8 %，端到端也只有 ~1 %；按 §4.1 的
−0.98 % 算，端到端 **~0.1 %**，落在吞吐噪声带里。§3.2 那个 +0.91 % 属同一条噪声带，
不要当收益引用。

## 五、遗留与观察

1. **跨会话 token 指纹漂移（exe 重链假设已证伪，仍未解释）**：同一个 spv（`F255BA09`）在
   `stilv.ps1` 批次里 6/6 轮都是 `0xd2acfd0/0x19fe`，在 `spin.ps1` 批次里 3/3 轮都是
   `0xd26732a/0x7004`；两批的**日志逐行比对只差这一行**（配置、绑定的 spv 名、
   `top_k`、VRAM 记账 5137/6498/8368/8553 MiB 全同）。同一批次内两臂交替仍逐位相同
   ⇒ 交错 A/B 的结论不受影响，但「拿历史指纹当不变量」这类论证要降级为
   「同批次内指纹一致」。
   **判定实验（本轮做完，结论=排除）**：`touch src/lib.rs && cargo build --release --example
   batch_decode_bench` → exe md5 `a24a1103…` 变 `4b747d49…`（**Rust 构建不逐字节可复现**，
   含路径/时间戳类元数据），两个 spv md5 不变，随后**同配置重跑** decode 指纹
   `sum=0x32c026 xor=0x18ea` **与重链前逐位相同** ⇒ 「代码生成挪了 fp 收缩/内联决策」这条
   解释**不成立**，指纹与 exe 二进制无关。剩下的候选只有驱动侧着色器编译缓存、以及日志
   没记到的环境差异；本轮不再追（性价比低于换杠杆），若下次再遇到同类漂移，先用
